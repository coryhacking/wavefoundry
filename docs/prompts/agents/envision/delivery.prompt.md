# Envision — Delivery and adoption

Owner: Engineering
Status: active
Last verified: 2026-11-04

Internal phase guidance before final validation, status and adoption handoff. Apply the core's authority and output boundaries, including when review was omitted.

At the document end, keep routine metadata and the core's compact review/adoption status current: what reviewers examined, material repairs, substantive later edits and pending findings. Use readable labels or an available Git reference when helpful; reference a commit only for content actually present in it, not later working-tree edits. No mandatory hash table, exact-byte accounting or new revision for a status-only edit is required. Formatting-only changes checked under the review guidance preserve substantive coverage. For other later authorized edits, identify which earlier checks still support the result and which affected passages remain unverified; a usable provisional vision may have pending findings.

Use source control for durable history at meaningful checkpoints, whether or not the vision is adopted. Commits remain optional and project/operator-owned: do not commit automatically or require a commit before each review. Keep the pre-repair text through this delivery account. If earlier reviewed text was not preserved, say so and describe subsequent changes without claiming reconstructable history; do not invent provenance or discard text needed by current verification. Explicit project evidence/provenance requirements take precedence, using source control where possible.

In the response, account for selected versus executed roles, identified drafts, optional forms/lenses, actual findings/verdicts, material feedback, resulting changes and unresolved uncertainty, verification contributions, open operator decisions and unavailable/omitted coverage. Disclose shared context, model and evidence limits; earlier approval does not cover later edits by implication. Retain material evidence, not routine transcripts. An explicit evidence-location instruction can move this accounting; otherwise create no review sibling. Report historical siblings left unchanged.

Check statement fidelity/status, citations, links, capability classifications, dependency order and horizons. Reuse the retained understanding check; final validation adds no reader or repair cycle. Run applicable docs validation: target-scoped `wf_validate_docs`, otherwise the supported project check (Wavefoundry CLI: POSIX `./.wavefoundry/bin/wf docs-lint`; native Windows `.\.wavefoundry\bin\wf.cmd docs-lint`). Fix introduced document defects within the authorized repair boundary; after verification disclose remaining substantive defects rather than repairing again. Report unrelated failures without widening scope. Lint proves document consistency, not future capabilities.

State adoption explicitly in that end status: authoring, review and Git tracking do not adopt the vision. Preserve existing designation. Otherwise explain the actual-path pointer the operator can authorize in `AGENTS.md` or project overview, for example `Canonical product vision and roadmap: VISION.md`; do not write it without direction.

Once adopted, Plan change identifies relevant horizon/outcome and consequential prerequisites without selecting different work to manufacture alignment. Designated uncommitted visions count; committed drafts do not. Delivery evidence informs horizon progress, but recording it in the vision requires Envision revision or explicit operator edit. Planning leaves vision/review artifacts unchanged, adds no tracker, mandatory section or vision prerequisite, and accepts legitimate changes without direct fit.

Return the path or requested read-only advice, central direction/value, horizons and ordered immediate advances, research/capability limits, actual review outcome and material decisions. Explain how the result meets the brief, what to inspect first and any directional change and reason, including consequential company evidence and unverified assumptions when applicable. Bring newly surfaced consequential choices back to a focused conversation under the core decision guidance, honoring explicit no-interview requests. Distinguish selected directions, provisional recommendations and deferred questions with their next tests. Any later authorized substantive revision needs accurate new revision/review coverage; preserve the bounded-repair stop. For a substantial outcome spanning waves, point to **Plan arc** (`docs/prompts/plan-arc.prompt.md`) when available as optional subsequent planning. Start no subsequent work automatically.
