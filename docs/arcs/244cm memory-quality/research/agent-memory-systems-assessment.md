# Wavefoundry's memory design is right but unproven

Owner: Engineering
Status: active
Last verified: 2026-11-23

The body below is copied unchanged from wave 245na's work folder on 2026-11-23 as the evidence base for arc `244cm-arc memory-quality`.

Wavefoundry's memory design is sound in its foundations and ahead of the market on the points the evidence supports most strongly. Those points are strict admission, evidence-linked records, non-destructive retirement, a small capped briefing and repo-visible storage. Its weakest parts are the ones no one has tested. Churn-based decay, the never-decay kinds, the least-recently-reviewed audit order and the retrieval stack have no direct evidence behind them, and nothing yet shows that the store improves agent outcomes in this repository at all. The best controlled study of memory management found that adding every memory performed **worse than a small fixed memory on all four tasks**, while strict selective admission beat it by **3.4 to 21.8 points** ([Xiong et al., ACL 2026](https://arxiv.org/html/2505.16067v2)). Wavefoundry's admission gate is aimed at exactly that effect. The most relevant coding-agent benchmarks are sobering: four existing memory systems **failed to beat a matched memory-off baseline in 11 of 12 pairings** ([VibeMemBench](https://arxiv.org/abs/2609.23570)), and agent-selected context fell **below the no-context baseline** ([SWE-ContextBench](https://arxiv.org/html/2602.08316)). The current evaluation cannot tell whether Wavefoundry is in that losing group, because querying 12 records with their own summaries measures indexing round-trip, not retrieval. The decisions that matter most are therefore about evidence, not mechanism. Build a situation-language evaluation with grep and full-context baselines first. Then add read-time verification of cited targets. Turn churn from a confidence penalty into a revalidation trigger. Resist adding retrieval or consolidation machinery until the baselines say it is needed.

## The verdict: keep the architecture, prove the value

The design gets the big structural choices right, and several of them are choices the vendors have moved toward only recently. Products split into three families: repo-visible instruction files, machine-local generated memory and vendor-hosted memory. **Only the first family is committed and reviewed with the code** ([Claude Code memory docs](https://code.claude.com/docs/en/memory); [Copilot Memory docs](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)). No surveyed product combines committed storage, agent-written entries and required evidence refs. GitHub Copilot comes closest in schema, with `subject`, `fact`, `citations` and `reason` fields, but its store is hosted and its memories cannot be edited directly ([GitHub engineering blog](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/)). The direction of travel favors Wavefoundry's choice. Cursor removed its Memories UI and told users to move memories into Rules ([Cursor forum](https://forum.cursor.com/t/are-my-memories-gone/144057)). Devin deprecated Knowledge in favor of Skills ([Devin Knowledge docs](https://docs.devin.ai/product-guides/knowledge)). Claude Code added timestamps, size nudges and an audit command to its auto memory ([Claude Code memory docs](https://code.claude.com/docs/en/memory)).

The candid part is that the design is unproven where it is most original. No published system ties decay to git churn on target files. No study compares human or agent record review with agent-only validation. No benchmark tests whether a repo-specific lesson stops a repeated mistake. All the conversational-memory benchmark numbers come from the vendors or the paper authors, and they are disputed. Mem0's own paper shows **full context (72.90) beating every memory system it measured on LoCoMo**, its own included ([Mem0 paper](https://arxiv.org/html/2504.19413v1)). An audit by a competing vendor found **6.4% of LoCoMo's answer key wrong** and a judge that accepted **up to 63% of intentionally wrong answers** ([Penfield Labs audit](https://dev.to/penfieldlabs/we-audited-locomo-64-of-the-answer-key-is-wrong-and-the-judge-accepts-up-to-63-of-intentionally-33lg)). The literature gives Wavefoundry vocabulary and warnings, not a validated recipe. With about 170 records, Wavefoundry's own evaluation would be primary evidence that the field lacks.

Evidence labels used below: **peer-reviewed** means a paper at a reviewed venue (ICLR, ICML, NeurIPS, ACL). **Preprint** means an arXiv paper without a confirmed venue. **Vendor-reported** means a claim by a company about its own product. **Independent** is reserved for third parties with no product at stake; almost nothing in this space qualifies.

## Design elements, one by one

| Element | Verdict | Evidence strength |
| --- | --- | --- |
| Repo-visible typed markdown records | Keep | Moderate (vendor convergence, security incidents) |
| Eight kinds | Keep, but audit for instruction overlap | Weak (no taxonomy evidence) |
| Required evidence refs and file or symbol targets | Keep, and use them at read time | Moderate (Copilot vendor A/B, staleness studies) |
| Confidence plus age and churn decay | Change: churn triggers revalidation instead of only lowering confidence | Weak (no direct test) |
| Never-decay kinds | Change: exempt from age decay, not from churn revalidation | Weak to moderate (stale-instruction harm) |
| Six statuses, non-destructive retirement | Keep | Moderate (Zep and Mem0g design, Mem0 deletion complaints) |
| Active-record budget | Keep | Moderate (universal vendor caps) |
| Evidence-derived candidates, agent validation | Keep, and harden the validator | Strong (peer-reviewed admission study) |
| Least-recently-reviewed batch of 15 | Change: order by signal before age | Weak (periodic deletion lost accuracy) |
| Keep re-stamps `Updated:` | Keep, only after an actual check | Moderate (Copilot design) |
| "Encoded elsewhere" with a whole-scope assertion | Keep | Weak (no study; conservative by construction) |
| Same-target consolidation | Keep, but cautiously | Weak to moderate (summaries get ignored) |
| Capped briefings of 5 at three trigger points | Keep, and allow empty briefings | Moderate to strong (instruction-scaling and context-file studies) |
| Advisories on code tools | Keep | Moderate (just-in-time guidance) |
| Hybrid dense plus BM25, RRF, cross-encoder | Keep, freeze further investment | Weak that it is needed at this scale |
| Queryless policy ordering | Keep, but test it | None |
| Self-summary evaluation | Drop as a headline metric; keep as a sanity floor | Strong that it is invalid |

### Records: repo visibility is a security property, not only a convenience

Both documented memory-poisoning incidents in coding agents hit stores outside the repository review path. In Windsurf, the `create_memory` tool ran without approval, so indirect prompt injection could plant persistent memories across conversations ([Embrace The Red](https://embracethered.com/blog/posts/2025/windsurf-spaiware-exploit-persistent-prompt-injection)). In Claude Code, an npm `postinstall` payload **overwrote every project's `MEMORY.md`** and the settings hooks, then re-enabled auto memory with a shell alias. Anthropic responded by removing user memories from the system prompt in v2.1.50 ([Cisco blog](https://blogs.cisco.com/ai/identifying-and-remediating-a-persistent-memory-compromise-in-claude-code)). Records under `docs/agents/memory/` show up in `git diff`, which is a genuine structural defense. It is not complete, because an agent can still validate a poisoned candidate, but it moves every write into a reviewable artifact. The Cisco case adds one rule worth stating: memory must never be able to rewrite the configuration that loads it.

The eight kinds have no evidence for or against them; no study tests taxonomy granularity. Claude Code's four `type` values are a lighter analogue with no decay attached ([Claude Code memory docs](https://code.claude.com/docs/en/memory)). The more important question is what records contain. The peer-reviewed AGENTS.md study found that context files gave **no improvement in task success and raised inference cost by more than 20%**. Repository overviews did not help, and context files were useful mainly for non-standard practices ([Gloaguen et al., ICLR 2026](https://arxiv.org/abs/2602.11988)). The lesson for Wavefoundry is to reject records that restate what the code already shows, which is the same filter Claude Code applies when it "skips anything derivable from the codebase" ([Claude Code memory docs](https://code.claude.com/docs/en/memory)). The kinds that carry non-derivable information, such as failed_attempt, environment_gotcha and dependency_gotcha, are the ones the experience-reuse literature supports best. Those gains cluster where memory carries human-verified or non-obvious knowledge ([MemGovern](https://arxiv.org/abs/2601.06789); [SWE-Exp, preprint](https://arxiv.org/html/2507.23361v2)).

Evidence refs and file or symbol targets are the most distinctive and most defensible part of the record schema. Copilot is the only surveyed product that requires citations at creation. It reports a coding-agent PR merge rate rising from **83% to 90%** and review precision up 3% and recall up 4% in an A/B test ([GitHub engineering blog](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/)). These are vendor-reported numbers without published sample sizes, but they come from the only production system that looks like Wavefoundry's. Keep the refs, and use them at read time as well as at admission (see Surfacing).

### Lifecycle: churn decay is a good hypothesis encoded as a fact

Decay driven by age and target-file git churn is original. Surveyed frameworks use only usage recency, as in Generative Agents' exponential decay with factor 0.995 ([Generative Agents](https://arxiv.org/html/2304.03442)), or LLM-detected contradiction, as in Zep's bi-temporal invalidation ([Zep paper](https://arxiv.org/html/2501.13956)). The idea is directionally supported. Staleness in code is event-driven, and stale instructions cause measurable harm. In a small preprint covering 732 trajectories, agents followed a stale test command at a cost of **about a third more tool calls**, and **none repaired the underlying file** ([When Instruction Files Go Stale, preprint](https://arxiv.org/abs/2611.09802)). A separate scan found stale code-element references in **23.0% of 356 repositories** ([Context rot in AI config files, preprint](https://arxiv.org/html/2606.09090)). Theory also says recency eviction is optimal when usefulness decays exponentially with age ([Forgetful but Faithful, preprint](https://arxiv.org/pdf/2512.12856)).

What is not supported is the specific translation: churn lowers a confidence scalar. Churn is a cheap signal that a record might be wrong, not evidence that it is. A heavily edited file can leave a fragile_file warning fully valid, and a single rename can invalidate a record instantly with almost no churn. The better use of the signal is as a trigger. When a target's churn since the record's last verification crosses a threshold, or when the target path or symbol disappears, mark the record "needs revalidation" and put it at the front of the audit queue. Confidence then changes only when a check actually happens. This matches Copilot's design point that **upvoting resets the expiry clock but mere retrieval does not** ([Copilot Memory docs](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)). Decay should reset on verification, never on reading.

The never-decay rule for fragile_file, decision and operator_preference deserves a second look. These are the kinds that read most like instructions, and agents treat instruction-like text as authoritative even when it conflicts with the code ([Coherence Debt, preprint, abstract only](https://arxiv.org/abs/2608.16630)). Exempting them from age decay is reasonable, since a decision does not weaken because a year passed. Exempting them from churn-triggered revalidation is not. A fragile_file record whose target was rewritten, or a decision whose code has been deleted, is exactly the stale-instruction case the studies document. Keep the age exemption and drop the revalidation exemption.

The six statuses and non-destructive retirement are well matched to the literature. Mem0's base design deletes on contradiction, and users report that auto-resolution "silently deletes one you still need" ([DEV post, anecdotal](https://dev.to/mukesh_13/mem0-auto-resolves-memory-conflicts-for-you-until-it-silently-deletes-one-you-still-need-4f4m)). Mem0g and Zep both invalidate rather than delete ([Mem0 paper](https://arxiv.org/html/2504.19413v1); [Zep paper](https://arxiv.org/html/2501.13956)). Zep's four-timestamp model separates when a fact was true from when it was recorded. Wavefoundry lacks that distinction, but at this scale the superseded status plus git history covers most of it. It is not worth adding unless records start to need "valid until version X" semantics.

The active-record budget matches universal practice. Claude Code loads only the first **200 lines or 25KB** of `MEMORY.md` ([Claude Code memory docs](https://code.claude.com/docs/en/memory)). Codex stops adding instruction files at **32 KiB** ([Codex AGENTS.md docs](https://learn.chatgpt.com/docs/agent-configuration/agents-md)), and Windsurf truncates rules at 6,000 or 12,000 characters ([Windsurf docs](https://docs.windsurf.com/windsurf/memories)). The budget is cheap insurance against the add-all failure. Its right size is unknown and should come out of the evaluation, not out of intuition.

### Admission: the best-supported part of the design

Strict write-side selectivity is the strongest finding in the lifecycle literature. Xiong et al. compared policies on four agent tasks with GPT-4o-mini. Add-all memory scored **-12.1, -3.7, -7.8 and -11.6 points** against a small fixed memory while growing memory by 2 to 41 times. Strict selective addition scored **+3.4, +21.8, +10.9 and +13.9** ([Xiong et al., ACL 2026](https://arxiv.org/html/2505.16067v2)). The tasks were not coding repositories, but the effect is large and consistent. Drawing candidates from review findings, which are already independently checked, and then validating them is the right shape. The coding-memory systems that report gains also use verified or governed sources ([MemGovern](https://arxiv.org/abs/2601.06789)).

The same paper carries the warning that matters for Wavefoundry: **coarse LLM judges captured only part of the gain**, and a stricter, fine-tuned judge came closer. Agent validation is the weak link in an otherwise strong gate, because the validator can share the authoring agent's errors. There are three cheap hardenings. Copilot rejects candidates that contain secrets or recognized model-control tokens ([Copilot Memory docs](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)). Codex's `disable_on_external_context` excludes sessions that touched MCP, web search or tool search from memory generation ([Codex memories docs](https://learn.chatgpt.com/docs/customization/memories?surface=app)). Wavefoundry's analogue would flag candidates whose evidence comes from untrusted text such as issue bodies or dependency output. The third is a mechanical check that every evidence ref and target resolves at HEAD before an agent judges the candidate.

The rewrite verdict needs one constraint. A causal study across 4 frameworks, 13 backbones and 9 environments found that agents **rely on raw experience but often disregard or misinterpret condensed experience**, even when it is the only experience given ([Not Always Faithful Self-Evolvers, preprint](https://arxiv.org/abs/2601.22436)). Rewrites should make a record more specific and keep its concrete anchor (the path, command, error string or finding). They should not abstract it into a general lesson.

### Maintenance: audit by signal, not by age alone

The least-recently-reviewed batch of 15 is a reasonable default, but nothing supports it, and one result cuts against blind periodic cleanup. In Xiong et al., periodic deletion cut memory by 60 to 70% with accuracy changes of **-3.3, -0.1, -0.1 and -4.6**. History-based deletion, which removes records that caused harm when retrieved, gave **-1.2, +3.4, +0.8 and +4.2** ([Xiong et al., ACL 2026](https://arxiv.org/html/2505.16067v2)). The effects are small and mixed, but the direction is clear: audits driven by observed problems beat audits driven by the calendar. Keep the batch size and fill it in priority order. Records with broken targets come first, then churn-flagged records, then records surfaced in sessions where an agent or reviewer disputed them, and only then the least recently reviewed.

A keep that re-stamps `Updated:` is correct if the keep followed a real check of the record against current code. If a keep can happen on a skim, the stamp makes staleness invisible, which defeats the point. Claude Code's write-time `modified` timestamp is the consumer-product version of the same idea ([Claude Code memory docs](https://code.claude.com/docs/en/memory)).

The "encoded elsewhere" rule, which requires a named assertion covering the record's whole scope, has no external analogue. It is conservative in the right direction. Retiring a lesson because a test or lint rule now enforces it is exactly the move vendors recommend, since **mandatory behavior belongs in hooks or checked-in instructions, not memory** ([Claude Code memory docs](https://code.claude.com/docs/en/memory); [Codex memories docs](https://learn.chatgpt.com/docs/customization/memories?surface=app)). Requiring whole-scope coverage prevents the partial-coverage retirement that would quietly lose the rest of the lesson.

Same-target consolidation is useful for keeping the store small, but it carries the faithfulness risk described above, because merging tends to condense. Merge records that say the same thing; do not merge records that say different things about the same file. The archive-versus-purge choice is sound, and archive should stay the default given Mem0's silent-deletion complaints. GitHub's team **considered an offline curation service and rejected it** as too costly and still needing read-time reconciliation ([GitHub engineering blog](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/)). That supports keeping consolidation on-demand and reviewed rather than automatic.

### Surfacing: the cap is right, and every surfaced record is an instruction

A cap of 5 is consistent with the evidence. Instruction-following degrades as instruction count grows: the best frontier models reached only **about 68% accuracy at 500 instructions**, and models favored earlier instructions ([IFScale, NeurIPS 2025](https://arxiv.org/abs/2507.11538)). Long inputs degrade performance even on simple tasks, and semantically similar but wrong passages hurt more ([Chroma Context Rot, vendor-reported](https://research.trychroma.com/context-rot)). Because agents obey injected context, every surfaced record acts as an instruction, and an irrelevant one costs steps. In SWE-ContextBench, free full context raised cost about 24% with no accuracy gain ([SWE-ContextBench, preprint](https://arxiv.org/html/2602.08316)). CTIM-Rover's episodic memory **did not beat its baseline in any configuration** (40% against 42%). The authors attributed this to irrelevant items, including a word match on "clean", and to unfiltered context given at the start ([CTIM-Rover, preprint, 45 samples](https://arxiv.org/html/2505.23422v1)).

Two changes follow. First, an empty briefing must be a normal outcome; showing nothing when nothing applies is better than filling five slots. Second, verify at read time. Copilot checks each memory's cited locations against the current branch before applying it, and corrects or refreshes the memory as a result. GitHub describes retrieval as "hard to solve, but easy to verify" ([GitHub engineering blog](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/)). Copilot seeded repositories with false memories and reports that agents "consistently" caught them. That claim is vendor-reported with no sample size. Wavefoundry can do the cheapest part of this mechanically: before surfacing a record, confirm that its target paths and symbols exist at HEAD, and withhold or flag it if they do not.

The session-start briefing is the weakest of the three trigger points, because it has the least task context and so relies most on queryless ordering. Pre-implementation and file-edit briefings and the code-tool advisories fit Anthropic's guidance to retrieve just in time rather than preload ([Anthropic, context engineering](https://anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Vendors agree on one boundary: memory is a recall layer, and must-always-apply rules belong in committed instructions ([Copilot Memory docs](https://docs.github.com/en/copilot/concepts/agents/copilot-memory); [Codex memories docs](https://learn.chatgpt.com/docs/customization/memories?surface=app)). An operator_preference that must always hold should migrate to `AGENTS.md`, not wait for a 5-slot briefing to surface it.

### Retrieval: already sophisticated enough, possibly more than needed

Dense plus BM25 with RRF and a cross-encoder matches Zep's documented best-quality configuration and exceeds the Mem0, A-Mem and Letta defaults ([Zep paper](https://arxiv.org/html/2501.13956)). At about 170 records, sophistication is unlikely to be the binding constraint. Letta reports that a GPT-4o-mini agent with the conversation as a plain file plus grep and search tools scored **74.0% on LoCoMo, above Mem0's best reported 68.5%** ([Letta blog, vendor-reported and adversarial](https://www.letta.com/blog/benchmarking-ai-agent-memory)). The broader benchmark analysis says simple full-context or retrieval baselines often suffice, and that most benchmarks fit inside a 128k window ([Anatomy of Agentic Memory, preprint](https://arxiv.org/html/2602.19320)). Keep the stack; it is built and costs nothing per query. Do not add to it until an evaluation shows it beating BM25-only and grep. Precision at the shown set matters more than recall, given the harm from irrelevant records documented above.

LongMemEval's indexing ablation offers one cheap idea. Indexing raw values was a strong baseline, condensed keys alone did not help, and **raw value plus extracted facts gave +9.4% recall@k** ([LongMemEval, ICLR 2025](https://arxiv.org/html/2410.10813)). For Wavefoundry, that suggests indexing a record's body together with its target paths and situation keywords, and not only its summary. Queryless policy ordering by kind and confidence has no external evidence either way. It is a reasonable design that the evaluation should test against plain relevance and recency.

### Evaluation: the current design measures the index, not the memory

Querying 12 sampled records with their own summaries is a near-duplicate lookup; any dense or BM25 retriever scores near ceiling on it. The information-retrieval literature documents how near-duplicate leakage between queries and targets **inflates effectiveness and can reorder systems** ([Frobe et al., SPIRE 2022](https://arxiv.org/abs/2206.14759v2)). LLM-generated queries also bias absolute scores toward LLM-based systems ([Rahmani et al., preprint](https://arxiv.org/html/2506.10301v1)). Spec 243hz's production-path row moves in the right direction because it exercises the code path agents actually use. Bounding the experimental row is also right. Neither fixes the core problem, which is the source of the queries.

## What to adopt and what to avoid

### Adopt

| Recommendation | Expected value | Cost |
| --- | --- | --- |
| Situation-language evaluation with grep, BM25-only and full-context baselines (next section) | High: the only way to learn whether memory helps here | Medium: query authoring is the main effort |
| Read-time check that targets and evidence refs resolve at HEAD; withhold or flag on failure | High: directly targets the best-documented harm | Low: mechanical, local |
| Churn and missing-target as revalidation triggers that set audit priority, with confidence changing only on a check | Medium to high | Low to medium |
| Churn revalidation applies to all kinds, including the never-decay ones | Medium | Low |
| Admission hardening: secret and control-token rejection, untrusted-source flag, mechanical ref resolution before agent judgment | Medium: closes poisoning and silent-failure paths | Low |
| "Not derivable from the code" admission criterion | Medium: avoids the AGENTS.md no-benefit cost | Low |
| Empty briefings as a normal result, plus a minimum relevance threshold | Medium | Low |
| Re-stamp `Updated:` only after a recorded check | Medium | Low |
| Promote must-always-hold preferences and decisions to `AGENTS.md` or a check | Medium | Low per item |
| Index body plus targets and situation keywords, not summary alone | Low to medium; confirm in eval | Low |

### Do not do

| Avoid | Why | Cost avoided |
| --- | --- | --- |
| Graph databases, entity resolution, community summaries (Zep, Mem0g, Cognee) | Built for conversational scale; Zep needs at least five LLM stages per ingest and Mem0 measured Zep's store at over 600k tokens ([Mem0 paper](https://arxiv.org/html/2504.19413v1)) | High |
| LLM-chosen automatic delete or update on write (Mem0 CRUD) | Silent loss of valid records; contradiction handling is always LLM judgment | Medium |
| Automatic rewriting of neighboring records (A-Mem "evolution") | Churns diffs and defeats review; A-Mem scored lowest in Mem0's re-run ([A-Mem](https://arxiv.org/html/2502.12110)) | Medium |
| Machine-local or hidden memory stores | Both documented poisoning cases hit stores outside review | n/a |
| Loading all records every session (Cline Memory Bank pattern) | Recurring context cost with no evidence of benefit ([Cline docs](https://docs.cline.bot/features/memory-bank.md)) | Ongoing tokens |
| Background auto-consolidation without review | GitHub rejected offline curation as costly and still needing read-time checks | Medium |
| Resetting decay or confidence on retrieval | Copilot deliberately does not; reading proves nothing | n/a |
| Further retrieval tuning before baselines exist | Unlikely to be the bottleneck at 170 records | Medium |
| Citing LoCoMo or LongMemEval numbers as evidence for Wavefoundry | Conversational, disputed and often not memory-bound | n/a |
| Merging distinct lessons into general summaries | Condensed experience is often ignored | n/a |

## How to evaluate it: four tiers, baselines first

The literature offers no off-the-shelf benchmark for a repo-specific lesson store, so Wavefoundry has to build a small one. Four tiers, from cheap to expensive, would answer the real questions.

The first tier is retrieval with honest queries. For most or all records, write two or three queries in situation language: the task statement, the error text, the touched path or a diff excerpt an agent would have before it knew the lesson. At least one query per record should come from a different author or model family than the one that wrote the record. Filter out queries whose embedding cosine to the target is 0.95 or higher, or whose sequence ratio is 0.9 or higher ([leakage audit practice, preprint](https://arxiv.org/pdf/2607.13311)). Keep the self-summary query only as a labeled sanity floor. Add **null queries**, where no record applies and the correct result is nothing, following LongMemEval's abstention category ([LongMemEval](https://arxiv.org/html/2410.10813)). Add **stale cases**, where a superseded record coexists with its replacement. Freeze the query set with a hash before tuning, and tune only on a dev split. Report recall@5, MRR, precision at the shown set, the null-query false-show rate and the stale-shown rate, each with bootstrap or Wilson intervals. With roughly 170 records the intervals will be wide, so compare configurations on paired queries rather than claiming absolute scores ([small-sample intervals, preprint](https://arxiv.org/html/2606.05308)).

The second tier is baselines and ablations on the same queries. The essential arms are no memory, grep over `docs/agents/memory/` using terms an agent would plausibly search for, BM25-only, dense-only, the hybrid without reranking, the full production path and **full context**, meaning all active records placed in the prompt. The full-context arm matters because it beat every memory system on LoCoMo in Mem0's own paper, and the whole store fits in a modern context window many times over. If the production path does not beat grep and full context on precision at the shown set and on null-query behavior, the retrieval stack is not earning its complexity. Queryless policy ordering gets its own comparison against relevance-only and recency-only ordering for the session-start briefing.

The third tier is mechanical staleness, which needs no judge. Measure the fraction of active records whose targets or evidence refs fail to resolve at HEAD, how that fraction changes over time, and whether churn-flagged records turn out stale on review more often than unflagged records of the same age. That last comparison is the only direct test available for churn decay. If churn-flagged records are not stale more often, the signal is not working.

The fourth tier is downstream, and it is the only tier that answers "does memory help". Run a small paired task suite, even 10 to 20 tasks with tests, drawn from past waves where a record exists because something went wrong. Each task runs with memory off, with the oracle record injected by hand, and with production retrieval. Record test outcome, tool calls and tokens. The oracle arm bounds the possible gain and separates "the lesson is useless" from "retrieval missed it". That is the design VibeMemBench uses: it keeps only targets where injected history helps in a reference setting ([VibeMemBench](https://arxiv.org/abs/2609.23570)). Treat the results as directional, since CTIM-Rover's 45 samples produced differences too small to separate from noise. If an LLM judges relevance in any tier, validate it against 50 to 100 human labels and use a different model family from the query author. LongMemEval reports **over 97% judge-human agreement** with a strong judge, while the LoCoMo audit shows how lenient a weak judge can be ([LongMemEval](https://arxiv.org/html/2410.10813); [Penfield Labs audit](https://dev.to/penfieldlabs/we-audited-locomo-64-of-the-answer-key-is-wrong-and-the-judge-accepts-up-to-63-of-intentionally-33lg)).

## What nobody knows yet, including us

The largest gap is the one no outside source can fill: whether this store improves outcomes in this repository. The literature cannot fill it either, because no controlled study of a lessons-learned store for one long-lived repository exists. The experience-reuse gains reported on SWE-bench, roughly 4.65 to 9.4 points, come from self-reported, cross-repository pools with backbones and baselines that are not comparable ([MemGovern](https://arxiv.org/abs/2601.06789); [MemCoder, preprint](https://arxiv.org/pdf/2603.13258)). They suggest that verified experience can help. They do not show that Wavefoundry's does.

Several specific mechanisms have no evidence at all. Nothing tests churn-coupled decay, the right budget size, the value of eight kinds over three, queryless policy ordering, or human or agent review against agent-only validation. Nothing isolates failure-type memories on coding tasks, although SWE-Exp uses failed trajectories without an ablation ([SWE-Exp, preprint](https://arxiv.org/html/2507.23361v2)). The evidence that a stale record is worse than no record rests on one small preprint and one abstract. Poisoning results such as AgentPoison's **about 80% attack success at under 0.1% poison rate** come from settings unlike a review-derived lesson store ([AgentPoison, NeurIPS 2024](https://arxiv.org/html/2407.12784v1)), and a follow-up says such results come largely from idealized settings ([Memory Poisoning Attack and Defense, preprint](https://arxiv.org/pdf/2601.05504)). Wavefoundry's exposure depends on whether review findings ever ingest untrusted text, and that has not been audited.

The research behind this report also has gaps. Many 2026 papers were read at abstract level only, including the AGENTS.md study's per-condition deltas, VibeMemBench's design details and the stale-memory revocation work (Memora, TEPA, AgingBench). Copilot's branch behavior is undocumented, so it is unknown how a memory valid on main and wrong on a feature branch is handled. That question applies directly to Wavefoundry's churn signal, which is computed on one checkout. Roo Code and Amazon Q were not researched.

## Conclusion

The research changes the question Wavefoundry should ask about its memory system. It is not "which mechanism should we add next" but "what evidence would let us remove one". The surveyed systems that published ablations show most of the value sitting at the two ends of the pipeline, what gets admitted and what gets shown, and little in the machinery between. Wavefoundry has already invested at both ends. Its untested middle, decay scalars, audit ordering and the retrieval stack, is where simplification is most likely once baselines exist. Churn is best treated as a cheap alarm that asks for a check, not as a judgment about truth.

The second implication is that read-time verification is the missing primitive, and Wavefoundry has an unusual advantage in building it. Copilot needs an LLM to judge whether a citation still holds. Wavefoundry's records name files and symbols in a repository it has already indexed, so the first-order check, "does the thing this record is about still exist", is free and deterministic. That one mechanism addresses the best-documented harm (stale guidance followed over live code), turns churn from a guess into a trigger, and gives the evaluation its staleness metric. If the evaluation then shows that grep or full context matches the production path, the honest response is to accept the simpler design, which is the kind of result Wavefoundry's own reduced-work principle asks for.
