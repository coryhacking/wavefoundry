Owner: Engineering
Status: active
Last verified: 2026-11-23

The body below is copied unchanged from wave 245na's work folder on 2026-11-23 as the evidence base for arc `244cm-arc memory-quality`.

## Key question 1: What do the main memory benchmarks measure, and what are their flaws?

### Takeaway
Public benchmarks (LongMemEval, LoCoMo, MemoryAgentBench, MemBench, BEAM) are all conversational-memory QA tests with LLM-judged answers. They share an ability taxonomy (extraction, multi-session reasoning, temporal reasoning, knowledge update, abstention) that is useful as a checklist for a coding-lesson system, but none transfers directly. LoCoMo in particular has documented answer-key and judge problems.

### Cited Findings
- LongMemEval (arXiv 2410.10813, submitted Oct 2024, ICLR 2025): 500 questions testing information extraction, multi-session reasoning, temporal reasoning, knowledge updates and abstention; commercial assistants and long-context LLMs lost about 30% accuracy over sustained interaction — [arXiv abs](https://arxiv.org/abs/2410.10813)
- LongMemEval has seven question types (single-session user/assistant/preference, multi-session, knowledge update, temporal, abstention); judge is gpt-4o-2024-08-06 with a reported >97% agreement with human experts; abstention is 30 questions rewritten as false-premise questions; haystacks are LongMemEval_S (~115k tokens, ~50 sessions) and _M (500 sessions, ~1.5M tokens) with evidence sessions inserted at random positions — [arXiv html](https://arxiv.org/html/2410.10813)
- LongMemEval reports retrieval separately from QA: Recall@k and NDCG@k, at session and round granularity. Keying the index on the raw value is a strong baseline; condensed forms alone (summaries, keyphrases, facts) did not improve recall; value plus extracted facts gave +9.4% recall@k and +5.4% QA accuracy on average (LongMemEval_M round-level top-5 recall 0.582 -> 0.644) — [arXiv html](https://arxiv.org/html/2410.10813)
- LoCoMo (arXiv 2402.17753, Feb 2024): conversations of ~300 turns, ~9K tokens, up to 35 sessions, generated by LLM agents from personas and temporal event graphs, then human-edited; tasks are QA, event summarization, multimodal dialogue generation; RAG and long context help but trail humans — [arXiv abs](https://arxiv.org/abs/2402.17753)
- LoCoMo audit by Penfield Labs (a memory-system vendor): 99 score-corrupting errors in 1,540 non-adversarial questions (6.4%), including hallucinated facts, wrong temporal reasoning, speaker attribution errors; a GPT-4o-mini judge accepts vague on-topic answers, up to 63% of intentionally wrong answers; ceiling about 93% — [DEV Community](https://dev.to/penfieldlabs/we-audited-locomo-64-of-the-answer-key-is-wrong-and-the-judge-accepts-up-to-63-of-intentionally-33lg)
- Zep reported LoCoMo category 5 (adversarial) lacked ground-truth answers so Mem0 and Zep excluded it, and disputed Mem0's SOTA claim — [Zep blog](https://blog.getzep.com/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/)
- Mnemosyne paper manually checked LoCoMo gold answers against sources and calls the benchmark inherently flawed — [arXiv 2510.08601](https://arxiv.org/pdf/2510.08601)
- MemoryAgentBench (arXiv 2507.05257, Jul 2025): four competencies: accurate retrieval, test-time learning, long-range understanding, selective forgetting; adapts long-context datasets into incremental multi-turn form; no tested method masters all four — [arXiv abs](https://arxiv.org/abs/2507.05257)
- MemBench (Tan et al., arXiv 2506.21605, 2025): factual vs reflective memory, participation vs observation scenarios; metrics are multiple-choice accuracy, Recall@10, capacity (accuracy drop as memory grows) and efficiency (read/write time); authors note it uses structured data only. A different "MemBench" (He et al., arXiv 2409.15240, 2024) targets emotional dialogue — name collision — [arXiv html](https://arxiv.org/html/2506.21605v1), [search listing](https://arxiv.org/pdf/2409.15240v1.pdf)
- BEAM (arXiv 2510.27246, Oct 2025, ICLR 2026): 100 conversations from 100K to 10M tokens with 2,000 probing questions; proposes LIGHT (episodic memory, working memory, scratchpad); 10M-token results come mostly from vendor write-ups — [arXiv](https://arxiv.org/abs/2510.27246), [Mem0 explainer (vendor)](https://mem0.ai/blog/what-is-beam-memory-benchmark-the-paper-that-shows-1m-context-window-isnt-enough)
- EverMemBench (arXiv 2602.01313, 2026) shows multi-hop reasoning collapsing in multi-party settings, oracle models near 26%; EvolMem lists Multi-Session Chat (Xu et al., 2022) as an older benchmark with subjective queries — [EverMemBench](https://arxiv.org/html/2602.01313v1), [EvolMem](https://arxiv.org/pdf/2601.03543)

### Inferences
- The shared taxonomy maps onto a lesson store: extraction = find the lesson for a situation; knowledge update = a lesson superseded by a newer one; abstention = query where no lesson applies (should return nothing); temporal = lesson valid only after/before a version or wave. Multi-session reasoning (combining several lessons) is probably rare for 170 records.
- Benchmark scale (100K-10M tokens, hundreds of questions) does not apply to ~170 records; borrow the question-type taxonomy, the retrieval-vs-answer split and the judge-validation habit, not the data.
- LoCoMo evidence is vendor-heavy; treat the 6.4% figure as unreplicated by an independent peer-reviewed source (the audit repo is said to be at github.com/dial481/locomo-audit; I did not open it).

### Gaps
- MemoryBank (2023, pre-window) and Multi-Session Chat details were not fetched; no primary-source metrics were read for them.
- MemoryAgentBench dataset names, metrics and per-task scores not read (abstract only). LoCoMo's metrics (F1, ROUGE, LLM judge variants) not verified here. LongMemEval per-type counts not extracted.
- BEAM headline scores not read from the paper.

## Key question 2: How is retrieval quality measured, and how are held-out queries built to avoid self-query leakage?

### Takeaway
Memory papers report retrieval separately (Recall@k, NDCG@k, sometimes Recall@10) from answer quality (LLM-judge accuracy). Queries come from independently authored questions about evidence, not from the evidence text. I found no source directly naming "self-retrieval inflation" in memory work, but IR literature documents near-duplicate leakage and synthetic-query bias.

### Cited Findings
- LongMemEval separates retrieval (Recall@k, NDCG@k) from end QA accuracy and shows the two respond to indexing choices differently — [arXiv html](https://arxiv.org/html/2410.10813)
- Near-duplicate queries between training and test inflated retrieval effectiveness on Robust04 and TREC Common Core and could reorder systems (Frobe et al., SPIRE 2022); the effect shrinks as leakage falls — [search summary of arXiv 2206.14759](https://arxiv.org/abs/2206.14759v2)
- Rahmani et al. (arXiv 2506.10301): LLM-generated queries and judgments favor LLM-based systems; bias matters more for absolute scores than for relative system comparison — [arXiv html](https://arxiv.org/html/2506.10301v1)
- Leakage audit practice: check each eval query against nearest synthetic/train query by embedding cosine (>=0.95) and sequence ratio (>=0.9); leave-one-corpus-out as a transfer check — [arXiv 2607.13311](https://arxiv.org/pdf/2607.13311)
- SeedRG (Microsoft Research) filters out questions answerable without retrieval, a knowledge-leakage filter — [Microsoft Research](https://www.microsoft.com/en-us/research/publication/generating-leakage-free-benchmarks-for-robust-rag-evaluation/)

### Inferences
- Querying a record with its own summary is lexically and semantically a near-duplicate of the indexed text; any embedding or BM25 retriever will score near ceiling. It measures indexing round-trip, not retrieval of lessons by the situations that call for them.
- A sound holdout: write queries from the situation side (the task description, error message, file path or diff an agent would have before the lesson is known), by someone/something that did not see the record text; then filter any query whose similarity to its target exceeds a threshold (e.g. the cosine/sequence-ratio audit above) or that is answerable by a no-memory model (SeedRG-style filter).
- Report recall@k and MRR with NDCG only if graded relevance exists; with ~170 records and perhaps 100-200 queries, report intervals (bootstrap), not point values.

### Gaps
- BEIR and TREC pooling methodology were not fetched; claims about them are not made here.
- No source found that names or quantifies self-retrieval inflation specifically.

## Key question 3: Are there evaluations of memory for coding agents?

### Takeaway
Yes, a small, recent set, and the results are sobering: memory often fails to help or hurts unless it is compact and correctly selected. VibeMemBench (Sep 2026) and SWE-ContextBench (Feb 2026) are the closest designs to "do past lessons help".

### Cited Findings
- SWE-ContextBench (arXiv 2602.08316, Feb 2026): 1,100 experience tasks and 376 related tasks over 51 repos and 9 languages; related tasks found via issue/PR cross-references; metrics are resolution rate and test pass rates vs a no-context baseline, plus time and cost. On Lite, oracle summaries raised resolution 26.26% -> 34.34%; agent-selected ("free") summaries fell to 22.22%, below baseline; free full context raised cost ~24% with no accuracy gain; Mem0 weakest, Supermemory best (30.30%) — [arXiv html](https://arxiv.org/html/2602.08316)
- VibeMemBench (arXiv 2609.23570, Sep 2026): 111 targets from 90 SWE-rebench V2 repos, 3,634 history trajectories; executable tests decide resolution; targets kept only if injected history improves the outcome in a reference setting; verified experience raised resolution on 4 of 5 held-out solvers by 1.1-4.5 points and cut steps on all five; four existing memory systems failed to beat matched memory-off baseline in 11 of 12 pairings — [arXiv abs](https://arxiv.org/abs/2609.23570)
- CTIM-Rover (arXiv 2505.23422, 2025): episodic memory on AutoCodeRover did not outperform baseline in any configuration (40% vs 42%; memory-only 31%); attributed to irrelevant items (a word match on "clean"), unfiltered context given at start, over-compressed memory; only 45 test samples — [arXiv html](https://arxiv.org/html/2505.23422v1)
- SWE-Bench-CL (arXiv 2507.00014): chronologically ordered SWE-bench Verified sequences for continual learning; MemGym (arXiv 2605.20833): memory events in coding trajectories (repeated evidence, stale observations, failed hypotheses); MemCoder (arXiv 2603.13258) self-reports +9.4% resolved rate on SWE-bench Verified (unverified) — [search listing](https://arxiv.org/html/2507.00014v1), [MemGym](https://arxiv.org/pdf/2605.20833), [MemCoder](https://arxiv.org/pdf/2603.13258)

### Inferences
- No benchmark found tests "lesson prevents a repeated mistake" directly on a repo-specific lesson corpus; closest is VibeMemBench's matched memory-on/off, test-verified design. That design suggests a transferable idea: keep only queries/tasks where oracle (hand-picked) lesson injection helps, so retrieval failures are separable from lessons that are useless.
- Because harm from irrelevant memory is documented (CTIM-Rover, SWE-ContextBench), precision at the shown set matters as much as recall.

### Gaps
- VibeMemBench design details (mixing, task counts per repo, statistics) came from the abstract-level fetch only; PDF was binary and unread.
- SWE-Bench-CL, MemGym, MemCoder were seen only via search snippets.

## Key question 4: How to measure precision, staleness and downstream effect?

### Takeaway
No standard exists for staleness or shown-irrelevant precision in published memory benchmarks I found; the closest are LongMemEval's knowledge-update and abstention types and coding-memory matched-ablation task outcomes. These must be defined locally.

### Cited Findings
- Knowledge-update and abstention are explicit LongMemEval categories (false-premise questions test "I don't know") — [arXiv html](https://arxiv.org/html/2410.10813)
- MemBench adds capacity (accuracy as memory grows) and efficiency metrics — [arXiv html](https://arxiv.org/html/2506.21605v1)
- Downstream with/without comparison, plus oracle-memory arms, is used by SWE-ContextBench (no-context baseline, oracle vs free) and VibeMemBench (matched memory-off) — [SWE-ContextBench](https://arxiv.org/html/2602.08316), [VibeMemBench](https://arxiv.org/abs/2609.23570)
- Irrelevant retrieved memory shifted agent behavior and cost: CTIM-Rover wrong-function investigations; SWE-ContextBench +24% cost with no gain — [CTIM-Rover](https://arxiv.org/html/2505.23422v1), [SWE-ContextBench](https://arxiv.org/html/2602.08316)

### Inferences
- Precision at shown set: for each query, label every shown lesson relevant/irrelevant/harmful; report precision@shown, fraction of queries with at least one irrelevant item, and a "null-query" rate (shown anything when nothing applies).
- Staleness: include records known to be superseded or invalid (deprecated, changed code paths); report rate at which a stale record is shown, and whether the superseding record outranks it; check cited file/symbol existence mechanically against HEAD where records cite paths.
- Downstream: paired runs per task with memory off, oracle lesson, and retrieved lessons; outcome via tests/lint or reviewer, plus steps/tokens; the oracle arm bounds the possible gain.

### Gaps
- No peer-reviewed definition of staleness metrics found; the above is design inference.

## Key question 5: What practices fit small corpora?

### Takeaway
Use a frozen, independently authored query set with a leakage filter, paraphrase variants, a validated judge (or human adjudication) with confidence intervals, and ablations. With ~170 records, expect wide intervals and avoid fine-grained ranking claims.

### Cited Findings
- ARES: fine-tuned judges plus a few hundred human annotations as a validation set; prediction-powered inference gives confidence intervals, which the authors say RAGAS lacks; 95% level — [ARES arXiv](https://arxiv.org/html/2311.09476v2)
- Small labeled sets give wide intervals (2026 Amazon preprint extending PPI to ranking metrics) — [arXiv 2606.05308](https://arxiv.org/html/2606.05308)
- Judge reliability varies: LongMemEval reports >97% judge-human agreement with gpt-4o, while a LoCoMo audit found a lenient judge accepting up to 63% of wrong answers — [LongMemEval](https://arxiv.org/html/2410.10813), [Penfield audit](https://dev.to/penfieldlabs/we-audited-locomo-64-of-the-answer-key-is-wrong-and-the-judge-accepts-up-to-63-of-intentionally-33lg)
- Synthetic LLM-authored evaluation sets bias absolute scores toward LLM systems — [arXiv 2506.10301](https://arxiv.org/html/2506.10301v1)
- Indexing ablation is standard: LongMemEval compared key designs (value, summary, keyphrase, fact, value+fact) — [arXiv html](https://arxiv.org/html/2410.10813)

### Inferences
Recommended practice for Wavefoundry (about 170 lessons), replacing the 12-record self-summary diagnostic:
1. Cover all or most records, not 12; for each, write 2-3 queries in situation language (task statement, error text, touched path), with at least one by a different author or model than the one that wrote the record, and a different style (paraphrase, keyword-poor, long).
2. Leakage filter: drop or flag queries with cosine >=0.95 or high token overlap to the target text; keep the self-summary query only as a labeled sanity floor, reported separately.
3. Add null queries (no lesson applies), and update/stale cases (superseded lesson present), scored for abstention and staleness.
4. Freeze the set (versioned file, hash) before tuning; tune on a dev split, report on a held-out split; never edit queries after seeing results.
5. Report recall@k, MRR, precision@shown, stale-shown rate, null-query false-show rate, each with bootstrap or Wilson intervals; per-type breakdown; paired comparison between configurations (same queries) rather than absolute claims.
6. Ablate: no memory, BM25 only, embedding only, hybrid, with/without rerank, raw vs expanded keys (value+summary), oracle lessons.
7. If an LLM judge scores relevance, validate it on a human-labeled subset (e.g. 50-100 items) and report agreement; use a different model family from the one that authored queries.
8. Downstream: a small paired task suite (even 10-20 tasks with tests) comparing memory off / oracle / retrieved; treat as directional given sample size (CTIM-Rover used 45 samples and differences were small).
