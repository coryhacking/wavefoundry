# Memory quality: written, maintained, indexed and evaluated

Owner: Engineering
Status: complete
Last verified: 2026-11-26

Record ID: `244cm-arc memory-quality`

## Outcome

Agents working in a repository get memory records that are worth surfacing, and maintainers can show it with numbers. Records must be properly written, maintained, indexed and evaluated (operator decision, 2026-11-23). The arc succeeds when three things hold:

1. A frozen situation-language evaluation reports, for each wave in this arc, whether the change moved its target metric.
1. No active record silently degrades from semantic to lexical retrieval after an edit outside Review memories.
1. Every surfaced record still points at code that exists, or is queued for revalidation.

**Beneficiaries:** agents that receive briefings and `memory_search` results, and maintainers who run Review memories.

**Boundaries:** the arc keeps the current architecture: repo-visible typed records, evidence refs, strict admission, non-destructive retirement and the capped briefing. The research assessment supports that architecture and calls it unproven where it is most original ([assessment](research/agent-memory-systems-assessment.md), "The verdict"). The arc proves or simplifies that architecture rather than replacing it. The downstream paired task suite (assessment tier four) is not planned in this arc.

**Evidence base:** the assessment and its four source notes are committed under [`research/`](research/). They were copied from wave `245na`'s work folder, which is deleted when that wave closes:

## Path

The tracks run as waves in this order. Evaluation comes first because every later track needs it to show an effect.

| Track | What it changes | How its signal is measured |
| --- | --- | --- |
| 1. Evaluation, including index signals | A frozen query set with about 2 or 3 situation-language queries per active record, authored independently of the record text. A leakage filter, null queries, stale cases and a dev/held-out split by record. Recall@5 and MRR first, then precision of the shown set, false-show rate on null queries and stale-shown rate, each with intervals from a bootstrap that resamples records. Baselines on the same queries and the same corpus: no memory, grep, BM25-only, dense-only, hybrid without rerank, production and full context. Memory index coverage that separates stale from missing sources, from a model-free helper track 2 can reuse, and a check that each active record is reachable by its own target path. The self-summary query stays only as a labeled sanity floor. The choice of embedded text (summary, body, targets) is measured with ablation arms. | The arm metrics on the held-out split, read by the operator; the report makes no verdict. Spec `245sp`, wave `245na`. |
| 2. Indexing freshness | A record edited outside Review memories, for example by `git pull`, must not leave semantic search silently degraded to lexical. Options: reindex on any change under the memory root, and report memory coverage in `index_health`. `AGENTS.md` already asks agents to run `index_health` after Git operations, so the work is to make that check show memory coverage. Measured in wave 245na: during a docs index publish, memory search falls back to lexical (`semantic_index_unavailable`); a 14-minute `wf_memory_eval` run through the MCP server lost 7 to 15 of 606 production probes this way, likely triggered by the server's own checkpoint writes to the open wave's `wave.md`. Memory search should keep using the last published index while a rebuild runs. Before `index_health` reuses `sqlite_vector_store.memory_vector_coverage`, the body-path and source-hash builder that `memory_eval.memory_body_paths` duplicates from `memory_handlers._memory_query_records` moves to a shared module, so health checks do not depend on the eval script. | Track 1's `index_signals.memory_vector_coverage` stays complete after an edit made outside the tools, and `production_retrieval.fallback_probes` stays 0. |
| 3. Admission hardening | Evidence refs and targets must resolve at HEAD before the agent judges a candidate. Reject candidates that contain secrets or model-control tokens, and flag candidates whose evidence comes from untrusted text. Admit a record only when it holds something the code does not already show. Rewrites keep the concrete anchor and stay specific. An empty briefing is a normal result. | The false-show rate on null queries, and precision of the shown set, compared before and after on the frozen set. A count of rejected candidates by reason. |
| 4. Maintenance | A deterministic check that every target still resolves at HEAD. Churn or a missing target queues a record for revalidation instead of silently lowering its confidence. Decay resets only on a recorded check, never on read. The audit batch is ordered by signal first (broken target, churn flag, disputed in a session), then age. `Updated:` is re-stamped only after a recorded check. The never-decaying kinds keep their age exemption but are still revalidated on churn. Records the frozen evaluation cannot cover are reviewed as one batch: the 4 records `1t78a`, `1vo1a`, `1ydvk` and `21rnt`, for which independent labelers rejected 53 of 64 situation queries; the 39 whose queries were written from targets only because their source gives no situation; and the lesson-free `1wxu2`. Each is rewritten to state when it applies (situation, then action), retired as encoded elsewhere, or kept with a recorded reason. Rewritten records then get queries in a new, versioned freeze of the query set, with its own lock and operator spot-check, so later results stay comparable to the 245na baseline instead of replacing it. | The fraction of active records with unresolved targets, over time. Whether churn-flagged records are found stale on review more often than unflagged records of the same age, which is the only direct test of churn as a signal ([assessment](research/agent-memory-systems-assessment.md), tier three). The count of active records the evaluation cannot cover, which should fall over time. |
| 5. Upgrade delivery | Tracks 3 and 4 reach a target repository as code, but upgrade preserves an existing Review memories prompt, so its agents never learn the keep rule, and upgrade recommends Review memories only when the active-record cap is reached. `memory_brief` reports read-only counts of active records with an unresolved, churned or bare-name target. Seed 160 merges the keep rule into the project's existing Review memories and Close wave prompts, and recommends Review memories when any target is unresolved or churned. Upgrade still never curates records (operator decision, 2026-11-24: plan it, add it to the arc, and release after track 5 closes). | The brief's counts equal `wf_memory_eval`'s `maintenance_signals` on the same repository. After release, whether upgraded target repositories report the counts and run Review memories. |

**Dependencies:** tracks 2 to 4 each read track 1's metrics. Track 4's target check and track 3's resolution check share one mechanical primitive, so whichever ships first owns it.

**Retrieval-stack pause:** investment in the retrieval stack (dense, BM25, RRF, reranker) pauses until production is shown to beat the grep, BM25-only and full-context baselines on track 1's held-out split. Lifting the pause is the operator's decision, made from track 1's report; the report computes no pause or "beats" verdict (coordinator decision, 2026-11-23, after readiness review found that an automatic precision gate rewarded an arm that shows almost nothing). If grep or full context matches production on recall and precision, the arc should accept the simpler design.

## Declined

The operator declined these on 2026-11-23, with reasons from the assessment's "Do not do" table:

| Declined | Reason |
| --- | --- |
| Graph or entity stores (Zep, Mem0g, Cognee) | They are built for conversational scale. Zep needs at least five LLM stages per ingest, and Mem0 measured Zep's store at over 600k tokens. |
| Automatic LLM delete or rewrite on write (Mem0 CRUD, A-Mem evolution) | They lose valid records silently, churn diffs and defeat review. A-Mem scored lowest in Mem0's re-run. |
| Hidden or machine-local stores | Both documented memory-poisoning incidents in coding agents hit stores outside the repository review path. |
| Always loading every record | It adds recurring context cost with no evidence of benefit (the Cline Memory Bank pattern). |
| Background auto-consolidation | GitHub rejected offline curation as costly and still needing read-time checks. |
| Decay reset on read | Reading proves nothing about a record's truth. Copilot deliberately resets expiry only on an explicit upvote. |
| Citing LoCoMo or LongMemEval numbers as evidence | They are conversational, disputed and often not memory-bound. An audit found 6.4% of LoCoMo's answer key wrong. |

Consolidation dry-run groups were left unapplied because each pairs unrelated lessons that share targets.

An author isolated from record text wrote the new queries and a separate labeler accepted 5 of 6. Both leakage filters rejected none. Version 1 and its lock are unchanged. Because the split is keyed by record id, rewritten records can change split, so version 2 is a new baseline, not a rerun of version 1.

## Closure

Closed November 26, 2026. The five delivery tracks and both follow-up waves are complete. Against the three original success criteria:

1. **Measure each change.** The frozen evaluation established a production baseline. Admission and maintenance used it as a control and measured their effects through admission replay, unmatched briefings and target checks. Upgrade delivery used a two-hop rehearsal with 108 checks. The waves established those outcomes; the two query-set versions do not establish a before-and-after retrieval gain. See the [baseline](../../waves/245na%20memory-eval-production-path/wave.md), [admission replay](../../waves/249as%20memory-admission-hardening/wave.md) and [upgrade rehearsal](../../waves/24buu%20memory-revalidation-upgrade-delivery/wave.md).
2. **Detect loss of semantic coverage.** The index reports stale and missing memory coverage. During a concurrent index build, all 606 production probes used the relevance model, with zero lexical fallbacks and vector coverage for all 174 active records. [Index freshness wave](../../waves/248lb%20memory-index-freshness/wave.md)
3. **Keep targets current or flag them for review.** The November 25 review left zero unresolved or noncanonical targets. The audit still flagged 58 records for target churn so reviewers could check whether the lessons remained applicable. [Maintenance wave](../../waves/249ar%20memory-maintenance-by-signal/wave.md)

Whether surfaced memories improve decisions during real engineering work remains unmeasured. The [research assessment](research/agent-memory-systems-assessment.md) describes the downstream paired-task evaluation as a separate follow-up outside this arc.

The arc met its final two closure conditions on November 25. [Wave 24bik](../../waves/24bik%20memory-add-rationale-lines/wave.md) closed after delivering rationale fields for memory creation and consolidation. [Wave 24a51](../../waves/24a51%20memory-validate-single-line/wave.md) closed after aligning validation with those writers. A rationale field records the reviewer's reasoning. Its presence alone does not establish the quality of that reasoning.

## Next step

No arc work remains. The operator's November 25 decision to pause retrieval changes stands. On the frozen version 2 evaluation, production memory search combined BM25 and vector ranks and screened the shortlist for relevance. It achieved .755 recall@5, .392 precision and .370 false-show on the rerun. The unscreened hybrid reached .899 recall@5 and .239 precision and returned a memory for every null query. These results support keeping the relevance screen. Any future retrieval experiment should report what it gains in recall and what it costs in irrelevant memories shown.
