# A Readiness Approval Is Accepted Silently Against An Already-Stale Receipt

Change ID: `1upba-bug failed-prepare-appends-receipt-and-lapses-approvals`
Change Status: `planned`
Owner: Engineering
Status: planned
Last verified: 2026-08-08
Wave: 1uprb review-authority-mutation-on-failure

> **The change ID and wave slug record the original hypothesis, which review falsified.** This is not a mutation-on-failure defect and nothing in the publication path is touched. Both council seats independently disproved that framing; the delivered scope is the silent acceptance of stale readiness approvals plus the missing attribution. The names are kept rather than churned so the ledger and the disproof stay linked.

## Rationale

`wf_review_event` binds a readiness approval to whatever receipt is currently in the ledger — `wf_review_event_response`, at the `readiness_approval` branch that stamps `semantic_event["policy_receipt_id"] = receipt["receipt_id"]` — and **never recomputes the policy inputs**. So when a policy input has already moved, the approval is recorded against a receipt that is already superseded-in-waiting, and the call returns `status: ok` with **zero diagnostics**. Executed:

```
[plan edit lands -> receipt_append_required already True]
wf_review_event(approval, wave-council-readiness, readiness): ok   diagnostics: []
council current? True
--> next prepare publishes the pending receipt; council current? False
```

The approval was **dead on arrival**. It can never satisfy any gate: `review_authority_projection` in `review_evidence.py` validates a readiness approval only while `approval_record["policy_receipt_id"] == current_receipt["receipt_id"]`, so either the next prepare mints the pending receipt and the approval is non-current, or no prepare runs and `review_policy_receipt_stale` blocks review and close. The system writes a permanently unusable record into an append-only authority ledger and reports success.

**Nothing tells the operator which input moved.** `prepare(mode='dry_run')`, the natural pre-flight, returns **no diagnostic** when a mint is pending; the signal exists only as `data.review_policy.receipt_append_required`, buried in the payload. `wf_mark_ac(state='~')` publishes a receipt on its success path with `status: ok` and an **empty** diagnostic list, silently moving a current council approval to non-current, with the signal buried in `data.review_receipt_refreshed`.

**Measured cost.** In wave `1ur6o` the `wave-council-readiness` readiness approval was recorded **six** times (ledger indices 1, 5, 10, 12, 14, 22); indices 12 and 14 are verbatim duplicates differing only in `context_id`. Every one of the six receipts differs from its parent in `policy_input_digest` **only** — `evaluator_version`, `required_lanes` and `delivery_council_required` are byte-identical throughout — so each supersession was a real canonical input change that the operator was never shown.

**What this change is NOT.** An earlier revision of this plan asserted that a failing prepare mutates review authority as a side effect, and proposed suppressing that write. Both council seats disproved it by execution. Prepare appends a receipt only when `receipt_append_required` is already true; a genuine no-op prepare returns `ok`, mints nothing, and lapses nothing. **Corrected by the sibling change `1urlc`'s measurement:** a change-doc edit is not the only way to make a mint pending. Editing the canonicalizer or the extractor does it with zero document edits, so the recovery is one prepare per canonicalizer edit rather than one prepare, and this wave must sequence `1urlc`'s canonicalizer work against this change's refusal. Prepare never invalidates a *live* approval; it materializes an invalidation the plan edit already caused. That correction is preserved in the Decision Log rather than deleted, because the rejected design was executed and found to be worse than the defect.

## Requirements

1. **A readiness approval must not be accepted silently against an already-stale receipt.** `wf_review_event` must recompute the policy inputs before binding, and when a mint is pending it must **refuse**, not warn. **Scope is every receipt-bound readiness approval, not just the council key.** the `readiness_approval` predicate in `wf_review_event_response` is true for every signoff key except `wave-council-delivery` and `operator-signoff`, so specialist lanes are receipt-bound too; the `1ur6o` ledger carries `policy_receipt_id` on `code-reviewer`, `qa-reviewer` and `release-reviewer` readiness approvals. Fixing only `wave-council-readiness` leaves half the defect shipping. **The recompute goes INSIDE `project_state_publication_lock`**, in `wf_review_event_response`'s inner `transact()`, beside the existing re-check that compares `live_receipt["receipt_id"]` against `semantic_event["policy_receipt_id"]`. That re-check compares receipt *ids*, so a plan edit that makes a mint **pending** without moving the current id passes it: an outside-the-lock check therefore leaves the exact defect this change exists to fix reachable under concurrency. The lock already exists on the mutating path, where `transact()` is called under `project_state_publication_lock(root)` for `mode == "create"`, so this adds no new lock structure; the cost is one `_prepare_policy_state` call per readiness approval, which is a handful of file reads. Refusal is correct because the record is dead on arrival either way, because it mirrors the refusal that already ships one branch above (`review_policy_reprepare_required` when no receipt exists at all, in `wf_review_event_response`), because the recovery is a single `wf_prepare_wave(mode='ready')` call, and because an append-only ledger cannot retract a warning that was ignored.

2. **The refusal must fire only on a positive determination of staleness, and the degradation must not become a bypass.** `_prepare_policy_state` returns `(None, errors)` from four sites, of which two are reachable at this check: an invalid `wave_review` config (the `normalize_wave_review_policy` branch) and an unreadable or undecodable change doc (the per-change read branch). The other two are already refused earlier by `validate_external_review_evidence`.

   - **Change-doc read errors degrade to a warning.** An unparseable plan must never make approvals unrecordable.
   - **Config errors REFUSE.** Degrading on a malformed `wave_review` config would turn one bad config into a global, config-controlled bypass of this entire change. State the consequence plainly rather than discovering it in the field: one bad config makes **every** readiness approval unrecordable repository-wide until it is fixed. That is accepted because the recovery is operator-controlled and `_wave_review_policy_diagnostics(root)` already surfaces config errors at review and close, but the refusal message must name the **specific** config error so the operator knows what to repair instead of reading a bare staleness refusal.
   - `_prepare_policy_state` can also return `(None, ())` — state absent with an **empty** error tuple, from the same `normalize_wave_review_policy` branch. An implementation branching on `errors` alone mishandles it, so this case must be handled and pinned explicitly.

3. **Every staleness signal must name what moved, within what the data supports.** A bare diagnostic code reproduces the confusion this change exists to remove. Four surfaces carry the shared attribution payload: the Requirement 1 refusal, the Requirement 4 dry-run diagnostic, `review_policy_receipt_stale` as emitted from `_review_policy_receipt_diagnostics`, and the Requirement 5 `wf_mark_ac` signal. The payload is the current receipt id, the pending receipt id, the differing `receipt_semantic_fields`, and the list of admitted change ids whose canonical bytes were digested.

   **Per-document attribution is NOT available and this change does not add it.** The per-change `sha256` values are computed into a local `change_inputs` list inside `_prepare_policy_state` and discarded; `policy_input_digest` is a single SHA over the whole payload; and `validate_policy_receipt` enforces a closed field set, so the map cannot be persisted without widening the validator and bumping `evaluator_version`. That bump supersedes every live receipt in every target repository on the first prepare after upgrade, lapsing every in-flight readiness approval — the exact harm this change exists to reduce. Declined on that trade; see the Decision Log. The signal must therefore say which inputs were digested, and must not imply it knows which one changed.

4. **`prepare(mode='dry_run')` must surface a pending mint as a diagnostic** and must continue to write nothing. Dry-run is the affordance an operator reaches for before mutating and is currently the one surface silent about the mutation it previews.

5. **`wf_mark_ac(state='~')` must not lapse a current readiness approval silently.** `wf_mark_ac_response`'s deferral path publishes a receipt on its success path and returns `ok` with an empty diagnostic list. This is the same defect class as Requirement 1 on a different surface. Its *write* is correct and stays; only the silence is in scope. It carries the same Requirement 3 attribution payload, because Requirement 5 calls it the same defect class and exempting it from the remedy would be inconsistent.

6. **Nothing in the publication path changes.** No write is suppressed, deferred, or reordered. This is a hard boundary, not a preference: both council seats executed the suppression design and found it either readies the wave on an approval bound to plan bytes that no longer exist, with a required lane and the delivery Council silently dropped, or refuses idempotently and wedges the receipt forever with no operator affordance to advance it. `wf_prepare_wave` has no force or confirm parameter, and adding one is a public MCP tool-surface change.

7. **The genesis path must keep working**, and is protected here by construction rather than by care: since no write moves, a new declared wave's first `prepare(mode='ready')` still returns `missing_wave_council_signoff` **and** still publishes the first receipt. The genesis fixture in `TypedExclusiveGateDerivationTests` (`tests/test_server_tools.py`), whose setup comment reads "Prepare first publishes the server-owned policy receipt/roster. The expected missing-approval result is still a successful publication boundary; readiness actors can only approve that current receipt.", must pass unmodified. Recorded because it is what killed the original design: `wf_review_event` refuses a readiness approval when no receipt exists, so withholding the genesis receipt makes readiness approval unrecordable and prepare permanently unsatisfiable.

8. **No approval-binding change ships.** Rebinding from `receipt_id` to `policy_input_digest` is declined on measurement. All six `1ur6o` receipts differ only in `policy_input_digest`, so digest binding would have lapsed at exactly the same six points and fixed nothing observed. It also reintroduces **approval revival**: `derive_receipt_id` hashes the semantic fields together with the parent receipt id, so an A → B → A' cycle yields three distinct ids (executed: `c3f25fc3…`, `4de83a71…`, `5103590b…`) and cannot resurrect the first approval, whereas a raw digest collides on the first and third. Separately, `receipt_semantic_fields` carries `required_lanes` and `delivery_council_required`, so a roster could in principle grow with the digest static; that argument is **defense-in-depth, not measured**, because every selector input is also a digest input and the state is reachable only via a selector code change that does not bump `evaluator_version`.

9. **The refusal must never leave the close gate more permissive than the silent accept it replaces.** `_required_wave_council_signoffs` is deliberately three-way under `transition_policy: applies-from-next-prepare`, which is the framework default (`seeds/007-review-system-overview.md`) and live in this repository (`docs/workflow-config.json`): a **stale** readiness approval keeps the key required, an **absent** one **drops it from the close roster**. The refusal converts stale into absent, so today's defect is accidentally self-healing and this change would remove that healing. Executed: after the very prepare the refusal instructs, the close roster falls from `['wave-council-readiness','wave-council-delivery']` to `['wave-council-delivery']`, with no residual blocking diagnostic. An operator who tries to do the right thing must not end up with weaker review than one who never tries.

   **Remedy:** condition the carve-out on the wave never having been prepared under the policy rather than on approval absence — fire it only when `current_policy_receipt(records) is None` **and** `not authority.ledger_errors`. The second conjunct is not optional: `resolve_review_authority` leaves `records` empty whenever `result.errors` is non-empty, so a receipt check alone would treat a corrupt ledger as "never prepared" and drop the readiness key, which is fail-open inside a fail-closed design. `ReviewAuthority.ledger_errors` exists and is populated by `resolve_review_authority`, and `authority` is **already in scope** at the close branch of `_required_wave_council_signoffs`, so the predicate is exactly `current_policy_receipt(authority.records) is None and not authority.ledger_errors` — which also avoids adding a second ledger read on the close path. This is a **gate read**, not the publication path, so Requirement 6's boundary is unaffected.

   **This moves the code toward its documented contract rather than away from it.** Seed 007 states that closure "does not retroactively require a missing readiness signoff for a wave that **never re-entered `Prepare wave`**". Receipt presence encodes "never re-entered Prepare" faithfully; approval absence does not, which is why the current predicate produces the inversion.

   **It is a deliberate, recorded behavior change to a pinned test.** `test_transition_policy_distinguishes_stale_absent_and_current_readiness` in `tests/test_server_tools.py` builds its `"absent"` fixture by publishing a receipt for **every** state and skipping only the approval, so that fixture has a receipt and today asserts `['wave-council-delivery']`. Under this remedy it must assert `['wave-council-readiness','wave-council-delivery']`, and a **sibling case must be added** pinning that a wave with **no** receipt still drops the key. Without saying so, AC-9 and AC-11 are in direct collision.

   **The amendment is continuous with that test's own governing principle, not a reversal of it.** Wave `1tsyx`'s change doc (`docs/waves/1tsyx review-lifecycle-simplification/1tr85-enh single-pass-review-lifecycle.md`) states it verbatim: *"A stale approval must block; it must never relax a requirement."* `1tsyx` fixed the stale case and left absent relaxing, because at that time absence implied "in flight from before the policy". This change's refusal makes absence reachable for **governed** waves, so extending the same principle to absent-with-a-receipt carries `1tsyx`'s intent forward. Measured blast radius: exactly **one** deviation across 1605 tests in `tests.test_server_tools`.

## Scope

**Problem statement:** The review ledger accepts readiness approvals that can never satisfy a gate, reports success for them, and never tells the operator which policy input moved — so the only visible symptom is having to record the same approval repeatedly, with no way to tell a live approval from a dead one.

**In scope:**

- Recomputing policy inputs in `wf_review_event`'s readiness-approval path and refusing a stale bind, with the malformed-input degradation.
- Attribution content shared by all four signal surfaces: the refusal, the dry-run diagnostic, `review_policy_receipt_stale` from `_review_policy_receipt_diagnostics`, and `wf_mark_ac`.
- A `review_policy_receipt_stale` diagnostic on `prepare(mode='dry_run')`.
- Surfacing `wf_mark_ac(state='~')`'s receipt supersession as a diagnostic rather than a payload field.
- The close-roster carve-out condition inside `_required_wave_council_signoffs` (Requirement 9). A gate read, not a write.

**Out of scope:**

- Any change to when or whether a receipt is written (Requirement 6).
- Rebinding approvals to `policy_input_digest` (Requirement 8).
- The digest canonicalizer. Wave `1ugk9` owns `canonical_review_policy_body`; this change must not move what is digested.
- Repairing `docs/architecture/data-and-control-flow.md` (line 476-477, prose with no containing symbol) ("Prepare is the sole writer of… the append-only `review_policy_receipt`"), which is **already false** — `wf_mark_ac` mints from an empty ledger, executed. Pre-existing drift, recorded here because this plan declares that doc affected; it needs its own change.

## Acceptance Criteria

- [ ] AC-1: Recording a readiness approval while a mint is pending is **refused**, reproduced as a red test first. Current code returns `ok` with zero diagnostics and must fail this test. The full response contract is asserted: `status`, the specific diagnostic code, that no evidence record was appended, and that the ledger is byte-identical across the refused call. **At least one specialist lane** (`code-reviewer`) is asserted alongside `wave-council-readiness`, because an implementation scoped to the council key alone would otherwise pass while leaving specialist lanes accepting stale binds. The **negative boundary** is asserted too: a `wave-council-delivery` approval and an `operator-signoff` are unaffected, since the `readiness_approval` predicate deliberately excludes them and an implementer who hoists the recompute above that branch would refuse them while still passing every positive case.
- [ ] AC-2: The degradation is pinned on **all three** of its distinguishable inputs, because an implementation branching on `errors` alone mishandles one of them: (a) a change-doc read error **warns and accepts**, and the warning states that the staleness check **could not be performed** and why, since the ledger will not record that this approval skipped verification; (b) an invalid `wave_review` config **refuses**, since degrading there would be a config-controlled global bypass; (c) `_prepare_policy_state` returning `(None, ())` with an empty error tuple — reachable by dropping `wave_review` from config mid-wave — **refuses**, with the named outcome asserted rather than a bare does-not-crash, which would pass for either branch.
- [ ] AC-3: The shared attribution payload appears on **all four** surfaces (refusal, dry-run, `review_policy_receipt_stale` from `_review_policy_receipt_diagnostics`, and `wf_mark_ac`), asserted on message content rather than diagnostic code. Content is the current receipt id, the pending receipt id, the differing `receipt_semantic_fields`, and the digested change ids. The test must also assert the message does **not** claim per-document attribution, which the persisted data cannot support. At least one fixture must differ in a **non-digest** semantic field, since every natural transition moves `policy_input_digest` only and an implementation hardcoding that one field name would otherwise pass; a Serialization Points edit that grows `required_lanes` and flips `delivery_council_required` produces such a state.
- [ ] AC-4: `prepare(mode='dry_run')` returns `review_policy_receipt_stale` when `receipt_append_required` is true, **and** `events.jsonl` and `wave.md` are byte-identical across the call. Both halves asserted, so the signal cannot be added by making dry-run mutate.
- [ ] AC-5: `wf_mark_ac(state='~')` that supersedes a receipt reports it as a diagnostic carrying the AC-3 payload. Pinned by a test asserting a current council approval goes non-current **and** the response says so; today the response is `ok` with an empty diagnostic list.
- [ ] AC-6: **No publication behavior changes**, pinned at `mode='create'` rather than `mode='ready'`, because `_activating` is create-only in `wf_prepare_wave_response` and the outcome this AC guards materializes only there. After a plan edit, `prepare(mode='create')` must still publish the pending receipt and still fail; and the test asserts (i) `Status` does **not** become `active`, (ii) the persisted `Required review lanes` bullet matches the **pending** receipt, and (iii) `delivery_council_required` matches it. Those three are exactly what the rejected design broke; a `mode='ready'` assertion cannot observe any of them.
- [ ] AC-7: Genesis is intact: a new declared wave's first `prepare(mode='ready')` publishes the receipt and returns `missing_wave_council_signoff`, after which a readiness approval is recordable. The genesis fixture in `TypedExclusiveGateDerivationTests` passes unmodified.
- [ ] AC-8: Anti-revival holds end to end: across an A → B → A' input cycle, three distinct receipt ids are produced, the A-bound approval is non-current **at the midpoint and after the revert**, and — symmetrically — an approval recorded at the midpoint against B is non-current after the revert. The symmetric half exists because the one-sided form would pass an implementation that special-cased the ledger's first approval.
- [ ] AC-9: **The refusal never leaves the close gate more permissive than the silent accept it replaces.** Asserted by comparing `_required_wave_council_signoffs` for close across the refused path and the current accept path, on a wave configured with `transition_policy: applies-from-next-prepare` (the framework default). The readiness key must remain required in both. Three further cases, each guarding a distinct way to get this wrong: a wave with **no** receipt must still drop the key, or an implementation that simply deletes the carve-out passes while breaking the legacy in-flight waves it exists to protect; a wave whose ledger cannot be read must **not** drop the key, since a receipt check alone fails open; and `test_transition_policy_distinguishes_stale_absent_and_current_readiness`'s `"absent"` case is **updated deliberately** to expect the readiness key, because its fixture publishes a receipt. That last one is a recorded behavior change, not a regression, and without naming it here AC-9 and AC-11 contradict each other.
- [ ] AC-10: Convergence, stated per lane rather than per wave: after a plan edit, one `prepare(mode='ready')` plus **one approval per receipt-bound readiness lane** restores current signoffs, with **zero** duplicate approvals. Pinning a single key would let the AC-1 lane-scoping defect ship green.
- [ ] AC-11: The full framework suite and docs-lint pass.
