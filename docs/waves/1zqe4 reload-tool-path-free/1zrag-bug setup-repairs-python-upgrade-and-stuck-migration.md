## Rationale

Two field defects hit one operator on 2026-10-03 when Homebrew moved `python3` from 3.13 to 3.14. Together they made `wf setup`, the documented repair for a stale tool venv, a dead end. They are planned as one change because the first defect's natural fix walks straight into the second: once setup proceeds past the venv check, the same run writes the receipt that setup then refuses to read.

**Defect 1: setup cannot repair a Python minor-version change.** The tool venv `~/.wavefoundry/venv` was built on 3.13. `wf setup` exited 2 with `the tool venv was built for Python 3.13 but this is 3.14 - run wf setup to rebuild it`, telling the operator to run the command that had just failed. Trace (verified against the tree):

- `wf_cli.main` skips activation for the setup subcommand (`if subcommand != _SETUP_SUBCOMMAND`).
- `setup_wavefoundry.main` calls `venv_bootstrap.activate_tool_venv(allow_version_mismatch=True)`, which returns without activating on a mismatch.
- `setup_reconciliation.session.__enter__` calls `sqlite_storage_migration.detect`, which calls `_database_schema` for each owned database name; when `index.sqlite` exists it runs `import sqlite_runtime`.
- `sqlite_runtime` runs `venv_bootstrap.activate_tool_venv()` at module import, without the allowance, so the version guard in `activate_tool_venv` prints the message and calls `sys.exit(2)`.

**Defect 2: setup writes a storage migration receipt it then refuses to read.** After the operator moved the stale venv aside to get past defect 1, `wf setup` stopped with `storage_receipt_supersedes_invalid`. The receipt is preserved at `.wavefoundry/index/sqlite-migration.json.stuck-2026-10-03`. It is `receipt_version` 2, kind `index_sqlite_schema8`, `state` `restart_required`, `reason` `index_database_rename`, `source_database` `current`, `source_version` = `target_version` = `1.28.0+ptiz`, `entry_path` `setup`. Its `supersedes` is the COMPLETE version-2 kind record of the 1.23 to 1.24 migration, which itself supersedes a complete version-1 record. Root cause, verified by execution (Progress Log 2026-10-03):

1. **Stale native binding.** With no usable tool venv, `import sqlite_runtime` in `_database_schema` (during `session.__enter__`) binds the module-level `apsw = None` and caches the module in `sys.modules`. Step 2 then builds the venv and `setup_index._reexec_with_venv_if_needed` activates it, but `session.prepare` ("Reclassify after canonical dependency provisioning") re-runs `detect`, and `_database_schema`'s `import sqlite_runtime` returns the cached module whose `apsw` is still `None`. `sqlite_runtime.connect` raises `RuntimeUnavailable`, so the probe still reports `runtime_unavailable`. The reclassification the code comments promise never sees the provisioned runtime.
2. **Misdetection.** In `detect`, `marker_satisfied` requires the authority schema to equal `SCHEMA_VERSION`; `runtime_unavailable` is not `"8"`, so `kind_required` is true for a perfectly current schema-8 database, and because the existing receipt is `complete`, `kind_can_start` is true. `prepare_upgrade` takes its `receipt["state"] == "complete"` branch and calls `_new_receipt(..., superseded=receipt)`. `_kind_dispatch` returns true (`runtime_unavailable` is not a legacy conversion schema), so the new record is the schema-8 kind with `reason` `index_database_rename` and `source_database` `current` (the authority role). `source_version` and `target_version` are both the installed `VERSION` because `session.__enter__` builds the setup context with `from_version=version, to_version=version`.
3. **Writer/reader disagreement.** `_new_receipt` embeds ANY superseded record under `supersedes` when the new record is a kind record. `read_receipt` accepts a version-2 record's `supersedes` only when `superseded.get("receipt_version") == RECEIPT_VERSION_LEGACY`. A kind record superseding a completed kind record is therefore written and then refused. `prepare_upgrade` wrote the record, `_refresh_hosts` rewrote it (the preserved receipt carries `hosts_observed_at`, equal to its `updated_at`), and the next `restore_checkpoint` call read it back through `read_receipt` and raised. From then on every reader refuses: `read_receipt` is called by `detect`, `require_ready` (indexer and `graph_snapshot` readiness), `restore_checkpoint`, setup and upgrade.

**The migration was not needed.** The live `index.sqlite` has inode 678055843, the same inode the stuck receipt recorded as `source_sqlite_identity`, and a read-only immutable probe of it returns `store_schema_version` `8`. The earlier aborted attempts (defect 1) exited inside `detect`, which writes nothing, so they did not cause the receipt; the write came from the later run with the venv moved aside, through the stale binding in item 1. After the receipt was moved aside, the next setup ran with a matching venv, the qualified probe returned `8`, no kind was required, and setup completed.

**Defect 3: rendered hooks exit 2 after a Python upgrade.** The operator approved folding this in (2026-10-04). Every hook body built by `render_platform_surfaces.compose_script` starts with `HOOK_BOOTSTRAP`, which wraps `_wf_venv_bootstrap.activate_tool_venv()` in `try/except Exception`. The version guard raises `SystemExit(2)`, which is a `BaseException`, so it escapes the handler and the hook exits 2. In Claude Code that night the pre-edit hook blocked every edit, because a `PreToolUse` exit of 2 blocks the tool call, and the rendered launcher in `.claude/settings.json` also exits 2 on failure. The `Stop` hooks (`session-capture`, `context-efficiency-project`) looped, because a `Stop` exit of 2 feeds stderr back and prevents the stop. The only rendered hook unaffected is `wf-session-start`, which is built by `compose_preactivation_script` and never activates.

Brief: the consumer is any operator whose Python minor version changes under an existing install (Homebrew, python.org, Windows Store, distro upgrades, `uv python`), on every OS. Success is that one ordinary `wf setup` rebuilds the venv and finishes without a spurious migration, and that a repository already holding a stuck receipt recovers through ordinary `wf setup` or has a stated, safe operator remedy.

## Requirements

1. **Deferral is sticky for the process.** When `venv_bootstrap.activate_tool_venv(allow_version_mismatch=True)` does not activate the tool venv (the venv is absent, or it was built for a different `(major, minor)`), `venv_bootstrap` records a process-local "activation deferred" state. While that state holds, any later `activate_tool_venv()` call in the same process that hits the same version mismatch returns without activating instead of calling `sys.exit(2)`. The first later call that activates successfully (the rebuilt venv matches the running interpreter) clears the state. The state is a module global only: it is not an environment variable and is not inherited by child processes. `venv_bootstrap` exposes a read accessor (for example `activation_deferred()`, returning `None`, `"absent"` or `"version_mismatch"`) and a reset accessor (for example `reset_activation_deferral()`). Because the state is process-global and tests call `setup_wavefoundry.main` in-process (`test_memory_backfill`, `test_setup_readiness_integration`), every test module that calls it in-process, and every test this change adds that sets the state, clears it with the reset accessor in `setUp`/`addCleanup` (or a shared fixture), so no test leaks a deferral into a later test.
2. **Native runtime is never imported while activation is deferred.** `sqlite_storage_migration._database_schema` returns `"runtime_unavailable"` for an existing database file WITHOUT importing `sqlite_runtime` when `venv_bootstrap` reports deferred activation and `sqlite_runtime` is not already in `sys.modules`. Its orphan-sidecar and `absent` handling is unchanged. After the deferral clears, the next probe imports `sqlite_runtime` for the first time in that process, bound to the provisioned `apsw`. Remaining exit-2 case, unchanged by this change: when `pyvenv.cfg` is unreadable or has no parseable version line, `_venv_python_version` returns `None`, the guard fails open, and `activate_tool_venv` (with or without the allowance) still prints its stderr message and calls `sys.exit(2)` if `_venv_site_packages` is missing for the running minor version. That path is POSIX-only in practice: on Windows `_venv_site_packages` is the version-free `Lib/site-packages`, so a stale venv there activates (fail-open) instead.
3. **Setup reclassifies a current store after provisioning.** In a setup run that starts with a mismatched or absent venv over an existing schema-8 `index.sqlite` with a complete receipt, `session.prepare` sees schema `8`, takes its "not migration_required" exit, writes no new receipt, and removes the setup checkpoint, which is the behavior `test_runtime_provisioning_reclassifies_current_store_without_restart` already asserts with a patched `detect`. If the deferral is still set when `session.prepare` runs (provisioning ended without activating the venv) and its `detect` reports the authority schema as `runtime_unavailable`, `prepare` raises `MigrationRequired("storage_setup_runtime_unavailable: ...")` before any receipt write instead of classifying from that probe. Ordinary setup is unaffected: Step 2 always builds the venv and activates it, which clears the deferral before `prepare` runs.
4. **Receipt contract: a kind record may supersede a completed kind record, verbatim.** `read_receipt` accepts a version-2 record whose `supersedes` is a dict that is either a version-1 record (as today) or a version-2 kind record in state `complete`; nested `supersedes` inside the superseded record are validated by the same rule, level by level, so every level is a dict with a supported `receipt_version`: a version-2 level carries a valid kind and is in state `complete`, and a version-1 level carries no kind and a recorded state (any of `STATES`), as before. `_new_receipt` embeds the superseded record verbatim (no flattening), since `setup_reconciliation.session._inspect` compares `_receipt_fingerprint(parent)` against the checkpoint's `setup_completed_parent.receipt_sha256` for crash continuity. Any other `supersedes` shape still raises `storage_receipt_supersedes_invalid`. Three writers in `sqlite_storage_migration` embed `supersedes`: `_new_receipt` (the `prepare_upgrade` complete-receipt branch), `_begin_chained_kind` (kind over a finished version-1 record) and `_install_kind_fence` (fence over a completed version-1 conversion). All three call the same helper `read_receipt` calls and refuse at write time any superseded record the reader would refuse, so writer and reader share one predicate.
5. **Recovery of a stuck spurious record.** Setup retires an unfinished record when ALL of the following hold, checked after dependency provisioning with a qualified runtime: the record is a setup-owned kind record (`entry_path` `setup`, no `pack_path`/`pack_sha256`); its state is `restart_required` or `quiesced`; it has no `work_dir` and no `candidate_sha256`, and no `index-migration-<id>` work directory exists (no staging began); `source_database` is `current`; nothing exists under the retired database name; `source_sqlite_identity` matches the live current database; and the qualified probe of that database returns `SCHEMA_VERSION`. The retirement is one receipt write and runs in `setup_reconciliation.session.prepare` after dependency provisioning and before `prepare_upgrade`. Setup then completes normally in the same run. A record failing any clause keeps today's behavior. The write depends on the record's `supersedes`:
   - **Complete version-2 parent (the field shape): restore it.** The embedded parent is written back verbatim: no field changes, not even `updated_at`, and the file is the canonical serialization of the embedded dict. Before that write, setup binds its checkpoint to the parent (`storage_migration_id` and `setup_completed_parent` with the parent's `_receipt_fingerprint`), so a crash between the two writes resumes through `_inspect`'s completed-parent continuity check, and a crash after both finds matching ids. The restored record is the shape runners 1.24 to 1.28 read (its own `supersedes` is version 1), it needs no host restart, and an older release can still be reinstalled over it. `validate_source_binding` returns early for a `complete` record, so a parent bound to older framework bytes passes setup on new bytes.
   - **Version-1 parent or no parent: close in place.** The record is set to `state` `complete` with `disposition` `already_current` and `reclaimed_bytes` `0` (the disposition `_migrate_schema8` writes when `schema == SCHEMA_VERSION and live == source`), and `installed_framework_sha256` is rebound to the current `framework_fingerprint`. This covers a legitimate pre-staging record written by `_begin_chained_kind` over a finished version-1 record when the authority is already the current name (N6). Restoring a version-1 parent would make `detect` require the fence again.

   In both paths setup then removes `.wavefoundry/upgrade-in-progress.json` on its ordinary "not migration_required" exit.
6. **Source binding tolerance is read-only.** `session._inspect` tolerates, without writing anything, a record that matches the structural clauses of Requirement 5 (everything except the qualified probe, which needs the runtime) when the installed framework bytes differ from its recorded `installed_framework_sha256`, for both its receipt binding check and its checkpoint fingerprint check. `validate_source_binding` itself is not relaxed. The only rebind is the one written by the Requirement 5 close-in-place path, after the qualified probe returns schema `8`; the restore path writes the parent unchanged. If the probe returns anything else, the retirement does not fire. `prepare_upgrade` then calls `validate_source_binding`, which refuses with `storage_setup_source_changed` exactly as today, and the receipt is left unchanged on disk. Every other unfinished setup record keeps the exact-bytes binding in `_inspect` too. Rationale: a pre-staging record has changed nothing on disk (the restart message itself says "No storage format change has occurred"), and the field recovery necessarily runs on new framework bytes.
7. **Operator remedy without the fix.** The CHANGELOG entry states the manual remedy for a repository on an unfixed release whose receipt reads `storage_receipt_supersedes_invalid`, and that it must be applied before upgrading. The remedy restores the embedded completed parent verbatim; it does not move the receipt aside. Steps: copy `sqlite-migration.json` aside for evidence, then rewrite the file as its own `supersedes` value. All of these must hold, and the text says how to check each:
   - the stuck record's `supersedes` is a version-2 kind record in state `complete`;
   - with every Wavefoundry host stopped, a read-only probe of `.wavefoundry/index/index.sqlite` returns `8`. The probe is Python, because stock Windows has no `sqlite3` command: `python3 -c "import sqlite3; c = sqlite3.connect('file:.wavefoundry/index/index.sqlite?mode=ro', uri=True); print(c.execute('SELECT value FROM meta WHERE key=?', ('store_schema_version',)).fetchone()[0])"` (table `meta`, key `store_schema_version`, as `_database_schema` reads them);
   - nothing exists under the retired database name;
   - the stuck record has no `work_dir`;
   - `.wavefoundry/upgrade-in-progress.json` is absent, or its `storage_migration_id` equals the parent's `migration_id`;
   - the tool venv's `pyvenv.cfg` version matches `python3 --version`.

   Then rerun `wf setup`. When a condition fails:
   - **Only the tool venv condition fails:** rebuild the venv without reading the receipt, then check every condition again. Rename the venv directory aside, then run `python3 .wavefoundry/framework/scripts/setup_index.py --root . --deps-only` (Windows: `python .wavefoundry\framework\scripts\setup_index.py --root . --deps-only`). Executed on a 1.28.0 fixture (Progress Log 2026-10-04): over the stale venv itself that command exits 2 with the version message, because `setup_index.main` imports `model_bundle`, which imports `sqlite_runtime` and activates; with the stale venv renamed aside it builds a matching venv, never opens the receipt and leaves the receipt and checkpoint byte-identical.
   - **Any other condition fails:** do not edit, move or delete the receipt, and do not upgrade. Keep `.wavefoundry/index/` as it is and report the receipt for a supported recovery.

   Why it is correct: `read_receipt` on 1.24 to 1.28 accepts the restored parent, because its own `supersedes` is version 1. `validate_source_binding` returns early for a `complete` record, so the parent passes on current framework bytes. `detect` finds the once-marker satisfied with a qualified probe, so no kind is required. The version-2 record stays in place as the fence `fence_required` exists to provide. The venv condition matters because, on an unfixed release, a setup without a usable venv repeats the stale binding and writes the same stuck shape again. In the stuck state the failing run has normally already built a matching venv.
8. **MCP stdout contract unchanged.** No new output is written to stdout by `venv_bootstrap` or the probe path; any new diagnostic goes to stderr. `server.py` is not edited, never passes the allowance, and its version-mismatch behavior (stderr message, exit 2) is unchanged.
9. **Platform behaviour.** Requirements 1 to 6 and 10 to 12 hold on Windows, macOS, Linux and WSL2 (see Platform Behaviour under Scope). The Windows venv layout (`Lib/site-packages`, no version in the path) and `pyvenv.cfg` parsing are unchanged.
10. **Hook bootstrap never exits on an unusable venv.** `HOOK_BOOTSTRAP` in `render_platform_surfaces` is the single canonical source every `compose_script` hook carries. Today it calls `_wf_venv_bootstrap.activate_tool_venv()` inside `try/except Exception`. It changes to:
    - call `activate_tool_venv(allow_version_mismatch=True)`, then read the Requirement 1 accessor;
    - catch `BaseException` other than `KeyboardInterrupt` around that call, so both the `SystemExit(2)` of the remaining Requirement 2 case and any other raised exception (for example a `UnicodeEncodeError` from a guard print on a console code page that cannot encode it) set the same degraded state;
    - record a degraded flag in the hook (for example `_WF_VENV_UNAVAILABLE`) when the accessor reports `"version_mismatch"` or when activation raised. An `"absent"` venv (pre-setup) keeps today's hook behavior and is not degraded;
    - when degraded, write exactly one stderr line naming the cause and the remedy (`run wf setup`), and nothing to stdout, because some hosts parse hook stdout as JSON.

    Verified at `venv_bootstrap.activate_tool_venv`: the allowance branch (`if allow_version_mismatch: return`) returns before the guard's `print`, so on a version mismatch the hook's notice is the only stderr line. In the remaining Requirement 2 case the guard's own site-packages message precedes it. Because the process-local deferral is now set, every later plain `activate_tool_venv()` call in the hook process returns without exiting. That covers the `indexer.py` module-level call and the `sqlite_runtime` import reached through `sqlite_vector_store`.
11. **Gate hooks fail closed but stay usable.** The edit-gate verdicts (`_GATE_FILE_PATH_SOURCE` used by `claude_pre_edit_source` and `copilot_pre_tool_use_source`, plus `windsurf_seed_protect_source`, `cursor_seed_warn_source` and `cursor_framework_warn_source`) are computed by the hook's stdlib-only helpers (`guard_enabled`, `is_seed_prompt`, `is_framework_maintenance_surface`), so they run without the venv. With the venv unavailable a gate hook behaves exactly as with it available. A gated path whose gate is closed is still blocked with today's per-host signal:
    - Claude Code `pre-edit` (`gate_file_path`): stderr message, exit 2;
    - Copilot `pre-tool-use` (`gate_file_path`): stderr message, exit 2;
    - Windsurf `seed-protect`: stderr message, exit 2;
    - Cursor `seed-warn` and `framework-plan-warn`: message on stdout, exit 10.

    A gated path whose gate is open, and an ungated path, is allowed (exit 0). A version mismatch never opens a gate and never blocks an ungated edit. The implementation confirms by test that the gate path imports nothing from the tool venv. If any gate helper needs a venv package, that helper is made stdlib-only instead of weakening the verdict.
12. **Non-gate hooks degrade quietly.** With the hook degraded, `claude_post_edit_source`, `claude_stop_source` (session-capture), `claude_context_efficiency_source`, `cursor_docs_lint_source`, `cursor_after_file_edit_source`, `copilot_post_tool_use_source` and `windsurf_docs_lint_source` exit 0 after the single notice line. A `Stop` hook never exits non-zero because of the venv.
    - **In-process loads of `indexer.py`.** Today every one is wrapped in `except Exception`, which `SystemExit` escapes. They are `_load_indexer_hook_helpers`, as called by `maybe_docs_lint` (`docs_lint_hook_timeout_seconds`), `_spawn_reindex` (`record_hook_reindex_spawn`), `mark_reindex_pending_for` (`mark_reindex_pending`) and `maybe_trigger_reindex` (`mark_reindex_pending`, `should_coalesce_hook_reindex`, `consume_reindex_pending`), and the separate `spec_from_file_location` load in `claude_stop_source._flush_reindex_if_pending` (`_index_build_lock_held`, `consume_reindex_pending`, `record_hook_reindex_spawn`). Executed on 2026-10-04: `indexer.py` loads at module level on the system `python3` 3.14 with no venv on the path. After the load, none of `numpy`, `apsw`, `fastembed` or `onnxruntime` was in `sys.modules`, and all six helpers named here resolved. Under a deferral these loads therefore keep running; marking reindex-pending is stdlib work. When the hook is degraded because activation raised (no deferral recorded), they are skipped, because loading `indexer.py` would re-run the failing activation.
    - **Self-activating children are skipped.** These are the `docs_lint.py` child of `maybe_docs_lint` (its exit 2 would otherwise read as a lint failure: the Claude post-edit returns 1 and Cursor docs-lint returns 10), the `_spawn_reindex` child, and the Stop flush's `indexer.py` spawn. A skipped flush does not consume the reindex-pending marker, so the first hook run after `wf setup` flushes it. `claude_context_efficiency_source` keeps its detached all-DEVNULL `project_context_efficiency.py` spawn, which is not an import-time activation site and whose exit never reaches the host.
    - **Carve-out: `claude_simulate_hooks_source`.** It receives only the Requirement 10 bootstrap fix. It keeps spawning the named hook body and returning that child's exit code, because the hook bodies it spawns are fixed themselves.
13. **Canonical source and regeneration.** Fixes land in `render_platform_surfaces` (the renderer and its templates). Rendered copies are regenerated with `wf_sync_surfaces` (CLI fallback `wf render-surfaces`) and are not hand-edited. Census predicate (seeds): `activate_tool_venv` in `.wavefoundry/framework/seeds/`, executed on 2026-10-04, returned 0 files, so no seed edit is expected. 14. **Upgrade from 1.28.0 with a stuck receipt.** Implementation executes that upgrade path with a named fixture:
    - **Install.** A scratch repository outside this checkout gets the released 1.28.0 framework: the `wavefoundry-1.28.0+ptiz` pack when it is available, otherwise `git archive v1.28.0 .wavefoundry/framework` extracted into the scratch repository. It runs `wf setup` with a matching-version tool venv at a scratch `WAVEFOUNDRY_TOOL_VENV`, which yields a real schema-8 `index.sqlite` and a complete version-2 receipt.
    - **Stuck receipt.** It is produced by the 1.28.0 code itself, as in the field: rerun `wf setup` with `WAVEFOUNDRY_TOOL_VENV` pointing at an absent scratch path. That builds the venv in Step 2 and writes the receipt through the stale binding. The result is compared field by field with `.wavefoundry/index/sqlite-migration.json.stuck-2026-10-03`: version 2, kind `index_sqlite_schema8`, state `restart_required`, `source_database` `current`, and a complete version-2 parent. The preserved file cannot be copied in as is, because `read_receipt` checks its `index_dir` and `root_identity` against the scratch root.
    - **Fixed pack.** `python3 .wavefoundry/framework/scripts/build_pack.py --version <next version> --output <scratch dist>` from this checkout.
    - **Command.** From the scratch root, with `WAVEFOUNDRY_TOOL_VENV` at that now-matching venv: `./.wavefoundry/bin/wf upgrade --pack <scratch dist>/<fixed pack>.zip --yes` (native Windows: `.\.wavefoundry\bin\wf.cmd upgrade ...`).

    `wf_cli.main` activates the venv for every subcommand except `setup`, so on a mismatched venv `wf upgrade` exits 2 before it reads the receipt. That is why the documented remedy order is `wf setup` first; the fixture's venv must match. The expected outcome is that the upgrade recovers the record, through the Requirement 5 retirement or by routing to a setup run that performs it. The release-notes alternative is allowed only on one stated condition: the executed run shows the refusal is raised by the installed 1.28.0 code before the new pack's code runs (the pre-extraction orchestrator reads the receipt through its own `read_receipt`), which this change cannot alter. In that case only, the CHANGELOG and release notes tell operators on a stuck receipt to apply the Requirement 7 remedy before upgrading.

`runner_stale` note: `venv_bootstrap.py` is one of the two runner files (`server.py`, `venv_bootstrap.py`) whose launch-time hash `compute_runner_identity` compares against disk, so after this change lands a running MCP server reports `runner_stale` until it is restarted. That is correct and expected; the delivery notes and CHANGELOG say a host restart is needed. `server.py` is not edited.

## Scope

**Problem statement:** after a Python minor-version change, `wf setup` exits before it can rebuild the venv; once past that, the same setup run misreads a current schema-8 index as needing the schema-8 rename and writes a receipt chain its own reader rejects, which blocks setup, upgrade and every index reader. Meanwhile every rendered hook exits 2, which blocks edits and loops `Stop` hooks.

**In scope:**

- `venv_bootstrap`: deferred-activation state in `activate_tool_venv`, with read and reset accessors.
- `sqlite_storage_migration`: the no-import guard in `_database_schema`; one shared `supersedes` predicate used by `read_receipt`, `_new_receipt`, `_begin_chained_kind` and `_install_kind_fence`; the pre-staging no-op retirement helper (Requirement 5), which owns the only rebind.
- `setup_reconciliation`: the read-only binding tolerance (Requirement 6) in `session._inspect` (`validate_source_binding` is unchanged); calling the retirement helper from `session.prepare` before `prepare_upgrade`.
- `render_platform_surfaces`: `HOOK_BOOTSTRAP` and the per-hook source functions (Requirements 10 to 12), then regeneration of every rendered hook with `wf_sync_surfaces`.
- Verification of the 1.28.0 upgrade path with a stuck receipt (Requirement 14).
- Tests and the CHANGELOG `Unreleased` entry, including the operator remedy.

**Platform Behaviour (Windows, macOS, Linux, WSL2):**

- **macOS:** the reported case (Homebrew `python@3.13` to `python@3.14`). Venv site-packages are `lib/pythonX.Y/site-packages`; after the rebuild the new path matches the running minor version and activation succeeds.
- **Linux:** distro or deadsnakes upgrades change `python3` the same way; behavior is identical to macOS.
- **WSL2:** Linux semantics inside the distribution. A venv under the Windows filesystem (`/mnt/c/...` via `WAVEFOUNDRY_TOOL_VENV`) is rebuilt by the same code; the `rmtree` slowness of DrvFs is unchanged.
- **Windows:** python.org and Store installs place minor versions side by side, and the `python3` alias can move to the new one; the venv layout is `Scripts\python.exe` and `Lib\site-packages`, and `pyvenv.cfg` still records `version`, so the mismatch is detected identically. Deferral matters most here: because the setup process never activates the stale venv, it holds no handle on its `.pyd`/`.dll` files, so `_rmtree_clearing_readonly` is not blocked by setup itself (a running MCP host can still hold them; the existing `Could not recreate the tool venv` guidance covers that). Identity comparison for Requirement 5 uses `storage_identity.compare_identity`, which already handles the Windows identity fallback; no new identity logic is added.
- **Hooks on every OS:** hosts launch hook bodies with `python3`, so after an upgrade the hook interpreter and the venv disagree on all four platforms. The fix is interpreter-independent: catching `SystemExit` and the one-line stderr notice behave the same on Windows (`Scripts`, `Lib\site-packages`) and POSIX, and the gate verdicts use only `pathlib` and `json`.

**Out of scope:**

- `wf setup --check-gpu` under a mismatched venv (its probe child activates and exits 2, which reports a failed probe rather than crashing).
- The rendered hook launcher commands in host settings (for example the `.claude/settings.json` pre-edit launcher whose `sys.excepthook` exits 2). They stay fail-closed for genuine hook crashes; this change removes the venv mismatch as a crash cause instead.

## Risks

| Risk | Mitigation |
| ---- | ---------- |
| The deferral hides a real mismatch from code that needs the native deps in the setup process. | The deferral is set only by the allowance caller, clears on the first successful activation, and Requirement 2 keeps the one native probe from binding early; AC-2 asserts `sqlite_runtime` is not imported before activation. |
| Relaxing source binding weakens the resume fence. | The tolerance is read-only in `session._inspect` and limited to the Requirement 5 structural predicate (pre-staging, source current, no retired-name file); `validate_source_binding` is unchanged, the only rebind is written by the retirement after a schema-8 probe, and AC-7 proves other unfinished records, and a restored older database, still refuse. |
| Runners on old code meet the chained shape. Runners 1.24 to 1.28 read version-2 records whose `supersedes` is version 1, and refuse only the chained shape (a version-2 parent) with `storage_receipt_supersedes_invalid`. Runners before 1.24 refuse every version-2 record. | The field receipt no longer stays chained: the Requirement 5 retirement restores its complete version-2 parent, which 1.24 to 1.28 read (executed with the 1.28.0 reader), so the recovered receipt itself needs no restart. The CHANGELOG says to restart every host (AC-8). The chain is validated level by level, and AC-4 covers malformed shapes. |
| Editing `venv_bootstrap.py` marks running MCP servers `runner_stale`. | Expected; CHANGELOG states a host restart is required (AC-8). |
