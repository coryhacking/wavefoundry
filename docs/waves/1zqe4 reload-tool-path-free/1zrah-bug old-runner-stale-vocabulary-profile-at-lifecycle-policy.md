# An upgrade from 1.28.0 crashes at the lifecycle-ID policy phase on a stale vocabulary profile

Change ID: `1zrah-bug old-runner-stale-vocabulary-profile-at-lifecycle-policy`
Change Status: `implemented`
Owner: implementer
Status: implemented
Last verified: 2026-10-04
Wave: 1zqe4 reload-tool-path-free

## Rationale

Found during wave `1zqe4` (change `1zrag`, AC-14 run). Upgrading a released 1.28.0 install to the current tree fails in phase `lifecycle_policy_materialization` with `AttributeError: module 'vocabulary_profile' has no attribute 'CHANGE_KINDS'`. Rerunning the upgrade gets past the phase, because the rerun is a new process running the new runner. Every 1.28.0 consumer hits the failure on its first upgrade, so it blocks the 1.29.0 release.

Root cause, reproduced by execution (Progress Log 2026-10-04):

- **Process.** `wf upgrade` runs `wf_cli.main` in one Python process, which calls the INSTALLED (1.28.0) `upgrade_wavefoundry.main` in-process. Extraction replaces the files on disk, but that process keeps running 1.28.0 code, and it keeps every module it imported before extraction in `sys.modules`.
- **Stale module.** Before extraction, the 1.28.0 runner imports `vocabulary_profile` in-process. Its 1.28.0 importers include `review_evidence`, `record_paths`, `review_policy_upgrade` and `gardener_metadata`, and the trace shows it loaded right after `review_evidence`, during the runner's pre-extraction lock and storage checks. An import-audit trace of a real 1.28.0 upgrade records `vocabulary_profile` loaded while `VERSION` still read `1.28.0+ptiz`.
- **Fresh consumer.** Phase 2c runs the 1.28.0 `upgrade_wavefoundry.materialize_lifecycle_policy` (v1.28.0 line 4780), whose first statement is `import lifecycle_id` (line 4786). The check that skips an already-provisioned policy comes after that import, so the import runs on every upgrade. `lifecycle_id` was never imported before extraction, so it loads from the NEW tree. Its module-level `KIND_CHOICES = _vocab.CHANGE_KINDS + ("wave",)` (current `lifecycle_id.py` line 605) then reads the cached 1.28.0 `vocabulary_profile`. That module predates `CORE_CHANGE_KINDS`, `CHANGE_KINDS`, `CHANGE_KIND_RE`, `RETIRED_CHANGE_KINDS` and `retired_kind_message` (added by unreleased waves `1zimf` and `1zli8`).
- **Why the existing guard misses it.** `upgrade_extensions._refresh_record_layout_modules` already reloads `vocabulary_profile`, `path_containment` and `record_paths` in place for an older runner (wave `1zeyo`, memory `1zf7r`). It is reached only from `pre_docs_gate`, `post_docs_gate`, `pre_index_update` and `repair_declaring_scaffold`, all of which run after Phase 2c.

Brief: the consumer is every operator upgrading a 1.28.0 install with a released pack, on every OS. Success is that one ordinary `wf upgrade --pack <1.29.0 pack> --yes` passes Phase 2c in its first run with no rerun.

## Requirements

1. **Refresh at extraction.** `upgrade_extensions.post_extract`, on its non-dry-run path, refreshes the record-layout leaf modules in place before it does anything else. It uses the existing `_refresh_record_layout_modules` and `_reload_in_place` seam, which keeps module identity and the identity of each exception class. The 1.28.0 runner calls the pack-loaded `post_extract` (v1.28.0 `_run_hook("post_extract", ctx, ext_mod)`, line 5966) immediately after extraction. That call comes before every new-tree module the runner imports in-process: `mcp_tool_roster` and `render_platform_surfaces` in Phase 1, `memory_records` in `legacy_memory_pointer_migration`, and `lifecycle_id` in Phase 2c. The refresh runs both on the extracting path and on the `_tree_already_at` idempotent path.
2. **The refresh set follows a stated rule.** A module is refreshed at `post_extract` when three things hold. The runner can hold it in `sys.modules` before extraction. A new-tree module that the runner imports in-process after extraction reads a name from it that the runner's version lacks. And it is a stateless leaf that is safe to re-execute: no locks, context variables or venv activation at import. The census below derives `vocabulary_profile` as the only module meeting the first two conditions for a 1.28.0 runner. The refresh set is the existing `_RECORD_LAYOUT_MODULES` (`vocabulary_profile`, `path_containment`, `record_paths`), refreshed leaf-first. `record_paths` imports `vocabulary_profile`, and the seam already declares those three compatible with old callers. The implementer re-derives the census against the final tree, and any module it adds to the set is named in the Decision Log.
3. **Dry run is untouched.** When `ctx.dry_run` is true (the `--dry-run` preview calls `post_extract` before anything is extracted), no module is reloaded.
4. **Identity survives a failed reload.** `_reload_in_place` re-binds the kept exception classes in a `finally`, so a reload that raises part-way still leaves every exception class name bound to its pre-call object. Today the re-binding runs only after `importlib.reload` returns. A failed reload re-executes the module's namespace up to the failing statement, so without the `finally` a class already re-executed stays split from the holders' `except` clauses. The change applies to every caller of `_reload_in_place` (`_refresh_record_layout_modules` and `_installed_memory_backfill`), which only strengthens them.
5. **A failed refresh stops the upgrade with a clear message.** Each module is reloaded in its own `try`, leaf-first. On the first failure the refresh prints a one-line note to stdout naming the module and the exception type (path-free), reloads no later module, and `post_extract` raises an error whose message names the module and tells the operator to rerun the upgrade. The 1.28.0 runner turns that into `Extension hook 'post_extract' raised: <message>` and exit 3 (v1.28.0 `_run_hook`, lines 1153 to 1159). The reasoning, from the code:
   - `vocabulary_profile` validates itself at import: `validate()` is its last statement (current line 329), and it raises `VocabularyProfileInvalid`. When that raises during a reload, every earlier statement has already run, so the cached module holds the complete new namespace that failed validation. If `post_extract` noted the failure and continued, Phase 2c would import `lifecycle_id` against that namespace. `CHANGE_KINDS` would then be present and the import would succeed, so lifecycle policy would be materialized from vocabulary that a fresh process refuses at import.
   - Any other reload failure (`SyntaxError`, `OSError` reading the source, a failed import inside the module) leaves a namespace that mixes old and new names. `record_paths` imports `vocabulary_profile`, so a later leaf cannot be trusted after an earlier one fails.
   - The existing seam already lets a refresh failure propagate out of `pre_docs_gate` (through `_reload_cached_review_evidence`), `post_docs_gate` and `pre_index_update` (through `_installed_memory_backfill`), none of which wraps the call. Continuing at `post_extract` would only move the same failure later, after Phases 0c to 2c had run on mixed code.
   - Stopping takes the same 1.28.0 failure finalization as today's Phase 2c crash: on the extracting branch `tree_mutated` is already true at the hook (v1.28.0 line 5958), so `_finalize_failed_upgrade` keeps the lock with a failure marker; on the `_tree_already_at` branch `tree_mutated` is still false, so the lock is removed unless a dashboard restart or index-guard handoff is pending, and the tree is already at the target version. The planning reproduction recovered from that state by rerunning the upgrade. A rerun is a new process on the new code: a transient failure passes, and a genuinely invalid profile fails at import with its own `VocabularyProfileInvalid` message, which is the honest result.
6. **No tolerance in consumers.** `lifecycle_id`, `wave_lint_lib/constants.py` and `wave_lint_lib/wave_validators.py` keep reading `vocabulary_profile` directly. No `getattr` fallback or copied kind list is added: change kinds have one source (memory `1zlpf`).
7. **Platform behaviour.** Requirements 1 to 5 hold on Windows, macOS, Linux and WSL2 (see Platform Behaviour under Scope).
8. **Every entry path.** The fix covers the CLI and the MCP entry. The 1.28.0 `wf_upgrade` MCP tool runs the installed `upgrade_wavefoundry.py` as a child script (v1.28.0 `wf_server/upgrade_handlers.py`: `cmd = [server_impl._preferred_python(), str(upgrade_script), "--root", str(root), "--yes"]`, run through `_mcp_subprocess_run`). That child is the same 1.28.0 runner, with the same pre-extraction imports and the same pack-loaded `post_extract` hook, so the crash and the fix are identical on that path.
9. **1.27.x runners.** v1.27.0 has no `vocabulary_profile`, so a 1.27.x runner cannot hold a stale copy, and its Phase 2c `lifecycle_id` import loads `vocabulary_profile` fresh from the new tree. A 1.27.x runner that has cached `record_paths` has it refreshed in `post_extract`, which v1.27.0 calls (line 5699) before Phase 0c (line 5755). This is the 1zeyo seam contract (memory `1zf7r`): every function 1.27 code calls on these leaves keeps a compatible signature, and the leaf-first order means `record_paths`' reload imports the new `vocabulary_profile` fresh.

## Scope

**Problem statement:** a pre-upgrade runner executes new-tree modules against its own cached old copies of their dependencies. The only crash this produces for a 1.28.0 runner is in Phase 2c.

**Census (re-derived 2026-10-04; the implementer re-derives it on the final tree).**

- **Cached set C.** Framework modules in the runner process's `sys.modules` that were loaded from the 1.28.0 tree. It was measured by a `sys.addaudithook` `import` trace of a real 1.28.0 to current-tree upgrade, keyed by process id and by the `VERSION` on disk at load time. The set has 53 modules, plus the flat `server_impl` alias and the runner `upgrade_wavefoundry` itself, including `vocabulary_profile`, `record_paths`, `path_containment`, `review_policy`, `review_evidence`, `lifecycle_lock`, `mcp_tool_extensions`, `sqlite_storage_migration`, `server`, `server_impl` and every `wf_server.*` handler.
- **Fresh set F.** The roots are every framework module that the v1.28.0 `upgrade_wavefoundry.py` imports at any scope, plus every module the current `upgrade_extensions.py` imports, plus the new-tree sources that `upgrade_extensions` loads under an alias or by re-execution even though a module of the same name is in C: `sqlite_storage_migration` (exec'd as `_installed_storage_migration` in `post_extract`), `upgrade_wavefoundry` (the `_wavefoundry_installed_upgrade_projection` module from `_installed_upgrade_module`) and `memory_backfill` (re-executed by `_installed_memory_backfill`). Plain-name modules already in C are then removed. F is that root set closed over the current tree's imports. The result is `agent_surface_integrity`, `index_state_store`, `indexer`, `lifecycle_id`, `mcp_tool_roster`, `memory_backfill`, `memory_records`, `model_bundle`, `reconcile_scan`, `render_agent_surfaces`, `render_platform_surfaces`, `setup_index`, `upgrade_extensions`, `_tag_utils`, `accel_embedder`, `change_doc_checklist`, `machine_authority`, `process_info`, `wave_lint_lib.constants` and `wave_lint_lib.wave_validators`. The trace shows only `mcp_tool_roster`, `render_platform_surfaces`, `memory_records`, `lifecycle_id` and `upgrade_extensions` actually imported in-process. Docs lint, the gardener, surface rendering, pruning and the index update run as child processes on new code.
- **Predicate P1 (new reads stale).** A module in F references an attribute of a module in C, either as `M.attr` after `import M` or as `from M import attr`. The predicate holds when that attribute is not a top-level name of the v1.28.0 module, or, for a call, when the call passes a keyword the v1.28.0 function does not accept (and it has no `**kwargs`) or more positional arguments than it accepts (and it has no `*args`). Calls with a starred argument are not checked. Flat shims (`sys.modules[__name__] = importlib.import_module(...)`) are resolved to their target first.
- **Predicate P2 (stale reads new).** v1.28.0 code in C, or in `upgrade_wavefoundry`, references an attribute of a module in F that is absent at the current tree, or passes a keyword that is not accepted.
- **Result.** P1 has five true sites:
  - `lifecycle_id` lines 605, 665 and 666 (`CHANGE_KINDS`, `RETIRED_CHANGE_KINDS`, `retired_kind_message`). Line 605 runs at import, which makes it the Phase 2c crash.
  - `wave_lint_lib.constants` line 320 (`CHANGE_KIND_RE`) and `wave_lint_lib.wave_validators` lines 115 and 122 (`CHANGE_KINDS`). These are reached in-process only through `indexer`, `machine_authority` and `render_agent_surfaces`, and the trace shows none of those three imported in the runner process.
  - `mcp_tool_roster` line 183 passes `core_tiers=` to the 1.28.0 `mcp_tool_extensions.validate_declaration`. This is reached only when a distribution declares extension tools, and only through the 1.28.0 runner's advisory `_count_unrecorded_roster_rules`. That function catches `Exception` and returns `None`, so the effect is a lost advisory count, not a crash. It is out of scope (see below).
  - The alias-loaded sources (`sqlite_storage_migration`, the `upgrade_wavefoundry` projection, `memory_backfill`, and `upgrade_extensions` itself), checked against C minus the three refreshed leaves, have no P1 site by attribute, keyword or arity. The keyword and arity check over the whole of F finds only the `mcp_tool_roster` line 183 site above (reviewer probes `alias.py`, `kw.py` and `kw2.py`, re-run 2026-10-04).
  - P2 has no true sites. Its candidate hits were local variables that shadow module names. The refresh direction was checked as well: no v1.28.0 module in C reads a name that the current `vocabulary_profile`, `path_containment`, `record_paths`, `repo_root` or `lifecycle_id` lacks.
- **Execution check.** The same 1.28.0 fixture was upgraded with only `vocabulary_profile` reloaded before `lifecycle_id` loaded (an audit-hook emulation, not the fix). It completed through Phase 4 with rc 0, and the import trace recorded the reload.
- **Predicate limits.** Name-level only. P1 does not see attributes of returned objects (the `1zeyo` `RecordRoots.archive` class), `getattr` by string, or a changed value under an unchanged name. These branches were not executed: a running dashboard, declared extension tools, existing memory records (already covered by `post_docs_gate`'s refresh) and a pending storage migration.

**In scope:**

- `upgrade_extensions.post_extract`: the refresh, its dry-run guard, and its per-module failure note and stop (Requirements 1 to 3 and 5).
- `upgrade_extensions._reload_in_place`: exception-class re-binding in a `finally` (Requirement 4).
- Tests that reproduce the stale-module condition without a 1.28.0 install, using a frozen v1.28.0 `vocabulary_profile` source fixture beside the existing `tests/fixtures/upgrade_old_runner/record_paths_v1_27_0.py.txt`.
- The real upgrade-from-1.28.0 verification (AC-5).
- CHANGELOG `Unreleased` entry.

**Out of scope:**

- The `mcp_tool_roster` advisory degrade under a declared extension. Refreshing `mcp_tool_extensions` re-executes extension module loading and registries, so it does not meet the stateless-leaf condition. The only effect is a lost advisory count on the release that crosses the 1.28.0 runner.
- Changing the 1.28.0 runner itself, which cannot be done. Changing the current runner to run phases in a child process does not protect 1.28.0 installs (see the Decision Log).
- Re-planning the `1zrag` stuck-receipt remedy.

**Platform Behaviour (Windows, macOS, Linux, WSL2):**

- **All platforms:** `wf` (POSIX) and `wf.cmd` (native Windows) both start `wf_cli.py` in one interpreter, and the 1.28.0 runner activates the tool venv in-process, so the stale-module condition and the fix are the same on every OS. `importlib.reload` re-reads the source through `SourceFileLoader`. Bytecode in `__pycache__` is revalidated against source mtime and size, and extraction writes new files whose size differs from the 1.28.0 `vocabulary_profile`.
- **All platforms, how the reload finds its source:** for a top-level module, `importlib.reload` re-finds the module through `sys.path` (a fresh `find_spec` with no parent package), not from the module's existing spec. It therefore reads the first `vocabulary_profile.py` on `sys.path`. In the runner that is the framework scripts directory the runner first imported it from, which extraction has just rewritten in place. The existing loaders (`_installed_memory_backfill`, `_installed_upgrade_module`) add that directory to `sys.path` only when it is absent; the refresh does the same. The tests must arrange `sys.path` the same way (the frozen fixture directory first), or the reload reads a different file.
- **Windows:** no file handle is held on `.py` sources after import, so reloading after extraction is not blocked by sharing violations. No new path string handling is added.
- **WSL2:** Linux semantics inside the distribution, including a repository under `/mnt/c`.
- **macOS:** reproduced here (Darwin, Homebrew `python3`).
