## Rationale

A downstream distribution reported a set of path-handling defects, verified at HEAD `06c02e63`. This change fixes five of them plus one lookup bug found alongside. The report is private; this document describes defect classes and fixes only.

Code-grounded facts this plan relies on (paths under `.wavefoundry/framework/scripts/`):

- **Member ids are not validated where they are read (report P2).** `lifecycle_gate_support._CHANGE_ID_PATTERN` and the archive-profile branch of `_extract_change_ids_from_wave_text` capture any backticked text after the member-id label (`[^`]+`, which can also span a line break). `_wave_change_doc_path` and `_plan_change_doc_path` join that text into `<folder>/<id>.md` without checks, and `_repo_rel` falls back to a lexical comparison. Docs-lint's own parser (`wave_lint_lib/constants.CHANGE_ID_PATTERN`) does validate the shape, and docs-lint reports a non-canonical member line as "unstable" (`wave_validators.py`), but the lifecycle tools read member docs before or without lint.
- **The argument check is a deny-list (report P6).** `server_impl._change_id_shape_error` (wave 1zv87) refuses only empty values, NUL, absolute or drive-prefixed values, path separators and `..`. It accepts line breaks and other control characters, a colon (which Windows reads as a drive or alternate-data-stream separator) and reserved device names. A trailing dot or space and a lone `.` are harmless here because `.md` is appended. An allow-list fixes this, and the same predicate also serves P2.
- **Bulk `wf_get_change` matches by substring.** `wf_get_change_response` in bulk mode walks `wave_dir.rglob("*.md")` and takes the first file whose stem contains `cid.lower()`, so it can return a sibling whose id contains this id. Its plans fallback joins the id unchecked. Census (predicate: each admitted id in every `docs/waves/**/wave.md`; command: a stdlib Python walk applying the extraction regex, run 2026-10-06): 1077 ids in 365 records (rerun after wave admissions; earlier runs gave 1069 in 360, then 1072). 1074 resolve by exact case-sensitive name `<wave dir>/<id>.md`, 3 have no document (wave `12pn3`), and 0 depend on substring matching. All 1077 match the canonical lint shape.
- **Path-helper call sites (census).** Predicate: a call of `_wave_change_doc_path(` or `_plan_change_doc_path(` outside `tests/`. Command: `grep -rn --include='*.py' -e _wave_change_doc_path -e _plan_change_doc_path .wavefoundry/framework/scripts | grep -v /tests/`. Result: 12 calls in 10 functions. `lifecycle_gate_support`: `_change_location_state` (2), `_prepare_policy_state` (1, the review-policy inputs). `server_impl`: `_mark_change_item_response` (1), `wf_add_change_response` (1), `_prepare_council_verdict_locations` (2), `wf_prepare_wave_response` (1, the index-refresh list), `_wave_code_footprint` (1), `wf_close_change_response` (3). The report counted 16, probably including direct joins. Direct joins of a record-derived id outside the helpers (predicate: an f-string `{<id var>}.md` joined to a wave folder or the plans root, outside `tests/`): `lifecycle_gate_support._collect_silent_unchecked_items_for_close` (the close gate, fed by `_close_gate_change_ids`, which deliberately keeps non-lint ids), `server_impl.wf_get_change_response` (plans fallback), `wf_implement_wave_response`, `_generate_wf_close_wave_summary` (close summary), and `dashboard_lib.collect_changes`. `wave_validators.member_status_drift` and the wave-owned-doc lint loop also join ids, but only ids that already passed the canonical lint pattern. `server_impl.new_change` joins its `change_id` argument at the plans root; its only non-test caller passes an id minted by `lifecycle_id.build_id`.
- **Location-state reads (census).** Predicate: a path returned by `_change_location_state` or `lifecycle_gates.change_location_gate` (`staged_path`, `wave_path`, `change_path`) that the caller then reads or writes. Command: `grep -n -e read_text -e write_text -e _move_change_doc .wavefoundry/framework/scripts/wf_server/server_impl.py`, then each hit was traced to its source path. The gate itself reads nothing. Result: 2 handlers.
  - `wf_prepare_wave_response` relocates a staged doc with `_move_change_doc` (a plain `rename`, which moves a link as a link) and then reads `change_path.read_text()` for each admitted member.
  - `wf_add_change_response` reads `_readability_probe.read_text` (source or target), moves the doc, reads `admitted_text = target_path.read_text`, then writes `target_path.write_text(...)`. That write follows a final-component link after a linked staged plan is moved. It then reads `_doc_check_path.read_text`.
  - Line numbers are omitted because other waves are editing the file; the handlers and variable names identify each site.
- **Extraction call sites.** Predicate: a call of `_extract_change_ids_from_wave_text(` or a direct `_CHANGE_ID_PATTERN.findall(`/`.search(` outside `tests/`. Command: `grep -rn --include='*.py' -e '_extract_change_ids_from_wave_text(' -e '_CHANGE_ID_PATTERN\.' .wavefoundry/framework/scripts | grep -v /tests/`.
  - 14 extraction calls in `server_impl` and 1 in `lifecycle_gate_support` (`_review_policy_receipt_diagnostics`). These gain the filter once it sits in the extraction function.
  - Direct pattern uses that bypass extraction:

    - `server_impl._read_wave_record` (`findall`). It feeds `list_waves`, and through it `wf_current_wave`, `wf_list_waves`, `wf_audit`, `dashboard_lib.collect_changes` and the dashboard rows. Most use a 4-character prefix. Some are deliberate lint negatives; the others drive lifecycle tools and will stop resolving once the filter lands. Ids built at run time are not counted, so the full suite is the final check.
- **Existing containment owner.** `path_containment.contained_path` (with `refuse_symlink_components`) is the documented single owner ("Forks should extend this owner"). `record_paths` discovery accepts a symlinked wave folder in its unguarded walk, so refusing every link component would change current behavior; the member-doc check below therefore pins the final component and the parent folder identity only.
- **Journal migration (report P3).** `upgrade_extensions._write_journal_exclusive` uses `O_CREAT|O_EXCL|O_NOFOLLOW` on an absolute path, which protects only the final component. `_remove_journal_source` re-checks with `contained_path` and `lstat`, then unlinks by path, so a directory component can change between check and use on POSIX. Two warnings embed raw exception text (`record discovery unavailable: {exc}`, `path containment unavailable: {exc}`). The inner `_rel` of `migrate_journals` falls back to an absolute path. `runtime_lock._open_lock_carrier` already shows the POSIX precedent: a walk from a base directory with `O_DIRECTORY|O_NOFOLLOW` and `dir_fd`, with the macOS `ENOTDIR` versus Linux `ELOOP` distinction.
- **Vendored-script check (report P4).** `verify_vendored_scripts.offline_problems` reads `(vendor_dir / f.path).read_bytes()` for every file-table row; `_FILE_ROW_RE` accepts any backticked path; the README is read the same way; no regular-file or size check runs, so a non-regular entry can block the read indefinitely, and a row naming a file outside the vendor folder makes the tool print that file's digest. The largest vendored file today is 1,585,569 bytes; `MAX_TARBALL_BYTES` is 32 MiB.
- **Provenance paths (report P5).** `server_impl._extension_provenance_for_response._rel` returns the input unchanged on `ValueError`, so `wf_server_info` `data.extensions` (`declaration.path`, `modules[].path`, `helper_modules[].path`) shows absolute paths whenever the loaded framework lies outside the target root.

## Requirements

1. **One allow-list predicate.** Add `CHANGE_ID_SHAPE_RE` and `is_change_id(value) -> bool` to `lifecycle_gate_support.py`. The shape is `<prefix>-<kind> <slug>`: the prefix and slug fragments are `wave_lint_lib.constants.LIFECYCLE_PREFIX_PATTERN` and `SLUG_PATTERN`, and the kind fragment is the kind *shape* `[a-z][a-z0-9]{1,15}` (the same shape `vocabulary_profile` enforces for extra kinds), not the live `CHANGE_KINDS` alternation. Then an archived record written under a profile that later dropped an extra kind stays readable, while every accepted value is still path-safe. Fullmatch only; non-`str` values are rejected. To avoid an import cycle with `wave_lint_lib`, the fragments are literal copies in `lifecycle_gate_support`, pinned equal to the constants by a test.
2. **Argument check uses it.** Move `_change_id_shape_error` into `lifecycle_gate_support.py` (re-exported by `server_impl` under the same name so existing callers and tests resolve). It keeps code `invalid_arguments` and its current specific reasons, and adds a final reason, "is not a change id of the form `<prefix>-<kind> <slug>`", for any value that passes the old checks but fails `is_change_id`. Apply it at entry to `wf_mark_ac`/`wf_mark_task` (already), `wf_close_change` (already) and `wf_remove_change` (new; it currently builds a location from the raw argument through `_change_location_state`).
3. **Filter at extraction (single choke point).** `_extract_change_ids_from_wave_text` (both the live and the `profile` branch) returns only ids that pass `is_change_id`, in record order. Add `_partition_member_ids(text, profile=None) -> (valid, rejected)`, where each rejected entry carries the 1-based line number of the member line and a reason class (`control character`, `path character`, `shape`). Neither the entry nor any message built from it includes the raw value. `_close_gate_change_ids` takes its column-0 ids through the filter rather than `_CHANGE_ID_PATTERN.findall`. `server_impl._read_wave_record` (behind `list_waves`) builds its `changes` list from `_partition_member_ids`. It pairs each valid id with the member-status line of its own block, meaning the first status line after that member-id line and before the next member-id line or heading. It never pairs by position, and a member with no status line gets `unknown`.
4. **Assert in the path helpers.** `_wave_change_doc_path` and `_plan_change_doc_path` raise `ChangeIdRejected` (a `ValueError` subclass defined in `lifecycle_gate_support`) for any id failing `is_change_id`, before touching the filesystem. Every call site in the census above receives ids from the filtered extraction or from a checked argument, so normal flow never raises. Two sources are not covered by those paths, and each validates first and refuses with a diagnostic: `wf_add_change_response` (the canonical id comes from a plan header) and `wf_remove_change_response` (Requirement 2). Route every direct join in the census (the close gate, the bulk plans fallback, `wf_implement_wave_response`, `_generate_wf_close_wave_summary`, `dashboard_lib.collect_changes`, and `new_change`'s plans-root join) through the helpers.
5. **Bad record line policy.** A wave record whose member line holds a rejected id is never a crash and never a read: no path is built from it.
   - Phase tools report a blocking `change_id_invalid` diagnostic naming the record path and line number. Its message says to edit that line by hand (no tool repairs it, and `wf_remove_change` refuses an invalid id) and then run `wf_validate_docs`. This covers `wf_prepare_wave` (it also fails `lint_gate` through the existing "unstable" lint rule), `wf_review_wave`, `wf_implement_wave` and the close gate (as a finding of item type `change id` in `_collect_silent_unchecked_items_for_close`, so `wf_close_wave` blocks exactly as it does for a missing member doc).
   - `wf_get_change` in bulk mode reports it as an advisory diagnostic and lists only valid members.
   - Every other reader omits the line: `_read_wave_record`/`list_waves` (and so `wf_current_wave`, `wf_list_waves`, `wf_audit` and the dashboard), the `_wave_match_payload`/`_archived_wave_matches` listings, `_wave_code_footprint`, `_prepare_council_verdict_locations`, review-policy inputs (`_prepare_policy_state` via its callers), the close summary and the dashboard.
   - The close-gate finding for a rejected line has `item_type` `change id`, `change_id` the empty string (never the raw value) and `item_text` the record line number only. `lifecycle_gates.close_checkbox_gate` currently renders every item that is not `change document` as `silent_unchecked_items_at_close`, so it gains a `change id` branch that emits `change_id_invalid` (blocking) with the hand-edit message. `wf_close_change` keeps only items whose `change_id` equals its own id, so an empty `change_id` never matches and the single-change close is not blocked.
   - Single-change tools (`wf_mark_*`, `wf_close_change`, `wf_add_change`) are not blocked by an unrelated bad line.
6. **Containment before every member-doc read.** Add one helper, `_read_member_doc_bytes(folder, path)`, in `lifecycle_gate_support.py`. It reads a member change doc only when all of these hold:
   - `path.parent` is the expected folder (the wave folder, or the plans root for a staged doc);
   - `os.lstat(path)` shows a regular file, not a link;
   - the resolved path is contained in the resolved folder (`path_containment.contained_resolved_path`);
   - the fully resolved path is contained in the resolved repository root, so a wave folder reached through a link that leaves the repository is refused for member-doc reads;
   - on POSIX, the bytes come from an `O_RDONLY|O_NOFOLLOW|O_NONBLOCK` open whose `fstat` shows a regular file with the `lstat` identity;
   - the read takes at most `MEMBER_DOC_MAX_BYTES + 1` bytes (new constant, 8 MiB), and more than the cap is refused. The `lstat` size is not trusted.

   Otherwise it raises `MemberDocRefused` (an `OSError` subclass, so existing `except OSError` branches report it as unreadable). Symlinked wave folders are not refused outright: one whose target stays inside the repository still works, and only a folder link resolving outside the repository is refused (a behavior change). Use the helper at every member-doc read in `wf_get_change_response` (bulk), `_mark_change_item_response`, `_prepare_policy_state`, `_prepare_council_verdict_locations`, `_wave_code_footprint`, `wf_implement_wave_response`, `_generate_wf_close_wave_summary`, `_collect_silent_unchecked_items_for_close`, `wf_close_change_response`, `wf_prepare_wave_response`, `wf_add_change_response`, `dashboard_lib.collect_changes` and `wave_lint_lib.wave_validators.member_status_drift`. In `wf_prepare_wave_response` and `wf_add_change_response`, the source (expected folder: the plans root, or the wave folder for an already-admitted doc) is checked and read through the helper before `_move_change_doc` runs. The target (expected folder: the wave folder) is read through the helper after the move and before any metadata write. A refusal uses the existing readability diagnostic (`change_doc_unreadable` or the handler's current equivalent) and stops before any move or write, so no write follows a link. `dashboard_lib.parse_change_doc` gains an optional `text` argument, and `collect_changes` passes the text decoded from the helper's bytes, so no second, unconfined read happens. `member_status_drift` imports the helper lazily, inside the function, to avoid an import cycle with `lifecycle_gate_support`. An existence probe (`exists()`/`is_file()`) feeding one of these reads uses the same `lstat` rule, so a link reads as absent or refused, never followed.
7. **Bulk lookup by exact name.** `wf_get_change` bulk mode resolves each member to `_wave_change_doc_path(...)` (exact name, no `rglob`, no substring), then falls back to `_plan_change_doc_path(...)`, reading through Requirement 6. `_archived_wave_response` has the same substring loop over the archived folder (`rglob`, `cid.lower() in candidate.stem.lower()`). It switches to the exact name `<archived folder>/<id>.md` and keeps its existing archive containment guard.
8. **Journal migration on descriptors (P3).** On POSIX, when `os.open`, `os.unlink` and `os.stat` are in `os.supports_dir_fd` and `os.O_DIRECTORY`/`os.O_NOFOLLOW` exist, `migrate_journals` walks from the repository root to the journals folder and to the destination wave folder one component at a time with `O_RDONLY|O_DIRECTORY|O_NOFOLLOW` and `dir_fd`. It follows the `runtime_lock._open_lock_carrier` pattern, including its `ELOOP`/`ENOTDIR` link confirmation, and keeps the walk local to `upgrade_extensions.py` because wave A edits `runtime_lock.py`. The destination is created with `os.open(name, O_CREAT|O_EXCL|O_WRONLY|O_NOFOLLOW, dir_fd=dest_fd)`, a failed write is cleaned up with `os.unlink(name, dir_fd=dest_fd)`, and the source is re-checked with `os.stat(name, dir_fd=journals_fd, follow_symlinks=False)` (regular, singly linked, same identity) and removed with `os.unlink(name, dir_fd=journals_fd)`. Source handling is descriptor-relative too. Journals are enumerated with `os.scandir(journals_fd)`, each entry is checked with `os.stat(name, dir_fd=journals_fd, follow_symlinks=False)`, and its bytes are read through `os.open(name, O_RDONLY|O_NOFOLLOW|O_NONBLOCK, dir_fd=journals_fd)` with an `fstat` identity check, so no source path is reopened by name. A refused walk leaves the journal in place and lists it under `left`. Where the capability check fails (Windows), the current path-based code runs unchanged.
9. **Path-free journal messages (P3).** The two warnings render exceptions through `lifecycle_lock.path_free_exception_text(exc, root)`, imported from the extracted tree under the module's existing guarded-import pattern. If that import fails, the class name alone is used. The inner `_rel` never returns an absolute path; its fallback is `<parent name>/<file name>`.
10. **Vendored-file reads (P4).** In `verify_vendored_scripts.py`, one helper reads a listed file (used by `offline_problems` and by the vendored read in `verify`). It reports a problem line, without reading or hashing, for a row whose path:
    - is absolute, drive-prefixed, or contains a backslash, an empty component, `.` or `..`;
    - resolves outside the resolved `vendor_dir`;
    - has any link component below `vendor_dir`;
    - is not a regular file by `lstat`;
    - exceeds `MAX_VENDORED_FILE_BYTES` (new constant, equal to `MAX_TARBALL_BYTES`).

    On POSIX the bytes come from an `O_RDONLY|O_NOFOLLOW|O_NONBLOCK` open checked by `fstat` identity, reading at most cap + 1 bytes rather than trusting the `lstat` size. The README is read through the same regular-file and size checks wherever it is read: in `offline_problems`, in `verify`, and in `unlisted_scripts`. A failure raises `ReadmeError`, whose message names `README.md` relative to the vendor folder and the cause class only. Today `offline_problems` embeds the absolute README path and the raw exception text. Problem lines name the row's path as written in the table, never an absolute path, and never print a digest of anything not read through the helper.
11. **Provenance labels (P5).** `_extension_provenance_for_response._rel` returns:
    - the repository-relative POSIX path when the resolved path is under the resolved root;
    - otherwise `framework:<path relative to the loaded framework directory>`, where that directory is `Path(server_impl.__file__).resolve().parents[2]` (`server_impl.py` sits in `<framework>/scripts/wf_server/`);
    - otherwise `external:<file name>`.

    It never returns an absolute path.
11a. **Lint message.** The docs-lint rule in `wave_lint_lib/wave_validators.py` for an unstable member-id line reports the record line number and the Requirement 3 reason class instead of the raw backticked value, so no surface echoes a rejected value. The sibling unstable Item ID message, for legacy item records in the same function, is changed the same way to report the line number and a reason class. The undeclared-kind message is unchanged, because it only fires for values that already fit the canonical prefix and slug.
12. **Docs.** Update `docs/specs/mcp-tool-surface.md` for the `wf_get_change` bulk exact-name lookup, the `change_id_invalid` diagnostic and the `wf_server_info` extension path labels. In `docs/architecture/cross-cutting-concerns.md`, add a Shared Utilities line naming `lifecycle_gate_support` as the owner of the change-id allow-list and the member-doc read rule.
13. **CHANGELOG.** Add one Unreleased entry under a security heading that names the hardening by class (change ids validated by an allow-list before any path is built, member change docs read only as regular files inside their folder and inside the repository, journal migration writes and removals bound to directory handles on POSIX, vendored-file checks confined to the vendor folder, extension provenance paths no longer absolute, bulk `wf_get_change` exact matching) and the recovery for a `change_id_invalid` line (edit it by hand). It states one behavior change: a wave folder that is a symbolic link resolving outside the repository no longer serves member change docs to the lifecycle tools, while in-repository folder links keep working. It carries no reproduction steps, sample values or crafted inputs.

## Scope

**Problem statement:** several readers and writers build or follow filesystem paths from repository-controlled text (wave record member lines, journal locations, the vendor README table) without an allow-list or containment, and two responses can disclose absolute paths.

**In scope:**

- Requirements 1 to 13: the allow-list, extraction filter, helper assertions, bad-line policy, member-doc containment, exact bulk lookup, journal descriptor operations and messages, vendored-file confinement, provenance labels, docs and CHANGELOG.
- Tests for each, extending `tests/test_change_id_path_guard.py`, the journal migration tests in `tests/test_upgrade_wavefoundry.py`, `tests/test_verify_vendored_scripts.py`, and the `wf_server_info` extension tests in `tests/test_extension_tool_modules.py`.

**Out of scope:**

- Report P1 (lifecycle and index lock semantics, handoff and prompt reader routing): wave A.
- Single-id `wf_get_change` (`_resolve_change_doc_matches`), the archived change lookup `_archived_change_matches` and the archived wave listing `_archived_wave_matches`: they enumerate existing files rather than join an id, and they are unchanged here. Requirement 7 changes only the bulk `_archived_wave_response` loop. **Named follow-up (separate change):** single-id `wf_get_change` enumeration can still return the content of a change doc that is itself a link, because it reads enumerated files without the member-doc rule. It should adopt `_read_member_doc_bytes`.
- Docs-lint's general reads of the docs tree and their link-following policy are unchanged. Only `member_status_drift` (Requirement 6) and the unstable-id message (Requirement 11a) change.
- A length cap on change ids: none exists today (the longest admitted id is 84 characters); an over-long name fails as an ordinary read error.
- Hard-linked member docs: a hard link inside the repository cannot point outside it in a way the reader can detect, and creating one already requires write access.
- The offline vendored check in `wf_audit` (wave C) and journal migration extension points (wave D); both build on this change's helpers.
- `skill_problems` exception text in `wf_server_info`.

## Platform Behavior

- **Allow-list (all platforms).** The same predicate runs everywhere. It excludes `:`, so a member id can never name a Windows alternate data stream or drive-relative path, and it excludes control characters and both separators. Every accepted stem contains `-` and a space after a 5 or 6 character prefix, so no accepted stem equals a reserved Windows device name (`CON`, `NUL`, `COM1` and so on), and none ends in a dot or space (which Windows would strip). Ids are lowercase only, so the case-insensitive filesystems (APFS default, NTFS) and case-sensitive Linux resolve the same name; the census found all 1074 existing docs at their exact-case names.
- **Member-doc containment.** `os.lstat` reports symlinks as links on POSIX and on Windows (Python 3.8+); a Windows junction is a directory and can only appear as a wave folder; because the repository-root check compares the fully resolved path (`resolve()` follows junctions and symlinks on every platform), a folder junction or link leaving the repository is refused the same way on Windows, macOS, Linux and WSL2. The `O_NOFOLLOW` plus `fstat` identity read is POSIX only. On Windows the `lstat` regular-file check plus resolved containment stands alone, and the check-to-use window is a documented limit, as in `runtime_lock`. WSL2 follows Linux semantics, including on `/mnt/c` DrvFs, where `O_NOFOLLOW` and `lstat` behave as on Linux.
- **Journal migration.** `dir_fd` and `O_DIRECTORY` are absent on Windows (`os.supports_dir_fd` is empty), so Windows keeps the current path branch with its containment re-check; its window is the same documented limit. macOS reports a symlinked directory opened with `O_DIRECTORY|O_NOFOLLOW` as `ENOTDIR` and Linux as `ELOOP`; both are confirmed as links by `os.stat(..., follow_symlinks=False)` before the walk refuses. `_same_journal_file` keeps its existing Windows exemption.
- **Vendored files.** Path-row validation is lexical and identical everywhere, with backslash and drive prefixes refused even on POSIX so a table that passes on one OS passes on all. The regular-file and size checks use `lstat` everywhere; `O_NOFOLLOW` is used where it exists.
- **Provenance labels.** Paths are compared after `resolve()`, so Windows drive-letter case and `\\?\` prefixes do not leak; outputs are POSIX-separated.
