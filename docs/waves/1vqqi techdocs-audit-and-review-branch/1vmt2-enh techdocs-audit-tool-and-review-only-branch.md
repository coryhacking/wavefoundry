## Rationale

Wave `1vj4e` ships the Backstage/TechDocs baseline (`wf techdocs-baseline`, the `wf_techdocs_baseline` MCP tool) and the **Refresh TechDocs** workflow (`wf-techdocs` skill, seed `178`), whose Step 3 validates the authored pages. During the `1vj4e` dogfood the coordinator hand-wrote the validation evidence the workflow's rules imply: which pages the site actually publishes (the `mkdocs.yml` `nav` plus the survivors of `exclude_docs`), which relative links on those pages dangle or escape the boundary, whether every `nav` target exists, whether the two agent startup-order documents kept their heading order, and what the trio's marker-derived ownership state is. Those checks are mechanical and repeatable, and nothing in the framework computes them.

The prepare council for this wave supplied the sharpest argument for building them. Its red-team seat reproduced the publication boundary with the pinned oracle's own matcher and found **two** `techdocs_link_outside_boundary` occurrences on `docs/references/codebase-map.md`, where three independent `1vj4e` delivery lanes had recorded one. Both counts are right for their own check: line 260 links `../../AGENTS.md`, which escapes `docs_dir` entirely, and that is the exception the lanes recorded; line 249 links `../design-system/AGENTS.md`, which resolves to a file that **exists** inside `docs_dir` but which `exclude_docs` removes from the built site. A link-resolution sweep passes the second; only a boundary-aware sweep catches it. That widening is this tool's demonstrated value: it sees a real 404 that a careful manual pass, run three times, did not.

The workflow also has no read-only form. **Refresh TechDocs** authors and refreshes; an operator who wants "tell me what is wrong with the published pages and what you would change" has no branch that returns findings and proposed edits without writing.

Naming follows the decision recorded in `1vj4e`: the workflow is the umbrella (`wf-techdocs` / **Refresh TechDocs**), tools are narrow verbs under the shared prefix (`wf_techdocs_baseline` writes, `wf_techdocs_audit` reads), and permission tier is per tool, so a read-only audit must not be folded into the write-tier baseline.

**Citation resolution is deliberately not in this change.** See the Decision Log: the prepare council falsified the resolver this plan originally proposed, and the replacement is a different mechanism in a different subsystem.

## Requirements

1. **One audit function, two entries.** A new library module `techdocs_audit_lib.py` exposes `audit_techdocs(repo_root, *, compare_to=None) -> TechdocsAuditReport`. A thin CLI entry `techdocs_audit.py` (the `gpu_doctor.py` / `techdocs_baseline.py` pattern: venv bootstrap at import, `--root`, `--json`, `--compare-to REF`) is dispatched by `wf techdocs-audit`; a read-tier MCP tool `wf_techdocs_audit(compare_to: str = "")` in `server_impl` calls the same function through a public-module import inside the response function, so one patch is observed by both entries and nothing is re-implemented. The report is a frozen dataclass rendered as one JSON envelope: `repo_root`; `trio` (per member `absent` / `generated` / `project_owned`, taken from `render_agent_surfaces.techdocs_member_states`, plus the marker-derived `partial` record or `null` from `classify_techdocs_baseline`); `publication` (`docs_dir`, parsed `nav` entries, the `exclude_docs` pattern list, `survivor_pages`, `survivor_count`); `findings` (typed records in canonical order by code then path); `audience` (per startup-order doc: `checked`, `baseline_ref`, `baseline_identical`, `preserved`, `missing_headings`); `summary` (`finding_count`, per-code counts, `citations_checked` is NOT part of this change, and `verdict`: `clean` | `findings` | `not_applicable` | `degraded`); and `degraded` (degrade reason tokens; Requirement 5). **A run that could not compute something never reports `clean`**: when `degraded` is non-empty and no finding fired, the verdict is `degraded`, because a boundary that was never computed and an identity-check audience pass must not read as a clean site (Requirement 8's Step 3 rule keys on the verdict).

   **Amended by the operator-directed repair:** `audit_techdocs` remains the single raw implementation, while both public entries now call `run_techdocs_audit`, which executes that implementation in an isolated worker with Requirement 11's hard worker deadline and repository-I/O-free expiry path. “One patch observed by both” therefore applies to the public runner seam, not to direct in-process invocation of the raw function.

   **Declared dependencies**, which the `layering-rules.md` row must match: the standard library, `wave_lint_lib` (metadata and link primitives), `render_agent_surfaces` (`techdocs_member_states`, `classify_techdocs_baseline`, `_contained_review_carrier_path`), and `index_state_store._run_git` / `_batch_git_blobs` for every git read (Requirement 4). The module never imports `server_impl`, which imports it. Note that the import chain transitively activates the tool venv through `lifecycle_id`, so the module is stdlib-only in its own code but not in a bare-stdlib process, and the architecture row says so rather than implying otherwise. Severity words are used as literal strings; `review_evidence` is not imported.

   `techdocs_member_states` is the named source for per-member state, not `classify_techdocs_baseline`: the latter returns `None` unless the trio is mixed, and using it for per-member state is exactly the defect `1vj4e` DEL-2 repaired. There is no fourth `non-regular` member state; `techdocs_member_states` deliberately folds a non-regular destination into project-owned, and the audit reports the same thing the baseline tool does about one tree.

2. **Publication boundary computed the way MkDocs computes it.** The library parses the recognized `mkdocs.yml` shape without third-party YAML: `docs_dir` (default `docs`), the `nav` list (`- Title: path`, one level of nesting), and the `exclude_docs` block. Survivors are decided per file, MkDocs style: MkDocs' default `.*` and `/templates/` exclusions are prepended, then the block's patterns apply in order, last match wins, `!` re-includes, a leading `/` anchors at `docs_dir`, `*` does not cross `/`, `**` does, a trailing `/` names a directory and everything under it.

   **A pattern the matcher cannot translate faithfully is refused, never approximated** (added at delivery reverification, ledger `DEL-12`). Refusal reports through `unsupported_patterns` and degrades the run, so a boundary measurement disproves is never presented as authoritative, and the report **names the refused patterns** in `publication.unsupported_patterns` (present only when non-empty): `mkdocs_shape` is shared with six conditions and identifies nothing, and refusal became a primary mechanism here, so without the names an operator would bisect their own block to find the dropped line. Two families reached this rule: the degenerate `/**/`, whose normalization stripped its whole body and left a matcher for nothing at all, published seven pages a real `mkdocs build` does not contain — the only fail-OPEN shape found in 1998 oracle-compared blocks, and now translated correctly rather than refused; and the bare `/` with the consecutive-slash run (`/`, `//`, `!/`, `**//`, `/*//`), which are refused, because `!/` is a live re-include at both the pathspec and the `get_files` layer while this module read it as inert. The earlier "matches nothing" record for `/` came from a pathspec-only measurement, which answers a lower-level question than the one this tool asks. The same rule reaches the parser: gitignore strips **trailing** whitespace and treats **leading** whitespace as significant, so a block-scalar line indented deeper than the block's first content line carries literal leading spaces in its pattern. The parser stripped both, which diverged from a loadable config in both directions (ledger `DEL-12`), and now degrades `mkdocs_shape` instead. Translating leading whitespace faithfully is the follow-up; the uniform indentation every real config uses is unaffected.

   Boundary failure modes are explicit rather than silent (`draft_docs_present` was added at delivery review; survivor containment now has its own token; the audience axis carries `compare_to_refused` and the four git-state tokens separately, and `docs/specs/mcp-tool-surface.md` lists the complete current set). A `mkdocs.yml` outside the recognized shape yields `degraded: ["mkdocs_shape"]` with the parsed subset used as far as it goes. A `mkdocs.yml` that parses but carries **no** `exclude_docs` block yields `degraded: ["exclude_docs_absent"]` and no boundary findings at all — never an empty exclusion set treated as "everything survives" — because `techdocs-cli generate` re-serializes the file in its own supported-key order and drops keys outside that allowlist (seed 178 Step 3 documents this; whether `exclude_docs` survives it is unrecorded, so the audit must not assume). The parser tolerates `|`, `|-`, quoted-scalar and re-indented serializations rather than keying on a literal `exclude_docs: |` line. And containment is applied **per path, not once**: `docs_dir` is resolved through `render_agent_surfaces._contained_review_carrier_path` (the reusable helper; `server_impl.resolve_path_under_root` is NOT usable here, since it returns a server envelope fragment and `server_impl` imports this library), and every candidate under it is re-checked during enumeration, because enumeration follows symlinks the way MkDocs does and a link can leave the root on the supported Python versions and a symlinked subdirectory inside `docs/` otherwise walks straight back out of the root. That is the convention every other bounded reader here follows (`memory_records`, `memory_backfill`). A `docs_dir` escape is refused with `degraded: ["docs_dir_escapes_root"]`; an escaping survivor candidate is named logically and refused with `survivor_target_escapes_root`. Neither path reads external content. The helper raises `RuntimeError` and its message names a review carrier, so the audit maps it to its own degrade token rather than echoing it; this refusal shape (a degrade inside a successful report) is deliberately a third shape, different from the helper's raise and from `resolve_path_under_root`'s diagnostic tuple, because a report-only tool has no envelope to refuse.

3. **Findings, each with a stable code, a severity word, a path, and a one-line detail.** In canonical order: `techdocs_trio_partial` (medium; the trio is mixed, detail is the marker warning text); `techdocs_nav_target_missing` (high; a `nav` path has no file under `docs_dir`); `techdocs_nav_target_excluded` (high; a `nav` path exists but `exclude_docs` removes it, so the built site 404s from its own navigation); `techdocs_link_outside_boundary` (medium; a relative link on a survivor page resolves to a path `exclude_docs` removes, or to a path outside `docs_dir`; the record names page and href always, and the resolved `docs_dir`-relative target in the `exclude_docs` case, which is the only one of the two where an in-site path exists to name [narrowed at delivery review, ledger `DEL-16`: the outside-`docs_dir` case has no site path, and the earlier wording promised one for both]); `techdocs_link_missing` (medium; a relative link on a survivor page resolves to no file); `techdocs_metadata_incomplete` (medium; a survivor page fails `wave_lint_lib.metadata_validators.check_metadata`, which covers a missing **or malformed** metadata block); `techdocs_audience_heading_lost` (high; a startup-order doc's baseline heading sequence is not a subsequence of the current file); `techdocs_index_generated` (low; `docs/index.md` still carries the generated-by stamp).

   Severity words are `low` / `medium` / `high` from `review_evidence.SEVERITY_ORDER`. The word `blocking` is not used: in this framework it is the derived review-evidence boolean about wave gates, and this tool gates nothing, so borrowing it as a severity rank would make copied findings read as gate claims. `critical` is never emitted (the bare-token false-trip rule).

   **Link extraction and normalization are not re-invented.** The audit uses `wave_lint_lib.link_validators`' rules as its contract: `_strip_code` (fenced blocks and inline spans removed before extraction), `_LINK_RE` (which excludes image links through its `(?<!!)` guard), `_SKIP_SCHEMES`, skip pure anchors, skip trailing-slash directory links, strip fragments, and `unquote` the href. The decode is load-bearing rather than cosmetic: a fresh resolver without it emits 14 spurious `techdocs_link_missing` findings on this repository alone, every one a percent-encoded ADR filename whose target exists. Prefer extracting those primitives into a shared public helper that `check_markdown_links` also consumes over copying them. One finding per distinct (page, href) pair. The deliberate divergence from `check_markdown_links`, and the reason the boundary check is additive rather than duplicative, is that the validator **skips** hrefs resolving outside the repository root while the audit reports them.

   **Canonical order** is the code sequence listed above (not alphabetical), then path, then href; the record's sort path is the page that carries the link. `techdocs_trio_partial` is emitted **once** with the path `mkdocs.yml` and the member lists in its detail, not once per member.

   Precedence, so two implementers emit the same record: a link that both dangles and lies outside the boundary is `techdocs_link_outside_boundary` only; a stamped `docs/index.md` beside project-owned YAML members reports both `techdocs_index_generated` and `techdocs_trio_partial`, which are independent facts about different things.

   Two of these codes are **not** additive on a default layout and the plan says so plainly: full docs-lint already runs `check_metadata` and `check_markdown_links` over every markdown file under `docs/`, and seed 178 Step 3 requires `wf_validate_docs` to pass first, so `techdocs_metadata_incomplete` and `techdocs_link_missing` can fire only where `docs_dir` is not `docs`, or where the validator's own scope excludes the tree (`check_metadata` returns nothing for `docs/reports/**`). They are kept for those cases and for a self-contained report, not claimed as new coverage.

4. **Audience invariant, with an honest account of what the baseline can and cannot tell us.** For `docs/references/project-overview.md` and `docs/ARCHITECTURE.md` (the canonical startup-order documents, keyed by those paths regardless of `docs_dir`), the audit compares the current heading sequence against the same file at a baseline ref; the check passes when the baseline sequence is a subsequence of the current one.

   The original plan claimed a default of "the last commit that touched the file, not `HEAD`". Three readiness lanes falsified that independently: the last commit that touched a path is by construction the commit whose blob for that path equals HEAD's, so the two defaults are byte-identical in every repository state, and the ratchet the plan attributed to `HEAD` applies equally to the replacement. The default is therefore simply **HEAD content**, and the check is honest about its scope: it is informative against an **uncommitted** authoring edit, which is exactly when Step 3 runs, and on a clean tree it is an identity check. That case is reported, not hidden: `baseline_identical: true` with `degraded` gaining `audience_not_informative`. An operator who wants the historical question passes `--compare-to <ref>` explicitly.

   **Every git read routes through `index_state_store._run_git` / `_batch_git_blobs`**, the sanctioned single entry point, which sanitizes `GIT_DIR` / `GIT_WORK_TREE` so an ambient environment cannot redirect a `-C <root>` command at a decoy repository, and which exists precisely because a bare `git show` conflated "missing object" with "real error" (a fail-open finding this framework already repaired). The audit needs exactly that distinction, so it must not reintroduce the mechanism that lacked it. `compare_to` is syntax-guarded before it reaches an argv: a value beginning with `-` is refused rather than passed to git.

   Four non-informative states are named and distinguished, and none is ever converted into a pass: `git_unavailable` (not a git work tree, or git failed), `baseline_untracked` (the file exists but no commit touches it, the state a freshly generated `docs/index.md` is in and the one that makes a last-commit lookup return an empty ref), `baseline_missing` (absent at the resolved ref), and `working_tree_missing` (absent from the working tree). The path goes in the diagnostic message rather than the code token, so every emitted code stays a literal constant. In all four, `checked` is `false`. A FIFTH non-informative state exists and is deliberate (amended at delivery review): the `mkdocs_absent` early return skips `audience_report` entirely, so `audience` comes back empty with no per-doc degrade naming why. `not_applicable` means the whole audit did not apply, and the code states that at the return site; this requirement previously implied the four were exhaustive.

5. **Not applicable is a first-class outcome, and every branch says what to do with it.** When `mkdocs.yml` is absent the audit returns `verdict: not_applicable` with `degraded: ["mkdocs_absent"]` and the trio state, and never invents a boundary from the golden template. The CLI exits 0 for that verdict when nothing else was found (it is a legitimate state, not a failure), but `not_applicable` is a forced verdict that wins over accumulated findings, so it never suppresses an exit 1 when the trio checks still reported something (amended at delivery review, DEL-5). Requirement 8's workflow text states the branch behaviour: in the authoring branch, `not_applicable` means Step 1 did not produce the trio and the run investigates rather than proceeding; in the review-only branch it is reported to the operator as the finding it is.

6. **CLI contract.** `wf techdocs-audit [--root PATH] [--json] [--compare-to REF]`; text mode prints `techdocs-audit: <severity> <code> <path>: <detail>`, with ` -> <href>` after the path whenever the finding carries one (every link finding does) per finding plus a one-line summary on stdout, with degrade reasons as `techdocs-audit: NOTE ...` on stderr; `--json` prints the report envelope. Exit codes follow the report's CONTENT rather than its verdict (amended at delivery review, DEL-5): **1** whenever any finding is present or the run degraded so something could not be computed, **2** when the audit could not run, **0** otherwise, so a plain `not_applicable` with no findings exits 0 while `not_applicable` alongside trio findings exits 1. This deliberately differs from `wf techdocs-baseline`, where 1 means precondition-unmet: there, 1 is a refusal; here, 1 is an informative result. The docstring states the difference so the two sibling verbs are not read as one taxonomy. The entry never writes; a whole-tree digest proves it in every mode.

7. **MCP contract and the gates a read-tier tool actually costs.** `wf_techdocs_audit(compare_to: str = "")` is registered `_READONLY_TOOL`, added to `mcp_tool_roster.TOOL_TIERS` as `TIER_READ`, is not a publication writer and takes no lock. Findings live in `data.findings` and are never blocking diagnostics. Degrade reasons and the not-applicable verdict surface as `advisory=True` diagnostics, following the sanctioned precedent for a read-only query tool that gates nothing (`_code_impact_graph_response` / `test_callers_not_visible`, wave 1vbuu), making the sanctioned advisory-site set a **fifth** gate rather than a parity chore: `test_advisory_tags_appear_only_at_the_sanctioned_sites` asserts set equality over `(function, callee, code)` triples resolved by an AST walk, and it reads the code from the first positional argument only when that argument is a literal. Each advisory code is therefore emitted from its own call site with a literal constant string, never from a loop over `report.degraded` and never as an f-string, or the triple collapses to `<helper-call>` and the pin stops meaning anything. The tool signature follows the universal wrapper convention (`**kwargs: Any` plus `_ensure_no_extra_args`), which a registry-wide test enforces.

   The prepare council measured the gate cost by experiment rather than inspection — baseline suite green at 7349/63 in an isolated copy, then one bare read-tier registration added and nothing else — so this requirement names the result instead of guessing. **Four hard gates:** `test_render_platform_surfaces.RosterRegistrationParityTests.test_roster_matches_registration_census` (satisfied by the `TOOL_TIERS` line alone; `server.py` needs no edit for an impl-registered tool); `test_server_tools.ServerToolRegistrationTests.test_agents_available_tools_census_matches_registration` (set equality against the real `AGENTS.md` **Available tools** block); `test_server_tools.TestMcpWrapperParameterExposure.test_review_ergonomics_preserves_review_event_schema_and_tool_roster`; and `test_server_tools.WaveUpgradeMcpToolTests.test_write_tier_permissions_delta_survives_bounding_with_counts`. The last is misleadingly named: `allow_rules(include_write=True)` returns read ∪ write, so a **read**-tier add breaks it. **Three numeric pins** move together: the roster count `89 -> 90`, the roster sha256 digest (measured target `e497f88258818f415468d708ac1624f74862ba5934c095012875e160edb8b7cb`, to be re-derived at implementation rather than trusted), and the permissions-delta count `89 -> 90`. Plus the re-measured advisory-site set above. `_help_catalog` is not a gate (spot-check assertions only) but is updated for parity.

   Two consequences the council flagged and this change accepts: the tool is cost-accounted like every other first-party tool (`_wrap_first_party_tool_costs` debits it because it is not in `_COST_EXEMPT_TOOLS`), which is intended for a tool that returns a substantive report; and AC-6 does not assert absence from `PUBLICATION_WRITER_REGISTRY` as a property, because the guard fails open for unregistered tools and nothing enforces it — the absence is a literal assertion, stated as such.

8. **Review-only branch of Refresh TechDocs, structurally read-only.** Seed `178`, the rendered `docs/prompts/refresh-techdocs.prompt.md`, and the `wf-techdocs` skill gain a review-only branch selected by an explicit read-only request, adopting the shape of the `Review memories` precedent in full (seed-050 task 23): a one-sentence router near the top of the prompt, and a separate short **read-only procedure** carrying an explicit forbidden-write list plus a stated read-only INVARIANT (amended at delivery review: the shipped branch deliberately drops the positive allowed-tool list, because a list is a surface a future host can widen while the invariant is not), as the precedent does. The forbidden list names its members rather than gesturing at them: no page file writes, no `wf_techdocs_baseline` in either mode, no `wf_garden_docs`, no `wf_sync_surfaces`, no docs or index mutation, and specifically not the trio marker-line removal that the authoring branch is permitted to make. A branch whose deliverable is proposed edits is one keystroke from applied edits.

   The branch runs `wf_techdocs_audit` (CLI `wf techdocs-audit`) and **does not call the baseline tool at all**. The original plan said Step 1 could run `wf_techdocs_baseline(mode='dry_run')` "or the CLI with no write"; the council found that false against the tree, since `techdocs_baseline.py` accepts only `--root` and `--json` and the `dry_run` keyword reaches the module solely from the MCP tool — so on a host without MCP the read-only branch would have generated the trio, the one thing it promises never to do. The audit already reports the trio state and the `not_applicable` verdict, which is the same information, so dropping the call makes the branch one tool call, identical on MCP and non-MCP hosts, and makes read-only structural rather than prompt-enforced.

   Step 2's supplier gathering is unchanged; the writer returns a **findings and proposed-edits table** (page, claim or rule, evidence with anchors, proposed edit, and the supplier that verified it, naming the degraded substitute where a lane was absent) plus the audit report and the operator follow-up checklist, writing nothing. The authoring branch is unchanged except that Step 3 additionally runs the audit and must report `clean` **with an empty `degraded` list**, or explain each remaining finding and each degrade reason, so that a run which computed nothing cannot read as a clean site. **The audit is additive: Step 3's existing manual re-resolve clause for `path:start-end` citations is retained**, because citation checking is not in this change and the literal pins on those clauses must keep biting. No new shortcut phrase, manifest entry, or install-log row.

9. **Carriers**, enumerated against what `1vj4e` actually had to touch for a new tool: `docs/specs/mcp-tool-surface.md` (signature-form entry beside `wf_techdocs_baseline`); the `AGENTS.md` **Available tools** list (hard gate) and the shortcut row; `docs/prompts/index.md`; seed `050` **task 24**, which needs the read-only-branch sentence its task-23 precedent carries; seed `100`'s `refresh-techdocs` rule and its no-raw-invocation line; seed `160`'s pointer phrase **and** the rendered `docs/prompts/upgrade-wavefoundry.prompt.md`; `render_agent_surfaces.SKILL_REGISTRY`'s `wf-techdocs` **description**, which is the host menu text and today names only the baseline tool; `README.md`; `docs/agents/platform-mapping.md`; the architecture docs (`data-and-control-flow.md` Path 3a read-only sibling and Path 6 tool list, `domain-map.md` read edge, `layering-rules.md` boundary invariant, `current-state.md` topology and MCP block); `CHANGELOG.md`; and the session handoff. Additionally: `.claude/settings.json`, which carries **two** parallel arrays that this change takes from 42 to 43 entries (stated as a delta at delivery review, ledger `DEL-16`: the earlier present-tense "42-entry" was a pre-change snapshot of a count this change moves), `permissions.allow` and the provenance key `wavefoundryManagedAllow`, both exactly `list(mcp_tool_roster.allow_rules())` in order. Both are regenerated from `allow_rules()` rather than hand-inserted, because the renderer claims ownership only by exact provenance membership: editing one array alone permanently converts a framework-managed rule into an operator-authored one in two subsystems, and no roster retirement could prune it afterwards. The render is reachable only from install and upgrade and this repository is never upgraded, so the refresh is done by hand here and targets pick it up at their next upgrade. Also `.wavefoundry/framework/seeds/233-technical-writer.prompt.md` and its self-hosted twin `docs/agents/specialists/technical-writer.md`, since the technical-writer role owns the new branch and is currently the one surface not told it exists; and the three rendered `wf-techdocs/SKILL.md` copies under `.claude/`, `.codex/` and `.agents/`, which carry the registry description verbatim and which no test compares against the registry, so a registry-only edit leaves all three stale.


**Amended at delivery review (DEL-4).** The MCP entry returns a BOUNDED report: `findings` and `publication.survivor_pages` cap at 200 each, with `findings_total` and `truncated` always present, `findings_omitted` and `publication.survivor_pages_omitted` present only when their own cap fires, and `publication.survivor_count` always carrying the true total. The CLI entry streams and is uncapped. Seed 178 Step 2 tells the reporting agent how to read those keys; this requirement set originally described only the unbounded shape.

10. **Escaping `nav` symlinks are an explicit refusal, never a silent disagreement.** After the lexical `nav` containment screen and before `Path.is_file()`, the audit resolves the candidate's real path and refuses any target outside the repository root. The report degrades with `nav_target_escapes_root`, names the refused logical entries in `publication.unsafe_nav_targets`, never calls `is_file()`, opens, or reads content on the resolved external target, and cannot report `clean`. Realpath resolution may perform metadata lookup (`lstat`) on path components, including the external target; that lookup is the mechanism that discovers the escape and is not presented as zero external filesystem access. This deliberately does not pretend the target is missing: MkDocs follows it, while the repository-bounded reader refuses it.

11. **A hard worker budget bounds repository-derived audit work at both public entry points.** The CLI and MCP entries call one bounded runner over `audit_techdocs`; the raw function remains the single implementation used by the isolated worker. The runner enforces a ten-second worker deadline by terminating the process, then constructs a constant-size report degraded with `audit_timeout` without calling trio, filesystem, git, or other repository-derived helpers. The deadline covers the worker rather than promising that interpreter startup and fixed response serialization take zero time; after expiry, response construction is bounded O(1) and repository-I/O-free. The worker is stdin-isolated, console-free on native Windows through `subprocess_util.isolated_run`, UTF-8 deterministic, and bytecode-disabled so the read-only claim remains true. Worker failures other than timeout keep the existing could-not-run behavior.

12. **A survivor containment refusal stays visible to the publication and link boundary.** When the MkDocs-style walk encounters a markdown file or directory symlink whose realpath leaves the repository, it refuses traversal before external `is_file`, open, or content read, records only the `docs_dir`-relative logical path under `publication.unsafe_survivor_targets` (directory names end in `/`), and degrades with `survivor_target_escapes_root`. Link scoring consults that refusal set: the normalized unsafe directory node and its descendants emit `techdocs_link_outside_boundary` even though `lexists` is true for the symlink; the existing trailing-slash Markdown-directory-link extraction skip remains explicit. The read-tier MCP response caps this tree-sized list at 200, reports `unsafe_survivor_targets_total`, reports `unsafe_survivor_targets_omitted` only when the cap fires, and includes that omission in `truncated`; the CLI remains uncapped. An in-root symlink retains the established polarity and is published normally. This closes the sibling path that the nav-only refusal left silently uncomputed and prevents a partial boundary from reporting `clean` or an unbounded MCP response.

## Scope

**Problem statement:** the Refresh TechDocs workflow's publication rules (boundary, nav targets, link boundary, trio ownership, audience invariant, metadata) are computed by hand today, and the workflow has no read-only "review and propose" form.

**In scope:**

- `techdocs_audit_lib.py`, `techdocs_audit.py`, `wf techdocs-audit`, the read-tier `wf_techdocs_audit` tool, their tests, and the four gates plus three pins Requirement 7 names.
- The explicit escaping-`nav` and escaping-survivor symlink refusals and hard worker deadline with repository-I/O-free expiry at both public entries (Requirements 10-12).
- The review-only branch of Refresh TechDocs and the authoring branch's Step 3 use of the audit.
- The carriers of Requirement 9.

**Out of scope:**
