# Report retained work after close and find older leftovers

Wave: 23q0t retained-work-cleanup-and-criterion-deferral

## Rationale

Tensorwell reports that a closed wave retained 1.8 GB of hand-created work for 19 days, until disk pressure interrupted review. The folder predates ownership markers. A test fixture's macOS deny-delete ACL also obstructed manual removal. Those field timings, sizes and ACL effects are reported, not reproduced here.

The operator corrected the original incident account:

> The 0cv0t close reported "ownership unproven and preserved the directory" once, in its response and a handoff line. Nothing tracked it after that: no later close, audit or dashboard mentioned it again, and it surfaced only when the disk hit 100% (about 800 MiB free) during a Review wave.

The primary visibility gap is therefore follow-through after an initial warning, not absence of a close report. The operator also reports a second confirmation of requested fix 6: maintained closure records cite disposable work paths. This reinforces the citation advisory in Requirement 5; it does not establish that unique evidence was lost.

Observed failures, executed on 2026-11-17 against the current `wave_work.py` in temporary directories (Progress Log has the commands and results):

1. An unowned folder under `.wavefoundry/work/<key>/` of a wave being closed: `cleanup_work` returns `outcome=preserved`, `notice=work_ownership_unproven; work preserved`, keeps the payload and creates no owner. Preserving unknown work is correct; the problem is what happens next.
2. Close puts that result only in `data.work_cleanup`. `wf_close_wave_response` builds its diagnostics from advisory and gate diagnostics and never translates the cleanup result into one (read, `server_impl.py`, the `work_cleanup = wave_work.cleanup_work(` call and the envelope after it). Expected: a top-level diagnostic an agent or operator will see.
3. An owned folder with entries `a1`, `a2` and a read-only subdirectory `zz/` holding a file: `cleanup_work` removed `a2`, then failed on `zz/locked` and returned `outcome=preserved`, `notice=work_io_failed:EACCES`. Actual: partial removal is reported as "preserved" and the failing entry is not named, because `_failure` reports only the errno. Expected: `partially_removed` with the failing relative entry, operation and errno.
4. `wf_audit_response` and `upgrade_wavefoundry.py` contain no reference to the work root (census: `wave_work` and `.wavefoundry/work` occur zero times in `upgrade_wavefoundry.py` and `wf_server/upgrade_handlers.py`; the audit handler reads wave, validation and index only). Nothing finds a leftover from an earlier close.

A live instance exists in this checkout: `.wavefoundry/work/23lxe/` (6.4 MB, with an owner file) has no wave record in `docs/waves/`. It is the "not found in this checkout" case this change must classify. It is left untouched.

## Product Intent

An operator can see, at close and later, disposable work left under `.wavefoundry/work/` after a wave closes, with its path, reason and approximate size, so a retained folder like the 1.8 GB one in the incident is noticed before disk pressure reveals it. This change only reports; it deletes nothing beyond what close already deletes. The reclaim step is the separate explicit cleanup operation in `23q0s-enh explicit-work-cleanup`, which depends on the inventory added here. AC-1 through AC-4 together demonstrate that the incident's leftover is visible at close and rediscoverable afterwards. This supports Horizon 1's dependable delivery in [the adopted vision](../../../VISION.md).

Platform behaviour: the inventory is read-only and works on macOS, Linux, WSL2 and native Windows. On native Windows, close already preserves work with `safe_work_io_unsupported` because descriptor-relative deletion is unavailable (`_SAFE_DELETE` is false there); this change makes that a visible top-level diagnostic and lists the folder in audit and upgrade, nothing more. On macOS a deny-delete ACL surfaces as a permission errno on the named entry; the change does not diagnose ACLs. WSL2 follows the Linux path, including repositories on a Windows drive mount, where the reported errno is whatever the mount returns.

## Requirements

1. **One read-only inventory of the work root.** Add one function in `wave_work.py` that lists the immediate children of `.wavefoundry/work/` (the `WORK_ROOT` constant; it is not configurable today and this change does not make it configurable). For each folder it reports: the work key, repository-relative path, ownership state (`valid`, `missing`, `invalid`; derived by reading `.owner.json` with the structural checks of sub-point 1 below, without writing), entry count, sum of regular-file logical sizes (`st_size`), and `complete` with a reason when not complete. It walks with no-follow metadata (`os.scandir` and `stat(follow_symlinks=False)`), never opens file payloads, never traverses a symlink or a Windows reparse point (`contained_files._is_link_metadata`), and never descends into a directory whose `st_dev` differs from its parent's. It visits at most 10,000 entries per call across the whole work root; when that bound or an unreadable directory stops the walk, the affected folders report `complete: false` with reason `entry_limit` or `unreadable:<errno name>`, and their counts are lower bounds. The bound is an entry count, not a time budget, so results are deterministic. Logical size is not a promise of reclaimed disk space. The function writes nothing and creates no directory when the work root is absent.
   1. **Owner checks.** The ownership state is structural, because `_read_owner` needs a directory descriptor, `O_NOFOLLOW` and `dir_fd` (absent on native Windows) and a live record path. `.owner.json` is `missing` when absent; it is `valid` only when it is a regular file with one link and at most 4,096 bytes, read without following a link and without blocking (on POSIX, `O_RDONLY | O_NOFOLLOW | O_NONBLOCK` relative to the folder descriptor and an `fstat` check; on native Windows, an `lstat` showing a regular file that is not a reparse point, then a bounded read by path), and parses as a JSON object with integer `schema` 1 or 2, a 32-hex `generation`, a string `wave`, an absolute-path string `repository` (checked as text only, never opened or stat'ed) and a `directory` pair that matches the folder's inode as `_persisted_identity` compares it. Anything else is `invalid`. The `wave` field is compared with the live record path only when the key has a live record; an archived wave's owner records its pre-archive path and a `not_found_in_checkout` key has no record, so those report the structural result.
   2. **Work root links.** Before listing, the inventory `lstat`s `.wavefoundry` and `.wavefoundry/work` and applies `contained_files._is_link_metadata`. When either is a link or reparse point, or is not a directory, it reports `complete: false` with reason `work_root_link` and lists no children. Every reader of the work root's children (Requirements 5 and 6, and the `23q0s` preview) uses this check.
2. **Classify each folder by wave state.** One classifier, in `wave_work.py` or a sibling module that does not import `wf_server`, maps each key to a state. It uses `record_paths.discover_wave_dirs` and `record_paths.discover_archive_dirs` with the record roots of the vocabulary profile, matches a key against a wave folder name's leading id as `_target` derives it, and reads the record's status line with a parser that does not import the server (the implementer names it). Close, `wf_audit`, the upgrade report produced by `upgrade_wavefoundry.py` (a separate process that cannot import `server_impl`) and `23q0s`'s `wf_cleanup_work` all call it; none uses `server_impl._waves_and_dirs` or `_archived_wave_matches`. Renamed record roots therefore classify the same way for every caller. `not_found_in_checkout` requires that no candidate folder for the key exists under the live or archive record roots (`record_paths.walk_wave_candidates` lists candidates whether or not they hold a record); a candidate folder whose record file is missing or not a regular file, or a record root that refuses as unreadable, classifies as `unreadable`. The states are: the live status (for example `active`, `closed`), `archived`, `not_found_in_checkout` (labelled as such in every output, with the note that the wave may exist on another branch or checkout), `ambiguous` and `unreadable`. A folder is a **leftover** when its wave is `closed`, `completed`, `archived` or `not_found_in_checkout`. A folder of a live, not-closed wave with `missing` or `invalid` ownership is reported separately as **live unowned** and is not a leftover. Valid live work is counted but not listed.
3. **Close reports retained work as a top-level diagnostic.** When create-mode close leaves the closed wave's work folder in place (any outcome other than `removed` or `absent`), close adds a top-level diagnostic `work_retained` with: the repository-relative path, outcome, the stable reason token from the existing notice (`work_ownership_unproven`, `cleanup_generation_unproven`, `cleanup_generation_changed`, `safe_work_io_unsupported`, `work_identity_changed`, `work_io_failed`, and the other `_Refused` tokens already in `wave_work.py`), the failed relative entry, operation (`unlink`, `rmdir`, `open`, `stat`) and errno name when known, the inventory's entry count, logical bytes and completeness for that folder, and a next action naming `wf_audit` and the explicit cleanup tool from `23q0s`. A permission errno is reported as an errno; close never states that an ACL is the cause. `data.work_cleanup` stays, with the same new fields. The wave stays closed whatever the cleanup outcome. Dry-run close writes nothing and emits no `work_retained`.
4. **Partial removal is reported as partial.** `cleanup_work` and `_empty_directory` count removed entries and record the first failing relative entry and operation. When at least one entry was removed before a failure, the outcome is `partially_removed` (not `preserved`), with `removed_entries` and the failure fields. Existing retry authority is unchanged: the owner file is still skipped until the end and restored after a post-unlink failure, as today.
5. **Close mentions older leftovers.** Create-mode and dry-run close list the keys of other leftover folders (Requirement 2) by reading only the work root's immediate children and classifying them with the discovery close already performs; no sizing walk. When any exist, close adds one advisory diagnostic `work_leftovers_present` with the count, keys and the next action `wf_audit()`.
6. **Audit and upgrade report leftovers.** `wf_audit` adds `data.work_root` with the inventory result (leftovers, live unowned, totals and completeness) and an advisory diagnostic `work_leftovers_present` when any leftover exists. The audit `ready` boolean does not change. The upgrade report produced by `upgrade_wavefoundry.py` lists each leftover (path, state, size, completeness) and the explicit cleanup tool, and deletes nothing; the implementer identifies the existing report output that `wf_upgrade` returns and the CLI prints by reading its reporting functions before changing code. Neither `index_health` nor the dashboard runs the inventory.
7. **Advisory about maintained records citing work paths.** Close (dry-run and create) searches the selected wave's `wave.md`, its admitted change documents and `docs/agents/session-handoff.md` for the text `.wavefoundry/work/<key>/`, where `<key>` is the closed wave's own work key, and reports each hit (file and line) in one advisory diagnostic `work_path_cited`, recommending that unique proof be copied to durable evidence before cleanup. It is not a gate, edits nothing, ignores the review ledger, and reports `coverage: incomplete` naming any input it could not read. The bare work-root text, or a citation of another key's folder, emits nothing.
8. **No write into the closed record.** Close does not add a cleanup note to the closed `wave.md` or to the handoff. The retained folder itself is the durable state, and Requirements 5 and 6 rediscover it.
9. **Changelog.** `CHANGELOG.md` Unreleased states in operator terms the new `work_retained`, `work_leftovers_present` and `work_path_cited` diagnostics, the `partially_removed` outcome, the `data.work_root` audit field and the upgrade report's leftover list, and that nothing new is deleted.

## Scope

**In scope:** the inventory and classification, close diagnostics (`work_retained`, `work_leftovers_present`, `work_path_cited`), partial-removal reporting in `cleanup_work`, audit and upgrade reporting, focused tests, and guidance for close and upgrade.

**Out of scope:** any new deletion path (that is `23q0s`), disk-space monitoring, age-based deletion, automatic adoption or ownership migration, ACL inspection or repair, making the work root configurable, a dashboard panel, a note written into closed records, and changes to acceptance or readiness rules.

Intended code edits: `.wavefoundry/framework/scripts/wave_work.py` (or a sibling module for the classifier of Requirement 2), `wf_close_wave_response` and `wf_audit_response` in `.wavefoundry/framework/scripts/wf_server/server_impl.py`, the upgrade report in `.wavefoundry/framework/scripts/upgrade_wavefoundry.py`, and tests in `.wavefoundry/framework/scripts/tests/test_wave_work.py` and `test_wave_work_lifecycle.py` plus the upgrade test that owns the report. No new MCP tool and no registration change.

Intended guidance edits: the closure procedure in `.wavefoundry/framework/seeds/190-close-wave.prompt.md`, upgrade reporting in `.wavefoundry/framework/seeds/160-upgrade-wavefoundry.prompt.md`, the installed close prompt `.wavefoundry/framework/install/lifecycle-prompts/close-wave.prompt.md`, the local `docs/prompts/close-wave.prompt.md` and `docs/prompts/upgrade-wavefoundry.prompt.md`, and the `wf_close_wave` and `wf_audit` sections of `docs/specs/mcp-tool-surface.md`. Protected: unrelated seeds, other agents' work, ledgers and closed records. The implementer owns writes; reviewers are read-only.
