# Explicit cleanup of one retained work folder

Change ID: `23q0s-enh explicit-work-cleanup`
Change Status: `implemented`
Owner: Engineering

Last verified: 2026-11-17
Wave: 23q0t retained-work-cleanup-and-criterion-deferral

## Rationale

Tensorwell's closed wave retained 1.8 GB of unowned work under `.wavefoundry/work/` for 19 days (field report; see `23phc-bug retained-work-visibility-and-cleanup` for the incident and the operator's quoted correction). `23phc` makes such folders visible at close, audit and upgrade. It deliberately deletes nothing, so after seeing the folder the operator's only remedy is manual deletion outside the framework, which a deny-delete ACL also obstructed in the incident.

Automatic cleanup cannot do this today, by design. Executed on 2026-11-17 in temporary directories against the current `wave_work.py`: `cleanup_work` preserves an unowned folder (`work_ownership_unproven`), and for a key with no wave record it returns `path: None` with `wave_record_unproven`, because `_target` requires a wave record and derives the key from it. Its `verify()` closure calls `_read_owner`, which refuses any folder without a valid owner. So reclaiming unowned or record-less work needs its own verification path; relaxing `cleanup_work` would weaken the automatic close path.

## Product Intent

An operator who has seen a leftover folder can preview exactly what one work key holds and then, by explicit direction, have the framework delete that one folder safely, without manual shell deletion, without changing the ownership rules that automatic close cleanup uses, and without touching anything outside that folder. On native Windows the framework cannot delete safely (descriptor-relative operations are unavailable, `_SAFE_DELETE` is false), so the tool previews and then refuses to apply, reporting that removal there is the operator's own action; it never falls back to unsafe deletion. AC-2 replays the incident's unowned closed-wave folder through preview and apply.

Platform behaviour: macOS and Linux preview and apply. WSL2 follows Linux; on a Windows drive mount the deletion still uses descriptor-relative calls, and any failure is reported with its errno. Native Windows previews and refuses apply with `safe_work_io_unsupported`. On any platform a permission failure (including a macOS deny-delete ACL) is reported with the entry and errno; the tool never changes permissions or ACLs.

## Requirements

1. **One tool, one key.** Add MCP tool `wf_cleanup_work(work_key: str, mode: str = "dry_run", confirmation: str = "")`. `work_key` must match `[0-9a-z]{5,12}` (the existing `_target` key pattern) and name an existing immediate child directory of `.wavefoundry/work/`; anything else (separators, `..`, a symlink, a file) is refused. `mode` accepts `dry_run` and `apply`; any other value is refused. There is no bulk form and no wildcard.
2. **Preview writes nothing.** `dry_run` returns: the folder path; the `23phc` inventory for that folder (entry count, logical bytes, completeness under the 10,000-entry bound); up to 50 immediate child names with their types; ownership state; the wave state from the `23phc` classification, with `not_found_in_checkout` explained as "no record in this checkout; the wave may exist on another branch or checkout"; the `23phc` `work_path_cited` advisory for `.wavefoundry/work/<key>/`, which always searches `docs/agents/session-handoff.md` and also the wave record and its admitted change documents when a record is found, so a record-less folder cited by the handoff is reported; whether apply is possible on this host; and a confirmation token. It creates, modifies and deletes nothing under the work root, the wave records or the handoff. The preview reads the work root through the `23phc` Requirement 1.2 link check.
3. **Which states may be cleaned.** Apply proceeds only when the wave state is `closed`, `completed`, `archived` or `not_found_in_checkout`. It refuses `ambiguous`, `unreadable` and every live not-closed status (for example `planned`, `ready`, `active`, `implementing`, `paused`), naming the state. The state comes from the one `23phc` classifier, so a wave folder under the live or archive record root whose record file is missing or not a regular file is `unreadable` and refused, never `not_found_in_checkout`. Ownership is not required: valid, missing and invalid owners are all eligible.
4. **What the token binds.** The token is the SHA-256 hex digest of a canonical JSON object holding: the resolved repository root path, the work key, the folder's `[st_dev, st_ino]` as seen through the no-follow parent walk (`_parent`), the SHA-256 of the raw `.owner.json` bytes or `"absent"`, and the wave state with the record's repository-relative path when one exists. It does not bind folder contents: a preview is not a content snapshot, and apply removes whatever the folder holds at that moment. The token proves the target is the one previewed; it is not authorization and not a secret. Because `st_dev` can change across a reboot or remount, an apply after such a change refuses as `preview_stale`, and the operator runs a fresh preview. That failure is safe and is documented, not repaired.
   1. **Owner fingerprint read.** The owner file is untrusted. It is opened relative to the folder descriptor with `O_RDONLY | O_NOFOLLOW | O_NONBLOCK`, checked with `fstat` to be a regular file with one link and at most 4,096 bytes, and read once with a 4,097-byte bound; its SHA-256 is the fingerprint. Absent gives `"absent"`. Any other kind (FIFO, device, directory, link), a second link or a larger size makes preview report the entry and apply refuse as `unsafe_owner_entry`, without blocking. The fingerprint is computed once per check by that one bounded read.
   2. **Unsupported host.** On a host where `_SAFE_DELETE` is false (native Windows: `_parent` raises `safe_work_io_unsupported` first, and `dir_fd` and `O_NOFOLLOW` do not exist), preview reads identity and ownership through the lexical no-follow `lstat` chain that `cleanup_work`'s unsupported branch already uses, returns the inventory with `apply_possible: false`, and returns no token.
5. **Apply checks and deletes under the lock.** Apply runs inside the lifecycle mutation lock that membership in `_LIFECYCLE_MUTATION_LOCK_TOOLS` provides, as `wf_close_change` does, and under `project_state_publication_lock`; the wave-state recheck runs inside that lock. It recomputes the wave state and the token from current facts and refuses `preview_stale` when the token differs or is empty. It then opens the work parent with `_parent` and the folder by descriptor, and refuses `work_filesystem_changed` when the folder's `st_dev` (from `fstat` of the opened descriptor) differs from the work parent's; the closure repeats that comparison. Same-device bind mounts cannot be detected this way, and the contract says so. It deletes through a new verification closure that, before every unlink and rmdir, calls `_anchor` and `_entry`, compares the folder's device with the parent's, and re-reads the owner fingerprint, refusing when any differs. This closure does not call `_read_owner`. Deletion reuses `_empty_directory` with the owner file skipped, then unlinks `.owner.json` if present, then removes the folder. A symlink inside the folder is removed as an entry and never followed; a directory inside the folder on another device is refused, as `_empty_directory` already does for entries within the descriptor it is given. On a host where `_SAFE_DELETE` is false, apply refuses with `safe_work_io_unsupported` before any change.
6. **Failure is reported, never repaired.** Apply returns `removed`, `absent` (the folder vanished before deletion began), `refused` with a reason, or `partially_removed` with the removed-entry count, the failing relative entry, the operation and the errno name, using the failure detail that `23phc` adds to `_empty_directory`. Apply never writes or restores an owner file, never changes permissions or ACLs, never elevates privileges and never invokes a shell. After a partial failure the operator repairs the cause and runs a fresh preview and apply.
7. **Normal cleanup policy is unchanged.** `cleanup_work`, `ensure_work`, `_read_owner` and the close path behave exactly as before this change, and the tool never writes an owner, so cleaning one folder does not legitimize any other folder for automatic cleanup.
8. **Authority.** The tool is registered in the `write` permission tier, so hosts prompt for it unless the operator has enabled the write tier. Guidance states that an agent calls `mode='apply'` only when the operator explicitly directs cleanup of that key in the current request, after showing the preview. Callers stop writers to that folder first; the lock serializes only cooperating lifecycle writers.
9. **Registration.** Register the tool everywhere the lifecycle-locked destructive tool `wf_close_change` is registered (the earlier census of `wf_mark_ac` and `wf_stats` was the wrong analogue: neither is in `_LIFECYCLE_MUTATION_LOCK_TOOLS`). The sites are: the `@mcp.tool(annotations=_DESTRUCTIVE_TOOL)` definition in `server_impl.register_mcp_surface` (destructiveHint true, as `wf_close_wave`, `wf_close_change` and `memory_purge` use); `TOOL_TIERS` in `mcp_tool_roster.py` (as `TIER_WRITE`); `_LIFECYCLE_MUTATION_LOCK_TOOLS` in `server_impl.py`; `PublicationWriter("wf_cleanup_work", "lifecycle", "fail_fast")` in `publication_control.PUBLICATION_WRITER_REGISTRY`, so `_wrap_upgrade_publication_guard` wraps it; the fixtures `tests/fixtures/register-surface-handler-digests.json`, `tests/fixtures/tool-surface-golden.json` and `tests/fixtures/tool-surface-golden/declared.json`; the Tool Index and a detail section in `docs/specs/mcp-tool-surface.md`; the mutating-tier enumeration in seed `050-agent-entry-surface-bootstrap.prompt.md`; and `docs/architecture/data-and-control-flow.md`. Adding it to `_help_catalog` `core_tools` is not required. The implementer reruns that census with `limit=0` before editing and adds the tool to any further per-tool table it finds; the pinning tests include `test_tool_surface_golden.py` and the roster parity test in `test_render_platform_surfaces.py`.
10. **Changelog.** `CHANGELOG.md` Unreleased states in operator terms the new `wf_cleanup_work` tool, preview before apply with a token, operator direction for apply, and the native Windows refusal.

## Scope

**Problem statement:** after `23phc` shows a leftover folder, there is no safe framework operation to reclaim it.

**In scope:**

- the `wf_cleanup_work` tool, its verification closure and deletion path in `wave_work.py`, its registration, tests, and guidance in the close and upgrade prompts and the tool contract.

**Out of scope:**

- bulk or age-based cleanup, automatic adoption or ownership migration, any change to automatic close cleanup, ACL or permission changes, a native Windows deletion backend, a CLI command, evidence promotion, and cleaning live waves.

## Acceptance Criteria

- [x] AC-1: Preview and defaults delete nothing: a call with only `work_key` (default mode) and an explicit `dry_run` leave the fixture tree byte-identical, create no owner file and return the inventory, child names, wave state and a token; an unknown mode and an invalid key (`../x`, `abc12/def`, a symlink named like a key) are refused with the tree unchanged. Known-bad: a default that applied would fail.
- [x] AC-2: The incident replays: for an unowned folder of a closed fixture wave, preview then apply with the preview's token removes the folder; a sibling work folder, the wave record and a file outside `.wavefoundry/work/` are byte-identical afterwards; no `.owner.json` exists anywhere under the work root; and a different unowned folder of another closed wave is still preserved by `cleanup_work` (normal policy unchanged). The same flow removes a `not_found_in_checkout` folder whose preview labels it so. A record-less folder whose path `.wavefoundry/work/<key>/` is cited by `docs/agents/session-handoff.md` returns `work_path_cited` naming the handoff line in its preview. Known-bad: a preview that searches only when a record exists reports no citation.
- [x] AC-3: Apply refuses and deletes nothing in each case, checked separately:
  1. Empty or wrong token.
  2. The owner file is created or changed after preview (`preview_stale`).
  3. The wave is reopened, or is `active`, `paused`, `planned` or `ready`.
  4. The wave id is ambiguous.
  5. The folder is renamed away and a new directory with the same name created after preview (`preview_stale`).
  6. A token computed with a different `st_dev` for the same folder (`preview_stale`, which is the documented reboot case).
  7. The work parent `.wavefoundry/work` is replaced by a symlink to another directory after preview.
  8. `_SAFE_DELETE` patched false: `safe_work_io_unsupported`, while preview still succeeds and returns the inventory with `apply_possible: false` and no token.
  9. A change during deletion: using the `wave_work._checkpoint("unlink")` seam (and `_checkpoint("rmdir_child")` for a nested directory), after one entry is removed the owner file is changed, and in separate cases the folder is swapped for another directory of the same name and the work parent is replaced. Each refuses with `partially_removed` and the refusal reason; the one entry removed before the change is the only one removed, the remaining entries are intact, and nothing outside the folder is touched (the one case in AC-3 where an entry is removed). Known-bad: a closure that checks only before the first unlink removes the rest.
  10. The work folder is on a different device from the work parent (a patched `os.fstat` device value, or a real mount where available): `work_filesystem_changed`, nothing removed.
  11. `.owner.json` is a FIFO, and separately a regular file over 4,096 bytes: preview and apply return promptly (a test timeout guards against a hang), apply refuses `unsafe_owner_entry`, and the tree is unchanged.
  12. A wave folder for the key under the live record root has no `wave.md`: the state is `unreadable` and apply refuses.
- [x] AC-4: A symlink inside the folder that points at a directory outside the work root is removed as a link; the target directory and its files are byte-identical afterwards. Known-bad: a following deletion would empty the target.
- [x] AC-5: An injected `PermissionError` on a later entry, after an earlier entry was removed, returns `partially_removed` with the removed count, the failing relative entry, the operation and the errno name, writes no owner file and changes no permissions; after the injection is removed, a fresh preview and apply return `removed`. On a macOS host, a fixture with a real deny-delete ACL entry yields the same partial report; if that host is not available the delivery evidence records it as unverified.
- [x] AC-6: The tool appears in every registration site named in Requirement 9 with tier `write`, membership in `_LIFECYCLE_MUTATION_LOCK_TOOLS` and in `publication_control.registered_publication_tool_names()`, and `destructiveHint: true` in the tool-surface golden fixture; with an upgrade checkpoint present, apply refuses and deletes nothing; the roster parity and tool-surface golden tests pass with the updated fixtures. Known-bad: removing the roster entry makes the parity test fail, and `_MUTATING_TOOL` fails the destructiveHint assertion.
- [x] AC-7: The tool contract and close and upgrade guidance state preview before apply, operator direction for apply, the token's bindings and its reboot behaviour, that same-device bind mounts are not detected, partial-failure handling, and native Windows refusal; `CHANGELOG.md` Unreleased carries the statements of Requirement 10; the change's own suites and every test it adds pass, and the documents this change edits validate.
