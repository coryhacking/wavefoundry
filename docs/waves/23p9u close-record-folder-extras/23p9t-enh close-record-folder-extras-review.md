# Review extra files in a record folder at Close

Change ID: `23p9t-enh close-record-folder-extras-review`
Change Status: `implemented`
Owner: Engineering
Status: planned
Last verified: 2026-11-18
Wave: 23p9u close-record-folder-extras

## Rationale

Record folders under `docs/waves/` accumulate supporting files that nobody reviews. Measured in this repository on 2026-11-18: 43 of 516 record folders hold a subfolder (78 named `evidence`, 2 named `archive`), 755 files and about 14.6 MiB in those subfolders, plus loose files beside the records (for example 9 `delivery-evidence.json`, 19 `readiness-review.md`). Of the 755 files, 241 are cited by path in their own records or ledger (140 of them in the ledger), 505 are covered only by a mention of their directory, and 9 are not cited at all.

The Close prompt already tells the agent to tidy the folder and to "Group movable supporting files under `evidence/` when useful", but Close shows the agent nothing about what the folder holds, and the guidance does not say what is worth keeping. The operator asked for both, in two messages on 2026-11-18: "Maybe we could evaluate the wave folder and look for extra folders in them and ask the agent to evaluate whether or not that should be checked / summarized / deleted." and "we should add a little more guidance on what is usefule to keep in a wave folder." The operator then scoped it: "yes, plan it as a spec, Close only".

This follows the operator's decision on `23q0s` the same day that `wf_cleanup_work` applies only to `.wavefoundry/work/` and that anything worth keeping belongs in the record folder. That decision makes the record folder the place where retention is judged, so the judgment needs a prompt and a list.

## Product Intent

The agent closing a record, and the operator approving the close, see what the record folder holds besides the record, its specs and its ledger, with sizes and whether anything cites each file, and the agent records one disposition per extra before the close is written. Before: extras stay unless someone remembers to look. After: every Close dry run lists them, the Close prompt says what is worth keeping, and the record states why each kept extra is kept. Boundaries: the tool only reports; it deletes nothing, blocks nothing and looks only at the record being closed.

## Requirements

1. Close reports extras. `wf_close_wave` in `mode='dry_run'` and `mode='create'` adds one advisory diagnostic, `record_extras_present`, when the folder of the record being closed holds any entry other than the recognized set of requirement 2. It is attached to both the normal response and the blocked (error) response. This matters because in `wf_close_wave_response` the existing work reporting runs after the `lifecycle_gates.has_blocking_diagnostics` early return, and a dry run taken before operator sign-off is always blocked by `missing_operator_signoff`; a report placed only on the normal path would never reach the agent at the disposition step. With no extras the diagnostic is absent. The diagnostic never changes the close outcome, the close status or any blocker: blocking behaviour is unchanged.
2. The recognized set is derived, not listed by name: the record file itself, the ledger file, and the spec documents the record admits, as the existing close path resolves them. Every other entry in the folder, file or directory, at any depth, is an extra. A Markdown file in the folder that the record does not admit is an extra.
3. The diagnostic's `detail` gives, for the folder as a whole: the count of extra files, their logical bytes, and whether the walk was complete. For each extra file, up to a cap of 50 listed files, with the total count always given and the number not listed stated when there are more than 50: its path relative to the record folder in forward-slash form, its size, and its citation state from requirement 4. Listed files are ordered largest first, so the cap drops the smallest. The detail also gives per top-level directory totals (file count, bytes, count `not_cited`), so a folder of many similar raw files reads as one line, in addition to the capped per-file list. Hidden and operating-system files (for example `.DS_Store`) are extras like any other.
4. Citation state is one of three values, computed from the text of the record, its admitted specs and its ledger only, using this matching rule. A file is cited by a text when the text contains the file's path relative to the record folder, in forward-slash form, such that:
   1. Left boundary: the match starts at the start of the text, or right after a character that is not a name or path character, or right after the record folder's own repository-relative prefix (the folder's actual path under the records root followed by `/`, including any space in the folder name). The repository-relative form is therefore cited.
   2. Right boundary: the next character is not a name character. A `.` that is not followed by a name character ends the path, so a sentence-final full stop does not prevent a match.
   3. So `a.json` is not cited by `data.json` or by `a.json.bak`. The rule was measured in this repository: of 140 ledger-cited files about 100 are cited in the repository-relative form, and right-boundary-only matching produced 4 false matches (for example `delivery-evidence.json` inside `arc-delivery-evidence.json`). The work-key pattern of `find_work_path_citations` is not reused unchanged.
   4. The states: `cited_in_ledger` when the ledger text cites the file; `cited_in_record` when the ledger does not but the record or an admitted spec does; `not_cited` when no text cites it by path.
   5. Each listed file also carries three booleans: `name_in_ledger` (the bare file name appears in the ledger text under the same boundary rule), `directory_in_ledger` and `directory_in_record` (a containing directory's relative path followed by `/`, or its repository-relative form, appears in the ledger, or in the record or an admitted spec). `not_cited` means only that no path citation exists; the booleans say whether the ledger or record still refers to the file loosely. Motive, measured: in record `1wfsl` the only `not_cited` file is named in its ledger by file name only, as the sole surviving copy of a baseline; across the records 73 of 536 `not_cited` files have their name in their own ledger (an upper bound, since common names also match). A mention of a containing directory alone never makes a file cited, so the 505-file case stays visible and is not mistaken for citation.
5. The walk is read-only and bounded: it follows no symbolic link, junction or reparse point (a link is reported as one entry with its own size, never traversed), stops at a stated entry limit and then reports `complete: false` with the reason, and reads no extra file's content. An unreadable entry or text input is named in the detail and makes coverage incomplete; it never fails the close. Paths are compared exactly as written, in forward-slash form, on Windows, macOS, Linux and WSL2; a citation written with backslashes or a different letter case is reported `not_cited`, and the shipped prose says so.
6. The diagnostic message, in one sentence, gives the counts (files, bytes, how many are `not_cited`, how many are ledger-cited) and points to the Close prompt's disposition step. It uses the neutral noun for the record container where the existing close messages do.
7. The Close prompt gains a disposition step in its existing folder-cleanup section (seed 190 and this repository's copy; the lifecycle template gains a compact form, see requirement 9). Before the final docs validation and the close write, the agent runs the dry run, reads `record_extras_present`, and gives every extra one of three dispositions:
   1. Keep: the file stays, and the record's Review Checkpoints carries one line naming it (or its group) and why it is kept.
   2. Summarize, then remove: the conclusion, the command that reproduces it, the source identity and the limits are written into the record's Review Checkpoints or a spec's Progress Log, then the file is removed.
   3. Remove: the file is removed with no summary because it adds nothing the record, the tests or Git history do not already hold.
   4. A `cited_in_ledger` file is always kept, because the ledger is never rewritten. A `cited_in_record` file is kept, or its citation is rewritten in the same edit that removes it. A `not_cited` file with `name_in_ledger` or `directory_in_ledger` true is kept, unless the agent establishes that the ledger text refers to a different file and says so in the record. When ownership, uniqueness or use is uncertain, keep and say why.
   5. The existing conditions for manual removal in the Close seed and the shared review-artifact guidance still govern every removal: only files established as belonging to this record, verified redundant or summarized, with no live references, removed with the contained and identity-checked deletion those sections already require. Dates and file names are not proof of ownership. Dispositions apply only to files established as belonging to this record; the agent removes nothing from another record's folder.
   6. Summaries and rewritten citations are written only into the record's Review Checkpoints or a spec's Progress Log, never another spec section, because an edit to a spec outside its Progress Log changes the review-policy digest and Close then blocks with `review_policy_receipt_stale`.
   7. Before removing a file, the agent checks the kept extras for references to it; a kept manifest that lists removed files is otherwise left pointing at nothing.
   8. The agent also reads `record_extras_present` on the close write's own response, since a file added after the dry run appears only there.
   9. Removal is the agent's edit under those conditions, visible in the diff the operator reviews; the tool never removes anything.
8. The same section states what is worth keeping in a record folder, as a short rule and examples:
   1. Keep by default: the record, the admitted specs and the ledger.
   2. Worth keeping: proof that cannot be reproduced from a recorded command, the tests and Git history. Examples: a baseline taken from a working tree that no longer exists, a measurement from a machine, data set or model that cannot be rerun, input received from outside the repository such as a field report, and a reproducer that is not suited to be a maintained test.
   3. Summarize and remove: output whose conclusion fits in a few lines and whose command is recorded. Examples: green test logs, probe captures, census dumps, per-reviewer reports, intermediate drafts of a result that the record states.
   4. Remove: copies of files that exist elsewhere in the repository, generated output that a recorded command rebuilds, scratch.
   5. A kept file is cited by its path, not only by its directory, and a large kept file needs a stated reason in proportion to its size.
9. The shared review-artifact guidance (seed 209, Review Artifact Discipline), the Close seed (seed 190) and `docs/contributing/build-and-verification.md` (section "Compact wave evidence and close work") are brought into agreement with requirements 7 and 8. All three currently say that no "reference resolver" is introduced; that sentence is narrowed in each to say that Close reports citation state for the closing record's extras and that no automatic deletion, expiry or gate exists. This is a stated change to shipped wording, not an addition beside it. The byte-exact test pin `test_compact_review_artifacts.CompactReviewArtifactContractTests` pins the seed 209 sentence in its `CONTRACTS` entry for the core seed; it is a byte-exact oracle that the implementer moves with the sentence, and the Progress Log says why at implementation. Prompt surfaces, as they stand: the lifecycle template `.wavefoundry/framework/install/lifecycle-prompts/close-wave.prompt.md` has no folder-cleanup section and no "reference resolver" sentence, so it gains a compact disposition step; `docs/prompts/close-wave.prompt.md` in this repository carries seed 190's text and is hand-edited to match the seed (it is not produced by a render).
10. Close only: no sweep of existing folders, no `wf_audit` field, no report at Pause, Prepare, Review or single-change close, and no change to `wf_cleanup_work`. A record closed before this change is never reported unless it is reopened and closed again.

## Scope

**Problem statement:** Close gives the agent no view of the supporting files in the record folder and no rule for what to keep, so files accumulate unreviewed and most are covered only by a mention of their directory.

**In scope:**

- The advisory `record_extras_present` diagnostic on `wf_close_wave`, both modes, with its bounded read-only inventory and citation state.
- The disposition step and the keep, summarize, remove guidance in the Close prompt (seed, lifecycle template and this repository's hand-edited copy), the matching sentences in seed 209 and `docs/contributing/build-and-verification.md`, and the byte-exact pin that holds the seed 209 sentence.
- The tool reference entry for the new diagnostic, the changelog entry, and tests.

**Out of scope:**

- Any deletion, move or rewrite by a tool. No change to `wf_cleanup_work` or to the work root handling.
- A blocking gate, a required disposition table, a lint rule, or a machine-checked record of dispositions.
- Existing closed records: no sweep, no migration, no report.
- `wf_audit`, the dashboard, the upgrade report, Pause, Prepare, Review and single-change close.
- Resolving citations beyond the record, its admitted specs and its ledger (other records, memory, the handoff).
- The parked plan `1rppn-enh wave-change-manifests-close-advisory`, which would write a manifest file into the record folder. If it is later implemented, its file joins the recognized set in that change.

## Acceptance Criteria

AC-1, AC-2 and AC-6 together test the intent: the agent is shown the extras with citation state and is told what to keep. Whether agents then leave tidier folders is not proven by this change; see Risks for how it will be observed.

- [x] AC-1: A close dry run and a close write on a record whose folder holds extras each return an advisory `record_extras_present` with the file count, bytes, completeness and a per-file list (relative path, size, citation state); a record whose folder holds only the recognized set returns no such diagnostic. A dry run blocked only by the missing operator sign-off carries the diagnostic on its error response. The detail carries the per top-level directory totals. A test with the reporting call removed fails.
- [x] AC-2: The three citation states are each produced by a fixture built with the real lifecycle tools: a file whose relative path appears in the ledger, one whose path appears only in the record or an admitted spec, and one that appears nowhere. Further cases:
   1. A file whose directory alone is mentioned is `not_cited` with `directory_in_ledger` or `directory_in_record` set.
   2. A path that only shares a prefix with a cited path (for example `evidence/a.json` against a cited `evidence/a.json.bak`) is `not_cited`.
   3. The repository-relative form (the record folder's path under the records root, then the relative path) is cited.
   4. `a.json` against a cited `data.json` is `not_cited`.
   5. A path followed by a sentence-final full stop is cited.
   6. A file named in the ledger by file name only is `not_cited` with `name_in_ledger` true.
   Each case fails when its rule is removed.
- [x] AC-3: The recognized set follows the record: an admitted spec is not an extra, the same file after it is removed from the record's admitted set is an extra, and the record file and ledger are never extras.
- [x] AC-4: The report never changes the close result. With extras present, the close status, blockers and written record are identical to a close of the same fixture without extras, apart from the added diagnostic. An unreadable extra and a walk that reaches its entry limit each yield the diagnostic with incomplete coverage and the reason, and neither raises or blocks. When a text input (the record, an admitted spec or the ledger) cannot be read, the close result is whatever it was without this change (blocked for its own reason where that applies, for example an unreadable ledger through the review-authority gate), and the diagnostic still appears with incomplete coverage naming the input and never raises.
- [x] AC-5: The walk does not traverse links: a symbolic link to a directory outside the record folder is reported as one entry and nothing behind it is counted or listed. The test runs where symbolic links can be created and is skipped with a stated reason where they cannot.

## Risks

| Risk | Mitigation |
| --- | --- |
| The agent treats the list as an instruction to delete and removes unique proof. | The guidance keeps anything ledger-cited, keeps on uncertainty, requires the summary before removal, and removal is visible in the diff the operator reviews. |
| Advisory output is ignored. | The disposition is a numbered step before the close write and leaves lines in the record; the measure above checks it at later closes. No gate is added on purpose. |
| Removing or editing files in an open record folder during a test run makes the runner refuse the run, and edits to the record may affect review receipts. | The step is placed before the final validation and suite, as the existing section already requires. Settled at readiness: removing a non-spec file moves neither the review-policy receipt (`review_policy.policy_input_snapshot` hashes admitted spec bodies through `canonical_review_policy_body`, plus config) nor the framework test receipt; a spec edit outside the Progress Log does move the digest and blocks Close, so requirement 7 confines summaries and rewritten citations to the record's Review Checkpoints and a spec's Progress Log. |
| `not_cited` errs toward removal: a file the ledger names loosely (by file name or directory) reads as uncited. | The `name_in_ledger`, `directory_in_ledger` and `directory_in_record` booleans of requirement 4 show the loose mention, and requirement 7 keeps such a file unless the agent establishes the ledger means a different file and says so in the record. |
| A large folder slows Close. | Bounded walk with an entry limit, no content reads, sizes from `lstat` only. |
| Windows path forms differ from the cited text. | Exact forward-slash comparison everywhere, stated in the tool reference; a mismatch errs toward `not_cited`, which leads to a look, never to a removal by the tool. |
