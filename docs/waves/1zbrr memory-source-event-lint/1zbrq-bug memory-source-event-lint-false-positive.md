# Memory Source Event Identifiers Do Not Trigger Secret-Assignment Lint

## Rationale

A downstream promoted memory generated by memory_propose cannot pass close: its source event is `decision-log:1v5sl-bug marketplace-queue-handlers-log-tenant-secret:6263b748459fc4fb`. The secret-assignment pattern mistakes the structural colon after the slug for a secret assignment. Rewording provenance breaks source linkage and re-drafting reproduces it. Correct lint classification without changing historical records or source identities.

## Requirements

1. Derive the supported event families from memory_supply.draft_candidates: decision-log (change identifier and 16-hex decision hash), repeated-repairs (wave identifier and target), and finding (wave identifier and finding identifier). Use the existing producer/identifier contracts, including supported lifecycle identifier lengths and target syntax; do not invent a fixed five-character identifier rule.
2. Recognize only a complete canonical Source event metadata line, anchored over the whole line with its backtick delimiters and valid structural fields. The only exempt match is the secret-assignment match that ends at the decision-log separator immediately before the decision hash (exactly 16 lowercase hex, `[0-9a-f]{16}`, immediately before the closing backtick), on a line whose change identifier matches the lifecycle change-stem grammar (lifecycle identifier, change type, slug). Finding and repeated-repairs events get no exemption regardless of grammar: generated wave identifiers are digit-led in practice, so no keyword appears there, and a keyword in that position (for example `finding:token:...`) receives ordinary scanning. The lifecycle prefix grammar itself (`LIFECYCLE_PREFIX_PATTERN`) accepts keyword-shaped tokens, so no validation branch is built for these families. Scan every match of every memory forbidden-content pattern (`finditer`, not first-match `search`), so recognizing the separator never hides a later match. Never blanket-exempt a Source event line or any payload field. Nested symbol:/community: target delimiters are payload, not event separators. The write-time `_FORBIDDEN` scans in `memory_handlers` do not check `source_event` and stay unchanged.
3. Preserve Source event bytes and provenance linkage. No record migrations, regeneration, rejection, revalidation, or changes to close-time identity matching. Existing journal checks are unchanged.
4. Malformed or unknown event forms receive ordinary scanning. Trailing text, injected secret assignments inside fields, additional backticks, and ordinary secret assignments remain detectable. Unknown forms are not automatically rejected merely because the recognizer cannot classify them.
5. Test every producer family using real memory proposal/rendering where practical, with independently specified lint outcomes. Include slugs ending in secret, password, passwd, token and api-key, the reported line, and controls demonstrating the content protection still fires. Cover metadata recognition boundaries and valid repeated-repair target forms without expanding allowed provenance syntax. Include a same-line two-match control (`finding:token:secret=fixture-value`), keyword-as-wave-identifier controls (`finding:token:hunter2` and `repeated-repairs:secret:x.py` must still fail), and a decision-log line whose change identifier is not a lifecycle change stem and whose slug ends in a keyword (must still fail). Exercise both five- and six-character lifecycle IDs through the real producer, nested symbol:/community: content, and a non-secret forbidden-content pattern. Existing non-canonical fixtures (for example `finding:x`, `decision-log:1zzzz-feat demo:abc123`) keep passing under ordinary scanning.
6. Document the fix in CHANGELOG and state that downstream local exemptions can be removed after upgrading to the release containing this fix.

## Scope
