Change ID: `1zx02-bug lifecycle-lock-ofd-and-reload-safety`

Wave: 1zxnz lock-integrity

## Rationale

A downstream distribution reported, privately, two defects in the runtime-lock layer. Both were confirmed against HEAD `06c02e63`. This change fixes the defect classes; it records no reproduction.

**P1, record locks are released by any descriptor close.** On POSIX the lifecycle mutation lock and the index-build lock are classic POSIX record locks: `runtime_lock.RuntimeFileLock(style="record")` calls `fcntl.lockf` on a sentinel byte (`runtime_lock.py`, `_acquire_os_lock`). The kernel ties a classic record lock to the process, so closing ANY descriptor of the lock file anywhere in the holding process silently releases it. Waves 1za2y, 1zimc, 1zv87 and 1zv8c built compensating controls (the in-process hold registry, the reader deny check `server_impl._is_runtime_lock_path`, the walker check, the acquire-time link scan `lifecycle_lock._refuse_lock_links`), but each is a perimeter that every in-process reader must remember to cross. The threat model already records the class (`docs/architecture/threat-model.md`, "Reading a runtime lock releases it"). Readers outside that perimeter remain: the handoff reader and writer (`edit_gate_handlers.wf_get_handoff_response`, `wf_set_handoff_response`), the pause and close handoff writes in `server_impl`, `server_impl.get_prompt`, and the resource helper `_read_doc_or_not_found`. The link scan runs only at acquire. The durable fix removes the class instead of adding readers to a deny list: open file description (OFD) locks belong to the open file description, so an unrelated open and close in the same process cannot release them.

**R6, a reload cannot import new names from `runtime_lock`.** `wf_reload_mcp` reloads `server_impl`, whose prologue evicts a fixed set of flat modules (`lifecycle_lock`, `review_evidence`, `context_efficiency`, `index_source_guard` and others) so they re-import fresh code. `runtime_lock` is deliberately NOT evicted because it holds the process hold registry `_PROCESS_RECORD_HOLDS` and its guard (wave 1za2y). The re-imported modules then import from the stale `runtime_lock`, so a release that adds a name to `runtime_lock` makes `wf_reload_mcp` fail with `ImportError` until the host restarts. This happened in this repository during wave 1zyc5 (its Progress Log records the failed reload). `runtime_lock` must load new code on reload and keep the registry.

## Requirements

1. **OFD acquire on supported POSIX.** `RuntimeFileLock` with `style="record"` acquires through `fcntl.fcntl(fd, F_OFD_SETLK, ...)`, or `F_OFD_SETLKW` when `blocking=True`. It locks the same `offset` and `length` it locks today, as a write lock (`F_WRLCK`, `l_whence` `SEEK_SET`, `l_pid` 0). OFD is used only where the packed `struct flock` layout is known: `sys.platform` is Linux or macOS, the interpreter is 64-bit, the machine is x86_64/amd64 or aarch64/arm64, and the `fcntl` module exposes all three `F_OFD_*` constants. The constants are never hard-coded.
2. **One layout owner.** `runtime_lock` owns the per-platform `struct flock` layout (moved from `indexer._FLOCK_STRUCT`). The packed buffer is padded to the platform's native `sizeof(struct flock)`: 32 bytes on 64-bit Linux, 24 on macOS. `indexer`'s `F_GETLK` probe reads the layout from `runtime_lock` through a function-local import inside the probe, never at module level: an older upgrade runner can import the new `indexer` (for example `upgrade_wavefoundry._verified_active_model_authority` runs `import indexer`) in a process whose cached `runtime_lock` is the pre-change module without the layout. There, the import or attribute error falls into the probe's existing catch-all and returns the undetermined result `(None, None)`, so importing `indexer` never fails. `runtime_lock` stays stdlib-only.
3. **Safe fallback.** Without OFD (Requirement 1's conditions fail), or when the OFD call fails with `EINVAL`, `ENOSYS`, `ENOTSUP` or `EOPNOTSUPP` (an older kernel or a filesystem that refuses OFD), the lock acquires with `fcntl.lockf` exactly as today. A busy result from OFD (`EAGAIN` or `EACCES`) raises `RuntimeLockBusy` and never retries with `lockf`. Any other errno raises `RuntimeLockError`. The fallback is decided per acquire, never cached across processes.
4. **Mechanism is recorded and released symmetrically.** After acquire, `RuntimeFileLock.mechanism` is `"ofd"`, `"lockf"`, `"flock"` or `"msvcrt"`. `release` unlocks with the mechanism that acquired: `F_OFD_SETLK` with `F_UNLCK` for OFD, `lockf(LOCK_UN)` for the fallback. The handle is closed in every case, as today.
5. **Cross-version exclusion is kept.** OFD holders and classic `lockf` holders exclude each other across processes in both directions, so a pre-change process (an older MCP server or upgrade runner still running) and a post-change process never hold the lifecycle or index-build lock at once. The upgrade bridge's `_StrictLock` keeps classic `lockf`: it is a short-lived standalone process, it opens no other descriptor of the lock file while holding it, and the cross-type conflict keeps it exclusive.
6. **The hold registry stays.** The in-process registry (`register_process_hold`, `process_hold`, `process_hold_guard`), the reader deny checks and the acquire-time link scan are unchanged. They remain the protection on fallback platforms and the fast in-process answer everywhere.
7. **Holder pid is never negative.** `indexer._index_build_lock_held_unguarded` returns `None` as the holder pid when the probe reports `l_pid <= 0`, which is what an OFD holder reports. `index_build_status` then reports the owner pid from the lock metadata, as its existing fallback already does.
8. **`runtime_lock` reloads in place and keeps its state and exception identity.** `server_impl`'s reload prologue re-executes `runtime_lock` in place when the module is already loaded. It does this before any evicted module is re-imported, so re-imported modules see the new names. A bare `importlib.reload` is not enough: it would re-create `RuntimeLockError` and `RuntimeLockBusy`, while unevicted modules that bound those names at import (`dashboard_lib` binds `RuntimeFileLock`, `RuntimeLockBusy`, `RuntimeLockError` and `write_json_in_place`; `scanner_skips` binds `RuntimeFileLock`) keep the old classes. Their `except` clauses would then stop catching what re-imported code raises: for example, `dashboard_lib.dashboard_lock` converts `RuntimeLockBusy` into `DashboardLockBusy`. The reload therefore follows the existing `upgrade_extensions._reload_in_place` idiom. Before reloading, it captures every exception class defined in `runtime_lock` (a `BaseException` subclass whose `__module__` is `runtime_lock`). It reloads, and in a `finally` it rebinds each captured class that still exists after the reload to its original object. The whole capture, reload and rebind runs under `process_hold_guard()`, so no in-process acquire or reader check interleaves with it. Only exception classes are rebound, because rebinding other classes would discard their new code. Stale-binding precondition: an old `RuntimeFileLock` instance or class still held by an unevicted module runs its old method code against the reloaded module's globals. This change therefore keeps the names and signatures of the module helpers those methods call unchanged (`_open_lock_carrier`, `_open_carrier`, `_open_retrying`, `_boundary_components`, `_link_refusal`, `_is_windows_link`, and the error classes). Old instances have no `.mechanism` attribute, and nothing reads it on them: only new-code callers and tests read it, on locks they created. Dashboard `flock` acquires run outside `process_hold_guard()`, so one can overlap the reload. The race is negligible, because those acquires take `flock` (not affected by the mechanism change) and keep the exception classes Requirement 8 rebinds. A release that changes the definition of a `runtime_lock` exception class must state in its CHANGELOG that a host restart is required (a docstring note in `runtime_lock` says so too). Every module-level mutable state in `runtime_lock` (`_PROCESS_RECORD_HOLDS`, `_PROCESS_HOLD_GUARD`) is initialized with a preserve-if-present idiom: the existing object is kept when the module namespace already holds one of the right type. The type checks are `isinstance(value, dict)` and `isinstance(value, type(threading.RLock()))`. `threading.RLock` is a factory function, not a class, so `isinstance(value, threading.RLock)` would raise `TypeError`. A hold registered before a reload therefore stays visible after it, including on the first reload from a pre-change `runtime_lock` whose namespace already holds these two names. Comments that say `runtime_lock` "is not evicted" or is "left loaded" (`runtime_lock.py`, `server_impl._is_runtime_lock_path`, `indexer.py`) are reworded to "reloaded in place, state preserved".
9. **Reload-closure guard test.** A test in `tests/test_lifecycle_gates_structure.py` computes the evicted and reloaded set from `server_impl`'s source (the purge literal, the `wave_lint_lib` prefix, `_PACKAGE_PURGE_KEYS`, the in-place reload of Requirement 8, and `server_impl`). It walks every import statement in those modules, at module level and inside functions. It fails when one imports a flat script module that is neither evicted, nor reloaded in place, nor on an explicit allow-list kept in the test (`_RELOAD_RETAINED_FLAT_MODULES`, name to a one-line reason). Each allow-list reason states why a stale module is acceptable until restart, for example runner bootstrap (the existing `_RELOAD_BOOTSTRAP_EXCLUSIONS`: `repo_root`, `setup_readiness`, `venv_bootstrap`, `subprocess_util`), a process-wide cache, or a stable API read lazily. The test also fails on an allow-list entry that is evicted, or that no evicted module imports any more. Its starting content is the 23 census names other than `runtime_lock`. A second check in the same test covers import-time bindings of `runtime_lock` names. It walks every flat module that is not evicted, including allow-listed modules and modules outside the census, and lists each MODULE-LEVEL `from runtime_lock import NAME` statement. Only module-level statements are checked. A function-local `from runtime_lock import NAME` runs at call time against the `sys.modules` entry, which is the module reloaded in place, and so does `import runtime_lock` followed by attribute access. Both therefore always see current code. Examples of function-local imports the check deliberately ignores are `indexer` (around lines 309, 950, 3149, 3156, 3164, 3221 and 3266) and `upgrade_wavefoundry` (around lines 320 and 2287). It fails unless each bound name is either an exception class (Requirement 8 keeps its identity) or is listed in a test-side `_RUNTIME_LOCK_STALE_BINDINGS` map (`(module, name)` to a reason). Its starting entries are exactly `dashboard_lib`'s `RuntimeFileLock` and `write_json_in_place` and `scanner_skips`'s `RuntimeFileLock`. They are old code that stays consistent until restart because those modules use only `flock`-style locks, and the check passes on the tree with exactly these entries.
10. **Defense in depth: one checked read helper.** `server_impl` gains a single helper, `_read_repo_text_checked(root, path)`. It resolves the target, refuses it without opening it when `server_impl._is_runtime_lock_path` over the resolved root and resolved target is true, and otherwise reads the text as today. The refusal is a dedicated exception (`RuntimeLockTargetRefused`) carrying only the repository-relative path. Every handoff, prompt and resource reader routes through it, and the handoff writes check the same predicate before writing. The census of sites, verified at HEAD `06c02e63`:
    - Handoff: `edit_gate_handlers.wf_get_handoff_response` (read) and `wf_set_handoff_response` (write); the pause handoff read and write and the create-mode close handoff read and write in `server_impl`.
    - Prompts: each candidate file in `server_impl.get_prompt` (slug pass and content-fallback pass).
    - Resources registered in `register_mcp_surface`: `_read_doc_or_not_found` (prompt index, architecture current state, session handoff, agents guide), `resource_project_overview` (each candidate), `_validated_wave_markdown` (current wave and `resource_wave`), `resource_seed`, `resource_architecture`, `resource_area_context`, `resource_codebase_map` (reads `docs/references/codebase-map.md`). `resource_change` reads through `_resolve_change_doc_matches`, so that function's read uses the helper too. Not routed: `resource_waves`, which reads wave records through the shared wave discovery (`_waves_and_dirs`, the same scan behind `list_waves_cached`). That scan is shared with every wave-listing tool, so it is named under the threat-model residual (AC-12) instead.
    Census command: `rg -n 'read_text|write_text' .wavefoundry/framework/scripts/wf_server/edit_gate_handlers.py` plus `rg -n 'def resource_|_read_doc_or_not_found|_validated_wave_markdown|def get_prompt|session-handoff' .wavefoundry/framework/scripts/wf_server/server_impl.py`, reading each resource body from the result.
    Outcomes: a refused handoff read or write returns an error envelope with diagnostic `runtime_lock_target_refused` (repository-relative text only). Pause and close skip the handoff write and add that diagnostic, and the wave or record transition they already made stands. A refused resource returns a `# Refused` markdown body naming the repository-relative path, never the file's content. In `get_prompt`, a refused candidate is skipped, not fatal: the search continues with the next candidate, so a lock target never hides a legitimate prompt. `get_prompt` keeps returning `Optional[str]` and gains an optional `refused` list argument; it appends each skipped candidate's repository-relative path to the list when one is passed. `wf_get_prompt_response` passes the list. When the lookup finds nothing and the list is non-empty, it adds `runtime_lock_target_refused` alongside `prompt_not_found`. When a prompt is found, it adds `runtime_lock_target_refused` as a warning diagnostic to the ok response. `resource_prompt` passes a list too, and its `# Not Found` body names the refused candidates. `McpRepoCache.get_prompt_text_cached` does not cache a miss whose lookup skipped a refused candidate, so the next call re-runs the lookup and reports the refusal again. Its existing mtime-keyed cache of ordinary hits and misses is unchanged.
11. **Windows unchanged.** On native Windows the `msvcrt.locking` branch is byte-for-byte unchanged and `fcntl` is never imported. The new attribute reports `"msvcrt"`.
12. **No tool-surface change.** No `@mcp.tool` handler source in `register_mcp_surface` changes. If one does, `tests/fixtures/register-surface-handler-digests.json` gets the recomputed digest of only that handler and one description sentence naming this wave and handler.
13. **Docs and release notes without reproduction steps.** The architecture and spec docs in Affected Architecture Docs describe the OFD mechanism, the fallback and the in-place reload. The CHANGELOG gets one `### Fixed` bullet under the in-progress release heading (currently `## [1.29.0]`), naming the defect class (a POSIX record lock lost on an unrelated descriptor close; a reload failing on new `runtime_lock` names) and the fix, with no reproduction or exploit steps.

## Scope

**Problem statement:** On POSIX, a record-style runtime lock is lost when the holding process closes any descriptor of the lock file, so lock safety depends on every in-process reader avoiding lock files. Separately, `wf_reload_mcp` cannot load a `runtime_lock` that gained names, because that module is never reloaded.

**In scope:**

- OFD mechanism, fallback, mechanism attribute and symmetric release in `runtime_lock.RuntimeFileLock` (Requirements 1 to 4), and the layout move (Requirement 2).
- Holder-pid normalization in `indexer` (Requirement 7).
- In-place reload of `runtime_lock` with preserved state, and the reload-closure guard test (Requirements 8, 9).
- One checked read helper and its use at every handoff, prompt and resource reader in the Requirement 10 census.
- Tests for every behavior above; doc and CHANGELOG updates (Requirement 13).

**Out of scope:**

- The upgrade bridge's `_StrictLock` (Requirement 5 keeps `lockf`).
- Removing the hold registry, the reader deny checks or the acquire-time link scan (Requirement 6). Re-scanning links after acquire.
- `flock`-style locks (publication, dashboard, install, codebase-map): `flock` locks already belong to the open file description and are not released by unrelated closes.
- Making the 23 allow-listed flat modules reload-safe. The guard test records them and names a reason for each; reducing the list is a follow-up.
- Change-id and path containment, journal writes and extension provenance (planned wave B); correctness and test hygiene (wave C); distribution extensibility (wave D); vocabulary-derived names (wave E).

## Platform Behavior

- **Linux** (glibc or musl, kernel 3.15 or later, x86_64 or aarch64): OFD through Python's `fcntl.F_OFD_SETLK`/`F_OFD_SETLKW` (37/38). OFD and classic record locks conflict within and across processes, and classic `F_GETLK` reports an OFD holder with `l_pid == -1` (Requirement 7). On an older kernel, or a filesystem that rejects OFD, the call fails with `EINVAL` or an unsupported errno and the lock falls back to `lockf`, which is today's behavior with the registry still in force.
- **macOS** (x86_64 or arm64): OFD constants 90/91/92 are exposed by the `fcntl` module. Behavior was checked on macOS 27.2 arm64 at planning time (Rationale): the lock survives unrelated closes, excludes classic locks both ways, and reports `l_pid == -1` to `F_GETLK`. The packed buffer is the 24-byte macOS layout.
- **WSL2**: the Linux kernel, so Linux semantics on the distribution's own filesystem. On a Windows drive mount (`/mnt/c`, DrvFs) the kernel's local lock handling is expected to accept OFD. If it refuses with an unsupported errno, the lock falls back to `lockf`. WSL1 is expected to fall back. Neither mount nor WSL1 was verified at planning time.
- **Native Windows**: `msvcrt.locking` byte-range locks belong to the handle, and closing another handle does not release them. The branch is unchanged, `fcntl` is not imported, and `mechanism` is `"msvcrt"`.
- **Other POSIX** (BSDs, 32-bit interpreters, other architectures): `lockf` fallback by Requirement 1's conditions. The registry and deny checks remain the protection there.
- **Mixed versions during upgrade**: a pre-change process uses `lockf` and a post-change process uses OFD; they exclude each other. A pre-change status tool probing a post-change holder may show owner pid `-1` (cosmetic, in code this change cannot update).
