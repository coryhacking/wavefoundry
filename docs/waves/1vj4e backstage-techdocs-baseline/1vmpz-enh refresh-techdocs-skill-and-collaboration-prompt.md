## Rationale

The Backstage catalog and TechDocs baseline (`1vj4d`) makes an installing project's generated documentation *eligible* for TechDocs, but the pages it publishes (`docs/references/project-overview.md`, `docs/ARCHITECTURE.md` and its children, `docs/references/*`, `docs/prompts/index.md`) were written for agents, not for the humans who read a TechDocs site. The value of the feature is decided by an editorial pass that turns those sources into reader-facing pages without forking the source of truth, and by a workflow that keeps them accurate: cited code facts from Guru, the current-state narrative from the architecture lane, the posture summary from the security lane, verified claims from qa/reality-checker, and a docs-contract signoff. The framework already ships the role for this, the `technical-writer` specialist (`seeds/233-technical-writer.prompt.md`), and already renders every lifecycle workflow as a `wf-` skill from one registry with doc-gated entries (`wf-package`, `wf-code-cleanup`). What is missing is the workflow that puts the technical writer at the head of that collaboration and the skill that makes it one command.

Doing this **before** rolling baseline generation into setup and upgrade (operator decision 2026-08-18) is deliberate: the skill is on demand, so content quality can be iterated with no blast radius on install/upgrade plumbing, and the always-on generation question (which needs an opt-in flag and a default chosen with evidence) is deferred to a later change.

The seed carries the workflow and is the canonical carrier of the operator follow-up checklist (seed-012 step 2.13.5 and seed-160 point at it with one line); the skill body and the rendered prompt point at it. 2. **Workflow, step 1: baseline.** Run the baseline (from `1vj4d`): the `wf_techdocs_baseline` MCP tool when the Wavefoundry MCP is attached (`mode='dry_run'` first to see what would be written, then `mode='run'`), otherwise the `wf techdocs-baseline` CLI (the install row and no-MCP fallback): if the readiness precondition holds (`docs/references/project-overview.md`, `docs/ARCHITECTURE.md`, `docs/prompts/index.md` exist) it generates `catalog-info.yaml`, `mkdocs.yml`, and `docs/index.md` missing-only with the generated-by marker and prints the partial-state warning when the trio is mixed; if the precondition fails the workflow stops and names the missing targets. 3. **Workflow, step 2: collaboration.** The `technical-writer` specialist coordinates (per its role doc: precision and findability over completeness, verify before restating). It requests, in isolation and with fresh contexts where the project's council policy requires it: cited code facts from Guru when the target has Guru and the Wavefoundry MCP (`code_ask` with symbol anchors, per the citation rule in `docs/agents/guru.md`), otherwise the writer's own `code_read`/`code_search`-grounded verification recorded as such (the seed is framework-generic and must not assume this repository's roster or MCP); the current-state and boundary narrative from `software-architect` / `architecture-reviewer`; the security posture summary from `security-reviewer` (sourced from `docs/SECURITY.md` and the threat model when present, never inventing controls); verification of every claim that names behavior from `qa-reviewer` or `reality-checker`; and a `docs-contract-reviewer` signoff that the pages match the code and the specs when that lane exists in the target (it is existing-only per seed-100), otherwise `qa-reviewer` or the writer records the docs-contract check by name. The writer then authors or refreshes the published pages: `docs/index.md` (landing narrative; the generated-by marker stays if the page is still the generated one; when the writer authors the page it removes the generated-by line from all three trio members, so the project owns the whole trio and a rerun of `wf techdocs-baseline` stays silent instead of warning about a mixed trio; the operator may keep the YAML members generated, accepting the warning), `docs/references/project-overview.md`, `docs/ARCHITECTURE.md` and its `docs/architecture/*` children (framing only: the Boundary Invariants, Interaction Edges, Dependency Direction, and State Ownership tables are review authority and keep their substance; the architecture lane, already a supplier, verifies every dogfood edit under `docs/architecture/`), `docs/references/*`. Pages summarize and link; they do not duplicate `AGENTS.md`, role docs, wave records, or prompt bodies. Every touched page keeps `Owner/Status/Last verified` metadata and passes the citation and link rules. When a named lane is not enabled in the target (`technical-writer` is a universal specialist enabled per config; `docs-contract-reviewer` is existing-only), the coordinating agent adopts that seed's stance directly (seed 233 for the writer) and says so in the report; a docs-contract check performed outside an open wave is reported as a fact to the operator. **Problem statement:** The published TechDocs pages are agent-facing and there is no workflow or one-command entry that authors reader-facing pages from verified sources and keeps them accurate.

**In scope:**

- Seed `178-refresh-techdocs.prompt.md`, its rendered public prompt, index/manifest/AGENTS.md rows (shortcut table and the § Skills paragraph's doc-gated enumeration), seed-050 registration and doc-gated-skill enumeration, `docs/agents/platform-mapping.md` § Skills (hand-maintained record of on-disk skills, per seed-050), the `wf-techdocs` skill registry entry, seed-100 usage-note update, seed-012/160 wiring, reviewer-routing lines, `CHANGELOG.md` `[Unreleased]`, tests.

- Baseline generation itself (`1vj4d`); auto-generation on setup/upgrade and its opt-in flag (later change).

- Any Backstage registration, publication, CI, or storage.
- Rewriting agent-facing surfaces (`AGENTS.md`, role docs, prompt bodies) for human readers.
