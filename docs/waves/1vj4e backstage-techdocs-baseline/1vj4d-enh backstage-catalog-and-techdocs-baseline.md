## Rationale

Wavefoundry creates and maintains documentation in each installing project, but does not create the Backstage descriptor and TechDocs configuration that make that documentation eligible for catalog ingestion and TechDocs generation. Every installed project should receive a safe, useful baseline without claiming automatic Backstage registration, successful publication, or an unverified product API, runtime resource, system, domain, or ownership model.

**Design revision 2026-08-18 (operator decision after an independent plan review).** The first readied plan generated the trio during Phase 1 of a fresh install and preserved the partial-state fact through a two-phase `pending`/`committed` record in the upgrade lock, a one-run nonce, and incoming-pack extension hooks. The plan review found that (a) a Phase-1-materialized `docs/index.md` links to three Phase-2 documents, so on every fresh install docs-lint reports three `broken link` errors that `wf_audit_install` classifies as blocking (the same class wave `1viyu` repaired for the lifecycle prompt baselines), (b) the same links fail the upgrade docs gate on an installed target that never produced `docs/ARCHITECTURE.md`, (c) `upgrade_lib.write_upgrade_lock` rebuilds the lock on a retry and would discard the pending record the design depended on, and (d) the plan added a third install-asset resolver and write loop next to the two families that already exist. The operator chose the simpler design recorded here: the partial-state fact is carried by a **generated-by marker in each generated file** and recomputed from the tree by any later reader, so no lock record, nonce, or hook is needed. **Second revision, same day (skill-first):** generation is triggered by an explicit command, `wf techdocs-baseline`, invoked by the **Refresh TechDocs** workflow (`1vmpz`) at the end of Phase 2 of a fresh install (row 2.13.5) and on demand thereafter, still gated on the navigation targets existing; it is **not** run by every `render_agent_surfaces` pass and **not** auto-run by upgrade. Always-on generation at setup/upgrade behind an opt-in flag is deferred to a later change, because a project that does not use Backstage would otherwise get a deleted `catalog-info.yaml` back at every upgrade with no durable way to decline.

## Requirements

1. **One command, gated on readiness.** A new `wf techdocs-baseline` CLI subcommand (dispatched by `wf_cli` to a thin `techdocs_baseline.py` entry that calls the `render_agent_surfaces` module function `render_techdocs_baseline(repo_root)`) owns generation of the root `catalog-info.yaml`, root `mkdocs.yml`, and `docs/index.md`. It is **not** part of the `render_agent_surfaces()` render pass, so `wf render-surfaces`, `wf_sync_surfaces(mode="run")`, setup Step 1, and the upgrade surface-rendering phase do not generate the trio (a later change may add opt-in auto-generation). Generation runs only when the **readiness precondition** holds: `docs/references/project-overview.md`, `docs/ARCHITECTURE.md`, and `docs/prompts/index.md` all exist as regular files; when it does not hold, the command writes none of the three files, prints one `techdocs-baseline: ERROR` line naming the missing targets on stderr (the prefix forms are defined once in Requirement 6), and exits with code 1 without touching the tree. Order of evaluation: the precondition first, then the containment classification of Requirement 5 for all three destinations, then the writes. On a fresh install the command is invoked by the **Refresh TechDocs** workflow at row 2.13.5 (end of Phase 2); after upgrades or content changes it is invoked on demand through the same workflow. This gating is what keeps every tree the command touches lint-clean: no generated landing page ever links to an absent document.
2. **Entity identity and shape.** The generated catalog entity follows Backstage's standalone-documentation `Component` shape. Derive a slug from the target repository directory name by lowercasing, replacing each maximal run outside `[a-z0-9]` with `-`, and trimming leading/trailing `-`; remove one existing terminal `-docs`, truncate the remaining stem to 58 characters and trim a trailing `-`, fall back to `project` if the stem is empty, then append exactly one `-docs`. The final name is therefore at most 63 characters and always identifies the documentation entity. This suffix reduces collision risk with a later product `Component` but cannot guarantee catalog-wide uniqueness. Generate `apiVersion: backstage.io/v1alpha1`, `kind: Component`, the final name, `metadata.title: <name> Documentation`, `metadata.description: Technical documentation for the <name> project.`, `backstage.io/techdocs-ref: dir:.`, `spec.type: documentation`, `spec.lifecycle: experimental`, and the plain default group reference `spec.owner: engineering`.
3. **Content contract and the generated-by marker.** When all three baseline files are absent (and the precondition holds), the renderer creates a root `catalog-info.yaml`, root `mkdocs.yml`, and `docs/index.md` that form one internally consistent configuration baseline for the installing project's generated documentation. The generated `mkdocs.yml` uses `<name> Documentation` as `site_name`, the catalog description as `site_description`, `docs_dir: docs`, `plugins: [techdocs-core]`, and exactly this docs-root-relative navigation: `Home: index.md`, `Project overview: references/project-overview.md`, `Architecture: ARCHITECTURE.md`, `Workflow and agent commands: prompts/index.md`. Use MkDocs `exclude_docs` gitignore-style patterns as a deny-by-default publication boundary: exclude every root entry, then re-include only `index.md`, `ARCHITECTURE.md`, all content under `architecture/` and `references/`, and `prompts/index.md` (not the prompt bodies or manifest). The landing page identifies the installing project, carries `Owner: Engineering`, `Status: active`, and creation-date `Last verified: YYYY-MM-DD` metadata, and links only to the three non-Home destinations. **Every generated file carries a one-line generated-by marker**: the YAML files begin with `# wavefoundry: generated missing-only Backstage/TechDocs baseline; project-owned, edit freely.` and `docs/index.md` carries `<!-- wavefoundry: generated missing-only Backstage/TechDocs baseline; project-owned, edit freely. -->` immediately after its metadata block. The marker is the ownership fact: a file that carries it was generated by the renderer; a file without it is project-authored. The renderer never claims Backstage has registered, built, or published the site.
4. **Missing-only backfill and one marker-based definition of the partial state.** Existing `catalog-info.yaml`, `mkdocs.yml`, and `docs/index.md` files remain byte-for-byte unchanged whether or not they carry the marker; the renderer only ever writes absent members. Evaluate the eight presence states in the canonical path order `catalog-info.yaml`, `mkdocs.yml`, `docs/index.md` and backfill exactly the missing siblings. **Ownership has exactly one signal, at render time and afterwards: the generated-by marker.** After the render, a member that carries the marker (written now or earlier, including a marked file copied from another project) is *generated*; a member without it is *project-owned*. The trio is **partial** when it is mixed, that is, at least one member is generated and at least one is project-owned; this includes the all-present-mixed case, where nothing is written. Whenever the post-render tree is mixed the renderer emits exactly one warning using the contract below, naming exactly the project-owned (unmarked) paths in canonical order without claiming the mixed result is a validated TechDocs site; when all three are project-owned it preserves them silently without adopting ownership or making a compatibility claim; when all three are generated no warning applies. Because the same rule reads the same marker, a rerun of the command, any later reader (a future opt-in upgrade scan included), and an operator all recompute the identical `preserved_paths`/`generated_paths`, so the fact needs no persistence of its own. A marked file is never re-validated (its `metadata.name` may be foreign); the follow-up checklist already requires operators to verify the owner and the catalog-unique name before registration. A user who edits a generated file and keeps its marker keeps it classified as generated; a user who removes the marker takes ownership, which is the conservative outcome. The classifier recognizes the exact marker line anywhere in the file, reading `utf-8-sig`, comparing per-line after stripping line endings and surrounding whitespace, so a BOM, CRLF, or an editor-prepended header line does not reclassify a generated file. The marker form is per destination: the YAML members carry the `# ...` line and `docs/index.md` carries the HTML-comment form; a `docs/index.md` holding only the YAML `#` form is project-owned. A member the classifier cannot decode as UTF-8, or that is not a regular file or resolves outside the repository root when the read-only classifier is called outside the command's preflight, is classified project-owned (the classifier never raises and never reads outside the root); an absent member is in neither list. Because nothing runs during upgrade, no upgrade summary record, lock field, or first-delivery disclosure is needed in this change; the command's own stderr warning and its structured JSON output (`--json`: the envelope of Requirement 6, whose `partial` member is the record below) are the operator surfaces, and the read-only classifier is a public module function (in `render_agent_surfaces`, a pack module the upgrade protocol admits) so a later opt-in auto-generation change can reuse it.
5. **Containment through the shared helper; the siblings' presence rule plus one deliberate tightening.** The command classifies all three destinations before its first write using `_contained_review_carrier_path` (the same helper the render preflight uses; the destinations are not added to `preflight_agent_surface_paths` because the render pass does not write them). Escape is refused by `_contained_review_carrier_path` as for every family. The **presence rule is the siblings'**: a destination that resolves through the containment check to a regular file inside the root, including via an in-root symlink, is *present* and preserved (never opened for writing, so a preserved symlink carries no write-through risk), which keeps a project whose `docs/index.md` or `mkdocs.yml` is a legitimate in-root symlink upgradeable. **The tightening, owned here and not claimed as parity:** an exact destination that is a dangling symlink, a directory, or another non-regular object is refused in preflight (the sibling families materialize through a dangling in-root symlink and refuse a directory only at write time, after earlier members were written; a FIFO would hang their `os.open`). The classification uses `lstat`/`stat` on the unresolved candidate (the helper returns the resolved path), runs for all three destinations before the first trio write, and reports one clear error naming the path; refusal writes none of the three files and exits non-zero. No ancestor-chain matrix is introduced.
6. **Reuse the existing baseline machinery.** The trio uses the same helpers as `LIFECYCLE_PROMPT_BASELINES` and `SCAFFOLD_BASELINES` without joining the render pass: templates ship under `.wavefoundry/framework/install/` under names that no catalog or MkDocs discovery glob matches (`catalog-info.template.yaml`, `mkdocs.template.yml`, `techdocs-index.template.md`; a literal `catalog-info.yaml` shipped into every target would be found by Backstage `**/catalog-info.yaml` location globs and ingest a placeholder entity) and are resolved with `_resolve_install_asset` (target root first, then the packaged module), rendered with the existing `{{generated_at}}` stamp plus one `{{entity_name}}` substitution for the normalized entity name, and written with `_write_review_carrier_text`. The module function returns a typed result (`written_paths`, `preserved_paths`, `generated_paths`, `missing_targets`, and `partial`, the record or `None`); containment and non-regular refusals raise `RuntimeError` exactly as the sibling families do, so a later flag-gated render or upgrade caller inherits both the precondition and the containment classification from the module function itself (neither lives in the CLI entry, and `render_agent_surfaces` never imports `techdocs_baseline`, which self-activates the venv at import). Trio writes pass a new keyword-only `exclusive=True` to `_write_review_carrier_text`, which then opens with `O_EXCL` instead of `O_TRUNC`, so missing-only is race-free rather than check-then-truncate (the sibling families keep the default); the templates of all absent members are resolved before the first write, so after preflight only an `O_EXCL` collision (a member appearing mid-run) can interrupt the writes. The function lives in `render_agent_surfaces` because the helpers it reuses are module-private and a `gpu_doctor`-pattern entry cannot host library logic, not because of pack admissibility (the upgrade protocol admits every top-level pack module); the module docstring names the family. A thin `techdocs_baseline.py` entry (the `gpu_doctor.py` pattern) is what `wf_cli` dispatches to (there is no subparser mechanism in `render_platform_surfaces`). Its interface: `--root PATH` (default: the repository root discovered by walking up from the current directory, the `render_platform_surfaces.discover_repo_root` rule; resolved before the basename is derived) and `--json`. Text mode prints `techdocs-baseline: generated <path>` and `techdocs-baseline: preserved <path>` lines on stdout and any `techdocs-baseline: WARNING ...` or `techdocs-baseline: ERROR ...` line on stderr; `--json` prints one envelope on stdout on every exit, `{"written_paths": [...], "preserved_paths": [...], "generated_paths": [...], "missing_targets": [...], "partial": <record or null>, "refusal": <message or null>}`, and keeps the WARNING/ERROR line on stderr. Exit codes: 0 (including the mixed case with its warning), 1 (precondition unmet; `missing_targets` non-empty), 2 (any `RuntimeError` raised by the module function: containment or non-regular refusal, a missing packaged template, or an `O_EXCL` collision; `refusal` carries the message and the envelope's path lists are empty because the function reports no progress on a raised refusal). No new resolver or write loop is added; if the implementer prefers, the shared `resolve_install_asset` + `materialize_baseline` helper recorded as follow-up debt RTD-2 in wave `1viyu` may be landed here and used by all three families, but that is optional and must not widen scope.

## Scope

**Problem statement:** Documentation generated for an installing project is not ready for Backstage catalog ingestion or TechDocs generation because the target repository receives neither a `catalog-info.yaml` descriptor nor the MkDocs configuration it references. External catalog registration and TechDocs publication remain separate operator/Backstage responsibilities.

**In scope:**

- Root catalog descriptor and TechDocs baseline generation through the `wf techdocs-baseline` command (a `render_agent_surfaces` module function), gated on the navigation-target precondition; missing-only behavior; generated-by markers; tree-derived partial-state warning; containment through the shared helper; idempotence; `--json` output of the typed record.
- Statements in seeds 011/040/160 that describe the command (the end-of-Phase-2 install-log row, the seed-012 step, and the seed-160 pointer are owned by `1vmpz`, which depends on this change's command).
- Canonical install/upgrade/documentation bootstrap guidance and rendered local prompt surfaces.
- Command, CLI dispatch, install-log parity, and packaging regression tests.
- Architecture and install-reference documentation that describe the new generated surfaces.

**Out of scope:**

- Registering repositories with a particular Backstage instance or modifying its `app-config.yaml`/catalog locations.
- Generating `API`, `Resource`, `System`, `Domain`, `Group`, `User`, or `Location` entities without verified project or organization data.
- Generating OpenAPI, AsyncAPI, GraphQL, or gRPC contracts.
- Rewriting a user-authored catalog entity or adopting a project-specific owner, lifecycle, source-control URL, CI, or system annotation.
- Generating provider-specific CI workflow YAML, Backstage-instance `app-config.yaml`, catalog `Location` entities, storage configuration, or credentials.
- Any upgrade-lock record, nonce handoff, or extension hook for the partial state (superseded by the marker design; see Decision Log).
- Auto-generation on setup/upgrade, its opt-in flag, and the upgrade summary record (deferred to a later change; the classifier is public so it can be reused).
- The Refresh TechDocs workflow and the `wf-techdocs` skill (`1vmpz`, same wave).

### Partial-State Warning Contract

The canonical baseline path order is `catalog-info.yaml`, `mkdocs.yml`, `docs/index.md`. The table below lists what is written per presence state; the warning column applies the single marker-based rule (Requirement 4): exactly one message whenever the post-render tree is mixed, substituting the comma-separated project-owned (unmarked) paths in canonical order (for the six write-partial states with unmarked pre-existing files that is exactly the present paths):

| State | Present before render (unmarked) | Generated | Partial warning |
| --- | --- | --- | --- |
| All absent | none | `catalog-info.yaml`, `mkdocs.yml`, `docs/index.md` | None |
| Catalog only | `catalog-info.yaml` | `mkdocs.yml`, `docs/index.md` | Exactly one; names `catalog-info.yaml` |
| MkDocs only | `mkdocs.yml` | `catalog-info.yaml`, `docs/index.md` | Exactly one; names `mkdocs.yml` |
| Index only | `docs/index.md` | `catalog-info.yaml`, `mkdocs.yml` | Exactly one; names `docs/index.md` |
| Catalog + MkDocs | `catalog-info.yaml`, `mkdocs.yml` | `docs/index.md` | Exactly one; names both present paths in canonical order |
| Catalog + index | `catalog-info.yaml`, `docs/index.md` | `mkdocs.yml` | Exactly one; names both present paths in canonical order |
| MkDocs + index | `mkdocs.yml`, `docs/index.md` | `catalog-info.yaml` | Exactly one; names both present paths in canonical order |
| All present | All three | none | No writes; warning only if the trio is mixed (some members carry the generated-by marker and some do not) |

```text
Backstage/TechDocs baseline is partial; preserved project-owned files: <project-owned (unmarked) paths>. Generated missing files only. Verify backstage.io/techdocs-ref: dir:., root mkdocs.yml docs_dir/navigation/exclude_docs, and docs/index.md before registration or publication; align the files or remove the generated-by line to take ownership.
```

The command captures presence before any write only to decide what to write; the record is classified after the render by the marker (Requirement 4). It emits the warning once on stderr (`techdocs-baseline: WARNING` prefix) and, with `--json`, prints the Requirement 6 envelope whose `partial` member is this typed record, produced by a public read-only classifier function (reusable by a later opt-in auto-generation change for the upgrade summary):

```json
{
  "channel": "backstage-techdocs",
  "code": "backstage_techdocs_partial",
  "detail": "<the exact warning text above>",
  "preserved_paths": ["<each project-owned (unmarked) path as a separate element in canonical order>"],
  "generated_paths": ["<each marked path as a separate element in canonical order>"]
}
```

**Recomputation rule (the same rule the renderer applies at render time).** `preserved_paths` are the trio members present without the generated-by marker (project-owned); `generated_paths` are the members that carry it (generated now or earlier); the record exists only when both lists are non-empty. Because the marker is written into each generated file, this classification is a property of the tree: a rerun of the command and any operator inspection derive the same record after the fact; a rerun in the all-present-mixed state writes nothing and still emits the warning until the operator reconciles the trio (by aligning the files or removing the generated-by lines to take ownership). Nothing is persisted in a lock, no nonce is handed to a child process, no extension hook is involved, and nothing runs during upgrade.

## Risks

| Risk | Mitigation |
| --- | --- |
| Default `engineering` owner does not exist in a Backstage instance. | Clearly label it as a conservative default; preserve the file so project owners can update it once. |
| Root documentation component name collides with an existing catalog entity. | Use a deterministic `-docs` identity, preserve a clear 63-character contract, and require operators to confirm catalog-wide uniqueness before registration. |
| Existing members of a partial trio are incompatible with generated siblings. | Preserve/backfill without parsing user YAML, emit an actionable warning, and reserve only the internal-consistency claim for the all-generated trio; buildability and exposure are always conditional on external Backstage steps. |
| A user removes the marker from a generated file, or edits a generated file while keeping it. | Both are honest outcomes by construction: no marker means project-owned (preserved); marker means generated (still classified as generated); the classifier documents the rule. |
| An installed target upgraded from an old pack never produced `docs/ARCHITECTURE.md`. | The precondition fails, nothing is generated, one informational line names the missing target; no docs-gate failure. |
| MkDocs `exclude_docs` is unsupported by the `techdocs-core`-pinned MkDocs. | Requirement 8 verifies before the golden is frozen; fall back to the documented alternative and record the decision. |
| TechDocs publishes operational records or future unknown root docs. | Use deny-by-default `exclude_docs` with explicit public survivors; verify ordered gitignore-style semantics with representative current/future paths and a removed-pattern mutant. |
| New writes escape or collide with a non-regular destination. | Shared-helper containment plus regular-file/absent classification of the exact destinations before any trio write; refusal exits non-zero without writing. |
| A project that does not use Backstage runs the workflow by mistake. | The command is explicit and missing-only; row 2.13.5 allows `[~]` to decline; nothing auto-runs at upgrade in this change. |
| Row 2.13.5 breaks the install-log parity tests or an in-progress log. | Decimal-extension insertion (no renumber); seed-012 mirrors it; `FreshInstallContractParityTests` covers seed/script reference resolution and one-to-one headings; live logs are never rewritten. |
