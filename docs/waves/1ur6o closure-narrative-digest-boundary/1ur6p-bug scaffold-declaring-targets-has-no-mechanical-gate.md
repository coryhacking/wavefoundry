## Rationale

Field report from a downstream repository that upgraded to 1.15.5, reproduced here. Its `docs/plans/plan-template.md` carries an **unfenced** example under the `**Review targets (repo-relative paths):**` marker, so the scaffold itself declares targets:

```
declared targets from the SCAFFOLD TEMPLATE: ('path/to/file.swift', 'docs/specs/')
```

Measured on this tree against the shipped parser, that exact shape declares two phantom paths. Every plan born from that template is therefore in declared mode before its author has declared anything: the operator reported losing `qa-reviewer` and `architecture-reviewer` and gaining `docs-contract-reviewer` from a placeholder path nobody chose. That is coverage silently removed, which is the defect class wave `1uo1x` exists to eliminate, reappearing through the scaffold.

**This repository is not affected, and that is exactly the problem.** Both local producers declare nothing:

```
our plan-template declares : ()
our embedded scaffold      : ()
THEIR shape declares       : ('path/to/file.swift', 'docs/specs/')
```

We are clean because wave `1uo1x` added `test_the_shipped_scaffolds_declare_nothing_until_an_author_edits_them`, a unit test in **our** suite. A target repository does not run our suite. What a target repository gets instead is prose: seed 160 now instructs the upgrade agent that any example written into the template must be fenced, and its audit checklist says to verify the template declares nothing. Both are instructions to an agent, not gates.

**Verified: no lint rule references the declaration parser.** A repo-wide search of `wave_lint_lib/` and `docs_lint.py` finds zero references to `serialization_point_paths` or the marker string. Nothing mechanical prevents a template, an embedded scaffold, or any change doc from declaring a placeholder path, in this repository or any target.

**The failure is silent and self-concealing.** A declaring template produces a plausible-looking roster, so the author sees lanes and has no signal that different lanes were suppressed. The downstream operator only found it by scoring a realistic plan both ways after reading the release notes. No diagnostic fired at Prepare, at docs-lint, or at close.

## Requirements

1. A docs-lint rule must fail when a scaffold declares review targets. **"Scaffold" is an explicit opt-in set, not a predicate**, and the set is `docs/plans/plan-template.md` alone. It must be a named set because the existing plan validators deliberately skip the template (`wave_lint_lib/wave_validators.py:900`, `skip_names = {"plan-template.md", "README.md"}`), so the new rule opts in by name rather than inheriting a population.

   **The embedded `_default_template()` scaffold is deliberately NOT in the lint set**, and the asymmetry is the reason. `plan-template.md` is operator-editable in every target repository and is **not** in the pack, so it persists across upgrades: the upgrade *agent* edits it per seed 160 rather than the upgrade replacing it. It can therefore be contaminated per-repo and stay contaminated, which is exactly why it needs a per-repo gate. `_default_template()` is framework-owned, arrives byte-identical from the pack, and no operator edits it — only this repository can contaminate it, and wave `1uo1x` already pins that here with `test_the_shipped_scaffolds_declare_nothing_until_an_author_edits_them`. Adding it to the lint rule would mean re-parsing a ~31,000-line module (`server_impl.py`, 30,883 lines) on every corpus lint to re-check a file the target repo cannot change. The gate belongs where the contamination is possible.
2. The rule must derive its verdict from the **shipped parser** (`serialization_point_paths`), not from a re-implementation. A second implementation would drift from the first and pass a template the real evaluator reads differently, which is the failure mode this rule exists to catch.
3. The error message must name the declared targets it found and state the fix (fence the example), because the author's next action is otherwise a guess.
4. **No placeholder heuristic ships.** An earlier revision required catching change documents that declare an obvious placeholder path. Measured and declined. Scan set, stated so the figures are reproducible: `docs/plans/*.md` plus `docs/waves/**/*.md`, excluding `wave.md`, `README.md` and `plan-template.md`. Across **819** change documents on this tree, 40 declare targets and **56** distinct targets exist between them, and every literal deny-list heuristic (`path/to/`, `example`, `foo|bar|baz`, `src/app/` prefix, `your|my|placeholder|todo|tbd`) matches **zero** of the 56. The corpus **includes this plan**, so the distinct-target count moves whenever this plan's own `## Serialization Points` changes; it read 58 before two targets were undeclared here. The conclusion is what is load-bearing, and it reproduced identically at both counts across four independent runs. The only heuristic with any reach — "the declared target does not exist on disk" — matches exactly one, a legitimately deleted historical path in a closed wave, so it is a false positive rather than a catch. A rule with zero measured reach and a non-zero false-positive rate trains operators to ignore it, which Requirement 5 exists to prevent. The scaffold gate is the whole change.
5. The rule must not fire on legitimate declarations. A rule that flags real plans is worse than the defect, because it trains operators to ignore it. This is satisfied **structurally, not statistically**: the rule reads `SCAFFOLD_DOCS` only, so an authored plan is never examined and cannot be flagged. The standing guarantee is `test_the_shipped_scaffolds_pass` plus the shared-constant test, not a corpus measurement. Attribution corrected on measurement: the qa lane widened the blocking set to a real declaring authored plan and that mutant SURVIVES `test_an_authored_change_doc_never_blocks`, whose fixture only covers this wave's own change doc; `test_the_shipped_scaffolds_pass` is what actually kills every widening.
6. **The blocking set and the repairable set must be identical.** A declaring scaffold silently removes review coverage, so a non-blocking warning there would reproduce the prose-instruction weakness this change exists to remove: severity is **ERROR, and the rule fires on the scaffold set only**. Nothing outside that set is examined at all, so nothing outside it can block. Any rule that can block a document the upgrade cannot repair strands the repository at `failed_phase == "docs_gate"` (`upgrade_wavefoundry.py:2477`) — and a post-gate reconciliation scan could not tell it why, because `_run_reconciliation_scan` is only reached from the summary and cleanup paths **after** the gate. That is why AC-6 reports from the **pre-gate repair** instead (`upgrade_extensions.py`, reached from `pre_docs_gate` at `upgrade_wavefoundry.py:4842`, before the gate at `:4843`), so the report arrives whether or not the gate later passes. Repair is safe in a scaffold and only in a scaffold: every declaration there is by definition an example, so fencing the marker block cannot destroy a real declaration.
7. **The repair must be class-a: it must protect the upgrade that installs it.** The new ERROR is already class-a, because `phase_docs_gate` subprocesses `SCRIPTS_DIR/docs_lint.py` (`upgrade_wavefoundry.py:2102-2116`) after extraction has overwritten that directory. A repair placed in `upgrade_wavefoundry.py` would be **class-b**: both launch sites resolve the *installed* orchestrator (`server_impl.py:13111`, `upgrade_bridge_bootstrap.py:426`), and each spawns a subprocess that loaded the orchestrator's source **before** extraction rewrote it, so the mitigation would arrive one upgrade after the gate it mitigates and every currently-contaminated repository would still halt. The repair therefore lands in the existing `pre_docs_gate` hook in `upgrade_extensions.py:1035`, which `_load_extension_module` (`upgrade_wavefoundry.py:1023-1030`) reads **from inside the pack before any files are extracted** and which runs at `:4842`, immediately before `phase_docs_gate(root)` at `:4843`. `_reconcile_graph_builder_doc_claim` (`upgrade_extensions.py:547`, called at `:1054`) is the in-tree precedent for exactly this.

## Scope

**Problem statement:** The property "a scaffold declares nothing" is enforced by a unit test that only this repository runs and by prose instruction an upgrade agent may follow loosely, so every target repository can ship a template that silently removes review coverage from every plan created from it.

**In scope:**

- A docs-lint rule keyed off the shipped parser, covering the scaffold set only (the plan template; the framework-owned embedded scaffold stays pinned by the `1uo1x` unit test, per Requirement 1).
- The error message naming both the found targets and the remedy.
- A corpus census as a **scoping-regression guard**: because the rule examines the scaffold set only, no authored change doc is ever read, so zero failures is guaranteed by scope rather than demonstrated by discrimination.
- Upgrade-side repair for repositories already carrying a declaring template.

**Out of scope:**

- Changing the declaration contract itself. The parser is correct; the gap is that nothing checks its output on scaffolds.
- The legacy whole-document trigger registry. Out of scope here and **not** decided by this wave: the decline recorded against it belongs to `1upqx`, which was withdrawn at readiness, and the 36-document figure that decline rested on did not reproduce (independent runs gave 51, 23 or 0). It must be re-measured before any wave relies on it.
- Rendering or regenerating target-repo templates wholesale. The rule reports; the operator decides.
