# Remove the historical-memory gate from upgrade and setup

Change ID: `20smo-enh remove-upgrade-historical-memory-gate`
Change Status: `implemented`
Owner: Engineering
Status: implemented
Last verified: 2026-10-16
Wave: `20t73 upgrade-memory-gate-removal`

## Rationale

Since 1.14.0 (change 1t0u4) the upgrade and setup commands pause after the docs gate to draft historical-memory candidates from closed waves, require agent validation, and then publish the index inside a receipt-owned scope that marks the memory run indexed exactly once. The gate protected one invariant: the lifecycle's index epoch must not include unvalidated candidates and must be published once. In the field it is the single most confusing part of the upgrade. It pauses on some projects and not others (the inventory sync reopens a finished run whenever waves were closed since the last upgrade), it has needed nine recorded repairs (1t9th, 1tz6l, 1u44m, 1uf67, 1zeyo, 1zfd9, 1zep5, the migrated-id repair, 20e63), and since 1.29.0 (change 20b34) every pause appends an unconditional "operator-run from an external terminal with all hosts stopped" instruction that agents read as a requirement even though `wf_upgrade(phase='resume_after_memory')` runs the same code with no host check.

The invariant no longer buys anything. Memory records are ordinary files under the memory root; the normal incremental index refresh indexes them idempotently; `memory_propose` already refreshes new candidates straight into the index; and `memory_search` and `memory_brief` surface `candidate` records by default (`DEFAULT_SURFACED_STATUSES` in `memory_records.py`). The only lifecycle-time needs are cheap and need no pause: keep the inventory and migrated-id repair converging, and tell the operator how much historical memory is still unprocessed. Backfill itself belongs with the other on-demand memory tools, driven by **Review memories**, not inside the upgrade.

Brief: goal is to delete the gate and its publication-receipt machinery, keep `memory_backfill` and `memory_validate` as the on-demand path, and leave upgrade and setup with a report line. Consumers are operators and agents running upgrades on every host. Constraint: the upgrade that installs this change still executes the previously installed runner, whose inline gate and whose copies of the extension hooks call the newly extracted modules, so those modules must make the old gate pass through rather than pause or fail. Readiness review (five seats, 2026-10-16) reshaped Requirements 3 to 7 around that window; the repairs are recorded in the Progress Log.

## Requirements

1. **No lifecycle pause for memory.** The upgrade runner (`upgrade_wavefoundry.py` `main` and `--resume-after-gate`) and `setup_wavefoundry.py` no longer create or advance a memory run for gating, draft candidates, write `action_required{kind: historical_memory}`, exit with `ACTION_REQUIRED_EXIT` for memory, write the `memory_backfill_*` lock fields, or publish the index inside `index_publication_scope`. Phase 4 always runs the ordinary `phase_index_update` path. `phase_index_update_parent_owned`, `_memory_gate`, the memory branch of `_new_code_upgrade_backstop`, `_memory_action_required_pause`, the memory wording of `_report_action_required_pause`, and the `awaiting_memory_validation`, `awaiting_memory_publication` and `memory_resume_preflight` phase labels are no longer written. `POST_DOCS_GATE_PHASE`, `_is_post_docs_gate_failure` and their mirrors stay: they label a crash inside the `post_docs_gate` hook (wave 1zeyo), which still runs; only their memory-pause wording changes. `resume_after_gate` recovers a docs-gate failure and then continues to the index phase exactly as the non-memory path does today. `--resume-after-memory` and the `resume_after_memory` MCP phase remain as documented deprecated aliases of `--update-index` and `update_index` for as long as the compatibility window in Requirement 4 is open: they run no memory logic and print no memory or hosts-stopped guidance, so saved operator commands, retained-lock continuation choosers and older emitters keep working. The `wf_upgrade` docstring and the phase guidance name them as aliases.
2. **Report instead of gate.** After the docs gate, the upgrade summary (the machine-readable sentinel and `data.summary`) and the end of `wf setup` carry one bounded historical-memory report consisting of exactly two integers, closed waves with no memory record yet and candidates awaiting validation, plus the one-line pointer to run **Review memories** (`memory_backfill(mode='create')` then `memory_validate`). The counts are distinct waves and distinct candidate sources across every run in `memory-state.sqlite`, computed by querying the existing rows (Requirement 6). Reuse one existing inventory pass: the only scan is the inventory walk that advisory `sync_inventory` performs once per lifecycle run (Requirement 4), and the report reads the rows that call wrote. Reporting adds no second walk and no new budget mechanism; this is not a fixed time, byte or file-count guarantee. On an unreadable waves root, an unavailable or corrupt `memory-state.sqlite`, or any other error it reports `unavailable` with a reason code, logged by exception type only, with no paths or record content. The report never fails or retains the upgrade or setup.
3. **Delete the publication receipt and its authority.** Remove the behaviour of `index_publication_scope`, `authorize_index_finalize`, `restage_index_finalize`, `record_publication_success`, `reconcile_index_publication`, `complete_index_publication` and `mark_indexed`, the `ready_for_index` and `publishing_index` states, `INDEX_PUBLICATION_RUN_ENV`, every propagation or stripping of `WAVEFOUNDRY_MEMORY_BACKFILL_RUN_ID` (`upgrade_wavefoundry.py`, `setup_index.py`, `setup_wavefoundry.py`), and the memory branch of `index_state_store.finalize_build_epoch`, which also removes the index-store to memory-backfill import; refresh the `_MEMORY_BOOTSTRAP_EXCLUDED` justification in `upgrade_extensions.py` accordingly. Also delete the parent-finalize receipt authority that existed only for the parent-owned path: `WAVEFOUNDRY_UPGRADE_PARENT_FINALIZE_RECEIPT` and its presence-only bypass clauses in `finalize_build_epoch` and `_authorize_build_epoch`, `finalize_staged_build_epoch`, the `upgrade-index-staging-receipt.json` staging receipt and the runner branches that read it, and the strip in `setup_reconciliation.py`; `cleanup` deletes a retained staging receipt. Task 1 confirms from source that no storage-migration production path sets that variable before it is removed; tests that set it are retargeted. `finalize_build_epoch` keeps the owner-pid check, `_upgrade_publisher_granted` and `publication_checkpoint_reason` unchanged. The run state machine becomes `inventory_pending`, `awaiting_validation`, `indexed`; `indexed` stays the physical terminal label so the `memory_backfill_one_active_run` partial index, the old runner's lock checks and existing rows keep their meaning, and rows holding `ready_for_index` or `publishing_index` are read as `indexed` and never rewritten in bulk. `run_summary` no longer writes state back on read except the terminal transition. No schema version bump and no data migration.
4. **Old-runner window.** The upgrade that installs this change runs the previously installed runner, and a project may skip releases and upgrade from any supported starting version directly; protocol-2 runners from 1.24 through 1.32 call an identical name set (verified at readiness against the release tags), and the accepted protocol-1 runners (`upgrade_protocol.SUPPORTED_RUNNER_PROTOCOLS` is `(1, 2)`) call a subset of it, so the same compatibility layer carries them and they pass through once the hook's protocol-1 pause is removed. After the docs gate that runner calls, on the newly extracted `memory_backfill`: `ensure_run(root, "upgrade")`, `sync_inventory`, `reconcile_index_publication`, `run_summary`, `validation_worklist`, `run_state`, `index_publication_scope`, `complete_index_publication`, `mark_indexed`, and the constants `ACTION_REQUIRED_EXIT` (read in the `SystemExit` handler on every failure path, so its absence would hide the real failure) and `MAX_CANDIDATES_PER_CALL` (read on the awaiting branch); it reads the summary keys `state`, `remaining_waves`, `candidates_pending`, `failures`, `last_failure` and `candidates_drafted` (`eligible_waves` is kept for the setup path); it reaches `server_impl._memory_backfill_batch_locked` only when the state is `awaiting_validation`. The new module keeps every one of those names as a compatibility layer: a run whose entry path is `setup` or `upgrade` is report-only, its summary reports `state` as `indexed` and `candidates_drafted` as zero with real counts in the other keys, `reconcile_index_publication` returns `run_summary`, `index_publication_scope` is a no-op context manager, and the remaining names are no-ops. Every compatibility entry point the old runner or the shipped hooks call is itself advisory: an unreadable waves root, an unavailable, locked or corrupt `memory-state.sqlite`, or any other `Exception` (never `BaseException`, so `SystemExit` and `KeyboardInterrupt` propagate) inside `sync_inventory`, `reconcile_index_publication`, `run_summary` or `validation_worklist` on a lifecycle run is caught at that boundary and returns the report-only summary carrying the full key set (`state` `indexed`, `remaining_waves`, `candidates_pending`, `failures`, `candidates_drafted` and `eligible_waves` all zero, `last_failure` a reason code); `ensure_run` keeps its string contract and returns a fixed sentinel run id on failure, which the summary functions recognise. The old runner's `post_docs_gate` hook and inline gate therefore never abort the upgrade on memory state. A failure to import or reload the extracted module itself is outside this boundary: it is a packaging defect the suite must catch, not an advisory case. The compatibility layer imports no new symbol from any module outside `_MEMORY_BOOTSTRAP_MODULES`, so the reload-in-place seam never produces a mixed module set. The extension hooks shipped in the pack also run under the old runner: `post_docs_gate` keeps refreshing the extracted memory modules in `sys.modules` and calling the advisory inventory sync but never pauses (its protocol-1 pause branch is removed with the window stated above); `pre_index_update` keeps the 1u44n publisher-grant bridge and drops its memory branch; `post_index_update` drops its memory seal and derives the index outcome from `ctx.index_published` or `_observe_parent_index_outcome`, never from memory state. **Window boundary:** the compatibility layer, the aliases in Requirement 1 and the exit-4 tolerance in Requirement 5 stay until runner protocol 2 is removed from `upgrade_protocol.SUPPORTED_RUNNER_PROTOCOLS` (the framework's existing supported-runner boundary; protocol 1 is still listed there today and leaves no later than protocol 2) or until the installing upgrade provably hands off to the newly extracted runner before its memory step; the follow-on tech-debt change minted at close names that trigger as its precondition, and no release deletes the layer on elapsed time alone.
5. **Retained legacy checkpoints recover through existing phases.** The old runner writes `memory_backfill_run_id`, `memory_backfill_state` and `current_phase=awaiting_memory_validation` on every run, paused or not, so those fields alone identify nothing. A lock is a legacy memory pause only when `action_required.kind == "historical_memory"`, or `failed_phase` is `awaiting_memory_validation` or `historical_memory_backfill` with no `action_required`, or `current_phase` is `awaiting_memory_publication` or `memory_resume_preflight`; never when `action_required.kind` is a storage migration, when `current_phase` is `storage_restart_required`, or when an index-guard handoff is pending, all of which keep their own hosts-stopped guidance. The 1zeyo shape (`failed_phase=awaiting_memory_validation`, `current_phase=docs_gate_complete`, no action) is checked first, as `_checkpoint_resume_flag` orders it today, and stays a post-docs-gate crash recovered by `resume_after_gate`. The old runner's index-failure lock (`current_phase=awaiting_memory_validation`, `failed_phase=index_update`, no action) is not a memory pause: it is recovered as an ordinary `index_update` failure through `update_index` or its alias, and recovery clears its stale memory fields on success. A legacy memory pause is index-pending: `update_index`, `rebuild_index` (and the aliases) and `cleanup` accept it and clear only the memory fields and the `historical_memory` action; the pending-upgrade refusal, `wf_upgrade_status`, `upgrade_bundle` recovery and `publication_control` name `update_index` then `cleanup` as the continuation and never print the external hosts-stopped command for memory. Every reader that keyed on `memory_backfill_state == "indexed"` (the manifest-retry check in `_pending_upgrade`, the cleanup owned-continuation check, `validate_index_guard_terminal_cleanup`, the index-guard continuation chooser and `_INDEX_GUARD_MEMORY_PHASES` in `upgrade_extensions.py`, `repair_ppol_memory_staging.py`) is retargeted to `index_rebuilt_at` or the recorded index-publication outcome and tolerates absent memory fields. The four mirrors of the post-docs-gate predicate (`_is_post_docs_gate_failure`, `upgrade_bundle._post_docs_gate_failure`, `upgrade_handlers._post_docs_gate_failure_phase`, `sqlite_storage_migration._checkpoint_resume_flag`) change together under their parity test. `wf_upgrade_status` stops publishing `data.memory_backfill`. `upgrade_handlers` tolerates exit code 4 from an old runner for the Requirement 4 window; no new code path exits 4 for memory, and the index guard (3) and retained-run report (5) codes are unaffected.
6. **On-demand tool contract.** `memory_backfill` keeps its bounded create/dry_run behaviour, server cursoring, claim and replay semantics, 20e63 exhaustion reporting and `memory_validate` worklists. Its `entry_path` parameter remains accepted for the compatibility window and is documented as deprecated; the response's `usage` names only the next memory tool, never an upgrade phase or external command. Pending sources and completed waves recorded under legacy `setup` or `upgrade` runs are not orphaned: the manual worklist, the manual run's remaining-wave census and the Requirement 2 counts query across every run's rows in place (no rows are moved or rewritten, preserving provenance and avoiding a migration). Counting rule: a closed wave is covered when any run completed it at its current source fingerprint, including a completed "no source" disposition, and `claim_next` on the manual run skips covered waves under that same predicate so claims and the census agree; a candidate source is pending when its newest outcome across runs is pending, ordered by `memory_backfill_runs.created_at` through the run id and deduplicated by `source_event`; waves and sources are counted once each, by identity, regardless of how many runs touched them. The background memory-index refresh deferral (`paused_run_for_source` and its callers in `memory_handlers.py`) is removed: nothing publishes deferred candidates any more, and `memory_propose` already refreshes candidates immediately. The `memory_recovery` exemption in `publication_control` is removed; it fired only for the retired `awaiting_memory_validation` phase, so removal fails closed and `memory_backfill` and `memory_validate` are refused under any retained upgrade checkpoint until recovery completes.
7. **Documentation and prompt surfaces.** Every surface that names the gate is updated to the on-demand model. The derived set is every file under `.wavefoundry/framework/seeds/`, `.wavefoundry/framework/README.md`, `.wavefoundry/framework/install/`, `docs/`, the repository README, and the operator-facing strings in scripts (the `wf_upgrade` docstring, tool `usage` and `next_step` guidance, and printed upgrade or setup messages) matching any of: `resume_after_memory`, `resume-after-memory`, `awaiting_memory_validation`, `awaiting_memory_publication`, `memory_resume_preflight`, `historical_memory`, `index_publication_scope`, `WAVEFOUNDRY_MEMORY_BACKFILL_RUN_ID`, `WAVEFOUNDRY_UPGRADE_PARENT_FINALIZE_RECEIPT`, `memory_backfill_run_id`, `entry_path="upgrade"`, `entry_path='upgrade'`, `entry_path="setup"`, `entry_path='setup'`, "historical-memory checkpoint", "Historical-memory gate", "memory pause", "historical memory validation", "exit 4", or `--entry-path upgrade`. Census exceptions, allowed by design: identifiers and predicates (never `usage`, `next_step` or printed text) in the compatibility layer and advisory boundaries of Requirement 4 and in the legacy-recovery predicates and their mirrors of Requirement 5, the archived-runner and old-runner test fixtures and the tests that exercise them, closed wave records, the changelog history, this change's own documents, and at most one legacy-recovery sentence per documentation surface that begins with the literal marker `Legacy recovery:` so the census can match it mechanically. Known members at readiness: seeds 008, 011, 100, 160, 190, 209, 240 and 250; the framework README; `docs/prompts/upgrade-wavefoundry.prompt.md`, `install-wavefoundry.prompt.md`, `close-wave.prompt.md`, `memory-review.prompt.md` and `agents/upgrade-wave-context.prompt.md`; `docs/specs/mcp-tool-surface.md`; `docs/architecture/data-and-control-flow.md` (Historical memory adoption, the upgrade rerun and cleanup outcomes, the index-guard handoff paragraph, the lock-domain exemption, Selective wave memory capture), `cross-cutting-concerns.md` (the memory capture sentence), `performance-budget.md`, `testing-architecture.md`; `docs/contributing/build-and-verification.md`; `docs/references/native-windows-support.md`; `docs/agents/memory/README.md`; and the `wf_upgrade` docstring in `wf_server/server_impl.py`. ## Scope

**Problem statement:** the upgrade and setup commands stop for historical-memory validation through a receipt-owned publication gate that is hard to reason about, breaks in new ways each release, and now emits contradictory resume guidance; its invariant no longer protects anything the on-demand tools do not already provide.
