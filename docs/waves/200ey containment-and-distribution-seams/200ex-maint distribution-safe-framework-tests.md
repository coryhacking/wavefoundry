## Rationale

A distribution merges the framework source, edits the declaration modules (`vocabulary_profile`, `record_paths`, `mcp_tool_extensions`), adds its own extension modules and prompt docs, and runs the framework suite on its tree. The Waveforge maintainers reported four framework tests that fail or prove the wrong thing there although nothing is broken: each reads something the distribution legitimately owns (its own modules, its own live declaration, its own record file name, its own prompt docs) as if it were framework state. A suite that fails on a correct distribution trains its maintainers to ignore failures, which is worse than a missing test.

Brief: goal is that each of the four tests (and the three addendum tests, A1 and A2) checks the framework-owned thing it was written for and nothing a distribution owns; consumers are distribution maintainers running the framework suite and this repository's own suite; success is that each test passes on a distribution-shaped tree and still fails on the defect it was written to catch. Test-only change: no shipped behavior moves.

Code-grounded facts (verified against the working tree at HEAD `b97fa4ba`, on 2026-10-07):

- R3, history-literal census: `tests/test_history_paths.py` `CensusTests.test_no_other_history_literal_exclusion` scans every `*.py` under the scripts directory (`SCRIPTS_ROOT.rglob("*.py")`) except `tests/` and six allowed framework files, and fails on any line holding the quoted `journals` or `snapshots` literal. A distribution's declared extension or helper module (for example the module holding its journal pre-migration hook, whose job is journals) is scanned too. `mcp_tool_extensions.FRAMEWORK_SCRIPT_MODULE_NAMES` already lists the stem of every flat framework script (a census test in `tests/test_extension_tool_modules.py` pins it to the directory), and the framework's script subpackages are `wave_lint_lib/` and `wf_server/`.
- R4 reset idiom: `record_layout_support.apply_profile` edits each named constant with a single-line regex and raises `ProfileInvalid` unless exactly one assignment matches, so appending `declaration_support.base_declaration_source` (which adds a second assignment of every declaration constant) before `apply_profile` makes it raise. `tests/test_profile_support.py` resets a copied tree with `apply_profile(scripts, shipped_default_profile())` before applying an asset; `shipped_default_profile()` covers `SHIPPED_DEFAULTS` (`vocabulary_profile`, `record_paths`) only, and `SHIPPED_DECLARATION` (`mcp_tool_extensions`) is also an editable profile module in `_EDITABLE`.
- R6 lookup sources: `ChangePromptLookupTests` hard-codes the shortcuts and filenames ("Plan change" and `plan-change.prompt.md`, "Implement change", "Close change", and the fixed "Init wave framework" alias of `install-wavefoundry`); `vocabulary_profile.shortcut(key)` and `vocabulary_profile.prompt_doc(key)` return the profile's shortcut and `docs/prompts/<slug>.prompt.md` for a mapped key. The retired-token pattern matches nothing under `.wavefoundry/framework/install/lifecycle-prompts/` and, among all seeds, only seed `160-upgrade-wavefoundry.prompt.md` (its 1zyc5 upgrade note names the retired paths, skill and shortcuts as removal targets).
- R4, per-profile tool-surface goldens: `tests/test_tool_surface_golden.py` `ProfileToolSurfaceGoldenTests` boots each declaring profile asset. In process (`_boot`), `declaration_support.base_declaration` replaces every declaration constant with `record_layout_support.SHIPPED_DECLARATION` plus the asset's entry, so the live declaration is ignored. For a module-declaring asset, `_boot_in_scratch` copies the live scripts tree (`copy_scripts_tree`), applies only the asset's constants (`apply_profile`), and the subprocess driver `_SCRATCH_BOOT_DRIVER` imports the server before it enters `base_declaration`. Constants the asset does not name therefore keep the live declaration's values in the copied module during `apply_profile`'s validation import and the server import. That this changes the result on a distribution tree is `inferred`; AC-2 reproduces it first.
- R5, archive vocabulary: `tests/test_upgrade_wavefoundry.py` `test_archived_wave_is_recognised_under_a_divergent_archive_vocabulary` builds an archive profile with `RECORD_FILENAME = "set.md"` and asserts `"set.md" != vocabulary_profile.RECORD_FILENAME`. A distribution whose live record file name is `set.md` (the `tests/fixtures/profiles/second.json` vocabulary) fails that precondition, so the test fails where it should test.
- R6, change prompt lookup: `tests/test_server_tools_lifecycle.py` `ChangePromptLookupTests` sets `REPO` to the live checkout (`Path(__file__).resolve().parents[4]`); `test_new_names_resolve_and_retired_names_do_not` reads four prompt docs from the live `docs/prompts`, and `test_no_prompt_doc_carries_a_retired_token` scans every live `docs/prompts/*.md`. A distribution that renames prompts (a prompt-name profile) or authors its own prompt prose fails both, although the lookup code is correct.
- The second-profile run (`run_tests._profile_run_in`) copies the tree, applies a profile asset and runs the suite there, so it is the in-repository stand-in for a distribution tree.

Public addendum (2026-10-07), from the Waveforge maintainers, adds three more tests of the same kind (A1, A2); facts verified against the same working tree:

- A1, member-doc containment config: `tests/test_change_id_path_guard.py` `MemberDocContainmentTests.setUp` reads the running checkout's config (`Path(__file__).resolve().parents[4] / "docs" / "workflow-config.json"`) and copies its `wave_review` block into the fixture's `docs/workflow-config.json`. It is the file's only read of the checkout config; `IsChangeIdTests.test_accepts_every_admitted_id_in_this_repository` also reads `parents[4]`, but only wave records, and is already skipped outside the shipped profile (`_same_profile_run`). `lifecycle_gate_support._prepare_policy_state` returns `PolicyInputError("config", ...)` from `normalize_wave_review_policy` before it reads any member doc, so in a repository whose config the validation refuses (for example `wave_review.enabled` without `delivery_mode`, before its upgrade writes one) the `_prepare_policy_state` reader never calls `_read_member_doc_bytes` and `test_every_member_doc_read_goes_through_the_helper` fails on `assertIn(doc.name, helper_calls)`. A known-good literal exists: `tests/test_lifecycle_golden.py` `_WAVE_REVIEW_CONFIG` (`{"enabled": True, "delivery_mode": "targeted"}`).
- A2, council key spelling: `tests/test_council_signoff_keys.py` hard-codes `OLD_READINESS = "wave-council-readiness"` and `OLD_DELIVERY = "wave-council-delivery"`, builds the old spelling in `_legacy` with `re.sub(rf"(?<!wave-){re.escape(key)}", f"wave-{key}", text)`, uses the literal `"wave-council-x"` in `CanonicalKeyTests` (`test_canonical_signoff_key`, `test_is_council_signoff_key`), and pins `DigestInputTests.PINNED["old"]`, a digest computed over the literal old spelling. The framework's own source of the old spelling is `review_evidence.LEGACY_COUNCIL_SIGNOFF_KEYS` (with `legacy_signoff_key_spellings` and `_LEGACY_COUNCIL_KEY_PREFIX`), and `review_policy._DIGEST_COUNCIL_SIGNOFF_SPELLING` is today the reverse of the built-in pair (`test_digest_spelling_mirrors_the_alias_map` asserts equality with the reverse of `LEGACY_COUNCIL_SIGNOFF_KEYS`, which holds only the built-in pair until `200ew` merges extra keys into it). Change `200ew` lands after this change and merges `vocabulary_profile.EXTRA_LEGACY_COUNCIL_SIGNOFF_KEYS` into `LEGACY_COUNCIL_SIGNOFF_KEYS` and freezes `_LEGACY_COUNCIL_KEY_PREFIX` to `"wave-council-"`, so a current key may then have more than one legacy spelling.
- A2, example prompt names: `tests/fixtures/profiles/prompt-names.json` (one of `tests/test_profile_support.FRAMEWORK_ASSETS`) renames the container prompts to `-set` names ("Create set", "Prepare set" with alias "Ready set", "Implement set", "Pause set", "Review set", "Close set") and the item prompts to `-wave` names ("Plan wave", "Add wave to set", "Remove wave from set", and the chain "Implement wave", "Close wave", which take the slugs the container prompts give up). `tests/test_vocabulary_prompt_names.py` asserts those names throughout (`PROFILE = load_profile("prompt-names")`; the chain assertions on `chain["implement-change"]["slug"]`; the rendered skill names such as `wf-plan-wave` and `wf-close-wave`, which the stale check keeps because "reused by the chain"; the moved prompt files such as `plan-wave.prompt.md` and `close-set.prompt.md`) and in `ValidationTests` override examples (`plan-set`, "Plan set", "Implement set"). These example names coincide with a real distribution's vocabulary, so in that distribution's tree an example rename collides with, or is indistinguishable from, the distribution's own names.

## Requirements

1. **R3 scope rule.** The history-literal census scans only the framework's own scripts: each flat `*.py` in the scripts directory whose stem is in `mcp_tool_extensions.FRAMEWORK_SCRIPT_MODULE_NAMES`, plus every `*.py` under the framework subpackages `wave_lint_lib/` and `wf_server/`, less the existing allowed files. Any other file (a distribution's extension, helper or journal hook module, or anything else a distribution adds) is outside the census by construction. The framework-owned name set, not a per-distribution list or the live declaration, decides the scanned set. The `upgrade_extensions.py` `"journals" in \w+\.parts` assertion is unchanged. `scripts/benchmarks/` is outside the census because it is source-only and not shipped (`build_pack.py` excludes it).
2. **R4 isolation.** Each profile golden boot depends only on the shipped declaration plus that asset. In `_boot_in_scratch` the copied tree is reset with the `tests/test_profile_support.py` idiom before the asset is applied: `apply_profile(scripts, shipped_default_profile())`, then `apply_profile(scripts, {"modules": {"mcp_tool_extensions": SHIPPED_DECLARATION}})` (`shipped_default_profile()` does not cover the declaration module), then `apply_profile(scripts, asset)`. `declaration_support.base_declaration_source` is not used: it appends a second assignment of every declaration constant, and `apply_profile` then matches two assignments and raises. Limit: `apply_profile` replaces single-line assignments only, so the reset covers a live declaration whose editable constants are each assigned on one line; a live constant assigned across several lines fails the reset with `ProfileInvalid` naming the constant, which the test reports rather than silently booting a mixed declaration. The in-process `_boot` is unchanged unless AC-2's reproduction shows it leaks; the Progress Log records which path leaked.
3. **R5 name.** The archive-vocabulary test uses a record file name that no profile can plausibly hold, and asserts that name differs from the live `vocabulary_profile.RECORD_FILENAME` and from the `RECORD_FILENAME` of every asset under `tests/fixtures/profiles/`. The test's behavioral assertions (journal left in place, archive byte-unchanged, preview agreement) are unchanged.
4. **R6 fixture.** `test_new_names_resolve_and_retired_names_do_not` runs against a fixture repository whose `docs/prompts` holds the four prompt docs the test needs, built by the test, never the live checkout. The three change prompts' shortcuts and filenames are derived from `vocabulary_profile.shortcut(key)` and `vocabulary_profile.prompt_doc(key)` for `plan-change`, `implement-change` and `close-change`; the fixed `install-wavefoundry` prompt and its "Init wave framework" alias stay literal (fixed names, not profile names). `test_no_prompt_doc_carries_a_retired_token` scans this exact framework-owned set instead of the live `docs/prompts`: every `*.md` under `.wavefoundry/framework/install/lifecycle-prompts/`, and the seeds `100-project-prompt-surface-bootstrap.prompt.md`, `170-plan-change.prompt.md`, `175-review-plan.prompt.md`, `180-implement-change.prompt.md`, `190-close-wave.prompt.md` and `240-memory-review.prompt.md`. Seed `160-upgrade-wavefoundry.prompt.md` is not in the set: its upgrade note names the retired names as removal targets, which is the one legitimate hit, and it renders no lifecycle prompt. The retired-token pattern is unchanged.
5. **Proposed CHANGELOG bullet.** This change records one bullet in its Progress Log for change `200ew` (the wave's last change), which writes it under `## [1.29.0]`.
6. **A1 fixture config.** `MemberDocContainmentTests.setUp` builds the fixture's `wave_review` block from a known-good literal template in the test (reusing `test_lifecycle_golden._WAVE_REVIEW_CONFIG["wave_review"]`, or a literal of the same shape with whatever `phases` the readers need), never from the running checkout's `docs/workflow-config.json`. No test in `tests/test_change_id_path_guard.py` reads the checkout's workflow config afterwards.
7. **A2 legacy council spelling derived.** `tests/test_council_signoff_keys.py` derives every legacy council spelling from `review_evidence`: the old readiness and delivery spellings from `legacy_signoff_key_spellings(COUNCIL_READINESS_SIGNOFF_KEY)` and `(COUNCIL_DELIVERY_SIGNOFF_KEY)` (the first spelling for fixtures; every spelling where a test enumerates), `_legacy` replaces each current key at a token boundary (not followed or preceded by a word character or `-`) instead of the `(?<!wave-)` lookbehind, and the custom-key subtests use `_LEGACY_COUNCIL_KEY_PREFIX + "x"` instead of `"wave-council-x"`. The pinned pre-change digest is historical input and keeps its literal input dictionary; that one assertion runs only when `review_policy._DIGEST_COUNCIL_SIGNOFF_SPELLING` maps to that literal spelling (skipped with a reason otherwise), while the old-and-new-hash-alike assertion always runs with the derived spellings. The derivation keeps working when `200ew` adds extra legacy keys (more than one spelling per current key) and freezes the prefix. `test_digest_spelling_mirrors_the_alias_map` is restated as "the digest map equals the reverse of the built-in pair": it compares `_DIGEST_COUNCIL_SIGNOFF_SPELLING` with the reverse of the built-in legacy mapping only (today all of `LEGACY_COUNCIL_SIGNOFF_KEYS`; after `200ew`, the built-in part it keeps apart from `EXTRA_LEGACY_COUNCIL_SIGNOFF_KEYS`), never with the merged map, so a distribution's extra spellings do not break it. The approving actor literal `"wave-council"` is not touched here; `200ew` renames it.
8. **A2 neutral example prompt names.** The `prompt-names` fixture asset and `tests/test_vocabulary_prompt_names.py` use example override names no distribution is likely to ship, for example "Plan task" and "Gather items": no override slug, shortcut or alias value in the asset or in the test's override examples contains the word `set` or `wave`, except where a case deliberately reuses a shipped slug or shortcut (a clash case such as "Pause wave", or a chain). The asset keeps a chain (one prompt takes the slug another prompt gives up, chosen so the taken name is a shipped item name such as `implement-change`, not a shipped container name), keeps at least one alias, and keeps renaming all eleven tier-named prompts; the test's assertions on moved files, rendered skills, stale cleanup ("reused by the chain"), localized headings and consumer literals are re-derived for the new names, with the same coverage.

## Scope

**Problem statement:** framework tests read distribution-owned state as framework state, or use example names a real distribution ships, and fail on a correct distribution.

**In scope:**

- Requirements 1 to 8, test files only: `tests/test_history_paths.py`, `tests/test_tool_surface_golden.py`, `tests/test_upgrade_wavefoundry.py`, `tests/test_server_tools_lifecycle.py`, `tests/test_change_id_path_guard.py`, `tests/test_council_signoff_keys.py`, `tests/test_vocabulary_prompt_names.py`, `tests/fixtures/profiles/prompt-names.json`, and support helpers they use under `tests/`.

**Out of scope:**

- `tests/test_profile_literal_census.py` and `tests/test_events_only_residue_census.py`, which also scan files a distribution may add but were not reported; a named follow-up if a distribution reports them.
- Any shipped framework module.

## Platform Behavior

Test-only edits. The derived census, the fixture repository and the record-name precondition use repository-relative POSIX paths and plain file reads, so they behave the same on Windows, macOS, Linux and WSL2. The scratch golden boot already runs in a subprocess on every platform; the declaration reset is `apply_profile`'s existing in-place constant edit of a copied file, with no link or mode handling.

## Affected Architecture Docs

`docs/architecture/testing-architecture.md`: one sentence that framework tests must not read distribution-owned state (live declaration modules, the live record file name, live prompt docs, the running checkout's workflow config) as framework state, nor hard-code names a distribution may own (legacy council spellings, example prompt names), with these tests as the pattern. No other architecture doc changes.
