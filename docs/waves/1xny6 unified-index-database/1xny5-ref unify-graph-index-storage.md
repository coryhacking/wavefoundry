## Rationale

Give project operators one local index database, one consistent publication boundary and simpler recovery. Consolidate graph extraction state, resolved nodes/edges, communities and semantic indexing into `.wavefoundry/index/index.sqlite`; preserve existing graph APIs and the fast resident `GraphQueryIndex`. Rename `index-state.sqlite` during the same migration because it already holds indexed content, not just bookkeeping.

The initial graph transition is a full rebuild from current project sources into the staged new database, not a conversion of old graph files or extraction caches. Preserve compatible semantic data, build and verify the new graph, then retire the old graph directory. This removes graph-format translation and old graph validity as prerequisites; normal indexing remains incremental after cutover.

Evaluation wave `1xny3` demonstrated scoped atomic publication and exact graph/query parity. The operator explicitly accepted its measured timings, including reports near 900 ms and incremental updates near 10 seconds. Performance is no longer a reason to repeat the evaluation before planning. Production epoch/cache integration, incremental writes and safe upgrades are the remaining engineering work. The prototype's larger footprint and unexplained first maintenance assertion remain disclosed; consolidation is not a proven memory or disk reduction.

The operator also requested a small ignore-rule enhancement: render `.wavefoundry/locks/` from the canonical ignore list so all contents stay ignored across surface regeneration, including future non-`.lock` files.

## Requirements

1. Make `index.sqlite` the only authoritative semantic/graph database after successful migration. Use one lightweight filename/path definition for runtime consumers; retain old names only in explicit migration readers, fixtures and historical evidence. Memory and unrelated host-local databases remain separate.
2. Persist graph nodes, independent edge evidence, per-file extraction/merge state, community membership, derived graph analysis and codebase-map fingerprint state in the shared store. Bind the map fingerprint to the graph/community generation it describes; retire `.wavefoundry/index/graph/.codebase-map.fingerprint`. Keep graph identities distinct from chunk identities, including external endpoints and zero/one/many symbol-to-chunk associations. Reuse canonical chunk text; do not duplicate it in graph rows merely to join retrieval results.
3. Prepare filesystem discovery, extraction, embeddings, global relationship resolution and clustering outside the writer transaction. A single indexing coordinator publishes all changed semantic and graph participants with their layer bookkeeping and final generation/attempt ownership check in one transaction. Preserve existing durable build-start/recovery fences; a single final publication does not mean eliminating necessary earlier control transactions.
4. Use stable graph keys and change-sized writes. Preserve invalidation of edges in unchanged callers when a provider is renamed, removed or restored. Global algorithms may recompute when their inputs change, but unchanged input must not rewrite every graph row or invalidate unrelated cached data. Keep optional igraph/Leiden and its fallback.
5. Keep the resident graph cache and algorithms. Bind cached graph, communities and semantic reads to one published generation for the entire response. In-flight readers may finish on their old coherent snapshot; subsequent readers acquire the new generation. Retry or return a typed recovery/state response when coherence cannot be established; never combine generations or silently substitute empty graph results. No per-query full SQL hydration is required.
6. Support fresh setup, graph-only/semantic-only/all-content builds, incremental hooks, CLI/MCP/dashboard consumers, health/audit and close-wave maintenance through the new authority. A graph schema mismatch or corrupt extraction cache must not reset/drop the shared semantic database through the old graph-store reset-on-open behavior.
7. Deliver the migration through standard `wf_upgrade` / `wf upgrade`, with no bridge release. Preserve direct legacy LanceDB upgrades, explicit `--rebuild-storage` recovery for incompatible/colliding legacy chunks, parent-owned memory/index publication authorization and existing receipt safety. A completed old migration receipt must not suppress this new migration; an incomplete old receipt must be resolved under its recorded package/target before beginning a distinct migration.
8. Preserve data and a deterministic continuation across interruptions, locked files, disk exhaustion, ambiguous old/new names and incompatible hosts. Remove obsolete owned artifacts only after fresh-process verification of the new store and publication authority.
9. Always rebuild the graph's extraction state, resolved relationships, communities and analysis from the current source walk for the initial transition. Do not import old graph payloads, merge state or community caches. This is automatic inside the standard upgrade and does not require `--rebuild-storage`; that existing option retains its separate legacy semantic recovery meaning. Missing, corrupt or outdated old graph artifacts must not block a valid source rebuild. Unexpected extraction failures must not publish an empty or partial graph as success.

10. Include `.wavefoundry/locks/` in the canonical renderer-managed `.gitignore` block while retaining `.wavefoundry/**/*.lock`. Preserve project-owned rules outside the markers and make repeated rendering idempotent.

11. Prepare semantic updates in memory by default before acquiring the shared database writer. Bound retained preparation memory, spilling only oversized updates to a disposable spool on the owned index filesystem; no-op, graph-only and ordinary small updates must create no preparation files or directories. Preserve ordered operations, worker serialization, all-or-nothing publication and cleanup on failure. The memory budget applies to pending encoded operations, not the embedding model or the whole process; measure full-rebuild peak RSS and actual spill costs separately.

## Scope

**In scope:** bounded in-memory semantic preparation with lazy overflow, shared graph persistence and publication, codebase-map fingerprint persistence in SQLite and retirement of its standalone file, runtime path consolidation and filename migration, read/cache coherence, incremental updates, lifecycle diagnostics/maintenance, standard upgrades and recovery, the canonical rendered locks-directory ignore rule, targeted regression tests, package qualification and user-facing documentation.

**Out of scope:** Cypher/extensions, retrieval-order changes, embedding-model/quantization changes, memory-store consolidation, replacing graph algorithms, automatic shared-venv dependency removal, cloud/service support, or another broad storage comparison. Existing evaluation evidence remains historical and is not rewritten to claim a new performance winner.

Old graph-format conversion and compatibility decoders for importing graph data are also out of scope. Retain only old-path/host/ownership inspection needed for safe cutover, rollback and cleanup. This does not remove existing legacy semantic upgrade support.

## Design and source anchors

Selected implementation: native indexed graph tables with stable keys, retaining the existing resident graph serving API. Re-extract every eligible source file into fresh graph tables and fresh extraction/merge/community state during the initial upgrade, using the ordinary full-build pipeline against the staged database. Newly generated extraction records may use the existing compact representation; they are not imported from the old cache. After cutover use normal incremental writes. Use the table/identity contract below; do not import the evaluation's full-table-rewrite strategy into routine incremental publication.

The three current stdlib accessors are dispositioned: `graph_indexer.GraphStateStore._open` is replaced by `graph_store.py` on the caller's runtime connection; `index_state_store.orphan_store_paths` reads the graph extraction manifest from the same `open_read_only` connection; `upgrade_wavefoundry._read_installed_graph_builder_version` reads through a tool-venv subprocess as stated in the Upgrade row. ## Readiness contracts and plan review

Self-answered branches (current source plus operator direction):

- **Database/schema:** `index_paths.py` will own the current filename and explicit legacy locator; new graph persistence belongs in `graph_store.py`, using the existing runtime connection policy. Allocate resident schema 8; keep graph semantic schema/builder, chunker and walker versions unchanged unless emitted content actually changes, in which case re-review that scope and bump its owning version. The storage transition itself already mandates a fresh graph rebuild.
- **Tables/identity:** namespace graph tables separately from semantic tables: nodes keyed by existing public symbol ID, edges keyed by stable source ownership plus full evidence identity and occurrence discriminator, per-file extraction keyed by normalized path, named merge state, and community/analysis rows with their input fingerprint. Index outgoing/incoming relation lookups. Preserve repeated evidence; an edge triple alone is not a unique storage identity. External endpoints do not require an owned declaration row. Symbol/chunk links use actual overlap/hash evidence and never force one-to-one coverage. Database surrogate keys stay private; an unchanged public ID/evidence record keeps its storage identity across unrelated edits. Per-layer generation binding lives in a `build_layer_state` table keyed by layer with `generation` and `attempt_id`; the single scalar `build_state.generation` remains the reader token consumed by `build_epoch_token`, `build_epoch_state_token` and the server epoch helpers. Community membership and betweenness are derived analysis stored either as one compact row per generation (distinct from the rejected whole-graph snapshot) or diffed by `(node_id, community_id)` so only changed members are written; merge state is keyed per file, not one whole-corpus blob.
- **Publisher:** ordinary builds use the existing index build lock and one caller-owned SQLite connection. Prepare graph/semantic changes before `BEGIN IMMEDIATE`; compare current attempt ownership, apply all affected rows and final layer/generation state, then commit once. A failed attempt cannot publish; keep durable start/recovery control fences. Graph-only builds preserve semantic rows and their freshness/version metadata. Semantic-only builds preserve graph content or mark the graph stale when source dependencies changed; they must not advertise cross-layer freshness they did not establish. All-content builds publish the fully reconciled participants together.
- **Readers/cache:** pin one SQLite read snapshot and its attempt/generation before indexed reads; acquire the immutable resident graph/community view bound to that generation. Do not swap a view beneath an in-flight response. If graph input is unchanged, share immutable content across generations with explicit provenance. Release SQLite reads before expensive model calls only after all required indexed inputs have been materialized consistently; otherwise preserve the snapshot through dependent reads. Retain the existing pre/post epoch checks as a fence until every consumer is migrated. Bound retries to one re-acquisition, then return the established typed not-ready/recovery response rather than loop indefinitely. Existing query-triggered rebuild behavior, where retained, must use the coordinated build entrypoint and never repair the shared file inside a reader.
- **Consumers:** in addition to server graph/cluster caches and health, migrate `dashboard_lib.read_graph_payload` / `read_graph_cluster_payload`, dashboard index file watches, `gen_codebase_map.generate_codebase_map` and its input fingerprints, graph MCP resources, setup/upgrade version probes, and close/optimize maintenance. Replace file mtime invalidation with graph/community content fingerprints and generation. Persist the map fingerprint in `index.sqlite` alongside graph generation metadata, replacing `gen_codebase_map._fingerprint_path` and its file writer. Preserve idempotent map rendering and changed-input invalidation; only record successful rendering against the inputs/generation actually rendered. Map generation must not create the retired graph directory or fall back to a standalone fingerprint file. Current persisted graph/cluster path fields must identify the new database and logical component; do not report deleted filenames as live artifacts. Compare these intentional path metadata changes separately from query-content parity.
- **Migration states:** reuse the standard coordinator with a versioned migration kind. The kind reuses the v1 state names (`restart_required`, `quiesced`, `staged`, `validated`, `cutover_pending`, `published`, `verified`, `cleanup_pending`, `complete`) and the `storage_restart_required` action code, so seed-160's operator tokens stay valid; the seed's "first storage conversion" wording generalizes to every storage conversion. Receipt layout: one `sqlite-migration.json`; the schema-8 record carries `receipt_version: 2`, `kind: "index_sqlite_schema8"`, and embeds the superseded v1 record under `supersedes`. New `read_receipt` accepts versions 1 and 2; v1 code's `read_receipt` rejects version 2, which is the deliberate old-code fence. Dispatch predicate: `detect` always probes `meta.store_schema_version` through the resolver for both filenames, never short-circuiting on receipt presence. Populations: a receipt-less schema-7 `index-state.sqlite` requires the schema-8 kind; a schema-7 store with a v1 `complete` receipt requires it exactly once (a v1 receipt in any pending state finishes its package-bound legacy recovery first); a receipt-less schema-4, 5 or 6 store, with or without Lance artifacts, dispatches the existing v1 legacy conversion first, unchanged, and the schema-8 kind then runs on the resulting schema-7 store within the same upgrade; both filenames present resolves authority only through a v2 receipt's state and recorded identities, otherwise returns `storage_authority_ambiguous` and preserves both. The durable once-marker is `meta.store_schema_version = 8` in `index.sqlite`; a v2 receipt in `complete` with schema 8 published is a no-op. Old-code fence: a v1-code `require_ready` must raise `MigrationRequired` on the v2 receipt before any store is opened, and a named subprocess test asserts that no `index-state.sqlite`, `-wal` or `-shm` is created; `_published_identity` and `_sqlite_schema` take the filename from the resolver so the post-cutover absent branch cannot fire while `index.sqlite` exists. The receipt fence covers only paths that pass `require_ready`. Old-code writers that open the store directly (`secret_scan_record` through `wf_scan_secrets`, direct `IndexStateStore` constructions, the query-triggered graph rebuild) are fenced by host quiescence before cutover, which the existing confirm-hosts-stopped handoff and `_hosts_gone` provide, and after cutover by detection: with a v2 receipt in a readable state, a newly appeared `index-state.sqlite` is classified as spurious, never adopted as authority, preserved, and reported with the offending host guidance. A named test runs a v1-code `secret_scan_record` subprocess after cutover and asserts the recreated file is reported as spurious by `detect` while `index.sqlite` remains the authority. A version-1-plus-kind marker is rejected because old code tolerates it and the fence reopens at `complete`. The kind owns its retired-artifact allowlist and file-deletion arm (refusing a non-empty `-wal`, mirroring `_publish_candidate`), a distinct work-dir prefix `index-migration-<migration_id>`, and its own staging allowlist describing the nested staging tree the Upgrade row requires: under `<work>/.wavefoundry/index/`, the `index.sqlite` family, the `rollback.sqlite` family, and the prepared-updates spool directory (`wavefoundry-sqlite-prepared-*` with its `prepared.sqlite` family), with cleanup walking exactly that structure and refusing any other entry as an unknown staging artifact (the staged build runs without the memory-run authorization environment, so no publication lock lands under the staging root; a `<work>/.wavefoundry/locks/` subtree, if present, is treated as owned); `LEGACY_NAMES` and the v1 staging set are not extended, so v1 code never gains authority over v2 artifacts and vice versa. No new CLI rebuild flag is needed for graph rebuilding.
- **Semantic reuse/source churn:** graph rebuild does not mean semantic re-embedding. Preserve compatible vectors and update only changed semantic inputs. Recheck prepared source hashes and build ownership before publish; discard/reprepare changed work, with bounded attempts and a retained typed retry if the source never stabilizes. Unreadable source scope cannot silently become deletion or a successful empty graph.
- **Comparison and qualification:** compare isolated same-source baseline/new rebuilds, not stale stored graphs. Run local correctness/recovery qualification before a candidate package; native target package testing remains a release gate. No second engine ships. Memory and shared dependencies stay untouched.

## Upgrade and recovery procedure

1. **Classify before mutation.** Distinguish empty installation, legacy LanceDB, schema-7 `index-state.sqlite`, already-current `index.sqlite`, and any pending receipt/staging state. Validate root/file ownership, supported schema, runtime/WAL capability and space on the index filesystem. Inventory all persistent graph producers/readers and identify incompatible hosts before publication.
2. **Record the migration.** Bind a versioned receipt to repository, source identities, target schema, package content digest and explicit source/staging/destination/rollback paths. Package paths remain locators. Do not overwrite a historical receipt's meaning or accept a different archive to bypass a pending conversion. Retain exact CLI continuation before an MCP restart; restart checkpoints are not upgrade failures. Stop only identified incompatible hosts for this repository, with best-effort discovery limitations stated.
3. **Preserve semantic data and rebuild the graph.** Use SQLite backup/checkpoint facilities to capture committed semantic/auxiliary source data, including WAL contents; never rename/copy only a live main file or delete a nonempty WAL. Stage beside the owned index. Preserve compatible vectors and other schema-7 state. Start empty graph/extraction/community tables and run the ordinary full graph builder against the current source walk, with all output directed into the staged `index.sqlite`, through the lock-free coordinator entry named in the Upgrade row while `migrate_legacy` holds the build lock. Do not seed this build from the old graph folder. Reconcile changed semantic sources through the ordinary pipeline while reusing unchanged compatible embeddings; sharing a generation must not disguise stale semantic content. Validate source hashes/version provenance before publication and retry affected work if sources changed during preparation. Use the existing explicit legacy semantic rebuild strategy only when faithful legacy vector conversion is impossible; it is independent of this automatic graph rebuild.
4. **Validate and publish.** Verify staging participant counts/digests, vector/FTS integrity, source/version provenance and build authorization. For the paired qualification run below, compare the baseline and staged rebuild results before allowing cleanup; unexplained mismatches block adoption. Quiesce incompatible file handles before the controlled filename/schema cutover. Record cutover intent durably, atomically publish the validated candidate and retain rollback identities until fresh-process verification finishes. A failure must leave the original data recoverable and prevent a partial target from being advertised ready. Recovery after a failed or refused cutover is forward: the standard upgrade is re-run from the retained `index-state.sqlite` and the recorded rollback identities; no backward rollback to the old runner is offered, and the rollback copy is never read back into service by product code.
5. **Resume deterministically.** If both filenames exist, select authority only through the valid receipt and recorded identities/state, never by mtime, size or newest schema alone. If neither a receipt nor an unambiguous supported state proves authority, return a typed diagnostic and preserve both. Handle interruptions before/after filesystem publication and before/after receipt advancement. Do not let old readers create a fresh `index-state.sqlite` beside the new store: the receipt fence, host quiescence and post-cutover spurious-file detection in Migration states apply. Existing public readers must fail safely during incompatible cutover.
6. **Verify, then delete the old graph directory.** A fresh process checks semantic/graph readiness, public retrieval, full participant consistency and restart recovery. Verify graph completeness against the current source manifest and a fresh-build oracle, not exact counts from potentially stale old artifacts. Only then remove receipt-owned `index-state.sqlite` and its verified obsolete companions, old graph extraction/payload/community files, the obsolete framework-owned `.codebase-map.fingerprint`, and superseded staging/rollback artifacts. Recompute map fingerprint state from current inputs rather than trusting the legacy marker. Remove `.wavefoundry/index/graph/` only after a pre-deletion inventory: lstat every entry without following links and classify it against the owned-name allowlist (`project-graph.json`, `project-graph-clusters.json`, `project-graph-state.sqlite` with `-wal`/`-shm`, legacy `project-graph-state.json`, `.codebase-map.fingerprint`, retired `framework-graph.json`, `framework-graph-state.json` and `framework-graph-clusters.json`, and the atomic writers' `<owned name>.*.tmp` siblings). Any unknown name, any nested directory, or any symlink/reparse node at any depth preserves the whole folder, reports the entries, and records receipt cleanup state `retained_unowned_contents`; the whole-tree primitive `_remove_retired_component` is invoked only when the inventory is all-owned and serves as the final delete step, never as the classifier. Normally the folder disappears entirely, including on installs that still carry retired framework-layer files. Do not follow symlinks/reparse points outside the owned boundary. Retain the old graph until new-store verification succeeds, including when the rebuild fails. Clean legacy `docs.lance`, `code.lance` and `__manifest` only on a verified legacy upgrade through its existing ownership rules. Preserve unrelated files, memory, current receipts and shared dependencies. A repeated upgrade is a no-op; a repeat after incomplete cleanup converges safely without rebuilding an already verified current graph.

### Fresh rebuild comparison

Use a paired rebuild as the conversion's correctness gate during implementation and local-package qualification:

1. Freeze the same eligible source snapshot, ignore/walker settings, extractor semantics and algorithm configuration. Before the first edit to `graph_indexer.py` or `graph_cluster.py`, capture the pre-change baseline in an isolated directory and retain the results with source/runtime fingerprints: three graph-only rebuilds, one builder-version-bump rebuild, and the ten-delta rename/remove/restore sequence, each timed, so every regression reference in the Gates section has a paired pre-change sample; in the same pre-edit step capture a repeatable fixture from the pre-change builder over the small corpus in `docs/evals/graph-quality-golden.json` (canonical nodes, edge multiset, community output under the stated normalization) so the parity clause is a repeatable test, not only a one-shot qualification. Build the new shared-store graph independently from those same source bytes. Neither build consumes the other's graph data.
2. Compare canonical node identities/attributes, edge evidence as a multiset (including multiplicity), extraction coverage and resolved relationships. Counts alone are insufficient. Compare community/analysis outputs with fixed seeds where supported; explicitly account for documented nondeterminism rather than discarding differences broadly. Normalize only identified volatile bookkeeping such as build timestamps, never missing edges, identities or confidence values.
3. ### Bounded preparation memory

Use a fixed internal 64 MiB budget for retained encoded operation tuples and their container, string and blob allocations; count shared values conservatively. Charge before retention, accounting for container capacity growth rather than only logical element count. The budget is not a cap on process RSS.

Rollover reuses the existing owned-index SQLite operations spool and is one-way for this preparation instance. Persist only prior successful adds as the committed prefix, then transfer the current add's prefix and remainder inside one rollbackable spool transaction. A failed add preserves earlier adds and removes all effects of the current add, including replace/delete prefixes, whether it fails before or after rollover. Spill setup failure restores the previous RAM state; uncertain I/O restoration must refuse later publication.

Do not duplicate an unbounded current add for rollback. A single oversized encoded operation may exist transiently before direct spill, but must never remain in the retained RAM queue above budget. Measure and disclose transient source-row encoding, the largest encoded operation, the largest decoded apply batch, and SQLite cache independently of retained preparation bytes. The 250-operation decode/apply limit bounds count, not bytes: its transient allowance depends on source-row size, so no universal transient-byte or process-RSS cap is claimed.

Prove actual production coordinator no-op, graph-only and below-budget semantic builds never invoke preparation TemporaryDirectory or open its SQLite spool. Prove exact-at-budget stays in RAM and first-over-budget spills in order, concurrent add serialization, failures during encoding and each spill transfer stage, caller transaction rollback and close-before-cleanup behavior. Test the default memory limit and a small injectable test-only threshold without adding user-facing configuration.
