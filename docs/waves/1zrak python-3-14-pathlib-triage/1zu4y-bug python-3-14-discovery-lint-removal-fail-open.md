# Refuse Uninspectable Wave Roots, Lint Inputs And Removal Sources Instead Of Reading Them As Absent On Python 3.14

Change ID: `1zu4y-bug python-3-14-discovery-lint-removal-fail-open`
Change Status: `implemented`
Owner: implementer
Status: implemented
Last verified: 2026-10-04
Wave: 1zrak python-3-14-pathlib-triage

## Rationale

Change `1zraj-bug python-3-14-pathlib-oserror-triage` found three sites where Python 3.14's `pathlib` predicates (`exists`, `is_file`, `is_dir`, `is_symlink`, which now return `False` on any `OSError`) turn an undetermined path into "absent", and listed them as needs-decision follow-ups. The operator decided on 2026-10-04 to fix all three in this release:

1. **Wave discovery.** `record_paths.walk_wave_candidates` gates the walk on `top.is_dir()` and `discover_archive_dirs` on `roots.archive.is_dir()`, outside any `try`. On 3.14 a waves or archive root under an untraversable parent reads as "no waves". On 3.13 the predicate raised `PermissionError` to the caller. Every lifecycle tool, docs-lint, memory backfill and the id mint use this discovery. A mutating tool that sees "no waves" can act on a partial view: for example, `wf_create_wave`'s collision scan and `lifecycle_id._existing_prefixes` stop seeing existing ids. Separately, on every supported Python, a root that `stat` can read but `iterdir` cannot (mode 0 on the root itself) already reads as "no waves", because `_list_subdirs` returns `[]` on a listing error. The same happens one level down, on every supported Python. A wave folder whose record-file probe fails (`_has_wave_md` catches `OSError` and returns `False`) is silently left out. In the nested layout, a grouping folder the walk cannot list is also left out, together with every wave below it.
2. **Docs-lint presence probes.** `_framework_internal_constants_enabled` (`wave_lint_lib/docs_constants_validators.py:122`) and the legacy pointer residue probe in `check_memory_docs` (`wave_lint_lib/wave_validators.py:1997`) read an uninspectable input as absent, so lint passes silently. On 3.13 the predicate raised and docs-lint stopped with a traceback.
3. **Index removal validation.** In `indexer._validate_prepared_removals`, when `requested_files` is set, an uninspectable requested file is dropped by `path.is_file()` (line 4083 at the time of the triage). It then never reaches the "became unreadable" check, so its removal goes ahead. On 3.13 `is_file()` raised inside the writer transaction and the build failed. The full-walk branch already classifies such a file as unreadable through `walk_repo`'s `unreadable_files` (wave `1zime`); the requested-files branch does not.

Python 3.14 is inside the supported range (3.11 through 3.14), so each of these is a product defect on a supported interpreter.

## Requirements

1. One shared helper in `record_paths` decides a record root's state with `os.stat` (following links, as `is_dir()` did) under the `1zraj` errno rule, the pattern of `review_evidence._authority_member_lstat`. `FileNotFoundError` and `NotADirectoryError` mean absent. A path that exists but is not a directory means "not a directory", as before. Every other `OSError` raises `record_paths.RecordRootUnreadable`.
2. `RecordRootUnreadable` subclasses `RecordLayoutInvalid` and carries path-free diagnostics. It uses one of two codes: `record_root_unreadable` for the waves or archive root itself, and `record_folder_unreadable` for a folder below it. Its `str()` contains only four things: the code, the repository-relative path (`roots.waves_rel`, `roots.archive_rel`, or the folder relative to the repository root), the exception class with the errno name (`lifecycle_lock._cause_label`), and the recovery. Its text never includes `strerror` or an absolute path. The diagnostic lines are exactly `record_root_unreadable: <rel>: cannot be inspected (<cause>); restore read and search access to <rel>, then retry` and `record_folder_unreadable: <rel>: cannot be inspected (<cause>); restore read and search access to <rel>, or move it out of <root_rel> if it is not a wave folder, then retry`, where `<cause>` is `lifecycle_lock._cause_label` (for example `PermissionError EACCES`) and `<root_rel>` is the waves or archive root the folder sits under. `RecordRootUnreadable` is defined reload-safe (Requirement 12).
3. `walk_wave_candidates` (for both the waves root and an explicit `base`) and `discover_archive_dirs` decide the root through that helper. They raise `record_root_unreadable` when listing the top-level root fails with an `OSError`.
4. Below the root, the walk raises `record_folder_unreadable` only for a folder it actually uses:
   - (a) **The record-file probe.** This is the `_has_wave_md` stat of a candidate's record file, run in both layouts and for the archive's record file. Any `OSError` other than `FileNotFoundError`/`NotADirectoryError` refuses, and the message names the candidate folder.
   - (b) **The listing of a nested folder the walk descends into.** This means `NESTED` is true, the depth is below `MAX_DEPTH`, and the folder holds no record file. Any listing `OSError` refuses, and the message names that folder.
   - (c) **An entry's own `lstat` while classifying it.** This fails only when its parent cannot be searched, so the message names the parent folder.

   Nothing else counts:
   - Dot-prefixed names are never refused, in either layout. The nested walk skips them before any stat. The flat walk still lists them as before, but a failed probe on one is skipped, not refused.
   - Symlinked entries are never refused because of their target. The nested walk skips them by `lstat`, as now. The flat walk `lstat`s each entry first; an entry that is a symlink keeps its pre-change handling (it is a candidate when its target stats as a directory, and its record probe reads any `OSError` as "no record file"), so it never reaches the refusing probe. A readable symlinked wave folder is therefore still discovered in the flat layout (`test_record_paths.test_flat_layout_still_enumerates_a_symlinked_child` stays green), and a symlink to an unstat-able target or to a mode-0 directory never refuses.
   - Files are never refused.
   - Depth, from `walk_wave_candidates`'s stack (the root is depth 0; a folder is listed only when its depth is below `MAX_DEPTH`; each listed child is appended and probed at depth plus one): a folder at depth `MAX_DEPTH` is still found and probed, so a failed probe there refuses, but it is never listed. A folder at depth `MAX_DEPTH + 1` is never seen and never refuses.
   - The subfolders of a folder that holds a record file are not part of discovery and are never refused.
5. Each caller-side root gate that short-circuits before discovery uses the same helper instead of `.is_dir()`, so the refusal is not bypassed. The gates are: `lifecycle_id._existing_prefixes` (two), `memory_supply.resolve_wave_dir`, `context_efficiency.resolve_open_wave` and `_non_closed_wave_ids`, `commit_provenance.resolve_via_evidence`, `server_impl._audit_commit_governance`, `wave_validators.check_wave_roots`, `wave_validators.check_orphan_wave_ledgers` (its own `waves_root.is_dir()` early return) and `docs_constants_validators.check_wave_scaffolding_integrity`.
6. Mutating lifecycle tools never act on a partial view. Of the 18 response functions decorated with `_fail_closed_on_record_layout`, the 17 below reach discovery (derived by a name-based call closure over `server_impl.py` from each decorated function to `discover_wave_dirs`, `walk_wave_candidates`, `discover_archive_dirs`, `build_id` or the cache's wave walk) and refuse through the decorator's `RecordRootUnreadable` branch, which returns a structured error carrying the refusal's own diagnostic code (`record_root_unreadable` or `record_folder_unreadable`) and its path-free recovery text; no read or write follows the refusal:
   - through `_waves_and_dirs`: `wf_current_wave_response`;
   - through `_waves_and_dirs` and `_find_wave_md`: `wf_list_waves_response`;
   - through `_resolve_wave_md_matches` and `_archived_wave_matches`: `wf_get_change_response`;
   - through `_find_wave_md_detailed`: `_mark_change_item_response` (`wf_mark_ac`, `wf_mark_task`), `wf_add_change_response`, `wf_remove_change_response`, `wf_review_event_response`, `wf_pause_wave_response`, `wf_review_wave_response`, `wf_close_wave_response`, `wf_close_change_response`;
   - through `_find_wave_md_detailed` and `_find_other_active_wave`: `wf_prepare_wave_response`, `wf_implement_wave_response`, `wf_reopen_wave_response`;
   - through `create_wave` (the collision scan and `build_id`): `wf_create_wave_response`;
   - through `change_create` and `build_id` (Requirement 13): `_change_create_response` (every `wf_new_*` tool);
   - through `_audit_commit_governance`, `_waves_and_dirs` and `current_wave`: `wf_audit_response`.

   `wf_list_plans_response` never touches the waves or archive root and proceeds unchanged. This means one stray uninspectable folder under the waves root refuses every decorated lifecycle tool until the folder is fixed or moved; that is intended under the fail-closed rule, and the message names the folder and both fixes. They never tell the operator to fix the layout constants.
7. Callers with an `OSError` or `ValueError` contract convert the typed error at their boundary, with path-free text. `memory_backfill` inventory raises `OSError`, which `memory_backfill_response` reports as `historical_memory_inventory_failed`. `review_policy_upgrade.plan_review_policy_upgrade` raises `ValueError`, which the three upgrade preflight handlers already catch. Observational callers whose existing handlers already swallow `RecordLayoutInvalid` or `Exception` keep doing so: the rendered hook's `_wave_dirs`, `resolve_open_wave`, `record_discovery_mismatch`, `_refuse_if_archived` and the telemetry re-resolutions.
8. Docs-lint fails closed on an uninspectable record root or record folder. Both the full and the incremental path run the waves and archive discovery walk once, right after the layout check. This is the same walk the validators use, so a root failure and a folder failure are both found before any validator runs. The refusal is returned as a bare failure string (the diagnostic line of Requirement 2, with no `ERROR: ` prefix, because `cli._emit` adds it; see the comment at `wave_lint_lib/core_validators.py:78`), so the operator sees `ERROR: record_root_unreadable: ...` or `ERROR: record_folder_unreadable: ...` once (exit 1), and the root-aware validators are skipped, as they are for an invalid layout. A `RecordRootUnreadable` raised later by a validator (if the tree changes mid-run) is caught at the lint run boundary and reported the same way, never as a traceback.
9. The docs-lint presence probes in `_framework_internal_constants_enabled`, `check_docs_constants` (the claims-doc `is_file()` probe and the `read_text` that follows it, whose `OSError` is now skipped silently by `continue`) and `check_memory_docs` (legacy pointer residue) decide presence with `os.stat`/`os.lstat` under the errno rule. Any other `OSError`, and an `OSError` from the claims-doc read, adds a blocking lint failure as a bare string `docs_lint_input_unreadable: <rel>: cannot be inspected (<cause>); restore read access to <rel>, then re-run docs-lint`, with no `ERROR: ` prefix (even though the sibling messages in `docs_constants_validators.py` self-prefix, a pre-existing double prefix this change does not touch) and no absolute path. These are failure branches of existing blocking validators, not new sensors, so `SENSOR_POLARITY_REGISTRY` is unchanged.
10. When `requested_files` is set, `_validate_prepared_removals` classifies each requested file with `indexer._walk_entry_is_regular_file`, the same helper and absence set (`_walk_stat_error_is_absence`) that `walk_repo` uses. A file it cannot stat for any other reason is added to the `unreadable` set. A removal for that path then raises `SourceChanged("... became unreadable ...")` instead of proceeding. This intentionally matches wave `1zime` rather than the `1zraj` errno rule (see Decision Log).
11. Behaviour is the same on Windows, macOS, Linux and WSL2 and on Python 3.11 through 3.14 (see Platform Behaviour).
12. `RecordRootUnreadable` survives an in-place reload by any shipped `_reload_in_place`, including v1.28.0's, which rebinds only the exception classes the OLD module already had. `record_paths` reads `_PRIOR_RECORD_LAYOUT_INVALID = globals().get("RecordLayoutInvalid")` at module top, before the `class RecordLayoutInvalid(Exception)` statement (a reload re-executes in the same namespace, so this is the class the old runner's holders captured; on a fresh import it is `None`). After that statement it sets `_RECORD_LAYOUT_INVALID_BASE` to `_PRIOR_RECORD_LAYOUT_INVALID` when that is a class and a subclass of `Exception`, otherwise to the freshly defined `RecordLayoutInvalid`, and defines `class RecordRootUnreadable(_RECORD_LAYOUT_INVALID_BASE)`. `RecordLayoutInvalid` keeps its current definition (an `Exception` subclass whose `__init__(diagnostics)` joins them into the message and stores `self.diagnostics`, identical in v1.27.0, v1.28.0 and HEAD), so the old base gives the subclass the same constructor. Interaction with `_reload_in_place`: it snapshots `kept` before `importlib.reload` and, after it, rebinds `RecordLayoutInvalid` (and, from the second reload on, `RecordRootUnreadable` itself) to the snapshot objects; the subclass's base is already that snapshot object, so after the rebinding `issubclass(record_paths.RecordRootUnreadable, record_paths.RecordLayoutInvalid)` holds and both old-bound and module-attribute handlers catch it. `upgrade_extensions.py` is not changed.
13. Change-ID and wave-ID minting never mints blind. `lifecycle_id._existing_prefixes` decides each prefix source with the `record_paths` helper and lists it through the `record_paths` listing seam (Requirement 14) instead of `.is_dir()` and `glob("*.md")`: the plans root, the waves and archive roots and the `docs/architecture/decisions` directory (a prefix-source root: `record_root_unreadable: docs/architecture/decisions: cannot be inspected (<cause>); restore read and search access to docs/architecture/decisions, then retry`) refuse as `record_root_unreadable` when present but uninspectable or unlistable; each flat-layout or nested candidate wave or archive folder whose listing fails refuses as `record_folder_unreadable`, except Requirement 4's exempt entries (a dot-prefixed name, or an entry whose `lstat` shows a link), which are skipped without refusing. The refusal reaches `wf_new_*` and `wf_create_wave` through the decorator, and the `lifecycle_id` CLI `main` reports it as `lifecycle_id: error: <diagnostic>` with exit 2 instead of a traceback. `scan_max_prefix_value` uses the same function and refuses the same way.
14. Every listing in the discovery walk and in `_existing_prefixes` goes through one module-level seam, `record_paths._scandir(path)`, which calls `os.scandir` and returns the entries; `Path.iterdir` and `Path.glob` are not used there, because their implementation moved between 3.11 and 3.14 and a pin that patches `os.scandir` or `os.listdir` would not be stable. Patched-listing pins patch `record_paths._scandir` and raise only for the target path.
15. The local dashboard's `_handle_doc` catches `record_paths.RecordRootUnreadable` around its discovery calls and responds `503 Service Unavailable` with the refusal's code as the reason and its path-free diagnostic line as the explanation, instead of letting the handler raise and drop the connection.

On 3.13, each of these cases raised an error.

**Effect of the below-root refusal on the callers (re-checked).** Every caller reaches below-root folders only through the same walk, so each row above applies unchanged with "uninspectable root" read as "uninspectable root or used folder". Two differences: the memory backfill's `_canonical_waves_dir` checks only the root, so for a folder failure the walk is the primary refusal, not a backstop, converted to `OSError` (Req 7); and `memory_supply.resolve_wave_dir` previously reported `wave_not_found` when a wave folder vanished, and now propagates the folder refusal. Observational callers (rendered hook, `resolve_open_wave`, `record_discovery_mismatch`, `_refuse_if_archived`, telemetry) keep swallowing. Legitimate-tree check against the current walk code: the nested walk skips dot-prefixed and symlinked entries before any stat and never lists past `MAX_DEPTH` or inside a folder holding a record file, so none of those can refuse; the flat walk keeps dot-prefixed and symlinked directories as candidates for compatibility, so Requirement 4 exempts both explicitly; files are only stat'd for their type; `__pycache__` or any other readable non-wave folder passes, and an unreadable non-wave folder at a used position refuses with a message that says to move it out of the root.

## Platform Behaviour

- **macOS, Linux and WSL2:** `os.stat` and `os.lstat` raise `PermissionError` (EACCES) for a path under an untraversable parent, and `os.scandir`/`iterdir` raise it for an unlistable directory, so all three items refuse or report where 3.14 predicates read absent. Mode-0 pins exercise a real untraversable parent (items 1, 2, 3), an unlistable root (item 1), and a mode-0 wave or nested grouping folder (item 1, below the root). They skip under root, which ignores mode 0. The tests use temporary directories on the native filesystem, so a WSL2 DrvFs mount without metadata (where `chmod` has no effect) is not in play.
- **Windows:** the 3.14 predicate change applies. CPython's `os.stat` on Windows falls back to `FindFirstFileW` on the parent when opening the path is denied (`ERROR_ACCESS_DENIED` or a sharing violation), so a denied directory whose parent can be listed usually stats fine; the denial surfaces at the listing (`os.scandir` through `record_paths._scandir`) or at the record probe of a file inside it (`PermissionError`, WinError 5). That is why Requirement 4 refuses at the listing and the probe, not only at the root stat. `os.chmod(path, 0)` does not deny traversal or listing, so mode-0 pins skip on `nt` with a stated reason. On Windows, each item is covered by a pin that patches `os.stat` (or `os.lstat`) to raise `PermissionError`, plus, for item 1's listing refusals (root, nested folder and the `_existing_prefixes` candidate listing), a pin that patches `record_paths._scandir` to raise for the target path only; the seam keeps those pins stable across 3.11 to 3.14, whose `pathlib` listing implementations differ. Items 1 and 2 follow the `1zraj` errno rule, so WinError 21, 123 and 1921 refuse. Item 3 follows `_walk_stat_error_is_absence`, which reads them as absent, as `walk_repo` does.
- **Python 3.11 through 3.13:** under the errno rule, EACCES and every other error still refuse (now as a typed, path-free refusal instead of a raw `PermissionError` or a traceback). ELOOP and EBADF on a record root now refuse where `is_dir()` read them as absent; layout validation already refuses a looping or dangling root. Item 3 classifies the same as the 3.13 walk did.
