## Rationale

Track 4 of the arc [`244cm-arc memory-quality`](../../arcs/244cm%20memory-quality/244cm-arc%20memory-quality.md) asks that every surfaced record still points at code that exists, or is queued for revalidation. Today the maintenance code does neither:

1. Churn silently lowers confidence. `memory_records.apply_decay` divides a `failed_attempt`, `review_finding` or `successful_pattern` record's confidence by `1 + churn / halving_commits`. Executed on 2026-11-23 with 3 commits on the target and confidence 0.8, it returned `effective_confidence` 0.615 with `needs_reverification: false`. Only `fragile_file` gets a flag instead of attenuation. `decision` and `operator_preference` get neither.
1. Decay never resets. Churn is counted from `created_at`, and time decay for `environment_gotcha` and `dependency_gotcha` is measured from `created_at`. The same execution, with `Created: 2026-01-01` and `Updated: 2026-11-01`, measured 321 days of age. A record checked yesterday decays as if it were never checked.
1. `Updated:` is re-stamped on every status transition. `reconcile_memory_record` rewrites the line whenever the status changes, so a keep made on a skim looks the same as a keep made after checking the code.
1. The audit batch is ordered by age alone. The `least_recently_reviewed` order in `wf_server/memory_handlers.memory_search_response` (change 244fh) sorts by `updated_at`, then effective confidence, then id. A record whose target was deleted waits its turn behind older healthy records.
1. Nothing reports whether targets still exist. `_memory_file_target_exists` checks the working tree with a suffix match, and only `memory_validate` calls it.

The research assessment ([Maintenance](../../arcs/244cm%20memory-quality/research/agent-memory-systems-assessment.md) and Lifecycle sections) recommends using churn and missing targets as triggers for a check, changing confidence only when a check happens, and ordering the audit by signal first. Wave `245na` also left 4 active records the frozen evaluation cannot cover and asked for a versioned re-freeze, so later results stay comparable to its baseline.

## Product Intent

**Who benefits:** maintainers who run Review memories, and agents that receive briefings.

**Before:** a record whose target was deleted or rewritten can surface at full or quietly reduced confidence, and the audit reaches it only when its age comes up. A keep stamp proves nothing about a check.

**After:** each surfaced record carries a visible revalidation flag with its reasons when a target no longer resolves in the current checkout, names its file only by a bare suffix, or has churned past its threshold since the last recorded check. The audit batch lists flagged records first. Confidence and `Updated:` change only when a check is recorded, and a keep is refused while a target is unresolved. The evaluation reports the maintenance signals, and a new versioned query set can be frozen without changing the `245na` baseline.

**First outcome worth delivering on its own:** the flag and the signal-first audit order (AC-1, AC-3, AC-5). A maintainer can show it by running the audit listing on this repository and seeing records with broken or churned targets at the front (AC-11).

**Boundary:** this wave builds the tooling. Rewriting or retiring this repository's memory records, and authoring and freezing the second query set, run after this wave closes as a Review memories pass with operator authorization (Decision Log, 2026-11-24).

## Requirements

1. **Derived revalidation flags.** For every record it scores, `apply_decay` returns `needs_reverification` and an ordered `revalidation_reasons` list. The state is derived on each read and never written to the record. Flags read each target ref's `state` from track 3's `memory_records.resolve_memory_refs(root, targets=..., tree=...)`, never its `blocking` list, which also holds `suffix_only` targets for the admission rule of `249aq-enh memory-admission-hardening` (Decision Log, 2026-11-24). It reads the working tree, which is what "at HEAD" means in this arc. The state-to-flag mapping is exhaustive:
   1. `target_unresolved`: a file target whose state is `unresolved` (absent, a directory, a line past the end, an escape or a refused symlink) or `ambiguous` (a suffix that matches more than one file), or a `symbol:` target whose state is `unresolved`.
   1. `target_not_canonical`: a file target whose state is `suffix_only` (a bare name or suffix that matches exactly one file). The record is current but names its target imprecisely.
   1. No flag: a target whose state is `resolved` or `unchecked`, including `community:` targets and a `symbol:` target with no resolved file target.
   1. Evidence refs are not passed and set no flag. They are an admission concern under 249as.
   1. `target_churn`: the commits on any file target's canonical path since the last recorded check reach that record's `adaptive_churn_halving_commits` value. The canonical path is the ref itself when `resolved` and `resolved_path` when `suffix_only`, so a bare-name target gets the same churn as its full path. The halving is computed from the same canonical paths. Unresolved and ambiguous targets contribute no churn.
   The list holds `target_unresolved`, then `target_churn`, then `target_not_canonical`, and is empty when none applies. `needs_reverification` is true when the list holds `target_unresolved` or `target_churn`; `target_not_canonical` alone queues a rewrite, not a revalidation.
1. **Churn does not lower confidence.** For every kind, churn changes only the flag. `effective_confidence` for the tactical kinds equals the base confidence, and `decay_basis` names the churn as `target_churn:<n> (flag only)`. The tactical churn floor that drops a record from briefings is removed. A flagged record is still surfaced, with its flag and reasons in the view.
1. **Decay resets only on a recorded check.** The last recorded check is the record's `Checked at:` timestamp (ISO 8601 UTC, written by a recorded check); without one, the `Updated:` date; without that, `Created:`. Churn counts only commits strictly after that instant, so a check made later on the same day as a commit clears the flag. Time decay for `environment_gotcha` and `dependency_gotcha` measures age from the same instant. Reading a record through `memory_search`, `memory_brief` or an advisory never writes to it.
1. **Never-decaying kinds keep the age exemption and gain churn revalidation.** `decision`, `operator_preference` and `fragile_file` never lose confidence to age or churn, and are flagged by the same reasons as every other kind. `fragile_file` moves from flagging on any churn since creation to the shared threshold since the last check (coordinator decision, 2026-11-24).
1. **Signal-first audit order.** `memory_search(order="least_recently_reviewed")` sorts by a signal rank first: 0 for a record with `target_unresolved`, 1 for `target_churn` without `target_unresolved`, 2 for `target_not_canonical` alone, 3 for no reason. Within a rank it keeps the 244fh order: `updated_at` ascending, effective confidence ascending, memory id. The sort runs before the cap. The order name is unchanged.
1. **A recorded check.** `memory_reconcile` gains a single-line `check_note` parameter, and `reconcile_memory_record` gains `check_note` and `checked_at` parameters. A call with a `check_note` is a recorded check: it re-stamps `Updated:` with the check's date and writes `Checked at: <ISO 8601 UTC>`, `Check note: <text>` and `Check flags: <reasons, comma-separated, or none>`, where the flags are those present just before the check. The note passes 249aq's `forbidden_content_reasons` before any write. The note is an audit trail, not proof of a check (Risks).
   1. A keep is a same-status `memory_reconcile(status="active")` on a record that is already `active`. It requires `check_note`; without one the handler returns `memory_check_required` and writes nothing.
   1. A keep calls `resolve_memory_refs` first. When any target sets `target_unresolved` it returns `memory_target_unresolved` naming each such ref and its state, and writes nothing; the reviewer rewrites or retires the record. A `target_not_canonical` target does not refuse the keep.
   1. Promoting a `candidate` to `active` is admission, governed by 249as. It needs no `check_note` and runs no keep refusal; with no note it changes only the `Status:` line.
   1. A transition to `stale`, `superseded` or `rejected` accepts an optional `check_note`. Without one, only the `Status:` line changes and `Updated:` is left alone. This covers the internal callers in `memory_add(supersedes=...)` and `memory_consolidate`.
   1. The refusals live in `memory_reconcile_response`; the low-level writer only stamps when given a note. Archival and `memory_validate` keep their current stamping.
1. **Maintenance signals, aggregate in the evaluation.** `wf_memory_eval` keeps its aggregate-only contract: it reports counts and never memory ids. Its `maintenance_signals` object is computed without any model and holds:
   1. `active_records`, `unresolved_target_records`, `unresolved_target_fraction` (rounded to 4 places, `null` when there are no active records), `not_canonical_target_records` and `churn_flagged_records`.
   1. `coverage_gap_records`: active records with a file target and a summary whose `source_id` has fewer than 2 answerable cases in the scored query set; `null` with no query set.
   1. `uncoverable_records`: the count of entries `memory_eval.uncoverable_records` returns.
   1. `check_outcomes`: over live and archived bodies that carry a `Check flags:` line, the count of `active` and of retired (`stale`, `superseded`, `rejected`, `archived`) records, split into flagged and unflagged.
   `memory_eval.py --json --curated-root ROOT` reports the same object for ROOT; without `--curated-root` it describes the hermetic fixture pass.
1. **Uncoverable-record helper.** The id list lives only in a separate maintenance helper that Review memories uses: the public function `memory_eval.uncoverable_records(root, query_set)` and the CLI `memory_eval.py --uncoverable-records ROOT`, which prints JSON. Each entry holds `memory_id` and sorted `reasons`: `coverage_gap` (as in Requirement 7) and `no_rationale` (an active record with neither a non-empty `Validation rationale:` line nor a non-empty `Action delta:` line, the only record fields that state when or why a lesson applies). Entries are sorted by id. With no query set, only `no_rationale` is evaluated. This set is the batch for the item 7 review.
1. **Versioned query sets.** Version 1 is the existing `docs/evals/memory-query-set.json` and its lock, which this change never rewrites. Version N of 2 or more lives at `docs/evals/memory-query-set.vN.json` with `docs/evals/memory-query-set.vN.lock.json`.
   1. `memory_eval.py --freeze-query-set ROOT --query-set-version N` freezes version N. For N of 2 or more, the lock adds `version`, `parent_version` (N minus 1), `parent_query_set_sha256` and sorted `added_case_ids` and `removed_case_ids`, computed by case id against the parent.
   1. The freeze first checks that the parent set's canonical hash matches its own lock. On a mismatch it exits 2, prints `parent query set does not match its lock` and writes nothing.
   1. A run scores the highest version that has both files, unless `--query-set-version N` names one. The report carries `query_set.version`. With no versioned file present, behavior is unchanged from 245sp.
   1. The operator spot-check and its outcome stay in the freezing wave's Progress Log, as in 245sp.
1. **Guidance on keeps.** Every place that tells an agent how to keep or promote a record states the new rule: a keep of an active record needs a `check_note` and is refused on an unresolved target, a candidate promotion needs neither, and a flag is a reason to check, not a verdict. The places are:
   1. Seed 240 steps 2 and 3 and its read-only procedure, rendered to `docs/prompts/memory-review.prompt.md` and `.wavefoundry/framework/install/lifecycle-prompts/memory-review.prompt.md`. Step 3 also describes the signal-first batch and `target_not_canonical`.
   1. Seed 190 step 12, rendered to `docs/prompts/close-wave.prompt.md` and `.wavefoundry/framework/install/lifecycle-prompts/close-wave.prompt.md`.
   1. The `memory_validation_required` recovery usage in `wf_server/server_impl.py`.
   1. The `memory_search` docstring in `wf_server/server_impl.py`, which says a keep stamp moves a record to the end.
1. **Line endings.** The `Checked at:`, `Check note:` and `Check flags:` lines are written through the existing `reconcile_memory_record` writer, which preserves the file's line endings with `line_endings.merge`. The versioned lock is written through the existing `freeze_query_set` writer as LF bytes. Neither is a new writer; if implementation adds one, it is classified in the line-ending census.
1. **Imports.** New or touched imports of server modules use the form `import wf_server.X as X`.

## Acceptance Criteria

- [x] AC-1: Churn flags a record without lowering it, on the canonical path. A fixture `failed_attempt` record with confidence 0.8, `Updated: 2026-11-01` and target `a.py`, with 12 commits on `a.py` after that date and an adaptive halving of 10, returns `needs_reverification: true`, `revalidation_reasons: ["target_churn"]`, `effective_confidence` 0.8 and `briefing_included: true`; with 9 commits it returns `false` and `[]`. ## Affected Architecture Docs

ADR `docs/architecture/decisions/1sk58-adr local-typed-agent-memory-records.md` states that confidence decays with churn for reproduction-bound kinds and that only `fragile_file` gains a flag. This change reverses that for churn, so the ADR gets a dated amendment. `docs/architecture/decisions/1sihk-adr annotation-first-temporal-decay.md` concerns documentation citations, not memory records, and is unchanged.

## Platforms

- **All platforms:** the change is pure Python. The flag is derived per read, and the record writer and freeze writer are unchanged.
- **Windows:** `Checked at:` is written as UTC with a `Z` suffix, so the instant does not depend on the local time zone. The `Checked at:`, `Check note:` and `Check flags:` lines keep a CRLF record CRLF through `line_endings.merge` (AC-6). The versioned lock is LF bytes and its hash covers parsed JSON, so a CRLF checkout matches. Paths are compared as POSIX strings. Resolution reads the working tree through `resolve_memory_refs`, with no Git subprocess; how a target that differs only in case is matched is that primitive's contract.
- **macOS:** the default case-insensitive filesystem has the same case question as Windows, settled by `resolve_memory_refs`.
- **Linux:** no differences.
- **WSL2:** under `/mnt/c` the working-tree walk and churn reads are slower only.
