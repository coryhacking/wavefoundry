## Rationale

A Rust project that installs the framework today gets two bullets of Rust guidance in the builder role (seed 222), one paragraph in the performance reviewer (seed 212) and a language-neutral check in the code reviewer (seed 221), all added by closed wave `237ee`. The fuller Rust policy the operator uses lives in one project only: `docs/contributing/rust-best-practices.md` in the Tensorwell repository, a table of practices each marked adopt, adapt, defer or decline with a rationale and a verification method, plus a review checklist. Each new Rust project would start from the two bullets and rebuild that table by hand.

The operator plans several Rust projects and asked for the baseline, quoted, 2026-11-18: "plan the framework-shipped Rust practices baseline as a spec; google and microsoft also recently announced best practices that I'd like to consider as part of this." Earlier the same day: "we have some rust bst practices that are part of the frameowrk for other projects. I'm looking for things that can enhance those. I'll be working on several rust projects in the future."

Three bodies of evidence were gathered for this plan on 2026-11-18 and are summarized in the Progress Log: the Tensorwell policy as it stands; a read-only review of a large open-source Rust workspace (16 crates, about 289,000 lines), which gives measured evidence on items that policy deferred; and the current Google and Microsoft Rust guidance with dates.

## Product Intent

A team starting or maintaining a Rust project with the framework has, from installation, a reviewed menu of Rust practices, each with the exact setting, a check that can fail and its cost, and a project-owned record of which practices that project adopted and why. Builders and reviewers work from the project's record. Before: two bullets, and each project invents its own policy. After: the framework ships the baseline, and an agent drafts the project's record from it for the operator to decide. Boundaries: the framework never enables a lint, installs a configuration file or adds a gate; every adoption is the project's own decision through its ordinary change process.

## Requirements

1. The framework ships one reference document, `.wavefoundry/framework/docs/rust-practices.md`, carried in the package and read in place in an installed project, like the writing guide. It is not copied into the project's `docs/`. It lives outside the linted `docs/` tree and is not indexed in installed projects, so docs lint never checks it; the content tests of AC-1, AC-6 and AC-7 check its structure and its `Owner:`, `Status:` and `Last verified:` lines.
2. Document layout and entry format:
   1. Below its title the baseline carries `Owner:`, `Status:` and `Last verified:` lines like the writing guide. It then opens with the usage statement of requirement 5, followed by an index table with one row per entry (practice, stance, link to the entry), so a reader can go to one entry without loading the whole document.
   2. Each practice is one entry: one heading followed by seven labelled fields in this fixed order with these exact labels: `Practice` (one sentence); `Applies when` (library, application, FFI, async, untrusted input, any); `Stance` (one of `adopt`, `propose` or `situational`, set by requirement 3.5); `Setting` (lint name and level, manifest key, tool and arguments, or the review question when no tool exists); `Check` (a check that can fail: the negative control that shows the practice is enforced); `Cost and caveats`; `Sources`. An entry without a check that can fail, or without at least one source, is not in the baseline.
   3. Inside `Cost and caveats` every entry carries a `Touches:` line whose values come from the closed list `processes`, `paths`, `line-endings`, `locking`, `linking`, `ffi`, `none`. Every entry whose `Touches:` is not `none` also carries a `Platforms:` line (requirement 6).
   4. Settings (lint tables, manifest keys, commands) appear only inside fenced text.
   5. The baseline contains a "Lints named" table giving each lint named in any `Setting` field, its group, its default level and the toolchain version it was checked against.
   6. The baseline contains a disposition table mapping each topic area listed in requirement 4 to its entries, or to "not included" or "left out" with a reason.
3. Which practices enter the baseline is decided by a rule, and the derived set governs:
   1. A practice qualifies when a named public source states it, or the operator's existing policy adopts or adapts it, and it has a check that can fail or a specific review question.
   2. Rules that bind one company's codebase (for example a ban on async or on standard threads in one product, a required allocator, internal build-system rules) are listed in a short "not included" section with the reason, not as entries.
   3. Where sources disagree, the baseline has one entry that states the disagreement and the choice a project must make, with no default stance stronger than `situational`. The known disagreements are: catching a panic and continuing; enabling Clippy's pedantic, restriction and cargo groups as groups versus naming individual lints; error types as situation-specific structs versus enums; where tests of the public API live; async.
   4. Every lint the baseline names is checked by the implementer against the Clippy and rustc lint lists for a stated toolchain version: that it exists, its group and its default level. The baseline states that toolchain version in its "Lints named" table. A lint that cannot be verified is left out.
   5. An entry's stance is `adopt` only when a named public source or the operator's existing policy recommends the practice, no named source disagrees with it, and it holds in every context listed in its `Applies when` field. It is `situational` when sources disagree or it holds only in some contexts; otherwise it is `propose`. Every `adopt` entry names the recommending source in `Sources`. Consequence: evidence from the reviewed workspace alone supports `propose`, not `adopt`. Of the panic-family lints, `unwrap_used`, `todo` and `unimplemented` with the test exemptions are candidates at `propose`, and `panic`, `unreachable` and `expect_used` at `situational`, because Google and Microsoft both say to panic on bugs and to use `expect` with a message.
4. The candidate entries the implementer starts from are listed in the Progress Log row "Candidate practices" with their origin. Requirement 3 decides which survive; the list is a starting point, not the contract. It covers: lint policy and exception reasons; panic-family lints by name with test exemptions; panics, `expect` and assertion messages; error types for libraries and applications; unsafe justification and FFI layout; API design (`#[must_use]`, `#[non_exhaustive]`, newtypes with fallible constructors, builders, no smart-pointer types in public signatures, `Debug` on public types with redaction for secrets); documentation sections and module docs; logging in production code; cancellation, guard lifetimes and lock poisoning; one owned process-spawning module with a deadline, drained output and whole-tree termination on Windows, macOS and Linux; workspace inheritance, manifest lints, toolchain and minimum-version pinning, additive features; dependency and source policy (advisories, licence allowlist, unknown registries and Git sources denied, Git dependencies pinned by commit, vendored patches with a removal note); a single task-runner entry point as the whole gate, including off-by-default feature passes and generated-artifact drift checks; crate layering checks; line-ending normalization for embedded files; continuous-integration actions pinned by commit; test placement and tests that restate the implementation; guidance aimed at coding agents.
5. The baseline states, at its top, how it is used: it is a menu, not a policy; a project's own record governs; an agent may propose an entry but never enables a lint, adds a tool, or creates or edits a configuration file for a practice without the operator's direction through an admitted change. This plan keeps the three decisions of closed wave `237ee`: lints are opt-in, language-neutral guidance stays in the all-stacks text, and there is no sensor or gate. They are restated, not weakened.
6. Platform statements: the `Platforms:` line of every entry whose `Touches:` is not `none` says what differs on Windows, macOS, Linux and WSL2, or says that nothing does. An entry that was verified on fewer platforms than it claims says which.
7. The project's record. For a repository where seed 222 detects Rust, the framework's guidance names one project-owned document, `docs/contributing/rust-best-practices.md`, as the project's Rust policy. The baseline gives the outline of that record in a short section, as text, so an agent can draft it. The outline keeps what makes the existing record useful:
   1. metadata lines;
   2. a preface saying that passing the checks does not establish full compliance or memory safety;
   3. the table of practice, decision (adopt, adapt, defer or decline) with the project's rationale, and verification;
   4. the mechanical checks and their limits;
   5. a review checklist per reviewer lane, recorded in the project's existing review record, with no new approval workflow;
   6. links to the project's canonical contracts.

   A project that already has this document keeps it unchanged; nothing in the framework rewrites, reorders or re-dates it.
8. Drafting the record. When seed 222's existing detection finds Rust (`Cargo.toml` and `*.rs` files) and the record is absent, the install and upgrade guidance tell the agent to report that fact and offer to draft the record from the baseline as an ordinary planned change, with every row's decision left for the operator. The report surfaces are the install seed's operator summary (seed `012-install-wavefoundry-phase-2.prompt.md`, as a bullet under an existing topic, without changing its topic count) and seed 160's operator summary. The offer is one informational line, not a step that blocks installation or upgrade, and not a new gate. That detection has no size threshold, so a repository with incidental Rust also gets the line.
9. Builder and reviewer guidance:
   1. Seed 222's Rust block, used only when Rust is detected, states the precedence: the project's record governs; where the record is silent, the project's existing configuration and dominant patterns govern; the baseline informs proposals only, and the builder consults the relevant entry through the index, not the whole document. The builder proposes (never applies) a baseline practice the record lacks. The existing workaround bullet and the opt-in lint rule stay.
   2. Seed 221's review check for statically checked languages gains one sentence for Rust: review the change against the project's record, citing the row, or state a reasoned N/A when the project has no record. A row's claimed verification is checked, not assumed from the presence of the row.
   3. Guidance that holds in any language stays in the all-stacks text; nothing Rust-specific is added there.
   4. A project's `docs/agents/software-engineer.md` is written by an agent following seed 222's generation-time instructions. No code renders it, and its content in a Rust project is observed at installs, not tested here.
10. Sources and reuse. The baseline paraphrases; it does not copy source text beyond short identifiers and lint names. It ends with a sources section giving, for each source, the title, the link, the licence and the date reviewed, with the attribution each licence requires: the Google Rust Style Guide (CC BY 3.0, attribution and a statement that the text is paraphrased and changed), Microsoft's Pragmatic Rust Guidelines (MIT, copyright notice), the Rust API Guidelines and the Clippy lint list (licences confirmed by the implementer before quoting anything). The implementer confirms each licence from the source at implementation; an unconfirmed licence means link only.
11. Currency. The baseline carries the date its sources were reviewed and says that a later change in a source is a reason for a scoped decision, not an automatic change of the baseline or of any project's record. Agents are not told to fetch any source at work time; the links are for people, and the framework stays usable offline. An agent drafting a project's record re-checks each lint it names on the project's pinned toolchain.
12. Seeds and the baseline carry no wave or change identifiers, no reference to the repositories reviewed for this plan, and no project names. Evidence from those repositories stays in this spec.

## Scope

**Problem statement:** The framework ships almost no Rust guidance, the operator's Rust policy exists in one project only, and newer public guidance and measured evidence are not reflected anywhere a new project would find them.

**In scope:**

- The new shipped document and its row in `docs/references/install-assets.md` (packaging needs no registration; see the Progress Log).
- The Rust sentences in seeds 222 and 221, the offer in seed 160 and in the install seed `012-install-wavefoundry-phase-2.prompt.md`, the seed 221 sentence in this repository's `docs/agents/code-reviewer.md`, and this repository's rendered copies of any prompt those seeds feed.
- Content tests for the baseline and the seed sentences, and the changelog.

**Out of scope:**

- Installing, generating or editing `Cargo.toml`, `clippy.toml`, `deny.toml`, `rustfmt.toml`, continuous-integration workflows or any other project file. The baseline shows settings as text.
- Any lint, sensor, gate, approval or review lane; any change to docs lint.
- Editing Tensorwell's record or any other repository. Bringing an existing record in line with the baseline is that project's own change.
- Baselines for other languages. The document is Rust only; a later language would be its own change.
- Fetching sources over the network at install, upgrade or work time.
- Rewriting the existing Python, JVM, C# or TypeScript blocks.
