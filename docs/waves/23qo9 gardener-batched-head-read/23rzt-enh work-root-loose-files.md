# Keep wave scratch inside the wave's work folder and report loose files in the work root

## Rationale

The framework gives each wave a disposable folder, `.wavefoundry/work/<wave-id>/`, and close removes that folder. The guidance says to use it for shared temporary work and to put its path in briefs. It does not say that the files an agent writes for a wave, such as coordinator briefs, build logs and test output, must be inside that folder, and it does not forbid writing files directly in the work root.

On 2026-11-18 a coordinator session wrote nine such files loose in `.wavefoundry/work/` over three waves (reviewer and implementer briefs named `<wave-id>-...md` and one build log). Close removed each wave's folder and left the loose files behind. No check showed them: `wave_work.inventory_work_root`, which feeds `wf_audit` and the close report, lists child folders only, and its docstring says "Plain files and links at the work root are skipped." The operator found the files by looking at the folder and said, quoted: "You should be working in the wave work folder not direclty in work". Asked how to make that a standing rule for every project, the operator said: "put this in the open wave."

## Product Intent

Anyone looking at a project's work root sees only per-wave folders, because agents put every file they write for a wave inside that wave's folder, where close removes it. When a file is written loose in the work root anyway, `wf_audit` and close say so by name, so it is noticed while its author still knows what it is. Before: loose files outlive their wave and no check shows them. After: the guidance states the rule, and loose files are reported. Boundaries: the report is advisory and read-only; nothing is deleted, moved or blocked.

## Requirements

1. Guidance. The "Disposable work" guidance (seed 180 and every lifecycle prompt that carries a "Disposable work" section) and the shared review-artifact guidance (seed 209, where it tells coordinators how to pass briefing packets) state the rule: every file an agent writes for a wave, including coordinator briefs, logs, captured test output and build output, goes inside that wave's own work folder, in a child folder when that helps; nothing is written directly in the work root; and before a wave exists, the content stays in task context until the lifecycle call reports the work area. The guidance also says who acts on a loose file: an agent that wrote a loose file for a wave moves it into that wave's folder while the wave is open, or deletes it; any other loose file is left in place and reported to the operator, who decides; an agent never moves a file it did not write into a wave's folder, because close removes that folder with everything in it. The existing statement that briefing packets are passed in task context stays; the new sentence covers the case where a file is written.
2. The set of prompt files to edit is derived, not listed. The rule sentence goes into each "Disposable work" section that carries the sentence telling the coordinator to include the work path in briefs, in the shipped seeds, the lifecycle templates under `.wavefoundry/framework/install/lifecycle-prompts/` and this repository's copies under `docs/prompts/`, and into seed 209's briefing-packet guidance. Sections with that heading about other matters are out of scope: the install and upgrade prompts' text about the ignore file, and the bold lead-in form in the upgrade seed. On 2026-11-18, 14 files carry the heading, and 13 of them carry the briefs sentence: seed 180, the five lifecycle templates (close, create, implement, prepare and review wave) and seven `docs/prompts/` copies (close, create, implement and prepare wave, implement spec, pause and review wave); the install prompt is the fourteenth. Copies that must stay identical to their seed stay identical.
3. Inventory. `wave_work.inventory_work_root` reports the entries directly in the work root that are not folders: each plain file and each link, with its name, its kind (`file` or `link`) and, for a file, its size from `lstat`. Links are never followed or opened. The entries count against the existing entry limit; the result gives the total count of loose entries and lists at most a number of them set by a named constant, largest files first, then links. When the listing stops at the entry limit, the loose count is a lower bound and the result says so through the existing `complete` field. Sizes are reported even when the caller asks for no measuring walk, since the listing already has them. The existing fields, their meaning and the folder classification are unchanged, and the function still never raises for file-system conditions and writes nothing.
4. Audit. `wf_audit` carries the loose entries in `data.work_root` and adds one advisory diagnostic, `work_root_loose_files`, when any exist: the count, the names shown up to the cap, and one sentence saying that wave files belong inside `.wavefoundry/work/<wave-id>/`, that an agent that wrote one of these files for a wave moves it into that wave's folder while the wave is open or deletes it, and that any other file is left in place and reported to the operator, who decides. With no loose entry the diagnostic is absent. It never changes `ready` or any other audit result.
5. Close. `wf_close_wave`, in both modes, adds the same advisory at the point where it already reports leftover work folders, and nowhere else. A close that returns before that point (for example a blocked dry run) does not carry it; `wf_audit` is the discovery point in that case, and the tool reference says so. The documentation that lists close advisories or describes the inventory changes with it, or is stated as left unchanged: in `docs/specs/mcp-tool-surface.md`, the sentence saying plain files and links at the work root are skipped, the `work_root` field list, the two lists of close advisories, and that a blocked close does not carry the advisory; the advisory list in seed 190 and in `docs/prompts/close-wave.prompt.md`; and the lists in `docs/contributing/build-and-verification.md` and `docs/architecture/data-and-control-flow.md` where they name each advisory.
6. No deletion and no new authority. Close, audit and `wf_cleanup_work` remove no loose file; `wf_cleanup_work` still accepts only a work key naming a folder. The advisory never names a tool that deletes.
7. Platform behaviour. The inventory uses the directory listing and `lstat` only, which behave the same on Windows, macOS, Linux and WSL2. A symbolic link or junction, as the existing link test recognizes them, is reported with kind `link` and not entered. Operating-system files that a file manager may create in the work root (for example `.DS_Store` or `Thumbs.db`) are reported like any other loose file; the advisory leaves them to the operator, since no agent wrote them.
8. The upgrade report, Pause, Prepare and Review are unchanged.

## Scope

**Problem statement:** Agents can write wave files loose in the work root, where close does not remove them and no check reports them, and the guidance does not say where such files belong.

**In scope:**

- The guidance sentences in seeds 180 and 209 and in the prompt files derived under requirement 2.
- The loose-entry report in `wave_work.inventory_work_root`, the `wf_audit` field and advisory, and the close advisory.
- Tests, the tool-reference entries for `wf_audit` and `wf_close_wave`, the other documents named in requirement 5, and the changelog.

**Out of scope:**

- Deleting or moving loose files, and any change to `wf_cleanup_work`.
- Refusing a write to the work root in a hook or tool. The work area is deliberately not a gate, and an unavailable wave folder is advisory.
- The upgrade report and every lifecycle tool other than audit and close.
- Files inside a wave's folder, which the existing inventory already sizes.

| --- | --- |
| The advisory is read as an instruction to delete. | It names no deleting tool, AC-4 pins that close leaves the files in place, and the advisory limits action to the file's author. |
