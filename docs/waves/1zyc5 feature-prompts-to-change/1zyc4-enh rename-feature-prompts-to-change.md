## Rationale

Waveforge, a downstream distribution, uses "feature" for a unit that sits above its "wave set". Wavefoundry's three single-change lifecycle prompts are named for "feature" (**Plan feature**, **Implement feature**, **Finalize feature**), so a Waveforge operator reading "Plan feature" cannot tell which unit is meant. The framework's own unit is already the change: seed 170 plans "a change of any kind", the `feat` change kind was retired in wave 1zli8, and `wf_new_feature` refuses. Renaming the prompts to "change" removes the conflict and matches what the prompts actually do.

"Finalize" is not lifecycle vocabulary either. The **Finalize feature** prompt (`docs/prompts/finalize-feature.prompt.md`) is a single-change alias for closing the wave: its nine steps (review lanes, council confirmation, change status, docs-contract disposition, memory propose and validate, wave-folder cleanup, `Status: completed`, handoff) are all **Close wave** closure items. Meanwhile the per-change close that does exist in code, `wf_close_change` (`.wavefoundry/framework/scripts/wf_server/server_impl.py`, `wf_close_change_response`), has no prompt or shortcut. So **Finalize feature** is replaced by a **Close change** prompt backed by `wf_close_change`, and **Close wave** stays the only wave close whatever the change count.

Code-grounded facts this plan relies on:

- `wf_close_change` gates (docstring and `wf_close_change_response`): the wave is OPEN (`active` or `implementing`); the change is admitted; its change doc exists and is readable; its status is closable (`ready`, `active`, `review`, `implemented`, derived from `wave_lint_lib/constants.py`) and agrees between wave record and change doc; it has no silent `[ ]` AC or task; every wave-record `Depends On:` dependency is done. It writes `complete` to both files, moves unblocked `planned`/`blocked` dependents to `ready`, reads and writes no review evidence, does not move the review-policy receipt, and cannot reopen a completed change.
- `wf_close_wave` blocks on `open_changes_remaining` using `DONE_CHANGE_STATUSES` (terminal statuses plus `implemented`), so a change in `implemented` does not block wave close. Close change is therefore the way to mark one change `complete` (and activate its dependents) inside an open wave; it is not a prerequisite of Close wave, and because a completed change cannot be reopened it belongs after Review wave has cleared that change.
- Target prompt surfaces are project-owned: seed 100 tells the installing agent to author `docs/prompts/plan-feature.prompt.md` etc.; only the files in `LIFECYCLE_PROMPT_BASELINES` (`render_agent_surfaces.py`) are materialized from `.wavefoundry/framework/install/lifecycle-prompts/`, missing-only. Skills are renderer-owned (`SKILL_REGISTRY`, `render_skills`), and `STALE_SKILL_PATHS` already deletes retired skill files on every render (precedent: `wf-interrogate-plan`).
- docs-lint requires `PROMPT_SURFACE_FILES` (`wave_lint_lib/constants.py`: `plan-feature`, `implement-feature`, `finalize-feature`) and fails when a `public_prompt_surface` manifest entry names a missing doc (`wave_validators.py`, "registered prompt doc ... does not exist"). A target that only received renamed constants would fail lint until its prompts move, so the migration must be deterministic, not agent-only.
- `get_prompt` (`server_impl.py`), which backs `wf_get_prompt` and `wavefoundry://prompt/{slug}`, slug-matches the stem first, then falls back to the first `docs/prompts/*.md` whose content contains the spaced phrase. A retired phrase left anywhere in `docs/prompts/` would therefore keep resolving (an accidental alias) to whichever prompt mentions it.

## Platform Behavior

- The renames change names, not case only, so case-insensitive filesystems (macOS APFS default, Windows NTFS) cannot collide old and new paths; the case-insensitive rename gate is not involved.
- The move is copy-bytes then unlink, not `os.rename`, so it behaves the same on Windows (where a rename onto an existing target fails), macOS, Linux and WSL2 (including `/mnt/c` DrvFs). Bytes are copied with no newline translation, so CRLF or LF endings survive unchanged (AC-8).
- A file locked by an editor on Windows makes the unlink fail; the migration then removes the new copy and raises, leaving the old file intact, and the operator retries.
- Symlinked or non-regular old paths are refused on every platform, as `migrate_review_plan_prompt` does.
- Manifest and scan paths stay repo-relative POSIX on all platforms. Seed renames use `git mv` and need no platform handling.
