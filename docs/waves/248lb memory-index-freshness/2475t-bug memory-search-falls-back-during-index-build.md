# Memory search keeps the published index while a build runs

Change ID: `2475t-bug memory-search-falls-back-during-index-build`
Change Status: `implemented`
Owner: Engineering
Status: implemented
Last verified: 2026-11-23
Wave: 248lb memory-index-freshness

## Rationale

Free-text `memory_search` drops to its lexical recovery path whenever any index build is in progress, even though the last published docs vectors are intact. Wave `245na` measured the effect: a 14-minute `wf_memory_eval` run through the MCP server lost 7 and then 15 of its 606 production probes to `fallback_reason: "semantic_index_unavailable"`, and a CLI run that overlapped spec edits lost 18. A CLI run with no concurrent build lost none ([245sp Progress Log](../245na%20memory-eval-production-path/245sp-enh%20memory-eval-situation-queries-and-baselines.md), entries for the live runs). An agent that calls `memory_search` during those windows receives worse results, and the eval cannot report a production number.

**Observed failure, reproduced on 2026-11-23** (`execution_status: executed`). With `index_state_store.build_epoch_token` patched to return `None`, which is what it returns while the store's `build_state.status` is `building`, a real `WaveIndex(root)` on this repository raised `IndexNotReadyError` from `_ensure_loaded`, and `memory_handlers._memory_query_records` returned `None` with `fallback_reason: "semantic_index_unavailable"`. The expected result is the screened hybrid order from the last published docs layer.

**Mechanism, verified against the tree:**

1. Every index build durably sets `build_state.status = 'building'` before its first mutation (`indexer.py`, `begin_recoverable_build_epoch` near line 5802; `index_state_store.begin_build_epoch`, line 3281). The status stays `building` through embedding, the single publication transaction (`BEGIN IMMEDIATE` near `indexer.py` line 6129) and the post-publication residents, until `finalize_build_epoch` (line 3314) sets it to `complete`.
1. `index_state_store.build_epoch_token` (line 3597) returns `None` for any status other than `complete`.
1. `WaveIndex._index_meta_signature` (`server_impl.py`, line 1789) returns the partial token only when `sqlite_vector_store.snapshot_active(index_dir)` is true, that is, inside `sqlite_vector_store.read_snapshot` (line 238). Otherwise it returns `None`.
1. `WaveIndex._ensure_loaded` (line 1815) invalidates a loaded index when the signature changes, and raises `IndexNotReadyError` when it is `None`.
1. `_memory_query_records` (`memory_handlers.py`, line 1629) calls `index._ensure_loaded()` outside any read snapshot. Its `except Exception` branch returns the initial `fallback_reason`, `semantic_index_unavailable`.
1. `docs_search` and `code_search` survive the same window because they run through `server_impl._partial_index_read` (line 5780), which wraps the whole read in `read_snapshot` (wave `215sy`). The memory path was never routed through it.

**Trigger.** Any build starts the window. In the MCP runs the likely trigger is the context-efficiency projection writing the open wave's `wave.md` (`context_efficiency_handlers.py`, `_atomic_replace_text` near line 255). The index monitor then finds the project inputs stale and starts a background refresh (`server_impl._maybe_refresh_if_stale`, line 8426). `index_build_status` showed generation 6354 completing during the second MCP run. That chain is `inferred`: the fix does not depend on which writer starts the build.

**Kind: `bug`.** Memory search was designed to use published vectors whenever they are current (`docs/architecture/search-architecture.md`, "Agent memory retrieval"); a build in progress is not a reason they are unusable. The shared path builder and the `index_health` coverage block are small supporting changes carried here because the health check is how an agent sees the state this fix depends on.

This is track 2, indexing freshness, of arc [`244cm-arc memory-quality`](../../arcs/244cm%20memory-quality/244cm-arc%20memory-quality.md). Its signals are track 1's `index_signals.memory_vector_coverage`, which must stay complete after an edit made outside the tools, and `production_retrieval.fallback_probes`, which must stay 0.

## Product Intent

**Who benefits:** agents that call `memory_search` while the MCP server refreshes the index in the background, and maintainers who run `wf_memory_eval` and `index_health`.

**Before:** a free-text `memory_search` made during any index build returns lexical results with `fallback_reason: "semantic_index_unavailable"`. `wf_memory_eval` through MCP reports `production_measured: false`. `index_health` says nothing about memory records, so an agent that runs it after `git pull`, as `AGENTS.md` asks, cannot tell whether memory search will use vectors.

**After:** during a build, memory search ranks from the last published docs layer and reports the same `index_coverage_incomplete` advisory as the other partial-read tools. It still falls back explicitly when a record's source differs from its published hash. `index_health` reports memory vector coverage with stale and missing sources counted separately. A memory record edited outside the tools reads as stale until the index monitor's refresh publishes it, then as covered.

**Boundary:** no change to ranking, the RRF fusion, the reranker threshold or admission. No change to how or when builds run. Memory search never serves a record whose published source hash differs from its file.

**First outcome:** AC-1 alone removes the measured failure, and it can ship without the health block. The operator can demonstrate it with AC-9: `wf_memory_eval` through MCP, while a background build completes during the run, reports `production_measured: true` with 0 fallback probes. AC-10 establishes the second signal, coverage after an edit outside the tools, on a temporary corpus.

## Requirements

1. `_memory_query_records` must read the index in three steps, in this order:
   1. Inside a first `sqlite_vector_store.read_snapshot(index.index_dir)` context, call `index._ensure_loaded()` and check the docs layer. Inside that context a `building` epoch with recorded docs model identity loads as the partial token, the same rule `_partial_index_read` uses. The load fills `index._meta`, from which `_get_embedder` chooses the query precision.
   1. With no snapshot active, embed the query. The query embedder must never run before the first load: on a cold `WaveIndex`, `_get_embedder` would pick full precision and cache it in `index._embedders` for the life of the process.
   1. Inside a second `read_snapshot` context, call `index._ensure_loaded()` again, then `sqlite_vector_store.dense_path_scores` with that vector. `dense_path_scores` already reads the published hashes and the vectors in one transaction.
1. `WaveIndex._memory_candidate_scores` is split so the query embedding and the dense read are separate calls, and the memory path and `memory_eval.dense_stream` both use the split form. The implementer chooses the method names.
1. No model inference runs while the memory path holds an SQLite read transaction: the query embedder and the reranker both run with no snapshot active.
1. A build that completes between the two snapshots needs no special handling. The second snapshot reads the newer published rows, the per-record hash check in `dense_path_scores` still compares every body against them, and the query precision stays the one chosen from the first load. The hash check does not detect a model change, so the second snapshot calls `index._ensure_loaded()` again before `dense_path_scores` and compares the recorded docs `model_versions` entry with the one from the first load. When they differ, as after a model-change rebuild that completed between the snapshots, the query falls back with `semantic_index_unavailable` rather than compare a vector from one model with rows from another.
1. The existing source-hash check stays the safety rule. A record whose body hash differs from its published `layer_path_state` hash in the snapshot still falls back with `memory_source_state_stale`, and incomplete vector coverage still falls back with `memory_vector_coverage_incomplete`.
1. When the dense read ran inside a snapshot of a `building` or interrupted epoch, `memory_search_response` passes its envelope through `server_impl._attach_partial_index_coverage` with tool name `memory_search`. The response then carries the same `index_coverage` object (`complete: false`) and `index_coverage_incomplete` diagnostic as `docs_search`, `code_search` and `code_ask`. The advisory is not a fallback: `retrieval.method` stays `hybrid_rrf` and `retrieval.fallback_reason` stays `null`. A result read from a complete epoch carries neither.
1. When no usable snapshot exists, the path falls back with `semantic_index_unavailable`, as today. These are fail-closed windows by design: an uninitialized store after a reset or first build, a `building` epoch with no recorded docs model identity, a model-change rebuild whose recorded identity names another model for the whole rebuild, a store that cannot be opened, and `IndexNotReadyError` inside the snapshot. A `StorageRecoveryRequired` or `RuntimeUnavailable` raised by `read_snapshot` also falls back; it is not re-raised from `memory_search`.
1. The body-path and source-hash builder moves to `memory_records.memory_body_paths(root, records)`, returning `(body_paths, expected_hashes)`:
   1. It skips `archive_register_entry` records, resolves each record path against the canonical root, keys by the POSIX repo-relative path, and hashes the file bytes with SHA-256.
   1. It raises `ValueError` for a duplicate resolved path or a path outside the root, and lets `OSError` from an unreadable body propagate.
   1. `_memory_query_records` maps `ValueError` to `memory_candidate_state_unavailable` and `OSError` to `memory_source_state_stale`.
   1. `memory_eval.memory_body_paths` is deleted and its callers use the shared function. `memory_eval` gains the duplicate-path refusal it lacked.
1. `index_health` adds a `memory` object to `data`, computed without loading `memory_eval`:
   1. `memory_vector_coverage` is `sqlite_vector_store.memory_vector_coverage(index_dir, "docs", expected_hashes)` over the records `memory_records.load_memory_records(root, statuses=list(DEFAULT_SURFACED_STATUSES))` returns, read inside one `read_snapshot`.
   1. `complete` is `true` when `covered_paths == requested_paths`.
   1. When `stale_paths` or `missing_paths` is above 0, a `memory_vector_coverage_incomplete` diagnostic names both counts, with `recovery_tools: ["index_build"]` and `recovery_usage: "index_build(content='docs', mode='update')"`.
   1. When the store or a record cannot be read, `memory` carries `memory_vector_coverage: null` and a `coverage_unavailable_reason` that is a fixed token (`store_unreadable` or `record_unreadable`), never exception text, and `index_health` still returns `status: "ok"` for its other fields.
1. `memory_search` stays read-only: the read path must not start, request or schedule an index refresh, including when it sees `memory_source_state_stale`. It reports the fallback reason and nothing else.
1. Edits outside the tools need no new trigger. The index monitor's staleness walk already covers the memory root: on 2026-11-23, `indexer.walk_repo` plus `_filter_project_index_excludes` returned 175 files under `docs/agents/memory/`, and the store's `file_meta` held the same 175 (`execution_status: executed`). The change pins that coverage with a test.
1. Implementer briefs and new test code must import server modules in the form `import wf_server.X as X`, for example `import wf_server.memory_handlers as memory_handlers`, `import wf_server.index_handlers as index_handlers` and `import wf_server.server_impl as server_impl`, never through a retired alias, so the retired-import census stays green.
1. `memory_eval.run_curated` runs its startup `index._ensure_loaded()` and docs-layer check (near line 1405) inside a `read_snapshot`, so an eval that starts during a build still runs instead of reporting `semantic index unavailable`.
1. Tests that pass a mock or stub index with no store to `memory_search_response`, `_memory_query_records` or `run_curated` patch `sqlite_vector_store.read_snapshot` to a null context (`contextlib.nullcontext`). The snapshot itself must never become optional in production code to keep those tests green. AC-1 to AC-4 use the real `read_snapshot` on a real store.
1. The change adds no file writer. `index_health`, the snapshot and the shared builder only read, so `tests/test_line_ending_census.py` needs no new classification; the implementer confirms the census passes unchanged.

## Platform Behavior

The fix uses the read path that `docs_search` already uses during builds, so its platform behavior is that path's behavior.

- **macOS and Linux:** the store runs in WAL mode. A read transaction pins the last committed state while the build process commits its publication, and neither side waits on the other. A reader holding a transaction stops a checkpoint from resetting the WAL past its mark. The memory path holds a snapshot only for the load, and then for one dense query, and runs the query embedder and the reranker with no snapshot held (Requirement 3).
- **Windows:** SQLite takes its WAL locks through `LockFileEx` on the `-shm` file, and WAL readers and the writer do not block each other there either. The read-only connection needs the `-wal` and `-shm` files to exist, which `read_snapshot` already requires for `docs_search`. No build path replaces `index.sqlite`. Two effects of a held reader remain: the WAL cannot be reset past the reader's mark, so it grows until the reader ends, and `index_state_store._delete_store_files` cannot delete a store that a reader holds open, because Windows refuses to unlink an open file; that function swallows the `OSError`, so a store reset that overlaps a reader leaves the files in place. Both effects already apply to `docs_search`. Keeping each snapshot to one short read, with no inference inside it, keeps the exposure the same as today's per-call reads.
- **WSL2:** behaves as Linux when the repository is on the Linux file system. A repository on a Windows drive mounted under `/mnt/` has unreliable SQLite file locking under any reader; this change neither improves nor worsens that.
- **Line endings:** hashes are of file bytes on the machine that built the index, so a CRLF checkout compares consistently with its own index. The change adds no writer.

| 2026-11-23 | Read the memory path through `sqlite_vector_store.read_snapshot`, the snapshot `docs_search` uses during builds. | Planner default. It reuses a shipped mechanism (wave `215sy`) and needs no new state. Efficacy: replaying the reproduction, the snapshot makes `_index_meta_signature` return the partial token, so `_ensure_loaded` loads and the dense read sees the last committed rows, which removes every `semantic_index_unavailable` probe the build window caused. It controls the outcome rather than advising. It would miss the fail-closed windows named in Requirement 7, an empty or reset store and a model-change rebuild, which correctly stay fallbacks. Measured after release by `production_retrieval.fallback_probes` in `wf_memory_eval` (AC-9). | Keep the old layer handle until the new epoch completes: `_docs_vector_layer` is only a layer-name token, not a pinned connection, so keeping it would read rows of an uncommitted or half-published epoch without a consistency guarantee. Treat `building` as servable without a snapshot: `dense_path_scores` already reads the hashes and vectors in one transaction, so the dense read is consistent either way. The snapshot's real gain is that `_ensure_loaded`'s model-identity read and the dense read see published state under one rule, and that the partial token loads at all; without it the load raises during every build. (Corrected 2026-11-23 after the red-team readiness probe showed the earlier claim, that a publication could split the hash and vector reads, was wrong.)
