## Rationale

Field feedback against v1.46.0 (item 5, first two bullets, in `.wavefoundry/work/23z45/field-feedback-v1.46.0.md`) reports two problems with the upgrade runner.

**The docs gate runs after the tree is replaced.** `upgrade_wavefoundry.py` extracts the pack (Phase 0b), renders surfaces, prunes, and only then runs `phase_docs_gate` (Phase 3). A docs-lint failure there leaves the new framework on disk with a retained upgrade lock (`failed_phase: docs_gate`). The repository is recoverable through `--resume-after-gate`, but the operator must repair documents on a half-upgraded tree, and the failure message names a flag rather than a command.

**The upgrade prints every seed diff.** `_print_change_plan` writes the full unified diff of every changed seed through `_log`, which goes to stdout and to `.wavefoundry/logs/upgrade.log`. The field run printed about 25,000 lines. The `wf_upgrade` MCP tool already caps its `output` at 60,000 characters and points at `log_path`, so an MCP caller loses most of the diff text from the response as well.

Evidence gathered on 2026-11-20 shapes the design:

- Executed: a target with one malformed document fails the installed linter before any upgrade step. In a scratch copy of the v1.45.0 tree, `docs_lint.py --read-only` with `PROJECT_ROOT` set to the copy exited 1 with four `ERROR:` lines for the added document and left `git status` unchanged. A failure that exists before the upgrade is therefore detectable on the unchanged tree.
- Executed: the incoming linter is not a valid blocking predictor on an unchanged tree. The current linter, run against scratch copies of older trees that pass their own linter, reported 5 errors on v1.43.0, v1.40.0, v1.36.0 and v1.30.0 and 27 errors on v1.20.0. Every error names a condition the upgrade itself resolves before its docs gate: `missing required Wavefoundry file` for renamed prompts, `rendered review-policy region differs`, `rendered review-protocol region differs`, and `lifecycle prompt-name migration pending`. Only the adjacent v1.45.0 tree passed. Blocking on the full incoming lint would refuse most multi-version upgrades.
- Executed: `docs_lint.py --read-only` does not exist before v1.31.0. The v1.30.0 linter rejects the flag through argparse (`unrecognized arguments: --read-only`).
- Verified by reading: the installed runner drives the upgrade in one process, and the incoming pack's `upgrade_extensions.py` is loaded from the zip and its hooks run inside that process. `post_preflight` runs before the upgrade lock is written and before extraction, and a hook that raises ends the run with exit 3 (`_run_hook`). `_check_review_plan_prompt` already blocks an upgrade this way.
- Verified by reading: `phase_dry_run` calls no `post_preflight` hook, but it does call the incoming extension's `post_extract` with `dry_run=True` for the migration preview, and it catches any exception from that call.

Evidence added by the readiness repair on 2026-11-20 narrows the design (finding ids in the Progress Log):

- Verified by reading: `post_preflight` also runs when the tree is no longer unchanged. `_pending_upgrade` lets a storage continuation, a MANIFEST retry and an index-guard restart re-enter the early phases over an already-extracted tree, and `main` then runs the hook. Executed by the red-team primer: a v1.43.0 tree carrying the current framework fails its linter with six `ERROR:` lines that the later upgrade phases repair. The pre-flight therefore runs on a fresh run only (Requirement 1).
- Executed in a scratch copy of the v1.31.0 tree (`git archive v1.31.0`, its own linter, `--read-only`, `-B`): the unchanged tree exits 0. After adding `review-evidence-protocol: 1` to the closed record `docs/waves/1293d mcp-server-foundation/wave.md` and staging one file that matches a secrets rule, it exits 1 with three `ERROR:` lines: one tagged `[secrets]`, and two that start with the closed record's path. The primer executed the same closed-record edit against v1.32.0, which passes. An installed linter can therefore fail for a closed record that the incoming release accepts, and for a secrets finding that the docs gate does not block on. The pre-flight ignores both (Requirement 1).
- Executed in a scratch root: entering and leaving `lifecycle_lock.lifecycle_publication_transaction`, which the runner holds before `phase_preflight`, leaves `.wavefoundry/lifecycle-mutation.lock` and `.wavefoundry/locks/review-evidence-adoptions.lock`. The state guarantee names them (Requirement 3).

## Product Intent

Operators and agents who upgrade a target repository benefit. Today a docs-lint failure surfaces after the framework tree is replaced, and the upgrade output buries its plan under thousands of diff lines. After this change, a docs failure that already exists in the target's live documents stops a fresh upgrade while the repository is still unchanged, with the findings and the exact command to run after the repair, and the dry run reports the same verdict beforehand. The upgrade prints a short seed summary and keeps the full diffs in a log file that the output names.

The first outcome worth delivering alone is the pre-flight (AC-1 to AC-5): it protects every target whose documents already fail lint, and it takes effect on the upgrade that installs it. The seed diff log (AC-6 to AC-8) is independent and can ship without the pre-flight.

Boundaries: the pre-flight predicts only failures that exist on the unchanged tree under the installed rules, plus one incoming rule: the control-character check from `23zl2` (AC-12). It runs on a fresh run only, never on a re-entry that finds retained upgrade state (AC-13). It ignores secrets findings and findings in closed history, which the operator cannot or need not repair before the upgrade (AC-4, AC-14). A failure that appears only after extraction, including one from any other rule the incoming version adds, still stops at the existing docs gate with a retained lock. The post-upgrade docs gate stays; the pre-flight never replaces it.

## Requirements

1. **Installed-rule pre-flight.** On a fresh run, a packaged upgrade (one that applies a pack) must run the target's installed docs linter in full, read-only mode against the unchanged tree before the upgrade lock is written and before extraction. When the linter reports at least one blocking finding, the upgrade must stop with exit 3.
   1. A run is fresh when none of three retained-state markers exists under `ctx.root`: the upgrade lock `.wavefoundry/upgrade-in-progress.json`, the MANIFEST snapshot `.wavefoundry/upgrade-manifest-old.json`, and a storage receipt `.wavefoundry/index/sqlite-migration.json` whose `state` is not `complete`. When a marker exists, or the receipt cannot be read, neither pre-flight stage runs, on an apply run or a dry run, and the upgrade proceeds under Requirement 5 with the marker as the reason. Verified by reading: the current runner reads these three in `_pending_upgrade`, and on a fresh run the current runner and both old-runner fixtures write the snapshot and the lock after the `post_preflight` hook. The runner's lifecycle transaction lock is not a marker, because the runner holds it on every run. Equality of the installed and incoming `VERSION` is not used: a partial extraction can replace the tree before `VERSION` (`inferred` by the architecture reviewer from the runner's snapshot comment).
   2. A blocking finding is a non-secrets `ERROR:` line that the hook can attribute to a live project document on the unchanged target. Classify each finding separately.
   3. The pre-flight ignores every `ERROR:` line that carries the `[secrets]` tag. The docs gate records secrets findings without blocking, and it selects them by the same tag. Executed by the code reviewer: one staged secrets match makes `docs_lint.py --read-only` exit 1 while the docs gate's lint exits 0. The tag is present in the v1.31.0 linter (executed, see the Rationale) and in the current one (read); the versions between are `inferred`. This filter on linter output is new review surface.
   4. Use the target's configured record layout and status, including nested records, closed or completed records, record archives and the memory archive. Exclude findings in any closed history. When a line has no identifiable document path, the target layout is unknown, or the record status cannot be determined, report the affected finding as indeterminate and continue. Never assume the shipped layout for a renamed target.
   5. Report the counts of ignored secrets and closed-history findings. Report unclassifiable findings with `docs_preflight_indeterminate`. Only confirmed live findings contribute to the blocking count. Preserve independently confirmed live findings in a mixed result. If none blocks the upgrade, continue to the incoming scan and the existing docs gate.
2. **Where the pre-flight runs.** The pre-flight must run from the incoming pack's `post_preflight` extension hook, so it acts on the upgrade that installs it, including when a supported older runner drives that upgrade. The hook must stay self-contained (standard library and names local to `upgrade_extensions.py`) and must read only `ctx.root` and the pack locator.
3. **State after a refusal.** After a pre-flight refusal the installed framework version must be unchanged, no upgrade lock may exist, and no file may differ from its state before the run, with three named exceptions that the run legitimately writes: files under `.wavefoundry/logs/`; the runtime lock files of the lifecycle transaction the runner holds, `.wavefoundry/lifecycle-mutation.lock` and the files under `.wavefoundry/locks/`; and the project bytecode cache under `.wavefoundry/cache/pycache/`, which the runner's own interpreter may write. The linter child must run with `-B` and without publishing scanner findings, skip-ledger entries or an audit report, so the child itself writes no bytecode and nothing outside `.wavefoundry/logs/`. Executed by the primer: with `-B` the linter leaves the tree byte-identical; without it the child wrote 124 files under the bytecode cache.
4. **Refusal message.** The refusal must carry the stable code `docs_preflight_failed`, the number of blocking findings, the findings themselves (the first 50 blocking `ERROR:` lines in linter order, then a count of the rest), a statement that the repository is unchanged, and the retry command. The retry command is the full dispatcher invocation of the same upgrade with its pack argument, rendered for the host platform: `.\.wavefoundry\bin\wf.cmd upgrade --pack <archive>` with Windows quoting when `os.name == "nt"`, and `./.wavefoundry/bin/wf upgrade --pack <archive>` with POSIX quoting otherwise. `<archive>` is the selected archive's locator when the context carries one, else the context's pack path. Verified by reading: the current runner and the v1.31.0 fixture set `ctx.selected_feature_zip`; the v1.22.0 fixture sets no locator on the context, so there the command names the runner's staged copy of the archive. The message must also name the MCP form `wf_upgrade(phase='preflight_to_docs_gate')`. The code, the count and the retry command must be part of the raised message, so they reach stderr, the upgrade log and the MCP response's `output`.
5. **Indeterminate results never block.** The pre-flight reaches a verdict only when the linter child exits and prints its `ERROR:` lines: exit 0 is a pass, and a non-zero exit with at least one `ERROR:` line is judged under Requirement 1. Every other result must let the upgrade proceed with one line that carries the code `docs_preflight_indeterminate` and names the reason: the run is not fresh (Requirement 1), the linter is missing, the installed linter rejects `--read-only` (installed versions before v1.31.0), the linter exits non-zero with no `ERROR:` line, it exceeded the time bound, or the pre-flight itself faulted.
   1. The pre-flight must catch its own faults. `_run_hook` turns any exception from a hook into exit 3, so an uncaught fault would be a refusal with no override. Only the refusal of Requirement 4 may leave the pre-flight as an exception.
   2. The pre-flight must decode the child's output as UTF-8 with replacement, so undecodable bytes cannot raise in the parent.
   3. The time bound is the project's `docs_lint.full_scan_timeout_seconds` value, or the framework default when the configuration cannot be read.
6. **No override.** A pre-flight refusal has no override flag or environment switch. The refusal happens before anything changes, and it is limited to findings in live documents on a fresh run (Requirement 1), so repairing the named documents is a remedy the operator can perform. One residual stays: an installed-linter defect that wrongly reports a live document still refuses with no override. No executed case of it is known, and Requirement 12 discloses it.
7. **Dry run reports the verdict.** A dry run of a packaged upgrade must run the same lint call and report one of three results: passed, would be refused (with the code `docs_preflight_failed`, the count and the capped findings), or indeterminate with its reason, which includes a run that is not fresh. The dry run must not change its exit code for a would-be refusal and must write nothing beyond what the pre-flight itself may write.
   1. The report must come from the incoming extension's dry-run preview path (`post_extract` with `dry_run=True`), so it appears on the dry run that precedes the installing upgrade, and it must record the result on the preview context.
   2. A runner that carries this change must read that result: when the verdict is would-be-refused, the final dry-run line must say the upgrade would be refused and must not invite the operator to run without `--dry-run`, and the dry-run summary must carry the verdict in an additive `docs_preflight` field.
   3. The dry run and the apply run must share one implementation of the lint call and its classification, and one dry run must lint once.
8. **Full resume command at the docs gate.** When the post-extraction docs gate fails, the runner's failure and cleanup messages must name the full resume command, rendered for the host platform under the same rule as Requirement 4 (`wf.cmd upgrade --resume-after-gate` on native Windows, `wf upgrade --resume-after-gate` elsewhere), together with `wf_upgrade(phase='resume_after_gate')`.
9. **Seed diff summary on stdout.** `_print_change_plan` must stop printing unified seed diffs to stdout, on an apply run and on a dry run. It must print the existing count line, then one line per changed seed with its file name, status and added and removed line counts, then the repository-relative path of the file that holds the full diffs.
10. **Seed diff file.** An apply run must write the full unified diffs, computed before extraction, to `.wavefoundry/logs/upgrade-seed-diffs.log` through the contained-file writer. A dry run must write them to `.wavefoundry/logs/upgrade-seed-diffs.preview.log` and disclose that file by path in the final line and in the summary's `preview_logs`. The dry run must not print the file's content: `phase_dry_run` prints the text of each migration preview log it lists (verified by reading), so the seed diff preview file must be kept out of that printing. The file holds plain unified diff text with no timestamp prefixes. A run with no changed seed writes no file and prints no path. A write failure prints one warning and never stops the upgrade.
11. **Diff survival.** The apply-run diff file must survive the continuation phases of the same upgrade (`--resume-after-gate`, `--update-index`, `--cleanup`), because seed 160 tells the agent to keep the pre-apply seed diff through the installing run. The next fresh upgrade run replaces it. A run that finds no changed seed, which includes a re-entry over an already-extracted tree, leaves an existing diff file untouched.
12. **Transition disclosure.** Seed 160 and the changelog must state, for the three upgrade-affecting changes of this wave, which parts act on the installing upgrade and which act one upgrade later (see the Decision Log). Each change's own Unreleased bullet carries its sentence.
    1. This change: the pre-flight, its incoming control-character scan and the dry run's verdict report act on the installing upgrade, because they run from incoming hooks. The dry run's final line and summary field, the seed diff summary and file, and the docs-gate resume text are runner code and act one upgrade later.
    2. `23zl1`: the status-block re-render runs from the incoming `pre_docs_gate` hook and acts on the installing upgrade. Its matching call in the resume branch is runner code that runs after extraction, so it also serves the installing upgrade.
    3. `23zl2`: the control-character rule blocks at the docs gate of the installing upgrade, because that gate runs the extracted linter. The pre-flight's direct call refuses before extraction on the installing upgrade when the incoming scan can be loaded; otherwise the target stops at the docs gate with a retained lock and the resume command.
    4. The text must include the sentence that the installing run printing full seed diffs, and its dry run ending with the old final line after a would-be-refused report, are expected and are not this change failing.
    5. The text must state the residual of Requirement 6: the pre-flight has no override, it excludes secrets and closed history, reports unclassifiable findings as indeterminate, and still refuses an installed-linter false positive against a confirmed live document.
13. **Platforms.** Behavior is the same on Windows, macOS, Linux and WSL2 apart from command rendering. Native Windows renders `wf.cmd` commands with Windows quoting. WSL2 is POSIX and renders `./.wavefoundry/bin/wf`, including on a `/mnt/c` checkout. The linter child runs under the runner's interpreter with captured output, so a console-free `pythonw.exe` runner on Windows needs no console.
14. **Incoming control-character scan.** On a fresh run, when the installed-rule stage produces no blocking finding, the pre-flight must call the incoming framework's control-character scan from `23zl2` directly against the unchanged tree's live documents and refuse on a finding, with the same code `docs_preflight_failed`, exit code, state guarantee and message contract as Requirements 1, 3 and 4. The message must say the finding comes from a rule the incoming version adds.
    1. The call uses the incoming pack's own function and its own scan set and history exemption, so closed history is exempt exactly as `23zl2` exempts it. The extension must not reimplement the scan, the scan set or the history predicate.
    2. This is one direct call. It adds no pre-flight-safe declaration, no registry field and no generic incoming-rule mechanism.
    3. The incoming code must be loaded from the pack without writing into the repository and without replacing modules the running runner has already imported. How it is loaded (a child process over the pack, or a private temporary copy removed on every exit path) is an implementation choice; it is `unverified` at plan time.
    4. A pack that lacks the function, a load failure, a crash or a timeout is an indeterminate result under Requirement 5 and never blocks. Judge history against the unchanged target's configured layout. Findings from paths whose live status cannot be verified, including layout mismatches between the incoming pack and the installed target, are indeterminate. Preserve any independent confirmed live finding.
    5. The dry-run report of Requirement 7 covers this result with the same three verdicts, and the scan acts on the installing upgrade under Requirement 12.
    6. `23zl2` must land the scan first and expose it as a callable that takes a repository root and returns findings.

## Scope

**Problem statement:** The upgrade discovers docs-lint failures only after it has replaced the framework tree, and it prints full seed diffs to stdout.

**In scope:**

- The installed-rule docs pre-flight in the incoming pack's `post_preflight` hook.
- The dry run's report of the pre-flight verdict.
- One direct call of the incoming control-character scan from `23zl2` in the pre-flight.
- Full resume commands in the runner's docs-gate failure messages.
- Seed diff summary on stdout, with full diffs in a log file for apply and dry-run modes.
- Seed 160, the rendered upgrade prompt in this repository, the MCP tool reference, the architecture flow and the changelog.

**Out of scope:**

- The other item-5 bullets, recorded as later follow-ups: extension module source behind `--verbose` in the dry run, `lifecycle_baseline_drift` masking, and setup checkpoint wording.
- Any other pre-flight on the incoming version's lint rules, in full or as a declared subset. The full incoming lint refuses upgrades for conditions the upgrade repairs (see the Rationale). The one exception is the direct control-character call of Requirement 14. The sibling change `23zl2-enh docs-lint-control-characters` carries no pre-flight declaration and no added registry field.
- An override for a pre-flight refusal (Requirement 6).
- A pre-flight for an upgrade from the current tree with no pack. That path loads no extension module and extracts nothing.
- Running the docs gardener in the pre-flight. The gardener writes, and the executed check found no lint failure that the gardener clears (the gardener reported nothing to do and the same errors remained).
- A flag that restores full diffs on stdout.
- Changes to the `wf_upgrade` handler's envelope or diagnostics.
