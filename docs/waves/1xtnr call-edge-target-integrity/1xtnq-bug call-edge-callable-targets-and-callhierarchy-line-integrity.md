# Call Edges Bind Only Callable Targets; Call-Hierarchy Lines Stay Inside Their File

Change ID: `1xtnq-bug call-edge-callable-targets-and-callhierarchy-line-integrity`
Change Status: `implemented`
Owner: Engineering
Status: active
Last verified: 2026-09-12
Wave: 1xtnr call-edge-target-integrity

## Rationale

A consumer field report (Java agent codebase, framework `1.24.0+ppdh`, builder version 51, 5,331 nodes / 20,489 edges) found 127 of 2,694 resolved-target `calls` edges pointing at `variable` or `constant` nodes, and 57 of those carrying `RECEIVER_RESOLVED`, the tier `code_impact` documents as the refactor-safety trust filter. The same report found `code_callhierarchy` outgoing entries naming the callee's file with the caller's call-site line, producing citations past the end of the named file.

Brief: the consumer is any agent applying the documented edge-trust policy (`code_impact`, `code_callhierarchy`, `code_risk_score`, `code_graph_path`); the goal is that a guessed `calls` edge never targets a data-only node, that `RECEIVER_RESOLVED` is never stamped on a bind that knew nothing about the receiver, and that every emitted `file:line` pair is a location inside that file. Deliverable: the repaired builder and response path, per-language fixtures, a two-sided census, and a builder-version bump. Exclusion: no new type inference beyond the Java scope-walk gap named below.

Source investigation (this repository, `graph_indexer.py` at builder 51) confirms the report and locates the mechanism. It is not Java-specific; it is the language-generic fallback that every per-language resolver falls into:

- **Every per-language receiver resolver refuses chained-call and array-index receivers** (Java `_resolve_java_receiver_type` returns `None` for `method_invocation` / `array_access` objects at `graph_indexer.py:4082`; probed with the same shapes, the Kotlin, C#, Go, Rust, Scala, Swift, TS/JS and PHP resolvers also return `None`, and Ruby, C, C++ and Objective-C have no resolver at all). Refusal is correct. The defect is what happens next.
- **The generic fallback emits the receiver expression as a call candidate.** `_ts_relation_candidates` for `relation="call"` reads the fields `("callee","function","name","object",...)` and returns every one that resolves (`graph_indexer.py:9912-9930`), and the extraction loop adds one edge per candidate (`graph_indexer.py:13778`). Probed on builder 51 with `children[0].getValue(1)` / `b.subject().authenticatedUser()` / `e.getKey()`:

| Language | Candidates emitted for `children[0].getValue(1)` | Candidates for `e.getKey()` |
| --- | --- | --- |
| Java | `getValue`, `children` (receiver base emitted via the `object` field) | `getKey`, `e` |
| PHP | `getValue`, `this-` | `getKey`, `e` |
| Go, Rust, C#, C, C++ | `children` only (member name lost) | `e.getKey` / `e-` |
| Scala, Swift | `children` (the subscript itself is walked as a call node) | `e.getKey` / `getKey` |
| Kotlin, Ruby, Objective-C | `getValue` | `getKey` |
| TS/JS | `this.children` | `e.getKey` (TS class properties are minted `function`, so the kind gate is inert for TS and Requirement 2 is the only TS protection) |

  A receiver base such as `children` or `e` is a field or a local, so when the project defines a unique symbol of that name the edge binds to a `variable`/`constant` node. This is the whole of the report's 34 `children` edges and the source of the `e`, `entry`, `out`, `url` targets.
- **The same-file promotion relabels those binds as `RECEIVER_RESOLVED`.** Wave `1p7dg` widened the v23 TS/JS symbol-table promotion to all tree-sitter languages (`graph_indexer.py:13792-13809`): in the `else` branch, any candidate that `_ts_resolve_target` binds to a non-`external::` node is promoted on the grounds that the bind is unique. Its stated safety argument was "relabel only, bind unchanged". The field data shows the bind was already wrong for receiver-bearing calls, so the relabel is what defeats the trust filter.
- **No binding site checks the target's kind.** `simple_name_index` and `qualified_index` (`graph_indexer.py:10390-10456`) are built from every node without reading `kind`; `_ts_resolve_target` / `symbol_lookup` is name-keyed. The one target-side guard, `_is_json_config_node_id` from `1wpai`, covers JSON/YAML/properties key nodes only and deliberately declined a kind gate because config keys are minted `class`. Source-declared fields, locals and constants are a different population whose kind is `variable` or `constant`, but that discriminator is only clean once node identity is: `add_node` in `_extract_tree_sitter_artifact` is first-wins on the node id, and `_TS_VARIABLE_DEFINITION_TYPES` maps a Java `field_declaration` to `variable`, so a class declaring a field and a method of the same name (builder pattern `private String name; Builder name(String n)`, or a plain `name()` getter) mints ONE node carrying the field's kind, and true method-call edges bound through the Java resolver land on it at `RECEIVER_RESOLVED`. The prepare council reproduced this with a built probe. A kind gate applied to that graph deletes true edges, and the consumer's 127/57 counts cannot separate "bound to a field" from "bound to the id a field stole from a method" until that split is measured.
- **Java's scope walk misses three declaration shapes.** `_search_java_declarations_in_scope` (`graph_indexer.py:3960`) recognises `local_variable_declaration`, `field_declaration` and `formal_parameter` only. An enhanced-for variable (`for (Map.Entry<K,V> entry : ...)`), a catch parameter, a try-with-resources resource or a typed lambda parameter is invisible, so `entry.getKey()` falls into the fallback instead of resolving to `external::Entry.getKey` and being honesty-downgraded. That is the `getKey -> ApplicationToken.getKey` and `isArray -> AstFunction.isArray` family.
- **`code_callhierarchy` outgoing entries mix two files.** `_node_entry` sets `file` from the callee node (`server_impl.py:23981-23999`); the outgoing loop then scans the caller's own file for the callee's name and copies that line and snippet onto the entry (`server_impl.py:24040-24055`). Incoming entries scan the caller's file and are consistent. The two existing line-number tests keep caller and callee in one file, so the mismatch was never exercised.

Local census on this repository (Python self-host, builder 51): zero `calls` edges target `variable`/`constant` nodes, because Python uses its own `CallCollector` path. The field oracle is the consumer's Java graph; the multi-language fixtures are the reproducible substitute.

## Requirements

1. **Callable identity first, then a callable-target gate at the guessing sites only.** (a) Scala `val_definition`/`var_definition` SHALL be added to `_TS_VARIABLE_DEFINITION_TYPES` under the same bump, because today a Scala `val` is minted `function` and no gate can tell it from a `def`. `add_node` SHALL become callable-wins on an id collision, in all three declaration orders (field before method, method before field, and constant after method, since `register_constant` writes `value` and enters `const_node_ids` after `add_node` returns and a losing constant registration SHALL do neither, so a callable node never becomes a `reads` target; when a callable replaces a previously registered constant, remove that id from `const_node_ids` and remove constant-only metadata such as `value`, with constant-before-method and method-before-constant controls): when a `function`/`class` declaration and a `variable`/`constant` declaration share a node id in one file, the node carries the callable's kind and location, so a `variable` node is only ever data. (b) A `calls` edge SHALL NOT bind by name to a project node whose `kind` is `variable` or `constant`. The discriminator SHALL be one named predicate, `graph_indexer._is_non_callable_call_target(kind)`, reading kind only, introducing no language or origin classifier, and leaving `module`-kind targets alone (3,400 `EXTRACTED` edges on this repository bind to module nodes through a different mechanism and are out of scope). It SHALL be applied at exactly the two sites where a bind is a name guess rather than a resolver result: immediately before the single return of `_resolve_external_call_target`, beside the existing `_is_json_config_node_id` guard (a refused bind leaves the original external target intact), and at the extraction-site fallback bind in `_extract_tree_sitter_artifact`'s `else` branch. `_resolve_external_call_target` receives only `simple_name_index`/`qualified_index`; the kind SHALL be read from the existing `node_map` the finalize `ctx` already carries (the same `ctx` serves the phase-1 rewrite, symbol-scoped incremental re-resolution, and `_apply_inheritance_output_passes(resolve_ctx=ctx)`), so no parallel kind map is minted. Mechanism: `_resolve_external_call_target` gains a `node_map` keyword; the guard sits beside `_is_json_config_node_id` before its single return and applies to `calls` edges only (the same function also routes `writes` and inheritance edges, which are not gated); `_resolve_fragment_edge` passes `ctx["node_map"]` as `_resolve_external_read_target` already does, `_arbitrate_static_or_inherited` passes its own `node_map` parameter, and the `resolve_ctx is None` minimal-context fallback gains `"node_map": node_map`. A missing node map SHALL be loud rather than silently inert; both are pinned by tests, including a gate-deletion mutant. At the extraction site the kind comes from `node_map[resolved]["kind"]`, which is in the closure and id-keyed (the name-keyed `symbol_lookup_kinds` misses import-alias binds). A kind-refused extraction-site bind SHALL emit no edge at all, not an `external::<name>` edge, because the refused candidate was the receiver, not a callee. Direct same-file `symbol_lookup[name]` binds in the Python `CallCollector` and the legacy `_JS_CALL_RE` path are resolver-exact rather than guesses and are NOT gated; a callable-valued Python constant (`HANDLER = build(); HANDLER()`) keeps its edge and is counted by Requirement 5.
2. **Receiver expressions are not call candidates.** In the generic fallback, a call node SHALL yield at most one callee candidate, and it SHALL be the invoked member, never the receiver expression. Concretely: when a call node exposes a member-name field (`name`, `callee`, `function`, `method`), its `object` field SHALL NOT contribute a candidate; Shapes whose callee text carries an intervening subscript or call (`x[0].m`, `x().m`, Scala `x(0).m`), where the candidate is derived from the callee expression's text, are owned by `1xtns` through its leaf-derivation rule, not here. Swift walks the subscript `children[0]` itself as a call node: its bracket suffix SHALL be inspected and no `calls` edge emitted for it. Scala `children(0)` is syntactically indistinguishable from a method call and SHALL NOT be special-cased: the edge is refused only by the Requirement 1 gate when `children` is a field, and survives when `children` is a `def`, which a positive control fixture pins.
3. **Promotion requires a known receiver.** The same-file promotion at `graph_indexer.py:13792-13809` SHALL fire only when the call node has no receiver expression, decided by one named helper `_ts_call_has_receiver(node)`: true when the call node has an `object` or PHP `scope` field, else when its callee-field child's type is not in `_TS_IDENTIFIER_TYPES` (with `scoped_identifier` treated as qualified, so Rust `a::b::c()` and PHP `A::stat()` count as receiver-bearing), else, for grammars with no callee field (Swift, Kotlin), when the first non-argument positional child is not a plain identifier, mirroring `_ts_extract_callee_positional`. A bare call is one where the helper returns false, which is what the `1p7dg` "same-file bucket" measured or when the bind came from a per-language resolver that established the receiver type. A receiver-bearing call that reached the fallback because its resolver returned `None` SHALL stay `EXTRACTED` even when the bare name is unique in the file. `RECEIVER_RESOLVED` keeps its documented meaning, "bound to a receiver-typed project node". Receiver-unknown fallback edges SHALL carry explicit extraction provenance (for example `receiver_unknown: true`) through artifact storage, fragment serialization, edge deduplication and incremental re-resolution. Every promotion point, including extraction import-target promotion and `_resolve_fragment_edge` exact cross-file promotion, SHALL respect that confidence ceiling. Missing provenance on unrelated legacy/exact paths retains existing semantics; the shared builder bump refreshes all old extraction artifacts. Where a known and unknown edge share a dedup key, only genuinely established evidence may justify a promoted edge; unknown provenance must not be lost through ordering. Add a separate-file unique-name collision control plus unchanged-file incremental re-resolution after a target edit. The per-language receiver-resolved counts will fall on consumer graphs; the `1p7dg` spike measured the same-file bucket at Java 247 and Swift 761 in 2026-06 on 1.8.1-era graphs, which are historical figures, not a baseline. The census in Requirement 7 supplies the current delta per language.
4. **Java scope walk covers the missing declaration shapes.** `_search_java_declarations_in_scope` SHALL additionally recognise `enhanced_for_statement` variables, `catch_formal_parameter`, try-with-resources `resource` declarations, and typed lambda parameters, returning the declared simple type as it does for locals. Lookup SHALL be reference-relative and lexical: select the nearest visible declaration, exclude sibling loops/catches/lambdas and declarations after the reference, and honor scope-specific resource/parameter visibility. A broad descendant search of the entire method is not sufficient. Test sibling enhanced-for loops with the same variable name and different types, catch/resource scope, typed-lambda shadowing and outer-variable controls; refuse uncertain shadowing rather than bind a different declaration. Untyped lambda parameters stay uncertain. A receiver resolved this way to a non-project type SHALL follow the existing `external::Type.method` path and the existing `_downgrade_unresolved_typed_calls` honesty pass; no new external binding branch is added.
5. **Build-time invariant, counting not dropping.** The finalize pass SHALL run the Requirement 1 predicate inside the existing final-map iteration that `_downgrade_unresolved_typed_calls` already performs, or over `calls` edges only, rather than as an additional full pass over the ~150k-edge map, and record the number of surviving non-callable targets in the finalize `stats` beside `edges_dropped_dangling`, as `non_callable_call_targets`, returned as `merge_stats` and printed on the merge line rendered by `indexer._build_graph_artifacts` (whose pin `test_finished_graph_line_reports_merge_delta_and_state_io` in `test_graph_incremental_merge` uses `assertRegex` search, so the two new counters must be appended to the pattern or the pin binds nothing). It SHALL also record `callable_wins_collisions`, the number of id collisions Requirement 1(a) resolved, with the colliding ids and their `(winner_kind, loser_kind)` pair. This counter counts callable-winning collisions only; same-kind constant/constant redeclarations are outside its population, because the swallowed method never became a row and no SQL over `index.sqlite` can recover that split after the fact. Counts are expected to be zero on this repository's rebuilt graph and non-zero on consumer Python graphs with callable-valued constants, which is normal. It SHALL NOT drop edges: after Requirement 1(a) a surviving edge is a genuine call to a callable-valued constant or a bind from an ungated exact path, which is information, not noise. This is deliberately different from the `1xtns` malformed-external-target predicate, which DROPS and counts (`malformed_external_call_targets_dropped`), because an `external::` id ending in `-` or holding an operator is not a symbol at all and can never be a true target; the finalize documentation names both counters and both dispositions side by side. The count is expected to be zero on the fixtures and on this repository except for the deliberate callable-constant fixture; tests read it from `stats`. It SHALL never raise inside a production build.
6. **Call-hierarchy location integrity.** Every `file`/`line`/`snippet` triple that `code_callhierarchy` emits on an incoming or outgoing entry SHALL describe one location inside that `file`. Outgoing entries SHALL carry `file` = the callee's file and `line` = the callee's definition line (from `source_location`), and the caller-side call site SHALL move to a nested `call_site: {file, line, snippet}` object whose `file` is the caller's file. Incoming entries SHALL gain the same `call_site` object (their existing `file`/`line` already describe the caller's file and are unchanged) so the two directions read symmetrically. On outgoing entries the top-level `snippet` SHALL be `null`; the call-site text lives only under `call_site`. Incoming entries keep their current `line`/`snippet` values (call site in the caller's file) and additionally carry `call_site` with the same values, so no incoming consumer changes. Any entry whose call site could not be located carries `call_site: null`, as `line: null` does today. The context-efficiency extractor `_context_source_paths` in `server_impl` credits an outgoing row only when top-level `snippet` is non-empty; it SHALL be extended to read `call_site.file` together with `call_site.snippet` for outgoing rows, with the outgoing case added to the `code_callhierarchy` fixture in `test_server_context_efficiency`, so nulling the top-level field does not zero source credit. A cross-file accounting assertion SHALL credit the caller and explicitly exclude the callee when no callee content was returned. External or missing definition locations remain null, never synthetic line zero. Seed `180-implement-feature` says "direct callers and callees with exact line numbers and snippets"; seed `211-guru` and its twin `docs/agents/guru.md` say outgoing entries carry "call-site line numbers and snippets" and recommend chaining `code_callhierarchy(direction="outgoing")` "for per-edge line numbers". All of these stay true through `call_site`, and the decision recorded here is (a): no seed edit; the tool-surface bullet carries the new shape and states that outgoing top-level `line` is the callee definition line, so a reader of seed 211 who wants the call site is directed to `call_site`. If implementation finds a reader-facing sentence that becomes misleading, the twins move together under `seed_edit_allowed`. The response path SHALL assert `line <= line_count(file)` for every emitted triple in tests; it is not a production check.
7. **Two-sided census, per language.** Before and after the repair, on this repository's live graph and on the synthetic multi-language fixtures (one file per language in the Rationale table), the change SHALL report: (a) `calls` edges targeting `variable`/`constant` nodes (declared false set; this repository's graph holds ZERO `variable` nodes of any language, so only the `constant` half is a live control here and the `variable` population exists on the fixtures and the consumer graph; a kinds-by-language row makes a vacuous zero visible); (b) `calls` edges targeting `function`/`class` nodes by confidence (declared positive set; any drop on this repository not attributable to Requirements 2 or 3 fails); (c) per-language edge counts by confidence on the fixtures, so the Requirement 3 demotion is visible as a number rather than a claim; (d) the `callable_wins_collisions` count and id list from Requirement 5, which is the only way to separate a bind to a field from a bind to an id a field stole from a method, since the swallowed method never became a node row; the consumer SHALL be sent a builder-52 rebuild whose merge line and collision list re-derive their 127/57, and AC-7 records that re-derivation as received or pending; (e) `reads` and `defines` edge counts before and after, expecting drops only, because a constant/function id collision flipped to `function` by Requirement 1(a) makes a unique-constant `reads` bind refuse; (f) `external::` call-target counts, so a refused bind that leaks as an external node would be visible. Both populations SHALL be re-derived from their SQL predicates at implementation time, not copied from this document. The consumer's SQL detectors are the census predicates for (a), (b), (c) and (f) and SHALL be shipped as a test helper that opens `index.sqlite` with `sqlite3.connect(path.resolve().as_uri() + "?mode=ro", uri=True)` and accepts only a path resolved under a caller-supplied root; it never writes, explicitly closes its connection, and verifies the resolved path remains beneath the supplied root before URI construction. Fixtures SHALL cover `#`, `?`, `%`, spaces and Unicode paths, assert the intended database is read and no new file is created, and cover Windows drive/UNC URI construction without claiming native execution.
8. **Builder version and mirrors.** `GRAPH_BUILDER_VERSION` in `graph_indexer.py` SHALL be bumped from `51` to `52` with a changelog line in the constant's in-code history; the pinned test `test_graph_builder_version_is_44`-family constant pin in `test_graph_indexer.py` (the `>= 23` floor test needs no change), the lint-bound claim in `docs/RELIABILITY.md` ("graph builder version `51`", the only site `docs_constants_validators._claims()` binds, so full validation fails without it), BOTH unbound mirror sites in `docs/architecture/graph-index-system.md` (the header note and the `### Versioning` block, which today still say `50` while the code says `51`, so this bump repairs an existing drift), and the CHANGELOG `Unreleased` section SHALL be updated in the same edit set as the constant, because `_CHANGELOG_CLAIM_RE` checks an Unreleased builder-version line against the live constant and a line landing first fails the docs gate. Existing persisted graphs SHALL re-extract an unchanged corpus on the bump.

## Scope

**Problem statement:** The language-generic call fallback binds receiver identifiers as callees, no binding site checks that a `calls` target is callable, the same-file promotion stamps `RECEIVER_RESOLVED` on binds that knew nothing about the receiver, Java misses three receiver declaration shapes, and `code_callhierarchy` pairs one node's file with another node's line.

**In scope:**

- The named callable-target predicate at both binding choke points, plus the finalize invariant.
- Candidate extraction for receiver-bearing calls across all tree-sitter code profiles.
- The same-file promotion gate.
- The Java scope walk for enhanced-for, catch, resource and typed-lambda declarations.
- `code_callhierarchy` entry shape (`call_site` object) in both directions, with cross-file tests.
- Per-language fixtures, the two-sided census, the builder-version bump and its mirrors, tool-surface and architecture docs, and the CHANGELOG line.

**Out of scope:**

- Chained-call recall (the outer member lost on `b.subject().authenticatedUser()` in TS/JS/Go/Rust/Scala/C#) and arrow-operator truncation in C/C++/PHP candidates (`e->getKey()` yields `e-`); both owned by `1xtns` in this wave.
- General type inference, inheritance walks, or any new cross-file binding branch.
- The `1wpai` JSON/YAML guard and `reads_config` provenance; unchanged.
- `code_callgraph` edge `line` semantics; it already reports edges rather than node-file/line pairs and is not in the report.
