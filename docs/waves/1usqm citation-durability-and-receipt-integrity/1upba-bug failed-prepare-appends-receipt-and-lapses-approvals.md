# A Readiness Approval Is Accepted Silently Against An Already-Stale Receipt

Change ID: `1upba-bug failed-prepare-appends-receipt-and-lapses-approvals`
Change Status: `implemented`
Owner: Engineering
Status: planned
Last verified: 2026-08-08
Wave: 1usqm citation-durability-and-receipt-integrity

> **The change ID and wave slug record the original hypothesis, which review falsified.** This is not a mutation-on-failure defect and nothing in the publication path is touched. Both council seats independently disproved that framing; the delivered scope is the silent acceptance of stale readiness approvals plus the missing attribution. The names are kept rather than churned so the ledger and the disproof stay linked.

## Rationale

`wf_review_event` binds a readiness approval to whatever receipt is currently in the ledger — `wf_review_event_response`, at the `readiness_approval` branch that stamps `semantic_event["policy_receipt_id"] = receipt["receipt_id"]` — and **never recomputes the policy inputs**. So when a policy input has already moved, the approval is recorded against a receipt that is already superseded-in-waiting, and the call returns `status: ok` with **zero diagnostics**. Executed:

```
[plan edit lands -> receipt_append_required already True]
wf_review_event(approval, wave-council-readiness, readiness): ok   diagnostics: []
council current? True
--> next prepare publishes the pending receipt; council current? False
```

The approval was **dead on arrival**. It can never satisfy any gate: `review_authority_projection` in `review_evidence.py` validates a readiness approval only while `approval_record["policy_receipt_id"] == current_receipt["receipt_id"]`, so either the next prepare mints the pending receipt and the approval is non-current, or no prepare runs and `review_policy_receipt_stale` blocks review and close. The system writes a permanently unusable record into an append-only authority ledger and reports success.

**Nothing tells the operator which input moved.** `prepare(mode='dry_run')`, the natural pre-flight, returns **no diagnostic** when a mint is pending; the signal exists only as `data.review_policy.receipt_append_required`, buried in the payload. `wf_mark_ac(state='~')` publishes a receipt on its success path with `status: ok` and an **empty** diagnostic list, silently moving a current council approval to non-current, with the signal buried in `data.review_receipt_refreshed`.

**Measured cost.** In wave `1ur6o` the `wave-council-readiness` readiness approval was recorded **six** times (ledger indices 1, 5, 10, 12, 14, 22). An earlier revision called indices 12 and 14 "verbatim duplicates differing only in `context_id`"; re-executed, they also differ in `observed` and `known_bad_detection_method` prose, so they are near-duplicates rather than verbatim ones. The correction is recorded rather than silently applied because it slightly weakens this paragraph's own evidence. Every one of the six receipts differs from its parent in `policy_input_digest` **only** — `evaluator_version`, `required_lanes` and `delivery_council_required` are byte-identical throughout — so each supersession was a real canonical input change that the operator was never shown.

**What this change is NOT.** An earlier revision of this plan asserted that a failing prepare mutates review authority as a side effect, and proposed suppressing that write. Both council seats disproved it by execution. Prepare appends a receipt only when `receipt_append_required` is already true; a genuine no-op prepare returns `ok`, mints nothing, and lapses nothing. **Corrected by `1urlc`, which has since SHIPPED:** a change-doc edit is not the only way to make a mint pending. Editing the canonicalizer or the extractor does it with zero document edits, so the recovery is one prepare per canonicalizer edit rather than one prepare, and `1urlc`'s canonicalizer work has already landed, so that sequencing constraint is discharged rather than pending. Prepare never invalidates a *live* approval; it materializes an invalidation the plan edit already caused. That correction is preserved in the Decision Log rather than deleted, because the rejected design was executed and found to be worse than the defect.

## Requirements

1. **A readiness approval must not be accepted silently against an already-stale receipt.** `wf_review_event` must recompute the policy inputs before binding, and when a mint is pending it must **refuse**, not warn. **Scope is every receipt-bound readiness approval, not just the council key.** the `readiness_approval` predicate in `wf_review_event_response` is true for every signoff key except `wave-council-delivery` and `operator-signoff`, so specialist lanes are receipt-bound too; the `1ur6o` ledger carries `policy_receipt_id` on `code-reviewer`, `qa-reviewer` and `release-reviewer` readiness approvals. Fixing only `wave-council-readiness` leaves half the defect shipping. **The recompute goes INSIDE `project_state_publication_lock`**, in `wf_review_event_response`'s inner `transact()`, beside the existing re-check that compares `live_receipt["receipt_id"]` against `semantic_event["policy_receipt_id"]`. That re-check compares receipt *ids*, so a supported Wavefoundry publisher that makes a mint **pending** without moving the current id can pass an outside-the-lock check; keeping the recompute inside the shared lock closes that race across cooperating lifecycle mutations. The lock already exists on the mutating path, where `transact()` is called under `project_state_publication_lock(root)` for `mode == "create"`, so this adds no new lock structure; the cost is one `_prepare_policy_state` call per readiness approval, which is a handful of file reads. **Accepted boundary:** the publication lock cannot linearize an ordinary editor, formatter, `apply_patch`, or other raw filesystem writer that does not acquire it. Such a write can land after the final policy read and before the ledger append, causing an approval call to return `ok` and append a record that the next policy-aware Prepare, review, or close gate detects as stale and blocks. In the project's mostly single-user, one-agent-per-wave operating model this requires an independent writer to hit a millisecond-scale window, so delivery review accepted the low-likelihood, bounded limitation rather than introducing a mediated/CAS authoring architecture. Refusal remains correct for every stale state positively observed by the transaction because the record is dead on arrival, because it mirrors the refusal that already ships one branch above (`review_policy_reprepare_required` when no receipt exists at all, in `wf_review_event_response`), because the recovery is a single `wf_prepare_wave(mode='ready')` call, and because an append-only ledger cannot retract a warning that was ignored.

2. **The refusal must fire only on a positive determination of staleness, and the degradation must not become a bypass.** `_prepare_policy_state` has **four** `(None, errors)` returns. **Two** are reachable at this check — the `normalize_wave_review_policy` config branch, and the shared change-document branch, which carries both read/decode failures (`OSError`/`UnicodeError` on `path.read_bytes()`) and `ambiguous_excluded_headings(text)` results from `gardener_metadata.py`, added by the shipped sibling `1urlc` and firing when `## Progress Log` or `## Session Handoff` appears more than once outside a fence. Those two returns carry **three distinguishable causes**. The other two returns — ledger parse errors and record-validation errors — are already refused earlier by `validate_external_review_evidence` at the top of `transact()`.

   **The third cause is why this requirement cannot degrade on `errors` as a whole.** Read failures and ambiguous headings append into the *same* `errors` list and reach the *same* `return None, tuple(errors)`, but they are opposite in kind. A read failure is environmental; an ambiguous heading is an **authoring defect with a one-line fix that any author can reach by typing a second `## Progress Log` heading**. Degrading the whole branch would let an author silently disable the entire staleness check for their own wave — a bypass reachable by ordinary authoring, inside the very requirement whose stated purpose is that the degradation must not become a bypass. An earlier revision of this plan censused only two causes and would have shipped exactly that hole.

   - **Change-doc read and decode errors degrade to a warning.** An unparseable plan must never make approvals unrecordable.
   - **Ambiguous excluded headings REFUSE.** The condition is author-caused, author-fixable, and self-inflicted on the wave that would benefit from the bypass. The refusal names the offending heading and document so the fix is one edit.
   - **Config errors REFUSE.** Degrading on a malformed `wave_review` config would turn one bad config into a global, config-controlled bypass of this entire change. State the consequence plainly rather than discovering it in the field: one bad config makes **every** readiness approval unrecordable repository-wide until it is fixed. That is accepted because the recovery is operator-controlled and `_wave_review_policy_diagnostics(root)` already surfaces config errors at review and close, but the refusal message must name the **specific** config error so the operator knows what to repair instead of reading a bare staleness refusal.
   - `_prepare_policy_state` can also return `(None, ())` — state absent with an **empty** error tuple, from the same `normalize_wave_review_policy` branch. An implementation branching on `errors` alone mishandles it, so this case must be handled and pinned explicitly.

3. **Every staleness signal must name what moved, within what the data supports.** A bare diagnostic code reproduces the confusion this change exists to remove. Four surfaces carry the shared attribution payload: the Requirement 1 refusal, the Requirement 4 dry-run diagnostic, `review_policy_receipt_stale` as emitted from `_review_policy_receipt_diagnostics`, and the Requirement 5 `wf_mark_ac` signal. The payload is the current receipt id, the pending receipt id, the differing `receipt_semantic_fields`, and the list of admitted change ids whose canonical bytes were digested.

   **The full payload is only constructible at one of the three `review_policy_receipt_stale` emit sites, and the requirement says which.** `_review_policy_receipt_diagnostics` emits that code from three places with different data in hand: the **error loop**, where `state is None` so there is no current receipt, no pending receipt and no semantic fields; the **roster-drift** site, where state exists but `receipt_append_required` may be false so there is no distinct pending receipt id; and the **`receipt_append_required`** site, which has full data. The payload-bearing site is the third. The error-loop site carries the reason the check could not be performed, and the roster-drift site carries the current receipt id and the drifted roster. An earlier revision demanded the full payload on all three, which is not implementable and would have been resolved by an implementer inventing placeholder values.

   **Per-document attribution is NOT available and this change does not add it.** The per-change `sha256` values are computed into a local `change_inputs` list inside `_prepare_policy_state` and discarded; `policy_input_digest` is a single SHA over the whole payload; and `validate_policy_receipt` enforces a closed field set, so the map cannot be persisted without widening the validator and bumping `evaluator_version`. Declined because Requirement 6 freezes the publication path and the validator widening is out of scope, **not** on transition cost: `REVIEW_POLICY_EVALUATOR_VERSION` is already `7` from the shipped sibling `1urlc`, and that bump is unreleased (no `v1.15.5` tag), so the global supersession has already been incurred within this same version. See the Decision Log, where the superseded transition-cost argument is recorded as withdrawn rather than deleted. The signal must therefore say which inputs were digested, and must not imply it knows which one changed.

4. **`prepare(mode='dry_run')` must surface a pending mint as a diagnostic** and must continue to write nothing. Dry-run is the affordance an operator reaches for before mutating and is currently the one surface silent about the mutation it previews. **This is wiring, not a new diagnostic.** `_review_policy_receipt_diagnostics` already emits `review_policy_receipt_stale` when `state["receipt_append_required"]` is true, and is already wired into the review, close and implement gates; prepare simply does not call it. Stated because an earlier revision read as specifying new behavior and would have invited a parallel second implementation of a diagnostic that already ships.

5. **`wf_mark_ac(state='~')` must not lapse a current readiness approval silently.** The handler is `_mark_change_item_response` — **not** `wf_mark_ac_response`, which does not exist anywhere in the repository; an earlier revision of this plan cited that non-existent symbol, which on a wave whose sibling change exists to make cited symbols resolvable is a self-violation, and is recorded rather than quietly corrected. Two structural consequences follow from the real symbol: it is **shared with `wf_mark_task`**, so any diagnostic added there is reachable from both tools and the tests must say which; and its publication path is already gated by `refresh_receipt` requiring `target_section == "Acceptance Criteria"`, so the scoping to ACs is structural and the implementer must not add a second guard for it. Its deferral path publishes a receipt on its success path and returns `ok` with an empty diagnostic list. This is the same defect class as Requirement 1 on a different surface. Its *write* is correct and stays; only the silence is in scope. It carries the same Requirement 3 attribution payload, because Requirement 5 calls it the same defect class and exempting it from the remedy would be inconsistent.

6. **Nothing in the publication path changes.** No write is suppressed, deferred, or reordered. This is a hard boundary, not a preference: both council seats executed the suppression design and found it either readies the wave on an approval bound to plan bytes that no longer exist, with a required lane and the delivery Council silently dropped, or refuses idempotently and wedges the receipt forever with no operator affordance to advance it. `wf_prepare_wave` has no force or confirm parameter, and adding one is a public MCP tool-surface change.

7. **The genesis path must keep working**, and is protected here by construction rather than by care: since no write moves, a new declared wave's first `prepare(mode='ready')` still returns `missing_wave_council_signoff` **and** still publishes the first receipt. The genesis fixture in `TypedExclusiveGateDerivationTests` (`tests/test_server_tools.py`), whose setup comment reads "Prepare first publishes the server-owned policy receipt/roster. The expected missing-approval result is still a successful publication boundary; readiness actors can only approve that current receipt.", must pass unmodified. Recorded because it is what killed the original design: `wf_review_event` refuses a readiness approval when no receipt exists, so withholding the genesis receipt makes readiness approval unrecordable and prepare permanently unsatisfiable.

8. **No approval-binding change ships.** Rebinding from `receipt_id` to `policy_input_digest` is declined on measurement. All six `1ur6o` receipts differ only in `policy_input_digest`, so digest binding would have lapsed at exactly the same six points and fixed nothing observed. It also reintroduces **approval revival**: `derive_receipt_id` hashes the semantic fields together with the parent receipt id, so an A → B → A' cycle yields three distinct ids (executed: `c3f25fc3…`, `4de83a71…`, `5103590b…`) and cannot resurrect the first approval, whereas a raw digest collides on the first and third. Separately, `receipt_semantic_fields` carries `required_lanes` and `delivery_council_required`, so a roster could in principle grow with the digest static; that argument is **defense-in-depth, not measured**, because every selector input is also a digest input and the state is reachable only via a selector code change that does not bump `evaluator_version`.

9. **The refusal must never leave the close gate more permissive than the silent accept it replaces.** `_required_wave_council_signoffs` is deliberately three-way under `transition_policy: applies-from-next-prepare`, which is the framework default (`seeds/007-review-system-overview.md`) and live in this repository (`docs/workflow-config.json`): a **stale** readiness approval keeps the key required, an **absent** one **drops it from the close roster**. The refusal converts stale into absent, so today's defect is accidentally self-healing and this change would remove that healing. Executed: after the very prepare the refusal instructs, the close roster falls from `['wave-council-readiness','wave-council-delivery']` to `['wave-council-delivery']`, with no residual blocking diagnostic. An operator who tries to do the right thing must not end up with weaker review than one who never tries.

   **The close branch has TWO exits that drop the readiness key, and the remedy governs both.** `_required_wave_council_signoffs`'s close branch is:

   ```python
   if prepare_signoff_recorded:
       return required                                     # A
   if has_review_signoff and review_key:
       return [review_key]                                 # B — drops prepare_key
   return [key for key in required if key != prepare_key]  # C — drops prepare_key
   ```

   An earlier revision of this requirement described a single carve-out and would have been implemented against **C** alone, leaving **B** shipping the inversion. **B is not a corner case: it is the normal end-state** of a wave whose readiness approval this change refuses and which then completes delivery review. Executed against the real handlers using the `WaveCouncilPolicyTests` fixture: with a receipt present, no readiness approval, and a **current delivery approval**, the close branch takes **B** and returns `['wave-council-delivery']` — strictly more permissive than today's silent accept, which yields both keys via **A**. Every fixture listed in AC-9's earlier form lacked a current delivery approval, so the fix would have shipped green with the inversion intact.

   **Remedy:** condition the carve-out on the wave never having been prepared under the policy rather than on approval absence — fire it only when `current_policy_receipt(records) is None` **and** `not authority.ledger_errors` — and apply that predicate to **both** exits B and C, not only the fallthrough. The second conjunct is not optional: `resolve_review_authority` leaves `records` empty whenever `result.errors` is non-empty, so a receipt check alone would treat a corrupt ledger as "never prepared" and drop the readiness key, which is fail-open inside a fail-closed design. `ReviewAuthority.ledger_errors` exists and is populated by `resolve_review_authority`, and `authority` is **already in scope** at the close branch of `_required_wave_council_signoffs`, so the predicate is exactly `current_policy_receipt(authority.records) is None and not authority.ledger_errors` — which also avoids adding a second ledger read on the close path. This is a **gate read**, not the publication path, so Requirement 6's boundary is unaffected.

   **This moves the code toward its documented contract, though not all the way to it.** Seed 007 states that closure "does not retroactively require a missing readiness signoff for a wave that **never re-entered `Prepare wave`**". Receipt presence encodes that far better than approval absence does, which is why the current predicate produces the inversion. **It does not encode it exactly, and an earlier revision's claim that it does so "faithfully" is withdrawn:** the architecture lane executed the counterexample — `wf_mark_ac(state='~')` is a second receipt writer, so one AC deferral on a never-prepared wave mints from an empty ledger and re-arms the readiness key. This plan records that second writer twice and then relied on a sole-writer assumption anyway. The gap is recoverable (one prepare plus one approval) and every other population was censused unaffected, so it ships with the discrepancy named rather than hidden; reconciling seed 007's wording to the implemented rule is a follow-up.

   **It is a deliberate, recorded behavior change to a pinned test.** `test_transition_policy_distinguishes_stale_absent_and_current_readiness` in `tests/test_server_tools.py` builds its `"absent"` fixture by publishing a receipt for **every** state and skipping only the approval, so that fixture has a receipt and today asserts `['wave-council-delivery']`. Under this remedy it must assert `['wave-council-readiness','wave-council-delivery']`, and a **sibling case must be added** pinning that a wave with **no** receipt still drops the key. Without saying so, AC-9 and AC-11 are in direct collision.

   **The amendment is continuous with that test's own governing principle, not a reversal of it.** Wave `1tsyx`'s change doc (`docs/waves/1tsyx review-lifecycle-simplification/1tr85-enh single-pass-review-lifecycle.md`) states it verbatim: *"A stale approval must block; it must never relax a requirement."* `1tsyx` fixed the stale case and left absent relaxing, because at that time absence implied "in flight from before the policy". This change's refusal makes absence reachable for **governed** waves, so extending the same principle to absent-with-a-receipt carries `1tsyx`'s intent forward. Measured blast radius: exactly **one** deviation across 1605 tests in `tests.test_server_tools`.

## Scope

**Problem statement:** The review ledger accepts readiness approvals that can never satisfy a gate, reports success for them, and never tells the operator which policy input moved — so the only visible symptom is having to record the same approval repeatedly, with no way to tell a live approval from a dead one.

**In scope:**

- Recomputing policy inputs in `wf_review_event`'s readiness-approval path and refusing a stale bind, with the malformed-input degradation.
- Attribution content shared by all four signal surfaces: the refusal, the dry-run diagnostic, `review_policy_receipt_stale` from `_review_policy_receipt_diagnostics`, and `wf_mark_ac`.
- A `review_policy_receipt_stale` diagnostic on `prepare(mode='dry_run')`.
- Surfacing `wf_mark_ac(state='~')`'s receipt supersession as a diagnostic rather than a payload field.
- The close-roster carve-out condition inside `_required_wave_council_signoffs` (Requirement 9). A gate read, not a write.

**Out of scope:**

- Any change to when or whether a receipt is written (Requirement 6).
- Linearizing readiness approval against arbitrary raw filesystem edits. The shared publication lock serializes cooperating Wavefoundry mutations; an unmediated editor write is detected by the next policy-aware gate. A lock-aware/CAS change-document mutation surface is a follow-up only if concurrent authoring becomes a supported operating model.
- Rebinding approvals to `policy_input_digest` (Requirement 8).
- The digest canonicalizer. Wave `1ugk9` owns `canonical_review_policy_body`; this change must not move what is digested.
- Repairing `docs/architecture/data-and-control-flow.md` (line 476-477, prose with no containing symbol) ("Prepare is the sole writer of… the append-only `review_policy_receipt`"), which is **already false** — `wf_mark_ac` mints from an empty ledger, executed. Pre-existing drift, recorded here because this plan declares that doc affected; it needs its own change.

## Acceptance Criteria

Current code returns `ok` with zero diagnostics and must fail this test.
