## Rationale

ADR `1z9df-adr psutil-process-info` decided that process information in tool-environment code comes from `psutil`, a required dependency, through one module. Today four pid-liveness copies, three command-line readers and a zombie check each query the operating system by hand. On native Windows, which enterprise consumers use heavily, they spawn `tasklist` (three copies with no timeout) and PowerShell CIM queries that have never run on a real Windows host in CI, and one `index_build_status` call can spawn several of them in series. The copies also disagree: the MCP server's copy has no zombie check and treats a process it may not signal as dead. This change adds `psutil` as a required dependency (like `apsw` and `sqlite-vec`) and the module, moves the tool-environment callers onto it and deletes their hand-rolled queries, so that follow-ups (CR-L1, change `1zc7k`) can rely on process identity on every platform.

## Requirements

1. **Dependency.** `psutil` is added to `setup_requirements.REQUIRED_IMPORTS` and to `pyproject.toml` `[project].dependencies` with the same spec: a floor at a release older than the 21-day package-age cutoff with abi3 wheels for Windows, macOS and Linux, and a cap below the next major version. A test pins the spec in both files, modelled on `test_mcp_is_pinned_below_2_in_every_declaration`. A census test asserts `REQUIRED_IMPORTS` and `pyproject.toml` agree, with the two known differences (`networkx>=3.0` only in `REQUIRED_IMPORTS`, `packaging>=24` only in `pyproject.toml`) allowlisted by name.
2. **Module.** A new flat `scripts/process_info.py`. Every caller uses a plain `import process_info` (never `_load_script`), so there is one module instance and one test seam.
   - **Required, like `apsw`.** `psutil` is imported inside a loader function so that importing `process_info` never fails; the first call that needs `psutil` raises `ProcessInfoUnavailable` (a typed error whose message names `wf setup`) when the import fails for any reason or the loaded version is below the declared floor. There is no hand-rolled fallback. A failed import is not cached, and the loader calls `importlib.invalidate_caches()` before retrying, so a server started before `wf setup` installs `psutil` (including into an existing site-packages directory) works on the next call without a restart. Concurrent first calls are safe. The loader is the seam tests patch to supply a fake or failing `psutil`.
   - **Every `psutil` call is guarded**: `NoSuchProcess` and `ZombieProcess` map to dead or `None`, `AccessDenied` to unknown or `None` (except as stated below), and any other `Exception` to unknown or `None`. Apart from `ProcessInfoUnavailable`, nothing in the module raises to a caller.
   - **API** (read-only queries only):
     - `pid_state(pid) -> "alive" | "dead" | "unknown"`: `pid <= 0` is dead before any `psutil` call; an absent process is dead; existence proven but a follow-up probe failed is alive; on Windows `AccessDenied` after existence is proven is alive. Zombie status is not folded into this answer.
     - `is_zombie(pid) -> bool | None`: `Process(pid).status() == STATUS_ZOMBIE`; absent is False; `AccessDenied` None; Windows False.
     - `cmdline(pid) -> str | None`, rendered exactly like today's sources, because `index_handlers._index_builder_cmdline_targets_root`, `_is_setup_entry_cmdline` and the lock classifier parse it: POSIX `" ".join(argv)` (as `ps -o args=` prints), Windows `subprocess.list2cmdline(argv)`.
     - `cwd(pid) -> Path | None` and `create_time(pid) -> float | None`.
   - It never decides policy: callers map "unknown" and "unavailable". It behaves the same on Windows, macOS, Linux and WSL2 (WSL2 is Linux to `psutil`).
3. **Callers that move** (tool environment only; each keeps its function name as a thin wrapper, so existing name-keyed test patches keep working; their `tasklist`, `ps` and PowerShell code is deleted):
   - `indexer._process_is_zombie` is `process_info.is_zombie(pid) is True`. `indexer._pid_is_running` maps `pid_state` alive to True, dead to False and unknown to True, then applies `and not _process_is_zombie(pid)` through the module-global name. The only behaviour change: a POSIX `OSError` other than `ESRCH`/`EPERM` (not reachable in practice) now reads live, the safe direction for lock reclaim.
   - `indexer._process_cmdline` is `process_info.cmdline`; `None` stays "unverifiable" for `_pid_is_index_builder` and `_pid_is_live_index_build`.
   - `wf_server/server_impl._pid_is_running`: alive True, dead False, unknown True, and a zombie False. This deliberately aligns the MCP server with the indexer (today it treats `EPERM` as dead and a zombie as alive). Because a pid recycled to another user's process now reads as running, the two call sites that do not check a command line, `index_handlers._index_build_active` and the foreground branch of `index_build_status_response`, also reject a pid whose `process_info.create_time(pid)` is more than 2 seconds after the recorded `started_at` (skipped when either is unknown). `dashboard_handlers._terminate_dashboard_pid` moves its `WNOHANG` `waitpid` ahead of the liveness check in both loops, so a zombie child is reaped before it reads as gone.
   - **When `psutil` is unavailable, liveness reads "not running" everywhere (single rule).** The liveness wrappers (`server_impl._pid_is_running`, `indexer._pid_is_running`, `indexer._process_is_zombie`, `indexer._process_cmdline`) catch `ProcessInfoUnavailable` and answer not running (`False`; `None` for the command line, which `_pid_is_index_builder` already treats as unverifiable). Correctness never depends on these answers: the operating-system locks in `runtime_lock` (POSIX record locks, Windows `msvcrt` byte locks) remain the only authority for index builds, upgrades and the dashboard, so every build and refresh path (`index_build`'s pre-spawn check, the edit hook's coalesce check, the refresh after a successful write, the quiet-period monitor, `_index_build_lock` itself) proceeds to the lock, which refuses a genuinely concurrent run exactly as today. No caller needs its own handling, and no tool that has already written returns an error. Two places decided by liveness instead of a lock and now ask the lock first: `index_handlers._index_build_active` returns active when `_index_build_lock_info(root).get("held") is True` (the same probe and `except` as `_background_refresh_active`), so a held lock yields `already_running` before `run_index_rebuild` touches the build log or `index-build.json`; and `wf_stop_dashboard_response` never deletes the metadata file, because it is the dashboard server's lifetime lock carrier (a dashboard that locked it between a check and a delete would keep a deleted inode while a second dashboard locked a fresh file). On both clearing paths (the already-stopped branch and the after-stop branch) stop takes the same lock itself, non-blocking (`RuntimeFileLock` on the metadata file at `dashboard_lib._LOCK_BYTE_OFFSET`, as `dashboard_lock` takes it), rewrites the metadata to `{}` in place while holding it, and releases; while stop holds it no dashboard can start. In the after-stop branch a busy lock is retried every 0.1 s for up to 2 s (the operating system may still be closing the stopped process's handles). When the lock stays held, or cannot be taken (`RuntimeLockError`, for example a read-only or otherwise unreadable carrier), the metadata is left untouched and stop reports shutdown unverified (`dashboard_lock_unverified`) with `stopped: False` and `already_stopped: False`; the diagnostic names the lock carrier path and its state and gives the remedy: stop the dashboard process manually, or restore write permission on `.wavefoundry/locks/dashboard-server.lock`, after which a later start succeeds. `wf_restart_dashboard_response` already refuses to start unless stop returned `stopped` or `already_stopped`, and the upgrade runtime-lock cutover (`upgrade_extensions._stop_dashboard_for_lock_cutover`) refuses to cut over, so neither launches a second dashboard in that state. On POSIX, `_terminate_dashboard_pid` confirms exit with `os.waitpid(WNOHANG)` or `os.kill(pid, 0)` (no `psutil`) rather than `_pid_is_running`, so SIGKILL escalation still happens. `process_info.create_time` is called only after `_pid_is_running(pid)` is True, and `ProcessInfoUnavailable` there skips the create-time guard. The remaining cost is reporting only: until `wf setup` runs, status can show a live build as not running, and a live dashboard that does not answer its URL may be restarted as an orphan (it is still verified as this repository's dashboard).
   - **Unavailability is reported loudly instead.** `index_health`, `index_build_status` and `wf_server_info` add a `process_info_unavailable` diagnostic whose message and recovery action recommend running `wf setup` (it names the import error), shown whenever the loader cannot import `psutil`, including when package metadata says it is installed (for example a Windows policy blocking its extension).
4. **Code that stays standard-library and never imports `psutil` or `process_info`**: `venv_bootstrap.py`, `setup_requirements.py`, `setup_readiness.py`, `setup_index.py`, `setup_wavefoundry.py`, `setup_reconciliation.py`, `upgrade_lib.py`, `dashboard_lib.py` (the upgrade runner calls its dashboard scan before dependencies are installed), `sqlite_storage_migration.py` (`_host_is_running`, `discover_hosts`, `_process_cwds`), every module in `upgrade_protocol.MANDATORY_FEATURE_MODULES`, and the macOS performance-core helpers. These keep their current code. A test asserts none of these files directly imports `psutil` anywhere (the upgrade import check walks function-local imports too) and none directly imports `process_info` at module level; transitive imports (for example `dashboard_lib` importing `server`) are harmless because importing `process_info` never fails. A function-local `import process_info` is allowed only in code that runs after `ensure_deps` (change `1zc7k` needs one in `setup_index` after its dependency step); that part is a review rule, not a mechanical check. `process_info` itself imports `psutil` only inside the loader.
5. **Bounded remaining subprocesses.** `upgrade_lib._pid_is_running` gains a module-level getattr `_run_tree_kill` resolver (the old-runner-safe pattern), its `tasklist` call a timeout, and `TimeoutExpired` maps to running, so the upgrade lock is never judged stale on "can't tell". `dashboard_lib`'s `ps -axww` scan gets a timeout. The tree-kill census (`tests/test_tree_kill_routing.py`) lists `upgrade_lib` in `RESOLVER_MODULES` and removes the keys for the deleted indexer calls.
6. **Readiness and visibility.** `setup_readiness` reports a missing `psutil` from `REQUIRED_IMPORTS` with no code change. Because readiness reads package metadata without importing, `index_health` also reports `process_info_unavailable` when `psutil` is installed but cannot be imported (for example a Windows policy blocking its extension), and `wf_server_info` reports the loaded `psutil` version. `process_info.py` joins `setup_readiness.SOURCE_FILES` (stale loaded code detection). Like `runtime_lock`, it is a plain-imported flat module that `wf_reload_mcp` does not reload (the reload purges only the script cache and `wave_lint_lib` and reloads `server_impl`), so a change to `process_info.py` takes effect after an MCP server restart; `SOURCE_FILES` makes the stale module visible, and the readiness notice names the restart. It is not an index producer and does not join `index_compatibility`.
7. **Docs.** `docs/references/native-windows-support.md` replaces the `tasklist`/CIM description (and its stale line references) with `process_info`, including the blocked-extension case; `docs/architecture/cross-cutting-concerns.md` names `process_info` as the single process-information seam; `native-windows-support.md` also states that application control (AppLocker/WDAC) must allow `_psutil_windows.pyd` in the tool environment, as it already must allow the `apsw` and `sqlite-vec` extensions. CHANGELOG Changed entry with operator notes: `wf setup` or the upgrade installs `psutil`, and until then readiness reports `dependencies_missing`, `index_health`, `index_build_status` and `wf_server_info` report `process_info_unavailable` recommending `wf setup`, index builds still run (the OS locks stay authoritative), and status may show a live build as not running; an offline upgrade stops at the index-update phase until `psutil` can be installed, and air-gapped sites can pre-stage the wheel (for example `pip download` of the pinned version into a local index); the MCP server now treats a process it may not signal as running.

## Scope

**Problem statement:** process information is queried by hand in several diverging copies, with untested Windows branches and untimed subprocesses on the MCP status path, and no way to read a Windows process's identity.

**In scope:**

- The dependency declaration and its tests; `process_info.py` and its tests; the moved callers in `server_impl`, `indexer`, `index_handlers` and `dashboard_handlers`, with their hand-rolled queries deleted; `upgrade_lib` and `dashboard_lib` timeouts; census, visibility and doc updates above.

**Out of scope:**

- Recording process identity in the build pid stamp (change `1zc7k`, next wave).
- Moving any pre-dependency or old-runner code onto `psutil`.
- Process control (`taskkill /T`, `killpg`) and the core-count helpers.

| Risk | Mitigation |
