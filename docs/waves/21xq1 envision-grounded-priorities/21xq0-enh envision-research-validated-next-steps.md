## Rationale

The Envision discussion produced recommendations to add project takeover and cross-agent handover even though the operator reports both working well. The workflow must use existing capability and operator experience before recommending work, and must turn relevant external research into a credible path to the product destination. The operator requests architecture, security, modernization, reliability and performance advances where they support that destination, including investigation of whether a burdensome interpreted runtime should evolve toward a compiled implementation. This change improves generic Envision guidance; it does not decide a Wavefoundry language migration. The later operator request also asks to re-envision Wavefoundry and update its creating guidance: the root author owns that separately authorized vision revision; this framework worker owns reusable instructions and their delivery.

## Product Intent

For operators developing a product vision, Envision should produce evidence-grounded immediate priorities that extend working strengths, address consequential gaps and include enabling technical changes when justified. A reader can distinguish what already works, what is missing, what needs investigation and why the next advances help achieve the destination. AC-2 and AC-3 test this outcome in bounded authored examples. The added AC-5 tests whether a reader can distinguish a transformative destination, unresolved breakthroughs and the useful path without mistaking a first investment for the destination. Text/parity checks alone do not establish behavioral improvement; no superiority or measured ambition effect is claimed.

## Requirements

1. Make research a deliberate part of grounding: use relevant available products, approaches, practitioner lessons, successes and failures; record dates/sources, evidence type, limitations and implications for choices. Reuse adequate current research, scale depth to stakes and uncertainty, and distinguish public research from customer validation. Preserve local-only and read-only boundaries; external access follows existing authorization, and missing access yields explicit gaps rather than fabricated research.
2. Before recommending immediate work, validate relevant existing capabilities using repository evidence, operating artifacts and operator experience. Distinguish already working, working with limitations, genuinely missing, and not yet established. Attribute operator reports honestly; lack of broad evaluation is not evidence that a working capability is absent. Resolve material contradictions or preserve them as uncertainty. Do not repeat broad installation or source audits without a decision-relevant reason.
3. Deliver a concise, ordered set of immediate advances tied to the destination and horizons. State the observed problem or opportunity, current capability, incremental outcome, why now, dependencies and evidence for continuing or reconsidering. Distinguish preserving, extending, investigating/validating and building capabilities. Choose a useful number, not a mandatory three-item quota; keep detailed tickets and automatic implementation outside Envision.
4. Consider architectural, security, modernization, reliability and performance constraints alongside product, adoption and nontechnical work where consequential. Connect proposed work to beneficiary value and a horizon; no mandatory item per category or unsolicited whole-project audit. Meaningful existing strengths are foundations, not shortcomings to recreate.
5. For substantial technical shifts such as runtime/language replacement, separate reported burden from established cause; use available workload, latency, memory, failure, deployment and maintenance evidence as applicable. Compare retaining/tuning the current design, a targeted component replacement or integration, and broader migration where credible. Assess compatibility, support, operational complexity, migration cost and a useful incremental path. Recommend a benchmark/prototype when evidence is insufficient and a bounded migration when supported; neither assume compilation guarantees improvement nor prohibit ambitious architectural change. This is generic guidance, not a Python/Rust/Go verdict.
6. Keep the destination and long-horizon roadmap primary. Integrate a compact capability assessment and immediate-priority synthesis into the existing argument; use an optional research companion when substantial, preserve existing artifacts and honor response-only requests. No new mandatory trackers, specialist reviews, permissions, lifecycle authority or fixed prompt-length ceiling.
7. Deliver canonical guidance in seed 179 and matching local prompt; reconcile affected upgrade guidance only if required for the changed contract, using the existing seed-179 merge mechanism. Preserve skill thin pointers, registrations, adoption semantics, ambition protection and review protocols. Update architecture description and unreleased changelog consistently. Report before/after prompt word count and what added text buys.

8. Distinguish a bold beneficiary-facing product destination and transformative capacity, unresolved breakthroughs or research bets, and a useful staged path. Missing present proof is not disproof of ambition: calibrate claims about current capability and the route while keeping genuine contrary evidence visible; strategic changes of destination return to the operator. A bounded first advance must not replace the ultimate destination. When reopening an early vision, retain valuable ambition as an explicit option rather than interpret permission to revise as permission to shrink; synthesize newly clarified beneficiaries or uses at the product-purpose level. Keep examples generic and do not export another project’s narrative. Expose this distinction concisely through the canonical thin skill pointer, preserving its backing prompt, registration and artifact/authority boundaries.

9. For new or substantially revised visions, default to independent advisory coverage of product strategy, the domain/application/user workflow, senior architecture and independent challenge. Give each a concrete outcome/evidence remit, distinguish assigned analysis from real credentials or customer validation, and scale scope/depth by stakes, maturity and uncertainty with honest omissions. Add finance/economics, security, reliability or UX when consequential. Archetypes remain optional thinking techniques or an explicitly requested standalone Council under its canonical protocol; Envision itself requires no five-seat stance roster, chair or consensus. The author synthesizes evidence, accepted improvements and unresolved operator decisions through the existing one-pass/bounded-repair/affected-verification flow; majority opinion never substitutes for strategic choice. Preserve missing-capability honesty and artifact-only authority. This changes Envision advisory selection only, not required implementation Wave Council roles, protocols or approvals.
