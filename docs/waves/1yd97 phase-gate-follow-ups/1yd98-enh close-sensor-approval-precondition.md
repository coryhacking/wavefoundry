# Close-sensor approval precondition

Change ID: `1yd98-enh close-sensor-approval-precondition`
Change Status: `complete`
Owner: framework maintainer
Status: planned
Last verified: 2026-09-18
Wave: `1yd97 phase-gate-follow-ups`

## Rationale

Wave `1y0h0` shipped configured phase gates with a trust asymmetry its own delivery review proved by probe. Prepare does not execute an unreviewed sensor edit, and the mechanism is worth stating correctly because the previous wave's decision record states it wrongly. The barrier is not the authority guard on the readiness stage, which is inert on a typed wave, and it is not a stale-receipt diagnostic either: neither of the two causes that produce a blocking `review_policy_receipt_stale` in prepare's mutating modes, policy-state errors and a failed receipt publication, is a command edit. Editing an approved sensor's command rotates the review-policy digest, which makes the recorded readiness approval no longer current, so `council_signoff_gate` emits a blocking `missing_wave_council_signoff`. Prepare's blocking early return fires on that diagnostic before the readiness gate tuple, where the sensor would execute, is reached. Red-team verified the effect by probe: it edited an approved sensor's command, re-ran prepare, and the new command did not execute. Close has no equivalent precondition. Its blocking predicate is evaluated after every gate has run, so on a wave with seven blocking diagnostics, including an invalid review-evidence ledger and no approvals at all, the configured close command ran to completion and wrote its marker file. The `apply` alias behaved identically.

That ordering was deliberate and is specified in `1y0bd` Requirement 5, pinned by its AC-2, and both carry recorded readiness approvals. It was not repaired inside `1y0h0` for exactly that reason; the delivery repair made the consequence discoverable instead, and the decision record now says that `phase_gates` carries the same trust requirement as a commit hook. This change revisits the design itself, which is the operator decision `1y0h0` deliberately left open.

The argument for the current ordering is that an operator sees sensor results beside the other blockers in a single pass. That benefit is narrower than it first appears. Under the precondition an operator still sees every other blocker in one pass and still sees that a sensor is configured, reported as `would_run`; what is deferred is only a pass or fail verdict on a close that was already doomed. The concrete cost is one extra iteration, and only when a wave has both a non-sensor blocker and a failing sensor. Against that, the current ordering executes declared commands on every doomed close retry that reaches the gate stage, which is both the wasteful path and the exposed one, and close is the call an operator retries most while working through a failing close loop. Two later checks can still doom a close whose sensors already ran, so the saving is bounded by what the gate stage can see.

## Requirements

1. `required_sensors_gate` executes at close only when no blocking diagnostic has accumulated at the point the gate runs. The precondition is a conjunct on the gate's existing `mutating` predicate, so it suppresses **execution only**. The pre-spawn refusals are untouched: an unknown sensor name or a non-list `command` still classifies `invalid` and still emits its blocking `phase_sensor_invalid`, because that branch spawns nothing and is a static configuration check that a blocked close has no reason to hide. When execution is suppressed the gate reports `outcome: "would_run"` and the advisory `phase_sensor_not_executed`, the same row shape and diagnostic code the read-only modes use, with the message branched on the reason: the existing text names read-only mode, and the new path must name the blocking-diagnostic condition instead rather than telling a create-mode caller its sensor was skipped for read-only. It names the condition, not the diagnostics themselves: the seam in Requirement 3 is a boolean, and widening it to carry the list would contradict that requirement's default. The gate has no read-only predicate today, only the mode-derived `mutating`, so the shape is stated rather than left to inference: the mode predicate is retained under a name of its own and `mutating` becomes that predicate conjoined with the absence of blocking diagnostics, so the single non-execution branch selects its message on the retained mode predicate. Read-only takes precedence over blocked when both hold, because a read-only close never executes regardless and telling its caller the sensor was withheld for blockers would be the same defect in the other direction. The diagnostic code stays a literal first argument at each emit site inside `required_sensors_gate`, so the landed advisory-site census continues to collect it.
2. "Blocking" means the advisory-aware predicate the close envelope already uses, `any(d.get("advisory") is not True for d in diagnostics)`, not a bare truth test on the diagnostics list. A close can legitimately carry advisory-only diagnostics, and a naive test would stop sensors executing on every such close. That expression is extracted into one module-level helper in `lifecycle_gates.py` taking the diagnostics list as a parameter. Two spellings exist today, the close envelope's inline test and prepare's `_has_blocking_diagnostics` closure, so a new one would be the third rather than the second. All three sites are repointed at the helper: the close envelope, the close orchestrator where it computes the keyword it passes to the sensor gate, and prepare's closure, which delegates to it. Exactly one implementation remains, asserted structurally by AC-11 rather than left as a stated intention. One landed obligation comes with this. A test from wave `1uugg` pins the predicate's literal spelling as a substring of `server_impl.py`, and that spelling occurs only in prepare's closure, because the close envelope names its loop variable differently. Repointing the closure therefore deletes the string the pin reads. The pin is retargeted to the helper's module and name, asserting the same predicate direction at its single implementation, while its two workaround-symbol absence checks stay against `server_impl.py`, which is what wave `1uugg` was actually protecting.
3. The gate learns the blocking state as a keyword argument the close orchestrator passes, following the landed `gardener_gate(ctx, garden_passed=...)` and `single_open_gate(ctx, other_active=...)` precedent, and defaulting to not-blocked so the prepare call site and the existing unit tests are unaffected. It is deliberately **not** a `GateContext` field: the context is pinned to exactly six fields by a structure test asserting set equality plus a two-distinct-reader rule, and a seventh field read by one gate would fail both. Because the close hard-gate tuple is iterated uniformly today, that loop stops being uniform, which makes Requirement 4 necessary. The loop form and the computation point are both specified rather than left open: the close orchestrator iterates `CLOSE_HARD_GATES[:-1]`, then computes the keyword from the diagnostics accumulated **after** that loop, then calls `CLOSE_HARD_GATES[-1]` explicitly with it. The computation point is load-bearing and is not an implementation detail: computing it before the loop would satisfy every criterion on a fixture that blocks on approval or evidence diagnostics, which is the ordinary case, while silently failing Requirement 4's invariant for any blocker produced by the checkbox or receipt gate inside the loop. Tuple membership is retained so Requirement 4's order pin stays load-bearing and so the `[:-1]` and `[-1]` indexing has something to index; the gate is collected as a unit either way, since it is also a member of the prepare tuple. Leaving the loop over the full tuple and adding an explicit call after it would spawn every configured sensor twice, the first time with the not-blocked default, silently reverting this change; the landed `CLOSE_SHARED_GATES[0]` and `[1]` indexing is the precedent for exactly this shape.
4. The precondition's correctness depends on every gate-stage diagnostic having already accumulated, which today holds because `required_sensors_gate` is last in `CLOSE_HARD_GATES`. That position was stated in prose by `1y0bd` Requirement 5 but never pinned mechanically, and it becomes a pinned invariant here: a structural criterion asserts the sensor gate is the final member, so a one-line reorder cannot silently revert this change with every other test green. Only that intra-tuple position is pinned. The diagnostics accumulated before the hard-gate loop, from the shared delivery, gardener, evidence, independence, memory-validation and secrets stages, are not pinned here, so the precondition is bounded by what the gate stage can see rather than by the whole close.

## Scope

**Problem statement:** The blocking-diagnostic barrier that stops an unreviewed sensor edit from executing during prepare has no counterpart at close.

**In scope:**

- The close precondition, its named predicate, its keyword seam, and the structural pin on gate order.
- The derived amendment set and the decision-record correction.
- Rehoming the close-sensor tests whose fixtures this change invalidates.

**Out of scope:**

- The prepare path. Its barrier is the blocking early return that fires before the readiness gate tuple, which is where the signal from a rotated receipt lands. A blocking diagnostic raised by `readiness_gate` inside that same tuple does not suppress the prepare sensor; that intra-tuple residual is out of scope.
- Legacy prose waves and waves with no current policy receipt, where no digest binds the command bytes at either phase. That residual is disclosed in the decision record rather than fixed here.
- Any change to what a sensor may be or how it is spawned.
- The guard and documentation tidy-ups carried by the sibling change.

| 2026-09-18 | Gate close sensors on the absence of blocking diagnostics rather than keeping the single-pass ordering | The single-pass benefit costs one extra iteration only when a wave has both a non-sensor blocker and a failing sensor, while the current ordering executes declared commands on every doomed retry and leaves the digest binding a control on prepare alone | Keep the ordering and rely on documentation: honest, and what `1y0h0` shipped, but leaves the asymmetry permanent.
