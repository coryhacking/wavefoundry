Change Status: `implemented`
Owner: Engineering
Status: planned
Last verified: 2026-10-02
Wave: 1zls8 extension-surface-two

## Rationale

Wave `1zimf` (change `1zimn-enh extension-public-helpers`) gave extension handlers a stable surface, `server_impl.EXTENSION_PUBLIC_HELPERS`, which names exactly `ensure_no_extra_args`, `make_response`, `make_diagnostic` and `change_doc_response`. A downstream distribution that wraps core lifecycle tools still reaches private names for the rest of a lifecycle handler's job: `_find_wave_md_detailed` to resolve a wave record, `_refuse_if_archived` to refuse a write to an archived record, the `_fail_closed_on_record_layout` decorator to turn an invalid record layout or a duplicated wave id into the structured refusal, `_attach_lint_to_response` to add post-write lint state, and `_trigger_background_index_refresh_for_paths` (defined in `wf_server/index_handlers.py` and imported into `server_impl`) to refresh the index after a write. It also uses `list_waves` and `wf_review_wave_response`, which are public by name but outside the named contract, so nothing pins their signatures. The spec says underscore helpers "are not a stable public API", so every such call is a dependency the framework does not promise to keep.

A second gap is in provenance and reload. `_load_extension_module` hashes and executes only the modules named in `EXTENSION_MODULES`; a module an extension module imports (a distribution's shared helper file) is imported by ordinary `import`, is absent from the `wf_server_info` provenance digest, and is never evicted by `wf_reload_mcp`: the purge block at the top of `server_impl` names a fixed set of framework modules and `server.py` evicts only `wave_lint_lib*`. After a distribution edits a helper file, a reload re-executes the extension modules but they keep the stale helper, and the operator cannot see which helper bytes are running.

## Requirements

1. **Seven more contract names.** `server_impl`, in the marked public-helper block that holds the current four, defines five new late-bound wrappers and adds them, with the two existing public functions, to `EXTENSION_PUBLIC_HELPERS`, which then lists eleven names in this order: `ensure_no_extra_args`, `make_response`, `make_diagnostic`, `change_doc_response`, `find_wave_record`, `refuse_if_archived`, `fail_closed_on_record_layout`, `attach_lint`, `refresh_index_for_paths`, `list_waves`, `wf_review_wave_response`. The new wrappers and their exact signatures:
   - `find_wave_record(root, wave_id_or_prefix, wave_dirs=None)` returns what `_find_wave_md_detailed` returns, the tuple `(wave_md, requested_read_error, unreadable_siblings)`, and raises what it raises (`record_paths.AmbiguousWaveId` for one wave id at two paths, `ValueError` for a prefix matching distinct ids, `record_paths.RecordLayoutInvalid` for an invalid layout);
   - `refuse_if_archived(root, token, kind)` returns the `archived_record_read_only` diagnostic or `None`, exactly as `_refuse_if_archived`;
   - `fail_closed_on_record_layout(tool)` returns the decorator `_fail_closed_on_record_layout(tool)` returns;
   - `attach_lint(envelope, root, mode)` returns `_attach_lint_to_response(envelope, root, mode)` (no lint on `dry_run` or on an error envelope; lint under `data.lint` otherwise, status unchanged);
   - `refresh_index_for_paths(root, paths)` returns `_trigger_background_index_refresh_for_paths(root, paths)` (a `{"project": bool}` mapping).
   Each is a `def` that looks up its private counterpart on `server_impl` at call time, so `patch.object(server_impl, "<private name>", ...)`, which existing tests already use for `_trigger_background_index_refresh_for_paths`, and an in-place `wf_reload_mcp` both reach the current function. `list_waves(root, wave_dirs=None)` and `wf_review_wave_response(root, wave_id, phase="implementation")` are already module-level public functions and are listed unchanged, without a wrapper. No private name changes and no core caller is migrated.
2. **Signature pin.** The `tests/test_extension_public_helpers.py` contract test pins the eleven names in order, each name's signature string, and, for `find_wave_record`, `refuse_if_archived`, `attach_lint` and `refresh_index_for_paths`, that the result equals the private counterpart's for the same arguments (for `find_wave_record`, also that the same exception type is raised for an ambiguous id and an invalid layout). `fail_closed_on_record_layout` returns a new decorated function on every call, so equality cannot hold; it is pinned by behaviour instead: a function decorated by the public wrapper and one decorated by `_fail_closed_on_record_layout` return the same pass-through result, and the same refusal envelope for an invalid record layout and for a duplicated wave id. `test_the_wrappers_are_distinct_functions_not_aliases` gains the five wrappers. Removing, renaming or re-signing a listed name is a breaking change recorded in `## [Unreleased]`.
3. **Helper module declaration.** `mcp_tool_extensions.py` gains `EXTENSION_HELPER_MODULES: tuple[str, ...] = ()`, flat module names that extension modules import, counted by `declared()`. Validation in `declaration_problems` applies the `EXTENSION_MODULES` name rules to each entry (an identifier, declared once, not in `RESERVED_MODULE_NAMES`, not a standard-library module name) and also refuses a name listed in both `EXTENSION_MODULES` and `EXTENSION_HELPER_MODULES`, and a value that is not a tuple (reported, never raised). Both declarations also refuse a name that matches any framework flat script: a new frozenset `FRAMEWORK_SCRIPT_MODULE_NAMES` in `mcp_tool_extensions.py` lists the stems of every flat `.py` file the framework ships in the scripts directory, and a census test pins it equal to the stems of the flat `.py` files in the scripts directory less the names the current declaration lists (so a distribution's own module files do not fail it). The existing collision check in `_load_extension_module` catches only a framework script the server has already imported, and most flat scripts (76 of the 105 counted at planning) are not imported once `server_impl` has loaded, while a helper needs no `register`, so without this refusal a helper declaration naming a framework script would execute that script as a hashed helper. `mcp_tool_roster` refuses the same declarations without starting the server.
4. **Helper modules load like extension modules, but register nothing.** `_install_extension_tools` loads each declared helper module, in declaration order and before any extension module, through `_load_extension_module`: the `.py` file must resolve directly in the scripts directory, it is executed from the exact bytes it hashes, it is marked `__wf_extension__`, and a name the server already imported that is not so marked is refused. A helper module's `register`, if it defines one, is never called, and nothing it defines is served. A helper may import only helpers declared before it: one that imports a later-declared helper leaves that helper imported unmarked, and loading it is then refused by the existing collision check, so the order mistake fails registration rather than running unhashed bytes.
5. **Reload evicts helpers.** The first statement of `_install_extension_tools`, before the existing `if not mcp_tool_extensions.declared(): return provenance` check, removes every `sys.modules` entry marked as an extension module, so an emptied declaration still evicts. It iterates over `list(sys.modules.items())` (never the live mapping) and treats an entry as marked only when `isinstance(module, types.ModuleType) and vars(module).get("__wf_extension__") is True`, so a lazy proxy or a module whose attribute lookup is dynamic is never evicted by accident. A `wf_reload_mcp` then re-executes every declared helper and extension module from current disk bytes, a helper dropped from the declaration is no longer in `sys.modules`, and a helper imported out of order is refused on reload exactly as at startup: without the eviction the earlier install's marked copy would satisfy the out-of-order import, and the loader overwrites a marked entry, so the order mistake would pass silently on every reload.
   **Failure cleanup.** When the install raises (any `ExtensionLoadError` or other exception from loading, registering or validating), `_install_extension_tools` pops, before re-raising, every name in `EXTENSION_HELPER_MODULES` or `EXTENSION_MODULES` that is in `sys.modules` but was not when this install began (the snapshot is taken after the start-of-install eviction, so a helper the previous install marked does not count as already present) and whose `__file__` resolves to a file directly in the scripts directory, marked or not. This includes a later-declared helper that an out-of-order import loaded unmarked, so after the operator fixes the order a `wf_reload_mcp` succeeds without a server restart.
6. **Provenance.** `wf_server_info.extensions` gains `helper_modules`: for each loaded helper, its `module`, `path` and the SHA-256 of the exact bytes executed; empty for the stock declaration. `extensions.declaration` reports the declared `helper_modules` names.
7. **Failure is the existing failure.** Any helper refusal or import error raises `ExtensionLoadError` through the existing path, leaving only runner tools served (startup refuses; reload reports `register_surface_failed`).
8. **Docs.** `docs/specs/mcp-tool-surface.md`: the declaration table gains `EXTENSION_HELPER_MODULES`; **Registration** lists the eleven contract names and their signatures, and the sentence "Each is a thin wrapper that calls its private counterpart at call time" is narrowed to the nine wrappers, stating that `list_waves` and `wf_review_wave_response` are the module-level functions themselves, looked up on `server_impl` at call time; **Failure**, **Provenance** and **Trust boundary** describe helper modules, and the sentence "Imports made by an extension module are not hashed" becomes: imports of declared helper modules are hashed and reloaded; any other import is neither. The extension-modules row of `docs/architecture/threat-model.md` gains the same sentence. One `### Added` entry in `## [Unreleased]`.
9. **Profile coverage.** `SHIPPED_DECLARATION` in `tests/record_layout_support.py` lists `EXTENSION_HELPER_MODULES` with its empty default, so the ships-empty test and the expected-profile guards cover it. In `tests/test_extension_tool_modules.py` the refusal driver's `empty = dict(...)` line (checked by `DeclarationConstantCensusTests.test_the_refusal_driver_resets_every_declaration_constant`) gains `EXTENSION_HELPER_MODULES=`, and `test_each_new_constant_alone_makes_the_declaration_declared` gains a helpers-only case.
10. **Platforms.** Windows, macOS, Linux and WSL2 behave the same. The wrappers are pure Python. Helper loading uses the existing `_load_extension_module` path check (`Path.resolve` and a parent comparison against the resolved scripts directory), which already runs on every platform. On a case-insensitive filesystem (default Windows and macOS volumes) a declared name whose case differs from the file must be refused, and the existing `source_path.stem != module_name` comparison is not enough: with `PYTHONCASEOK=1` on a case-insensitive volume `PathFinder.find_spec` resolves a mis-cased name and `Path.resolve` can keep the declared case, so the stem check passes. `_load_extension_module` therefore always, for helper and extension modules alike and on every platform, compares `f"{module_name}.py"` with the exact file names listed in the scripts directory (`os.listdir` of the resolved directory) and refuses when no entry matches exactly. A subprocess test runs the load with `PYTHONCASEOK=1` in the child environment and asserts the refusal for a mis-cased helper and a mis-cased extension module; on a case-sensitive volume the same test asserts the same refusal (there `find_spec` already misses).
11. **Transition.** Additive. Extensions calling the private names keep working; the stock declaration serves the same surface, with only the new empty provenance key.

## Scope

**Problem statement:** a distribution that wraps lifecycle tools must call private helpers, and the helper modules its extensions import are neither hashed nor reloaded.

**In scope:**

- The five wrappers and the extended `EXTENSION_PUBLIC_HELPERS` in `wf_server/server_impl.py`.
- `EXTENSION_HELPER_MODULES`, its validation and `declared()` coverage in `mcp_tool_extensions.py`.
- Helper loading, the start-of-install eviction and provenance in `_install_extension_tools`.
- Tests in `tests/test_extension_public_helpers.py` and `tests/test_extension_tool_modules.py` with fixture helper modules; `SHIPPED_DECLARATION`.
- The spec sections, threat-model row and CHANGELOG entry in Requirement 8.

**Out of scope:**

- Public wrappers for any other private helper (for example the lifecycle lock or the busy response, decided against in change `1zimn-enh extension-public-helpers`).
- Hashing or reloading arbitrary transitive imports; only declared helpers are covered.
- Moving `_trigger_background_index_refresh_for_paths` out of `index_handlers`.

## Risks

| Risk | Mitigation |
| --- | --- |
| A future refactor renames a private helper and silently breaks a wrapper | The equality and signature pins in AC-1 fail first |
| `wf_review_wave_response` is called by an extension expecting the served tool's lifecycle telemetry | The spec states it is the response function: the served `wf_review_wave` adds focus and context-efficiency recording around it |
| A helper imports another helper out of order | Requirement 4 makes that a registration refusal (AC-6), and the spec names the order rule |
| Platform path differences (Windows case-insensitive volumes, macOS default APFS, Linux, WSL2 on its own filesystem or on `/mnt/c`) let a mis-cased name load | Requirement 10: an unconditional exact directory-listing comparison for helper and extension modules; AC-6 pins the refusal with a `PYTHONCASEOK=1` subprocess test on every platform |
| A concurrent lazy import during a reload inserts an unmarked copy of a helper between eviction and load | The loader's collision check refuses it, so the reload fails closed with `register_surface_failed` and the failure cleanup pops the copy; the next reload succeeds |
