## Rationale

An operator who wants to know the size and shape of a project today has to assemble it by hand: a line counter that may not be installed (`loc`, `cloc`, `tokei`), a directory listing of the wave records, a search for checkboxes, and three separate index tools. The answers differ between runs and between agents, and none of the external counters know what a wave, a change, an acceptance criterion or a memory record is. The framework already owns every one of those record formats and the index, so it can report them in one deterministic call.

## Product Intent

An operator or agent in any repository that carries the framework asks for project statistics (skill `/wf-stats`, MCP tool `wf_stats`, or CLI `wf stats`) and gets one report: lines of code by language, lifecycle record counts, acceptance-criterion and task completion, TODO markers, decision records, agent roles, memories, index statistics, the framework's token-savings estimates and secret-scan finding counts (false positives and confirmed secrets). Before this change there is no such report. The report is read-only and works with no network access and no external counter installed. Figures the dashboard also shows are the same figures, from the same code. It reports numbers; it draws no conclusions and gates nothing.

AC-1 to AC-5 together with AC-7 and AC-10 to AC-12 test whether the intent was established.

## Requirements

1. A new module computes a statistics report for a repository root as one structured value. The same value backs the MCP tool `wf_stats`, the CLI subcommand `wf stats` and the skill `wf-stats`; no surface computes its own figures.
   1. **One source with the dashboard.** Wherever the dashboard already computes a figure, the report takes it from the dashboard's own collectors in `dashboard_lib` (`collect_waves`, `collect_changes`, `collect_agents`, `collect_health`, `read_prompt_manifest`) and does not count it a second way. That covers lifecycle records, acceptance criteria and tasks, agent roles, and the index figures (requirements 4, 5 and 7). The agreement is with the snapshot: the agent count is the snapshot's, which can exceed the page's grid where the grid hides inactive roles or categories it does not list.
   2. **One Progress scope and truthful checkbox states.** `dashboard_lib` owns one shared Progress value consumed unchanged by the dashboard snapshot, Progress card and statistics report. Its criteria and task scope is every admitted change document found across all wave statuses, including closed/completed, active/implementing, planned and paused waves. Scope never switches when an open wave exists or disappears. Unadmitted plans are reported separately and never enter admitted Progress, even when their `Wave:` metadata names a known wave. For criteria and tasks, `[x]` means done, `[~]` means deferred and `[ ]` means open; `total = done + deferred + open`. A wave or change's closed/completed status never changes an item's checkbox state. `not-this-scope` criteria are counted separately and excluded from all four in-scope counts. The Progress card displays done, deferred, open and total explicitly for criteria and tasks; missing snapshot Progress must not trigger a second calculation or imply zero completion. Wave and change rows retain lifecycle-based done/total semantics over all wave records and admitted changes, with the existing closed/done status sets; they are labelled as lifecycle status, not checkbox completion, and do not manufacture deferred states. Missing admitted documents retain their declared record count but contribute no invented checkbox items; missing/unreadable document counts and an explicit incomplete-checklist warning accompany both consumers. The report's admitted raw breakdown references the same shared criteria/task state counts rather than independently recounting. `Metrics`, per-wave cards and their helpers (`acProgressStats`, `waveStats`, `computeProgress`) remain out of scope unless an unchanged label would falsely claim this new all-admitted scope; narrowly correct such labels without changing their calculations. The existing `_wave_only_metric_counts` active-scope figure is not the source for Progress.
   3. The dashboard has no figure for code lines, TODO markers, documents, memories, token savings or secret findings. Those sections are computed in the new module, which is then their single source: a later dashboard panel for any of them must call the new module. No dashboard panel is added by this change; only the Progress contract and any conflicting scope labels change.
2. **Code lines.** The file set is what `indexer.walk_repo` returns after `indexer._filter_project_index_excludes` has been applied with the project's own configured opt-in prefixes for docs and code together (what `indexer._merged_project_include_prefixes_for_graph(root, ())` returns). The framework's seed fold that the docs and meta index layers add is not applied, and `_filter_code_files` is not applied, so test files stay in the set. `walk_repo` alone keeps the vendored `.wavefoundry/` tree; this filter removes all of it in a repository with no opt-ins. For that file set the report gives per language: file count, total lines, blank lines, comment lines and code lines.
   1. Language comes from the file extension through `chunker._EXT_TO_LANGUAGE`; an extension absent from it is reported under its own extension.
   2. Each language has one category, held in one table in the new module: `documentation` (the chunker's Markdown extensions plus `.txt`, `.rst` and `.adoc`), `data` (JSON, YAML, TOML, XML, CSV and similar formats listed in that table), or `code` (everything else). The report gives a total row per category and never adds categories together into one headline.
   3. Among candidates returned by the walker, a file whose first 8 KiB contains a NUL byte is counted only in `binary_files`. Label this as binary candidates detected, not a repository-wide binary census: the walker already excludes known binary extensions and binary-sniffed unknown extensions.
   4. Comment lines are counted for the languages listed in one comment-syntax table in the new module (line and block delimiters). For a language absent from that table, comment lines are reported as `null` and code lines are total minus blank.
   5. Counting is lexical: a comment delimiter inside a string literal is counted as a comment. The report states this limit in its output.
   6. Test code is reported separately for the `code` category only: every `code` language row and the `code` total carry the five counts as production, test, and both together, and the report gives the test share of code lines as a ratio. A `code` file is test code when `indexer._is_test_code_path` holds for its path (a `test`, `tests` or `__tests__` directory, or a `test_` or `_test.py` file name), or when its file name matches, case-sensitively on every platform, one of the conventions in one table in the new module: `*_test.go`; `*.test.<ext>` and `*.spec.<ext>` where `<ext>` is `js`, `jsx`, `ts`, `tsx`, `mjs` or `cjs`; `*Test.java`, `*Tests.java`, `*Test.kt`, `*Tests.cs`, `*Tests.swift`; `*_spec.rb`, `*_test.rb`. Each pattern needs a non-empty stem before the suffix. The indexer's rule and what it indexes are not changed. The report names the rule it applied.
   7. Lines are counted the same way for `\n` and `\r\n` endings; files are read as UTF-8 with undecodable bytes replaced.
   8. Code and TODO output name the walker/index exclusions and effective `indexing.max_file_bytes` cap (default 5 MB; zero disables the cap). Pass sets for the walker's `unreadable_dirs` and `unreadable_files`; also catch failures reading returned files. If either traversal or a file read fails, return the affected requested code/TODO section with `available: false`, `complete: false`, a reason and failure counts; do not present partial totals as complete. No walker changes are in scope.
3. **TODO markers.** Over the `code` category files of the same file set, the report counts the markers `TODO`, `FIXME`, `HACK` and `XXX` (upper case, whole word), per marker and in total, and names the ten files with the most markers.
4. **Lifecycle records.** From `dashboard_lib.collect_waves` and `collect_changes` (both uncapped) the report counts:
   1. wave records by status;
   2. change documents by kind and by status, for admitted changes and for unadmitted plans separately;
   3. the Progress block from requirement 1.2, labelled as the figures the dashboard shows;
   4. the same admitted criteria/task counts from requirement 1.2, and a separately labelled unadmitted-plan breakdown using the same checkbox meanings. Both report total as done plus deferred plus open and keep not-this-scope criteria separate. There is no closed-wave completion credit and no explanation claiming Progress and admitted raw states differ. The report identifies the dashboard metric tiles as a different, active-scope view. The existing dashboard checklist parser remains the shared owner. It must retain the explicit checkbox marker in an additive field for Progress: legacy parsed done flags can infer completion from terminal status and therefore cannot supply literal checkbox truth. Preserve those legacy fields for metric/per-wave-card consumers; Progress reads the explicit marker. This change does not alter close-gate authority or legacy-card calculations.
   5. the number of admitted changes whose document is missing on disk (a wave's recorded change count minus the documents found), and the number of change documents the collectors could not read. Both Progress consumers expose these counts and mark checklist coverage incomplete when either is nonzero. They report counts observed in readable documents, not inferred states for missing items; metadata alone never invents checklist totals or completion.
5. **Documents and roles.** Agent roles are counted by category from `dashboard_lib.collect_agents`, and public prompts from `dashboard_lib.read_prompt_manifest`, the count the dashboard shows. The report also counts specification documents, architecture documents and decision records (files of the `adr` kind under `docs/architecture/decisions`, the directory `lifecycle_id` mints them into), each from the directory the framework assigns to it. A directory that does not exist yields a count of zero.
6. **Memories.** Through `memory_records`, the report counts memory records by status, archived records once (from one source, not from both the archived bodies and the archive register), and active records by their `kind` field.
7. **Index.** The index section is what `dashboard_lib.collect_health` returns for the project index, reduced to figures: for the embedding index, files indexed, doc chunks, code chunks, built-at time and model names; for the lexical index, the `lexical_statistics` values (status, entries, term occurrences, distinct terms); for the code graph, node, edge and cluster counts with its generation and build time. Node and edge lists and other bulk payload are not included in the report. `files_indexed` is labelled as the index's file set, which is not the code section's file set.
   1. The section starts no build, download or model load, and does not call `index_health`; for staleness and integrity verdicts the report points at `index_health`.
   2. When the dashboard collector reports the index as not present or returns a store diagnostic, the section is returned with `available: false` and that reason.
8. **Token savings.** The report sums the Context Efficiency figures the framework has already published: for every wave record whose record file carries a context-efficiency state marker, the totals and the per-stage figures for calls, credits, debits and estimated tokens saved; the number of records with a marker and without one; and the count of records by `measurement_status`.
   1. The marker is read with `context_efficiency.parse_checkpoint_block`, and the record file name comes from the vocabulary profile. The report does not re-derive any credit and does not open the live Context Efficiency store: the marker of a record still in progress is already published into its record file, so the live store would count it twice.
   2. A record whose `measurement_status` is not `healthy` is counted and listed, and is excluded from every summed figure (calls, credits, debits and savings, in the totals and per stage). The parser sets such a record's total estimated savings to zero and keeps its per-stage figures, so the exclusion is applied by the report. The report also gives the number of markers whose `pending` flag is set, since those can trail the most recent calls.
   3. Every figure in this section is labelled an estimate, and the report carries the framework's existing limitation sentence for these estimates.
9. **Secret findings.** The report counts the entries in the secrets scan findings file (`docs/scan-findings.json`) by status: `false-positive`, `confirmed-secret`, `suspected-secret` and `pending`. A missing status counts as `pending`, as docs-lint reads it; any other value counts as `unclassified`. The same breakdown is given per rule.
   1. For false positives the report gives the distribution of distinct confirmations per finding (0, 1, 2, 3 or more) and the number carrying a non-empty `override_reason`. It does not decide whether a finding satisfies the confirmation policy: that rule needs Git history, and docs-lint remains its authority.
   2. The report states when the findings file was last modified, and does not run a scan.
   3. The section carries counts, rule ids and statuses only. It never includes a finding's matched text, line content, hashes, file path, confirmer identity or override text, in the structured value, the text output or any diagnostic.
   4. A missing findings file yields zero counts with `available: true` and a note that no scan has recorded findings; an unparsable file yields `available: false` with a reason that quotes none of the file's content.
10. **Degradation.** Each section is computed independently. A section that cannot be computed (no index, an unpublished index, an unreadable directory) is returned with `available: false` and a reason, the other sections are still returned, and the overall status is still `ok`.
11. **Read-only.** The report's own code creates, modifies and deletes no file outside the index directory `.wavefoundry/index/`. Inside it, three effects of the dashboard's health collector are allowed, as they happen for the dashboard: SQLite `-wal` and `-shm` sidecar files are created or updated, `index-build-stats.json` may be rewritten from a finished build log, and a finished `index-build.json` may be removed. The Context Efficiency store is not opened. The MCP server records a `wf_stats` call in its telemetry as it records any tool call; that is the server's write, not the report's.
12. **Surfaces.**
    1. MCP tool `wf_stats(sections: list[str] | None = None)` in the read tier, returning the standard envelope; `sections` limits the report to the named sections and an unknown name is a validation error. Unrequested sections are not computed; only the index section calls `collect_health`. Shared dependencies are collected only when a requested section needs them.
    2. CLI `wf stats` prints a human-readable report; `--json` prints the structured value; `--root` selects the repository; `--section` may repeat.
    3. Skill `wf-stats` renders to every active skill host with no backing prompt document, so it reaches every target on the next render without prompt reconciliation. Its body tells the agent to call `wf_stats` (CLI when MCP is not attached) and present only returned data: a concise summary, clear section headings and tables, retaining estimate labels, counting rules, scope distinctions and unavailable/incomplete reasons. It must not recount with shell tools, infer missing numbers, or calculate alternative figures. Formatting and structure belong in the skill; computation belongs in the tool.
    4. Human-readable labels take their lifecycle nouns from the vocabulary profile. Keys in the structured value are fixed names and do not change with the profile.
13. The new module, tool, subcommand and skill are added to every registry that the existing registration tests pin for a flat script, an MCP tool, a CLI subcommand and a registry skill. The derived set governs: whatever those tests require, not the examples named in Tasks.
   1. No new `wf_server` module: `project_stats.py` computes payload and diagnostics, while the tool closure and response envelope live in `wf_server/server_impl.py`.
   2. Keep `dashboard_lib` retained across MCP reload, preserving its existing lock exception identity; update its retained-module explanation to state that edits to dashboard-sourced report figures require a host restart. `project_stats` joins the ordinary purge list.
14. Platform behaviour: the report spawns no subprocess and adds no third-party dependency of its own; the framework modules it reuses load the index's existing dependencies. The dashboard's Git statistics and activity collectors are not called. Paths go through `pathlib`. It behaves the same on Windows, macOS, Linux and WSL2, and the CLI entry point writes no bytecode beside the framework sources.

## Scope

**Problem statement:** There is no single, deterministic report of a project's size and lifecycle statistics; assembling one needs external tools and several manual counts.

**In scope:**

- The statistics module, its MCP tool, CLI subcommand and skill.
- Revising shared dashboard Progress and its snapshot/report consumers to all-admitted scope and explicit done/deferred/open/total checklist states, with tests and documentation for the intentional change from legacy completion credit.
- Tests for each section and surface.
- The dashboard retained-module explanation in `tests/test_lifecycle_gates_structure.py`; `docs/architecture/domain-map.md`, `docs/architecture/data-and-control-flow.md`, `docs/architecture/performance-budget.md`, `docs/references/dashboard-adapter-model.md`.
- Every document and fixture the Tasks name: the tool-surface spec and golden fixtures, the tool list and skills paragraph in `AGENTS.md`, the platform mapping skill table, the `README.md` skill table, one qualifying clause in seed 050, and a changelog entry.

**Out of scope:**

- Running a secrets scan or changing any finding's status.
- New token measurement, pricing or cost conversion, and any read of the live Context Efficiency store; the section only sums published estimates.
- Index freshness, staleness and integrity verdicts; `index_health` reports those.
- Deciding whether a false positive satisfies the confirmation policy.
- Git history statistics (commits, contributors, churn).
- Trends over time, stored snapshots, or any written report file.
- A dashboard panel for the new sections or changes to metric/per-wave-card calculations. Only Progress figures and conflicting scope labels are changed as specified in requirement 1.2.
- A shortcut phrase and backing prompt document for hosts without skills; those hosts use the MCP tool or the CLI.
- Complexity metrics and test coverage.
- Language-aware comment parsing beyond the lexical rule in requirement 2.

## Risks

| Risk | Mitigation |
| ---- | ---------- |
| The report is slow on a large repository | One pass over the dashboard collectors' output. `collect_health` builds the whole graph payload to read its counts (4 to 10 seconds and several hundred megabytes on a cold copy of this repository's store); that cost is accepted so the figures are the dashboard's, and the measured time is recorded in the Progress Log |
