## Rationale

**Brief.** Goal: let a target repository require additional named sensors at prepare or close through committed, typed configuration, with the framework's own checks unchanged. Audience: Waveforge and any team with policy beyond the defaults, plus maintainers who want policy visible in one reviewed file. Approach: a new `phase_gates` key in `docs/workflow-config.json` consumed by a gate unit appended to the phase tuples from `1y044-ref extract-lifecycle-gate-units`. Constraints: no repository code loaded by the server; enumerated fields only; fail-closed in the mutating modes (prepare `ready`/`create`, close `create`); nothing executed in `dry_run`; provenance in every response. Success: a fixture repository declares a close-time sensor, and the phases block or pass exactly as declared.

This is the posture selected by the operator on 2026-09-14 over the RFC's convention-discovered policy modules. Verification found three config-driven policy mechanisms already shipped in `server_impl.py`: `sensors` (project commands run by `wf_run_sensors_response`, read by `_read_project_sensors`), `required_review_lanes` (read by `_read_project_required_review_lanes` and fed to `review_policy.select_required_review_lanes` from `_prepare_policy_state`), and the `wave_review` council block. It also found that the `review_policies` key is hashed into `review_policy.policy_input_digest` but never parsed, so that block is not a safe home for new fields. The established pattern is one dedicated top-level key with a small reader threaded into the lifecycle call site, and this change follows it. `1y0bf-ref codenav-graph-handler-modules` (wave `1y0h2`, readied, not landed) plans the same no-`server_impl`-import rule for its own extracted modules, following the rule `techdocs_audit_lib.py` already applies; `1y044` adopts it for `lifecycle_gates.py`, and this change inherits it.

## Requirements

1. A new optional top-level `phase_gates` object in `docs/workflow-config.json` with at most two keys, `prepare` and `close`. Each is an object with one optional list field, `required_sensors`, whose entries are names from the list-form `sensors` entries. Any other key inside `phase_gates` at any level (`review`, `required_lanes`, or an unknown field inside a phase object) and any unknown sensor name is a docs-lint error naming the config path; strictness applies inside `phase_gates` only, and the rest of the config keeps its existing tolerance. A `sensors` key that is not a list (the dict form carrying `retrieval_posture`, read by `_retrieval_posture_thresholds`, which declares no sensors) is an error only when a `phase_gates` block names a required sensor; without such a block it stays accepted as today. Required sensors must be list-form commands; a required sensor whose `command` is a string (which today runs with `shell=True`) is a lint error naming the path. Validation is a helper `review_policy.normalize_phase_gates(config) -> (normalized, errors)` (stdlib, errors naming config paths, mirroring the `normalize_wave_review_policy` precedent), called by `wave_lint_lib/core_validators.check_workflow_config` beside its `wave_review` branch and by prepare beside `_wave_review_policy_diagnostics`, so `wave_lint_lib` stays a leaf and the same errors surface as a prepare diagnostic without the lint subprocess (AC-4's "prepare refuses readiness").
2. Today the loop is inline in `wf_run_sensors_response` and calls `_mcp_subprocess_run(cmd, shell=<command is not a list>, cwd=root, timeout=120)`; a sensor passes when `returncode == 0`; `subprocess.TimeoutExpired` and any other exception yield `passed: False, exit_code: None`. This change extracts the loop body into a new module `sensor_runner.py` with no `server_impl` import (it imports `subprocess_util` for `isolated_run`, function-locally, the spelling `techdocs_audit_lib` uses). It joins the purge set after `lifecycle_gate_support` and `lifecycle_gates`, is imported at module top in `server_impl.py` after the purge block, and is covered by the reload pickup test beside those two (`1y044` AC-4 derives its stub set positionally from the purge literal, so `sensor_runner` joins it with no edit to that test). `run_sensor` calls `subprocess_util.isolated_run(cmd, shell=not isinstance(cmd, list), cwd=str(root), timeout=timeout_seconds, capture_output=True, text=True)`. Writing the call out matters: `isolated_run` supplies stdin `DEVNULL` and the no-window creation flags unconditionally, but it pins no `stdout` or `stderr` and applies the UTF-8 `errors="replace"` decoding only when the caller passes `text=True`, despite its own docstring claiming `capture_output=True` suffices. Without both kwargs the captured streams come back as bytes and the existing summary construction raises, failing `test_passing_sensor`, which this change promises passes unchanged. Nothing moves and nothing is inlined: `techdocs_audit_lib`, the module this change cites as the no-`server_impl`-import precedent, already calls `isolated_run` directly, and `server_impl` itself calls it at two sites, one carrying a comment naming it in preference to `_mcp_subprocess_run`. Rewriting `_mcp_subprocess_run` to delegate was considered and rejected: it has eleven call sites and is patched on about thirty-five lines under `tests/`, it is the one spawn helper that pins stdout and stderr to `DEVNULL` when capture is off so a child never inherits the JSON-RPC streams, and changing it inside a wave whose sibling change is defined by having no behavior change buys nothing. `subprocess_util` is not in the purge set, so a reloaded `sensor_runner` calls a cached copy of it; that is the pre-existing condition of every module importing it, and this change adds no new semantics there. Signature: `run_sensor(root, sensor, *, timeout_seconds, shell=False) -> SensorResult` with fields `name`, `dimension`, `passed`, `exit_code`, `output_summary`, and `duration_ms`; the timeout message interpolates the effective timeout. Two `wf_run_sensors` response details therefore change even though its four tests assert subsets and pass unchanged: each result row gains `duration_ms`, and the fixed `Sensor timed out after 120s.` message becomes the interpolated one. The caller resolves the timeout: `wf_run_sensors_response` and the gate read `subprocess_ops.sensor_timeout_seconds` through the shipped `subprocess_ops_timeout_seconds(root, op)` reader, which gains a `default` parameter so these callers pass 120 where the family's default is 180, and whose docstring gains `sensor` to the ops it enumerates. That reader, `_read_project_sensors`, and the new `_read_phase_gates` all move into `lifecycle_gate_support.py` beside `_read_workflow_config`, because the gate is a unit in `lifecycle_gates.py` and `1y044` AC-8 forbids that module from importing `server_impl` at any scope. These moves obey the same AST-closure rule `1y044` Requirement 3 states, and that closure adds one member this change must carry with them: `SUBPROCESS_OPS_TIMEOUT_DEFAULT`, which the reader returns and which `_subprocess_timeout_summary` still interpolates. All three readers and that constant join `server_impl`'s `from lifecycle_gate_support import (...)` block, which `1y044` builds from its own census and cannot anticipate a later change's moves; that binding is what keeps the two existing bare-name calls in `wf_validate_docs_response` and `wf_sync_surfaces_response` working, along with the direct `srv.` reads in the lifecycle-lock tests; reimplementing the read in two callers would put one config key behind two readers with two different defaults. The key is documented by rewording the `subprocess_ops` row of `docs/architecture/performance-budget.md` (the family's only current home), which today states one sub-180-second bound for the whole family and would be false if this key were added beneath it unchanged, and in the `phase_gates` text of `docs/architecture/cross-cutting-concerns.md` `## Configuration`. `wf_run_sensors_response` loops over `run_sensor` passing `shell=not isinstance(cmd, list)`, so its four existing tests (`test_no_sensors_configured`, `test_passing_sensor`, `test_failing_sensor`, `test_sensor_with_invalid_command`) pass unchanged. The advisory `phase_sensor_not_executed` emit adds a site to `test_advisory_tags_appear_only_at_the_sanctioned_sites`, whose scan `1y044` extends over `lifecycle_gates.py`; this change adds the sanctioned tuple for it, and because that assertion is unconditional on configuration the unchanged corpus does not cover it. A `required_sensors_gate` unit refuses a non-list `command` before calling `run_sensor` (blocking `phase_sensor_invalid` naming the config path; nothing spawns), calls `sensor_runner.run_sensor` through the module attribute (so a test spy on the module intercepts it) for each named sensor, and emits a blocking `phase_sensor_failed` diagnostic carrying the phase, the sensor name, `exit_code`, `output_summary`, and `duration_ms` for any non-zero exit, timeout, or failure to run. The gate never passes on error.
3. `required_lanes` is not part of `phase_gates`; lane policy stays in `required_review_lanes`. A `required_lanes` entry anywhere inside `phase_gates` (for example `phase_gates.close.required_lanes`) is a lint error naming the path, and prepare refuses readiness while it stands.
4. `phase_gates` enters `review_policy.policy_input_digest` only when present and non-empty: inside `if phase_gates:` the payload gains `phase_gates` and the referenced `sensors` entries (`name`, `command`, `dimension`), so swapping a required sensor's command after readiness stales the receipt just as editing the key does. When the key is absent the payload is byte-identical to today (`payload["phase_gates"] = ...` runs only inside that branch, never as `None` or `{}`; no evaluator or schema version bump), pinned by a test comparing the absent-key digest to a pre-change capture, so no readied wave's receipt moves on upgrade. After either edit, prepare `dry_run` reports `review_policy_receipt_stale` as an advisory diagnostic and `wf_review_wave(phase='prepare')` reports the readiness approval stale, the same signals other policy edits produce.
5. Sensors execute only when the phase mutates: prepare in `ready` and `create` (the orchestrator's `_mutating` modes) and close in `create` (`apply` is accepted as an alias). Prepare `dry_run` and `evaluate` and close `dry_run` execute nothing: each configured gate is listed with `outcome: "would_run"`, and the response carries one advisory diagnostic `phase_sensor_not_executed` per would-run gate, so an agent reading `diagnostics` is not told the close is ready. In the mutating modes each gate is listed as `passed` or `failed`, so the operator sees what blocked. Scope limit on ordering: in `ready` mode `_publish_prepare_policy_state` has already written the roster and receipt by the time `PREPARE_READINESS_GATES` runs, since its own guard is evaluated earlier, so a failing required sensor refuses readiness without unpublishing the receipt. Nothing is falsely approved by that, because the receipt is not a readiness approval and the missing approval still blocks activation. Scope limit on the compatibility path: `PREPARE_READINESS_GATES` runs only when `typed or (verdict_present and verdict_valid)`, so on a legacy-authority wave whose council verdict is absent or invalid a declared prepare sensor does not execute and prepare can still succeed; the response reports an empty `configured_gates`, which is how an operator sees it. `required_sensors_gate` sits in `PREPARE_READINESS_GATES` after the readiness-run evidence check and at the end of `CLOSE_HARD_GATES`, the post-secrets-gate close tuple `1y044` Requirement 2 defines. At close the blocking predicate is evaluated after every gate has run, so the sensor executes in `create` even when an earlier close gate already produced a blocking diagnostic; AC-2's failing-sensor fixture pins that the sensor result is reported beside the other blockers rather than skipped.
6. Provenance: every prepare, review, and close response carries a fixed-shape `configured_gates` list (present on every phase response; the review list is always empty because `phase_gates` has no `review` key; a gate is listed only once the response reaches the phase's gate tuple, so every prepare response that returns before `PREPARE_READINESS_GATES`, or completes with the READINESS guard `typed or (verdict_present and verdict_valid)` false, carries an empty list. That governing rule is the contract; the returns it covers today include the mode and wave-lookup errors ahead of PREFLIGHT, the post-garden `wave_record_unreadable` re-read, the first `_has_blocking_diagnostics()` return, the legacy `ready_for_council_review` return, and the `create`-mode return after `prepare_council_verdict_invalid` or `council_seats_misaligned`) with entries `{phase, gate, source: "phase_gates.<phase>.required_sensors", outcome, duration_ms}`. `outcome` is one of `would_run`, `passed`, `failed`, or `invalid`, declared as `CONFIGURED_GATE_OUTCOMES` in `public_contract.py` and consumed by the handler and pinned against `docs/specs/mcp-tool-surface.md` by a new row in `wave_lint_lib/docs_constants_validators._claims()` (today that table covers only `performance-budget.md` and `RELIABILITY.md`; CHANGELOG claims run through the separate `check_changelog_unreleased_constants` engine; so the row is added by this change, and the `wf_prepare_wave` bullet in the tool-surface doc carries the vocabulary in claim form, `configured_gates outcomes: ` followed by the backticked `/`-joined values, following the `INDEX_BUILD_CONTENT_VALUES` precedent); `duration_ms` is `null` unless the outcome is `passed` or `failed`. An operator can answer which project policy applied from the response alone.
7. The default is unchanged: with no `phase_gates` key, the phase tuples end where `1y044` left them, `configured_gates` is empty, and the existing lifecycle corpus passes unchanged.
8. Documentation: `docs/architecture/cross-cutting-concerns.md` `## Configuration` documents `phase_gates` (shape, validation rules, an example, and the policy-extension boundary sentence: project policy enters through typed configuration, never through imported code; and what a required sensor inherits when it runs, namely the server's own environment and `PATH` and a working directory of the repository root, which previously happened only on an explicit `wf_run_sensors` call and now happens automatically inside prepare and close). `docs/specs/mcp-tool-surface.md` gains one bullet per tool under `### Lifecycle Mutations` for `wf_prepare_wave`, `wf_review_wave`, and `wf_close_wave` naming `configured_gates` and the dry-run `would_run` posture, one bullet carrying the outcome vocabulary in the claim form Requirement 6 names; that bullet and the `_claims()` row land in the same change, since the lint fails on either alone. `docs/architecture/layering-rules.md` `## Boundary Invariants` gains two rows. `1y044` authors row (a) and this change authors row (b) and the `## Violation Detection` edit that names the AST tests; row (a)'s text is not repeated here, so the two documents cannot drift into two spellings of one row, and the implementer pastes it from `1y044`. Row (b), Edge `docs/workflow-config.json -> lifecycle gates`: project policy enters through typed `docs/workflow-config.json` only, the server never imports repository Python, prepare `ready`/`create` and close `create` may execute list-form `sensors` commands named in `phase_gates`, and the read-only modes execute nothing (`dry_run`, and `evaluate` which normalizes to it); verified clause by clause, the execution rule by `1y0bd` AC-2 and the provenance an operator reads it from by `1y0bd` AC-6. The decision record is `<fresh id>-adr config-declared-phase-gates.md` under `docs/architecture/decisions/` (id minted with `wf_new_change` at implementation time), linked from `docs/architecture/decisions/README.md` and `docs/ARCHITECTURE.md`.
9. The golden tool-surface fixture is unchanged: no tool gains or loses a parameter. The `1y044` lifecycle golden is regenerated once `configured_gates` lands (see Tasks).

## Scope

**Problem statement:** A team that needs a policy beyond the defaults, such as a release checklist script that must pass before close, has no declarative way to attach it to a lifecycle phase.

**In scope:**

- The `phase_gates` key, its validation helper, `sensor_runner.py`, the `required_sensors_gate` unit, digest inclusion, `configured_gates` provenance, and documentation.
- Fixture repositories exercising pass, fail, timeout, unknown-shape, and dry-run cases.

**Out of scope:**

- Loading Python policy modules from the repository by convention or by config (rejected posture; see Decision Log).
- `required_lanes` inside `phase_gates` (dropped 2026-09-18; see Decision Log). Lane policy stays in `required_review_lanes`.
- New sensor kinds or changes to how `sensors` entries are shaped.
- Requiring a specific signoff key other than the existing lanes.
- Seed and `AGENTS.md` prose describing the key in target repositories; recorded as a seed-gated follow-up in the wave watchpoints.

## Risks


| Risk | Mitigation |
| ---- | ---------- |
| A required sensor is a long-running command and slows every mutating prepare or close call | `run_sensor` applies the caller-resolved `timeout_seconds` (`subprocess_ops.sensor_timeout_seconds` when set, otherwise 120) and reports `duration_ms` in `configured_gates`; the configuration documentation recommends fast checks |
| Mutating lifecycle calls (prepare `ready`/`create`, close `create`) now execute repository-declared commands that today run only through `wf_run_sensors` | Honest trust-boundary widening, mitigated three ways: only list-form commands are accepted as required sensors (no `shell=True`; a non-list command is refused before any spawn), `dry_run` and `evaluate` execute nothing, and the commands are committed, reviewed configuration rather than discovered code |
| "The existing sensor execution path" was an unnamed proposition, not falsifiable as written | Archetype Council (Spock, 2026-09-17): the function is now named, `sensor_runner.run_sensor`, with its signature, result fields, and passing signal (`returncode == 0`) stated in Requirement 2 rather than left to be discovered at implementation time |
| The `phase_gates` validation helper and the existing `wave_review` branch of `check_workflow_config` do not compose in one lint pass | A fixture with an invalid `wave_review` block and an invalid `phase_gates` block asserts both errors report in one docs-lint run (AC-4) |
| Waveforge's real fork has a git-branch-integrated, PR-gated review workflow (`review_policy.mode: pr_review`, `branch_at: wave`, `allow_self_attestation`) that `required_sensors` does not express | Confirmed 2026-09-17 (`docs/reports/waveforge-fork-audit.md`, whose `required lanes` mention predates operator decision B); explicitly out of scope for this change, not silently missed. Branch emission and PR-gating are a separate policy axis worth its own change if the operator wants Wavefoundry to generalize what Waveforge already built rather than leave it as their own fork-only code |
