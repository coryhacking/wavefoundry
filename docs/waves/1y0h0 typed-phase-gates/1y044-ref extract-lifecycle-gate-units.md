## Rationale

**Brief.** Goal: turn the prepare, review, and close checks into an ordered list of named, independently tested gate units per phase, with no behavior change, so the companion change can add config-declared gates at a seam instead of inside orchestrator bodies. Audience: framework maintainers. Approach: a flat sibling module with a small context type and phase lists; checks extracted one to one. Constraints: diagnostics identical on the existing corpus; evidence read only through the `review_evidence` facade; hot-reload safe. Success: the lifecycle test corpus passes unchanged against gates driven from the lists.

Verification found the checks partly factored already. The orchestrators `wf_prepare_wave_response`, `wf_review_wave_response`, and `wf_close_wave_response` in `server_impl.py` run several hundred lines of inline sequencing each, but the load-bearing checks live in named helpers: `_evaluate_shared_delivery_state`, `_review_evidence_diagnostics`, `_wave_review_policy_diagnostics`, and the framework test receipt pair `_framework_test_receipt_status` and `_framework_test_receipt_diagnostic`. `events.jsonl` is already the only signoff authority through `review_evidence.read_review_event_ledger`. The RFC's claim that gating is uniformly interleaved holds for one phase only: review and close are cleanly factored (each reads its evidence once, runs its checks, and returns), but prepare is interleaved. Its checks fall into four clusters separated by three writes (`_move_change_doc` inside the per-change loop in the mutating modes, `run_garden`, and `_publish_prepare_policy_state`) and five early returns the orchestrator retains between the clusters (the post-garden `wave_record_unreadable` re-read, the first `_has_blocking_diagnostics()` return, the legacy `ready_for_council_review` verdict return, the `create`-mode return after `prepare_council_verdict_invalid` or `council_seats_misaligned`, and the second `_has_blocking_diagnostics()` return); two further returns (`review_projection_failed` and the live re-read) and the review-status projection write sit after the last tuple and do not affect placement. `_review_evidence_diagnostics` is called at three points of prepare's control flow: before gardening, and then once in each of two mutually exclusive branches (typed authority; legacy authority with a present and valid verdict) where calls 2 and 3 are the readiness-run check itself. The extraction is therefore small for review and close; prepare needs staged tuples rather than one list, and the helper set the units reach transitively is the Requirement 3 list, derived by AST closure in the census task rather than by hand.

Re-verified 2026-09-18 after `8545c4f9` (wave 1y0gz): `review_policy.py` gained `import record_paths`, `SCAFFOLD_DOC_NAMES`, and `scaffold_docs()` only; the eight functions above are body-unchanged; three of them (`wf_prepare_wave_response`, `wf_review_wave_response`, `wf_close_wave_response`) gained the `@_fail_closed_on_record_layout` decorator, a success-path pass-through, and `review_policy.py` also rewrote `SCAFFOLD_DOCS` to derive from `record_paths.PLANS_ROOT`. Separately confirmed no vocabulary collision: the new `setup_readiness.py` module (from `1y3og setup-local-reconciliation`) introduces its own `ready` / `action_required` / `indeterminate` status concept for environment and index readiness, entirely distinct from wave-lifecycle prepare/review/close readiness and its own config surface. The two never share a config key or a status enum.

## Requirements

1. A new module `.wavefoundry/framework/scripts/lifecycle_gates.py` defines `GateContext`, `GateDiagnostic` (the `_diagnostic` payload dict as produced by `lifecycle_gate_support._diagnostic`: `code`, `message`, and the optional `recovery_tools`, `recovery_usage`, and constant `advisory` keys the producer emits only when non-empty or true; units emit literal codes so the advisory-site AST scan reads each site's code from a literal first argument rather than recording `<helper-call>` in the code slot, with one carried-over exception the scan's expected set already holds, the dry-run advisory whose first argument is a helper call rather than a code, and the `advisory` key stays a constant so `_has_blocking_diagnostics`, which keys on that flag rather than the code, works unchanged). `GateContext` is a dataclass, so AC-6 can compare context reads against `dataclasses.fields(GateContext)`, `GateResult(diagnostics: list[GateDiagnostic], data: dict)`, and a `Gate` signature `check(ctx) -> GateResult`. The tuple entries are the units, adapters included, and every one is a module-level function, never a `partial` or a lambda, so AC-2's meta-test has one name per entry: the advisory-site scan keys each sanctioned tuple on the bare enclosing function name, so class-shaped units would key every tuple on a shared method name and lose the owner resolution that test is built on. `GateContext` carries data only, never callables (AC-6 also fails any `ctx.<field>(...)` call and any alias assignment of the context parameter), and carries an input only when at least two units read it (the converse is not a rule: a closure argument with two readers may stay a closure argument, and AC-6 enforces only the necessary direction); single-reader inputs (the framework test receipt, the gardener result, the orchestrator's `other_active` lookup for the single-OPEN guard) stay unit-local closure arguments. Its fields are exactly six, each read by at least two distinct units, and stay six for `1y0bd` as well, whose `required_sensors_gate` reads `phase_gates` through a config reader from `ctx.root` like every other config reader rather than adding a field, each named with the two or more distinct units that read it, which AC-6 enforces: the repository root and the wave record path `wave_md` (nearly every unit), `wave_text` (PREFLIGHT, READINESS, the close checkbox unit, and the shared delivery unit), `mode` (the POLICY dry-run advisory unit, the ACTIVATION single-OPEN guard, and the per-change location unit, which owns the `_mutating`-gated `change_doc_not_relocated` emit), `lint_result` (prepare PREFLIGHT (iv), review's `prepare` branch, and the shared delivery unit), and `phase`, whose value domain is the lifecycle phase `prepare`, `review`, or `close`, exactly the vocabulary `_evaluate_shared_delivery_state` already takes as `lifecycle_phase` and exactly the vocabulary `phase_gates` keys. Its readers are the gardener translation unit, the shared delivery adapter, and `1y0bd`'s sensor gate. Review's own sub-phase (`prepare` or `implementation`, from which the prelude derives its `required_run_kind`) is a different vocabulary and stays a closure argument the review orchestrator passes to the prelude and branch units; conflating the two would feed `prepare` into the council-signoff key selection, which keys on the lifecycle phase and would silently change the required set. A field rather than a per-tuple closure argument because `1y0bd`'s sensor gate is one module-level function in two tuples, and binding the phase per placement would make it two unit names, splitting AC-2's coverage and the advisory scan's owner keying. Everything else is a closure argument the orchestrator passes, not a field, because it has one reader or none: the review-event records (every evidence consumer re-reads through the `review_evidence` facade from `ctx.wave_md`), the workflow config, which is not a field and not a closure argument either, because each reader calls the support module's config reader itself, the admitted change doc, which the per-change units receive as a loop argument while the close checkbox unit derives its own ids from the wave text, `policy_state` and `policy_state_errors`, which only the POLICY units consume, and `council_brief`, which no unit reads at all (the orchestrator computes it for the receipt binding, the inline verdict block, and the response payload). The orchestrator computes that policy data by calling `_build_prepare_council_brief` and `_prepare_policy_state` under their bare bound names, since the module-attribute rule of Requirement 3 exists for units, whose calls a `patch.object(server_impl, ...)` cannot reach, and orchestrator calls have no such need; those two move to the support module with their callees (Requirement 3) because `_review_policy_receipt_diagnostics`, which the POLICY advisory, `_evaluate_shared_delivery_state`, and review's `prepare` branch all reach, calls both, and a support module that called back into `server_impl` would fail AC-8. The ledger is read only through the facade: every unit that needs records calls the facade with `ctx.wave_md`, so "read once" is not claimed. Units that feed response data contribute it once through `GateResult.data` rather than being recomputed by the orchestrator: `framework_test_receipt`; `required_lanes`, `lane_results`, `council_results`, and `operator_current` from `_evaluate_shared_delivery_state`; `active_wave_id` and `active_wave_path` from the single-OPEN guard; and `required_council_signoffs`, `max_severity`, `blocking_diagnostics`, and the resolved `authority` object (internal, never serialized). ## Scope

**Problem statement:** Gate checks are named helpers called from long orchestrator bodies, so adding a check means editing the orchestrator and there is no single place that states what a phase requires.

**In scope:**

- The gate module, the `lifecycle_gate_support.py` helper module, context, diagnostic and result types, and the phase tuples (single for review and close, staged for prepare).
- One-to-one extraction of the existing checks and their unit tests.
- The facade-only evidence test, the import-direction test, the AST field-reader test, the reload pickup test, and the purge-set entry.
- The three lifecycle fixture repositories and their committed golden.

**Out of scope:**

- Any new gate, any config-driven gate, and any change to which lanes or signoffs a phase requires.
- Extracting the orchestrators' non-check sequencing (mode validation, wave lookup, garden and lint invocation, `_publish_prepare_policy_state`) out of `server_impl.py`.
- The inline `_find_other_active_wave` calls in `wf_implement_wave_response` and `wf_reopen_wave_response`; they stay where they are.
- `_force_gates_closed` in `wf_pause_wave_response` and `wf_close_wave_response`.
- The upgrade-time hook system in `upgrade_extensions.py`.
