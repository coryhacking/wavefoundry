# Wavefoundry Documentation

Owner: Engineering
Status: active
Last verified: 2026-08-18

Wavefoundry is an agent harness: the Wave Framework seed pack, the framework scripts that do the mechanical lifecycle work, a local MCP server that AI coding agents talk to over stdio, and an optional loopback-only dashboard. Installed into a target repository, it wraps AI coding agents with feedforward guidance (seed prompts), feedback sensors (computational checks and reviewer lanes), and structural lifecycle enforcement, and it keeps that state in plain files that survive context loss ([Project overview](references/project-overview.md), What Wavefoundry Is). Wavefoundry is a framework and tooling repository, not a product application; it ships no networked service ([Architecture](ARCHITECTURE.md), Scope). The MCP server is one Python process, `server.py`, that builds a FastMCP app and runs it over stdio (`server.build_server`, `server.py` lines 486-563; `server.main`, lines 582-624).

## Who this site is for

This site is for people: developers evaluating or adopting Wavefoundry in their own repositories, operators who install, upgrade, and run the wave lifecycle, and maintainers of the framework itself. The same pages are also read by AI agents at session start; the [Project overview](references/project-overview.md) and [Architecture](ARCHITECTURE.md) pages are agent startup-order surfaces and MCP resources (`wavefoundry://overview`, `wavefoundry://architecture/current-state`; [Data and control flow](architecture/data-and-control-flow.md), Path 6b step 2; the `@mcp.resource` registrations in `server_impl.register_mcp_surface`). Reader-facing framing on those pages sits around the agent-orientation content, never in place of it. Agent operating surfaces such as the root `AGENTS.md`, `docs/agents/`, the prompt bodies under `docs/prompts/`, and the wave records under `docs/waves/` are named here by repository path and are not part of the built site.

## Install and upgrade at a glance

- **Prerequisite.** Python 3.11 or newer on PATH as `python3`; the tooling uses a shared user-level venv at `~/.wavefoundry/venv` ([Architecture: current state](architecture/current-state.md), Python environment contract). Native Windows, WSL2, macOS, and Linux are first-class ([Project overview](references/project-overview.md), Supported Platforms; [Native Windows support](references/native-windows-support.md)).
- **Install** is two-phase and gated by a markdown install log ([Install log format](references/install-log-format.md), lines 7-14). `wf setup` (`setup_wavefoundry.py`; `wf_cli.py` line 54, writer-verified) completes Phase 1 in a fixed order: absent-only workflow config, host surface rendering, dependencies into the tool venv, an MCP server dry-run, then the semantic and graph index (`setup_wavefoundry.main` steps 0-4; `server.main --dry-run`, `server.py` lines 586-615). After the agent host restarts, Phase 2 proceeds under `wf_audit_install()`, which reads the live install log and reports one of `missing_log`, `unparseable_log`, `lint_errors`, `checked_but_missing`, `next_step`, `phase_complete`, or `complete` (`server_impl.wf_audit_install_response`).
- **Upgrade** (`wf upgrade`, `wf_cli.py` line 53, writer-verified; `wf_upgrade` over MCP) is phased: pre-flight, surface rendering, prune, docs gate, then index update and cleanup, with exit codes 0-3 plus 4 from the memory-backfill action-required path (`wf_upgrade`, `server_impl.py`; `upgrade_wavefoundry.py` lines 25-30; `memory_backfill.ACTION_REQUIRED_EXIT`). It speaks upgrade protocol 2 (`upgrade_protocol.UPGRADE_PROTOCOL_VERSION`) and extracts only zip members under `.wavefoundry/` plus one transient root bootstrap file, so a release archive cannot scatter files across the target project (`upgrade_wavefoundry._EXTRACT_MEMBER_PREFIX`, line 910; `_extract_feature_members`, lines 914-928).
- **Packaging** (maintainers). `build_pack.py` stamps `.wavefoundry/framework/VERSION` as `MAJOR.MINOR.PATCH+<build>` and writes a source-only zip under `~/.wavefoundry/dist/` by default; tests, the test runner, and `build_pack.py` itself stay out of the pack (`build_pack.write_pack_version`, lines 256-259; `build_zip`, lines 742-876; `_DEFAULT_DIST_DIR`, line 68; `EXCLUDED_REL_PATHS`, lines 39-47). Model assets are an optional, separately versioned zip; the active bundle is model set 3 (`model_bundle.MODEL_SET_VERSION`, line 21): the same Arctic Embed S plus MiniLM L6 reranker weights as set 2 with one reference file corrected and the embedding fingerprint unchanged ([Model selection](references/model-selection.md); [Architecture: current state](architecture/current-state.md), `build_pack.py` block and Model set contract). Release mechanics: [Release flow](references/release-flow.md).

Local-only means no hosted service and no listener, not an air gap: setup may install Python packages and download embedding models on a cold cache, then verifies the model cache in offline mode so later queries do not need the network (`setup_index.prewarm_models`; `accel_embedder._hf_download_cached_first`, lines 225-273; `setup_index._offline_env`, lines 597-607).

## The wave lifecycle in one list

Every code change moves through the same lifecycle. The bold phrases are shortcut commands agents understand; in Claude Code, Codex, and Antigravity each is also a `/wf-` skill that points at the same prompt ([Project overview](references/project-overview.md), Workflow Overview; full catalog: [Workflow and agent commands](prompts/index.md)).

1. **Plan feature**: author a consolidated change doc under `docs/plans/`.
2. **Create wave / Add change to wave**: admit the change into a wave under `docs/waves/<wave-id>/`.
3. **Prepare wave**: confirm readiness. Readying does not open the wave; any number of waves can be readied in parallel.
4. **Implement wave**: open a readied wave and execute the admitted changes. Only one wave may be OPEN at a time, and that guard fires here, at activation, not at readiness (`wf_prepare_wave` docstring and `wf_implement_wave`, `server_impl.py`).
5. **Review wave**: run the required review lanes. Review evidence lives in `docs/waves/<id>/events.jsonl`, the sole machine authority; `wave.md` is a generated projection ([Data and control flow](architecture/data-and-control-flow.md), State Ownership; [Domain map](architecture/domain-map.md), Dependency Direction Rules).
6. **Close wave**: record closure and archive the wave.

## Search and navigation

Wavefoundry builds exactly one semantic index per project at `.wavefoundry/index/` (gitignored, derived, rebuildable): docs and code Lance tables plus a graph store, with `index-state.sqlite` as the sole index-state authority ([Chunking and indexing pipeline](architecture/chunking-and-indexing-pipeline.md), lines 51-68; [Cross-cutting concerns](architecture/cross-cutting-concerns.md), line 30; `indexer.INDEX_DIR_NAME`, line 46). Framework seeds fold into that same docs table at setup and upgrade, so no separate framework index ships ([ADR index](architecture/decisions/README.md), Index row `1p4xx-adr`), and only the MCP server reads it ([Domain map](architecture/domain-map.md), Dependency Direction Rules item 6). `index_health` reports whether each layer is ready (`index_health`, `server_impl.py`).

Agents reach the index and the repository through MCP tool families; every tool below is registered in `server_impl.register_mcp_surface`:

| Family | Examples |
| --- | --- |
| Semantic search and codebase Q&A | `code_ask`, `code_search`, `docs_search` |
| Exact navigation | `code_read`, `code_keyword`, `code_outline` |
| Symbol and graph navigation | `code_definition`, `code_references`, `code_callhierarchy` |
| Wave lifecycle | `wf_implement_wave`, `wf_upgrade`, `wf_audit_install` |
| Docs gate | `wf_validate_docs`, `wf_garden_docs` |
| Agent memory | `memory_add`, `memory_propose`, `memory_search` |
| Index operations | `index_health`, `index_build`, `index_build_status` |

Read-only MCP resources such as `wavefoundry://overview` and `wavefoundry://waves` expose the same documents without a tool call (the `@mcp.resource` registrations in `server_impl.register_mcp_surface`; [Data and control flow](architecture/data-and-control-flow.md), Path 6b step 2). Retrieval design lives in [Search architecture](architecture/search-architecture.md) and [Graph index system](architecture/graph-index-system.md); the full tool contract is `docs/specs/mcp-tool-surface.md` (repository path, outside this site). Before opening files, the generated [codebase map](references/codebase-map.md) shows the code's major areas and entry points (its per-area "Area context" entries link to `AGENTS.md` files that this site does not publish, which `wf techdocs-audit` reports as two `techdocs_link_outside_boundary` findings; the repair belongs in `gen_codebase_map._area_context_link_href`, which should emit those targets as prose paths).

> **Docs gate.** Every page under `docs/` carries `Owner`, `Status`, and `Last verified` metadata and passes docs lint. Agents run `wf_validate_docs` and `wf_garden_docs` over MCP (`wf_validate_docs` and `wf_garden_docs`, `server_impl.py`; `docs_gardener.gardener_run`, lines 282-320); the CLI fallback is `wf docs-lint` (`wf_cli.py` line 37, writer-verified).

> **Dashboard.** `wf_start_dashboard` (`server_impl.py`) or `dashboard_server.py` serves a loopback-only, read-only viewer of waves, plans, and repository state from `.wavefoundry/framework/dashboard/`. It binds to `127.0.0.1` by default and warns on any other host (`dashboard_lib.read_dashboard_config`, lines 193-214; `dashboard_server.main`, lines 990-996; `_LOOPBACK_HOSTS`, line 629), writes only host-local state: its lock/metadata carrier at `.wavefoundry/locks/dashboard-server.lock` (`dashboard_lib.dashboard_metadata_path`, lines 217-225) and a diagnostic log at `.wavefoundry/logs/dashboard.log` (`dashboard_server._dashboard_log`), and never mutates docs, wave state, git-tracked state, or the index ([Domain map](architecture/domain-map.md), Dependency Direction Rules item 5). Its browser assets (pinned React, React DOM, and elkjs) load from unpkg on first load ([Data and control flow](architecture/data-and-control-flow.md), Path 7 step 5). Setup notes: [Dashboard install and upgrade](references/dashboard-install-upgrade.md).

## Security posture

Wavefoundry is local developer tooling that runs with the operator's own authority. It exposes no network-facing service: the MCP server speaks over stdio (`server.main`, `server.py` lines 582-624) and the optional dashboard binds to `127.0.0.1` by default and warns on any other host (`dashboard_lib.read_dashboard_config`, lines 193-214; `dashboard_server.main`, lines 990-996). The operator, the repository's own contents, and same-user local processes are trusted; the [threat model](architecture/threat-model.md) reserves security severity for findings that pass its five-factor credible-threat gate and names the deployment changes (non-loopback binding, multi-user operation, untrusted-repository analysis, forked-PR CI, privilege separation) that would re-scope it (Threat Actors and Trust Classification, Credible-Threat Gate, Promotion Triggers; `docs/SECURITY.md`, Security Posture). Shipped guardrails are conservative rather than defensive: MCP navigation tools confine every path argument to the repository root the server was started with (`_resolve_repo_path`, `server_impl.py`); seed prompts and framework surfaces are edit-gated behind a local, gitignored approval file plus a rendered pre-edit hook (`_VALID_GATES`, `server_impl.py`; `claude_pre_edit_source`, `render_platform_surfaces.py` lines 624-650), which a plain shell edit can bypass, as the trust model accepts; renderers refuse to follow a symlink out of the repository before they write (`_preflight_platform_render_paths`, `render_platform_surfaces.py` lines 140-176); lifecycle mutation tools default to a dry run (`wf_prepare_wave` and `wf_close_wave`, `server_impl.py`); and a Gitleaks-derived secrets scan (`wf_scan_secrets` over MCP, `wf secrets-scan` on the CLI, rules in `.wavefoundry/framework/scan-rules.toml` plus the project `docs/scan-rules.toml`) feeds a triage lifecycle in `docs/scan-findings.json` that blocks wave close on unclassified findings (`wf_scan_secrets_response` and `_check_secrets_gate`, `server_impl.py`; `wave_lint_lib/constants.py` lines 271-274). Two items the security docs still label as future rather than shipped: a configurable allowed-roots allowlist (the shipped mechanism is per-tool confinement to the startup root) and diff-plus-confirmation on mutation tools (`docs/SECURITY.md`, Future Security Concerns). The project does not claim authentication on the MCP server or the dashboard, code signing or checksums for release zips, sandboxing, or protection against a hostile same-user process; the "low-risk" line in `docs/SECURITY.md` is a self-assessment tied to the current single-user loopback deployment, not an audit result.

## What this site publishes

The built site contains this landing page, [Architecture](ARCHITECTURE.md) and everything under `architecture/`, everything under `references/`, and the [command catalog](prompts/index.md). Agent operating surfaces are referred to by repository path instead: those under `docs/` (`docs/agents/`, prompt bodies under `docs/prompts/`, `docs/waves/`, `docs/plans/`, `docs/specs/`, `docs/contributing/`, `docs/reports/`) are removed by the `exclude_docs` block in `mkdocs.yml`, while root-level files such as `AGENTS.md` sit outside `docs_dir` and are never site sources at all. `catalog-info.yaml`, `mkdocs.yml`, and this page were first materialized by `wf techdocs-baseline`, an explicit, missing-only command that runs only when the three navigation targets exist, is never run by setup or upgrade, and registers nothing with Backstage and builds nothing (`render_agent_surfaces.render_techdocs_baseline` and `techdocs_missing_targets`; the thin entry `techdocs_baseline.py`); the project now owns all three files. Registration and publication remain operator-owned.
