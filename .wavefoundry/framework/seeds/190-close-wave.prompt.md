# 190 - Close Wave (Shortcut)

Use this when you want a single command-style request such as:

- `Close wave`
- `Close spec` (alias: `Close change`; one change inside the open wave; see **Close spec** below)

Intent:

- Close a wave after implementation is complete, required reviews are recorded, and durable learnings are ready for promotion or archival. **Close wave** is the only wave close, whatever the change count.

Operator trigger:

- Run this body only when the operator invoked **`Close wave`** in the current request **or** explicitly confirmed closure (e.g. yes after you asked). Do not infer it from a prior **`Implement wave`** / **`Implement spec`** request alone.

Required closure tasks:

1. Confirm every admitted change is `implemented`, `complete`, or `deferred` with rationale, matching the `wf_close_wave` open-changes gate. **Close spec** is optional: use it to mark a single change `complete` and activate its dependents inside the open wave.
2. Verify that all waves are `completed`, `superseded`, or intentionally archived.
3. Confirm each wave's chronology metadata is up to date, especially `Completed at`.
4. Confirm each closed wave has a readable final `Title` and folder-safe summary slug derived from the implemented changes.
5. Reconcile plan-index and wave-listing surfaces so a closed wave and its admitted specs are no longer advertised as `active`.
6. Reconcile behind-the-scenes operational artifacts: wave memory and next-step handoff state.
7. For each applicable review lane, produce an actual review output rather than a pass/fail placeholder — record the findings in the wave's review checkpoint section in wave.md; retain a separate file only for justified unique long-run proof:
   - **code review** (`code-reviewer`): patch-level logic and state handling; required whenever `docs/contributing/agent-team-workflow.md` / the final readiness evaluation selects `code-reviewer` or the wave changed non-trivial control flow or product implementation. The output must be more than "LGTM": explicitly address **branch completeness** and **re-entrant state** when the change touches per-key mutable state (for example `[String: Date]` grace maps, caches, or actor fields updated across timer/loop/step calls). Minimum bar: for each such map or field, either note "not touched by this wave" with evidence, or walk **set / clear / unchanged** across **every** branch (including `else` arms when a flag like `powerStateChanged` splits paths) and across **repeated calls** of the same function; when two similar functions exist (for example `checkDawnSleepOverridesWithDelays` vs `checkDawnSleepOverrides`), call out symmetry or intentional differences. Omit only for trivial docs-only changes
   - **architecture review** (`architecture-reviewer` — `seed-214`): when `architecture-review` is declared in `required_review_lanes` or when the wave touched module boundaries, use `214-architecture-reviewer.prompt.md` to run a structured review. The reviewer reads `docs/architecture/` before assessing; record the structured verdict (`approved`, `approved-with-notes`, or `needs-revision`) with severity and findings in Review Evidence. For ad-hoc assessment without the seed: describe what boundaries or module interfaces were touched, whether the change is consistent with existing patterns, and any design decisions that should be recorded. Omit only when the change clearly touches no module boundaries and `architecture-review` is not a declared required lane.
   - **QA review** (`qa-reviewer`): **required for any bug fix** affecting product behavior (`change-id` kind `bug` or user-visible defect repair) — minimum bar; describe what behaviors were verified, which behavior contracts or other contracts were checked against, and any edge cases confirmed or deferred; when state persists across steps or timer ticks, require or record **multi-step** verification (match → mismatch → match, or equivalent) or an explicit deferral with residual risk. For non-bug changes, omit only when the change is trivial docs-only work or when `docs/contributing/agent-team-workflow.md` / readiness evaluation explicitly does not select `qa-reviewer` (record why). For closed waves that predated this policy, a **retrospective QA** entry in **Review checkpoints** is acceptable when bringing the record into compliance
   - docs-contract review: name which canonical docs were updated to reflect durable outcomes from this change, including behavior contracts when runtime contracts changed rather than only workflow or wave-local artifacts; if a follow-up review finds stale docs after a wave was marked complete, repair both the canonical docs and the wave checkpoint text before treating the review lane as reconciled
   - security review: confirm no new surfaces, data exposures, or trust boundary changes were introduced, or document what was scoped in; required for any change touching notification, network, or persistence surfaces
   - performance review: confirm no hot-path regressions, polling frequency changes, or synchronous additions were introduced without guards; required for any change touching scheduling, timers, or per-request paths
   - record why a lane was skipped rather than leaving the checkpoint blank
   - **Close wave and behavior contracts:** When using `Close wave`, if the wave’s admitted changes touched any `docs/specs/*.md` or other canonical docs that define runtime behavior, closure is incomplete until **docs-contract review** (behavior contract review) is recorded in the wave’s **Review checkpoints** — scope, evidence, findings or explicit clean bill. If no behavior contract or equivalent canonical doc changed, record **Docs-contract review: not applicable** with a one-line rationale; do not omit the checkpoint entirely.
   - **product-owner review** (`product-owner`): when the wave changed product behavior, UX, or durable feature semantics, record alignment with the wave **Objective** and admitted changes' **Product Intent**, list **`docs/specs/*.md`** files updated to reflect **final** intent, or **product-owner: N/A** / no behavior contract promotion with rationale. Framework-only or internal-tooling waves may use **N/A** when no product semantics moved (`docs/agents/product-owner.md`)
8. Confirm the readiness Council signoff when review is enabled and the delivery Council signoff when the current Prepare receipt/configured delivery mode requires it (on a wave declaring `review-evidence-source: events.jsonl` these are phase-scoped typed approval events via `wf_review_event`, projected into `## Review Evidence`; prose signoff lines count only on legacy waves):
   - `council-readiness`
   - `council-delivery`
   Record the narrative council synthesis in `## Review checkpoints`. The council-chair owns those verdicts. The checkpoint must include the phase roster, the rotating fifth seat when present, any material disagreements between seats, and how those disagreements were resolved or why they remain unresolved. Wave Council is universal meta-review and does not waive blocking required specialist lanes.
9. **Design language closure checkpoint**: when the closed wave's admitted changes touch any source path in `docs/repo-profile.json` `design_system.ui_roots` (or when the `design_review` trigger fired during the wave), record a design-language review checkpoint before closure: (1) confirm that new color usage, component patterns, or HIG departures introduced by the wave are either already documented in `docs/design-system/design-language.md` or are scheduled for promotion in a follow-up; (2) if any `## Design Intent` section from the wave's specs contains departures from the HIG, verify those departures were not silently dropped; (3) note whether `docs/design-system/design-language.md` needs a `Last verified:` date refresh; (4) if the wave's `## Design Intent` named a platform surface and `docs/design-system/platforms/<surface>/` exists (Split C), confirm that any per-surface token overrides or narrative deltas in that directory are up to date with what the wave delivered — record "Platforms delta: not applicable" when `platforms/` is absent or the wave targeted no specific surface. If the wave touched no `ui_roots` paths, record "Design language checkpoint: N/A — no UI surface changes" and continue.
10. Final review evaluates any reviewer/persona lanes newly applicable to the delivered scope. This is not a blanket rerun of an unchanged readiness Council. Material policy, roster or readiness changes follow existing re-Prepare and current-approval requirements; otherwise consume the current readiness authority and complete the required delivery reviews. A change admitted after delivery review makes the earlier delivery approvals not current once the wave is re-prepared, so re-Prepare, then record the affected delivery approvals again before closing.
11. Capture durable operating-memory signals as typed memory candidates: high-salience observations, operator directives, bugs that reached review, rework cycles, invalidated assumptions, hard-to-find constraints, and mistakes corrected. Do not record tasks that completed normally — absence of new candidates is correct when work went smoothly; the close-time validation checkpoint triages every candidate that exists.
12. Update core memory with durable lessons. Memory captures recurring patterns and critical constraints — things that would help a future agent avoid a mistake, retrieve the right guidance, or preserve role/persona behavior after context loss. Do not add memory entries for routine outcomes that taught nothing non-obvious. When MCP memory tools are attached, first run `memory_propose(wave_id, mode='dry_run')`. Assess each proposal for concrete future action, canonical overlap and current contained target before creating anything. Select only useful source-event IDs with `memory_propose(wave_id, mode='create', source_events=[...])`; omitted selection creates nothing and explicit empty selection is a no-op. Record the retrospective and any no-new-memory rationale inline in wave.md, without per-repair rejection files. Review every actual wave-linked pending candidate, even when its target disappears or it no longer appears in proposals. Use `memory_validate` for evidence-derived records; review manually selected candidates through the existing `memory_reconcile` status transition to active or rejected: follow the linked evidence and current target; state what changes the next action; check durability, canonical overlap, target accuracy, duplicate/contradictory records, and confidence; choose promote, retain, reject, or rewrite. A canonical contract that already fully owns the rule is normally a rejection, while a practical action-time gotcha may supplement it. This is a bounded focused pass, not a new council; a wave may correctly yield zero memories. History and rejected source dispositions are preserved so later runs do not regenerate or silently rewrite them.
   - `docs/references/project-context-memory.md` — reusable workflow guidance derived from real incidents or recurring patterns; add an entry only if it would prevent a future mistake or surface a non-obvious constraint
   - `docs/RELIABILITY.md` — reliability patterns, recovery behaviors, catch-up policies, or failure modes addressed by this change
   - `docs/ARCHITECTURE.md` — hub updates when child architecture docs changed
   - `docs/architecture/domain-map.md`, `docs/architecture/layering-rules.md`, `docs/architecture/cross-cutting-concerns.md` — when boundaries, dependency rules, or shared concerns moved
   - `docs/architecture/data-and-control-flow.md` — when control paths or authoritative state ownership changed
   - `docs/architecture/testing-architecture.md` — when test tiers, target ownership, CI gates, or doubles policy changed
   - `docs/architecture/decisions/` — new or superseded records when durable choices were made
   - `docs/QUALITY_SCORE.md` — quality posture changes or tech debt resolved by this change
13. Promote repeated durable lessons to their correct destinations (persona docs, canonical behavior contracts, workflow docs). When a repeated finding can be checked mechanically, name a check as a destination too: a sensor registered under `sensors` in `docs/workflow-config.json` (run by `wf_run_sensors`), a docs-lint rule or a test, and plan it as a change unless this wave already delivers it.
14. Archive or freeze change-local wave memory and close or clear transient handoff artifacts.
15. Confirm the wave-owned specs are already in place. For each item in the closed wave(s), verify `docs/waves/<wave-id>/<change-id>.md` exists and repair any stale references that still point at `docs/plans/` staging paths before closure. The wave folder is the permanent archive and active working home; normal wave flow should not route admitted docs through `docs/plans/completed/`.
16. Consolidate routine review outcomes in wave.md. Retain and archive only justified unique long-run reports owned by this wave into its folder. Use references and contents to establish ownership; dates within `Activated at`–`Completed at` are discovery hints only. Leave unrelated reports in place. Summarize archived findings in the existing `## Reports` section of `wave.md`, then follow **Wave-folder cleanup** below before final validation. Preserve ledger-cited report paths rather than moving them for tidiness. Duplicate reports may be removed only under the cleanup checks below.
17. Refresh role/persona guidance when lessons changed their operating advice, and retire stale cautions. For each active caution and memory record touched by this wave: ask whether the risk still exists in the current codebase. If the root cause was fixed by this change, retire or supersede the memory record — do not leave it as a false warning for future agents. Stale cautions are actively harmful: they train agents to distrust memory.
   - When physical memory archival is available, treat it as a separate,
     explicit retention judgment after reconciliation—not an age-based cleanup.
     Only `stale`, `superseded`, or `rejected` records are eligible through
     `memory_reconcile(status='archived', archive_reason=...)`. Before setting
     `eligibility_confirmed=true` for a decision, operator preference, or
     fragile-file record, verify against current evidence that it is no longer
     operational. Archival renames the body and leaves a compact active pointer;
     it never deletes history.
18. Framework test receipt (framework SOURCE repositories only, and automatic): where a repository carries its own framework test runner, `wf_close_wave` verifies the EXISTING test receipt rather than running anything — it reads the recorded result and the recorded input hash, and blocks close as "not proven" when that receipt is missing, red, unreadable, or written for a different framework tree. The check runs no suite and spawns no subprocess; it hashes the framework tree once, which is milliseconds, not a test run. Its scope has two halves and both matter: the receipt's hash covers `.wavefoundry/framework/` only, so a documentation edit never makes a standing receipt stale; but the receipt is written only on a WHOLE-suite pass, so a suite failure triggered by documentation content prevents a NEW receipt from being written. The practical consequence: if the framework tree also changed, the standing receipt is stale and close is blocked; in a documentation-only wave a current green receipt persists and close is not blocked despite a red suite. A green receipt attests the framework code, not the tree. In a repository that consumes the packaged framework, the runner and its receipt are not part of the distribution, so the check is a documented no-op that neither blocks close nor claims proof. There is nothing to do by hand here; read the `framework_test_receipt` field on the `wf_close_wave` response.
19. Run the docs gate: **agents with MCP** — **`wf_garden_docs`** then **`wf_validate_docs`** (or **`wf_audit`**); **operators / CI / no MCP** — **`wf docs-gardener`** then **`wf docs-lint`**. Pass `--date <YYYY-MM-DD>` only when overriding today’s date; use `--paths <doc>` or `--all-docs` to stamp files that are not git-changed.

Finish material documentation, source and surface-rendering edits before the canonical source suite. Validated routine ledger/projection updates and normalized progress/status/completion may continue under seed 209's Continuation And Qualification Discipline; they alone require neither another suite nor another reviewer cycle. Use Progress Log during a run; the standalone session handoff and other documentation outside the wave under test may also change during it, as seed 209 describes. A current green receipt with matching inputs is reusable; changed, red or unproven inputs require fresh qualification. Consume successful `wf_review_event(mode='create')` continuation actions without repeating list/full-review calls. When current authority already proves closure readiness, perform one operator-authorized close mutation; a dry-run remains useful for unresolved checks, not a compulsory extra gate. Full docs validation and required reviewer authority remain fresh.

Consumer upgrades retain render → docs gate → incremental index ordering. They gain no source/profile suite, routine evidence generation or broad memory-maintenance pass.

Before closure, explicitly author one concise `Intent outcome:` paragraph in the existing exact `## Review Checkpoints` section: state achieved, partial or not established, cite evidence, and retain material limitations. When the plan states a measure of success, cite it and say whether it can be read yet. It may cover changes sharing an outcome. The close-summary composer carries the last such paragraph or list item (optionally dated `YYYY-MM-DD: `) into Wave Summary, preserving its text and qualification; do not infer achievement from titles or checked ACs. Legacy records without this assessment remain closable under existing gates and retain their existing summary behavior; this adds no schema or blocking gate. When the current `council-delivery` approval records `intent_fit: does_not`, Review and Close report the `delivery_intent_not_established` advisory; it does not block, and the operator's sign-off accepts that outcome.

## Close a paused delivery

When the operator authorizes closure, pass the ID of the paused delivery directly to Close. Keep the currently open wave’s handoff, focus and edit gates intact, including when Close refuses or retries. The reviewed delivery still goes through the ordinary close checks, including any required current test receipt.

## Wave-folder cleanup

Before finalizing evidence, promote unique long-term proof out of disposable work into maintained wave records, tests or explicitly retained evidence. New durable approvals must not depend solely on work-area paths. Before final docs validation and the close mutation, tidy only artifacts established to belong to this wave. Dates and filenames are discovery hints, not proof of ownership.

- Keep `wave.md`, admitted specs and authoritative `events.jsonl` in place. Routine briefings, per-seat reports, raw probes and green logs belong in task context or temporary storage, not a permanent repository file forest. Preserve unique review evidence, reproducible probes and historical fingerprints needed to substantiate claims. Never rewrite ledger history for cosmetic cleanup.
- Manually remove only verified wave-owned disposable scratch output or redundant copies with no unique evidence and no live references, using contained I/O and a parent-descriptor identity check before unlink. Keep cited originals and unreconstructable dirty-tree baselines. The sole automatic-cleanup exception is the newly designated owned `.wavefoundry/work/<wave-id>/`: after successful operator-authorized whole-wave closure, the tool attempts contained cleanup; failure is advisory and unsupported safe deletion preserves files with a notice. Dry-run, failed close and single-change close retain work; an authorized repeated close may retry, and reopening protects its fresh generation. Close reports the citation state of this wave folder's extra files and never deletes them (below); no other automatic deletion, expiry policy or cleanup gate is introduced. If ownership, uniqueness or reference use is uncertain, retain the artifact and note why.
- Close reports work it leaves behind; it deletes nothing beyond the owned cleanup above. When the closed record's own work folder stays in place, the response carries an advisory `work_retained` diagnostic with the path, the outcome (`preserved`, or `partially_removed` when some entries were removed before a failure), the reason token from the notice (for example `work_ownership_unproven` or `safe_work_io_unsupported`), the failed entry, operation and errno name when known, the folder's entry count, logical bytes and completeness, and a next action; the record stays closed. Every close, dry-run included, lists other leftover folders in an advisory `work_leftovers_present`: folders whose record is `closed`, `completed` or `archived`, or is not found in this checkout (it may exist on another branch). It reads only the work root's immediate children, without sizing; `wf_audit` reports their sizes in `data.work_root`. At the same point an advisory `work_root_loose_files` names the plain files and links left directly in `.wavefoundry/work/` (the count, up to 20 names with sizes from the listing, a lower bound when the listing stopped early) and says who acts: the agent that wrote one for a wave moves it into that wave's folder while the wave is open, or deletes it; any other file is left in place and reported to the operator, who decides. Close moves and deletes none of them, and a close that returns before this report, such as a blocked dry run, does not carry it; `wf_audit` reports the same entries. An advisory `work_path_cited` names each line of the record, its admitted change documents or `docs/agents/session-handoff.md` that cites this record's own `.wavefoundry/work/<key>/`, with `coverage: incomplete` naming any input it could not read: copy unique proof to durable evidence before the folder is cleaned up. A permission failure is reported as an errno; close does not diagnose its cause, such as an access control list. On a host without descriptor-relative deletion (native Windows) close preserves the folder with `safe_work_io_unsupported`; after review, remove it by hand. Close writes no cleanup note into the closed record or the handoff: the folder itself is the durable state, and later closes, `wf_audit` and the upgrade report rediscover it.
- To reclaim one retained or leftover folder through the framework, preview it with `wf_cleanup_work(work_key='<key>')` and show the preview to the operator. Call it with `mode='apply'` and the preview's `confirmation` only when the operator directs cleanup of that key in the current request. The token binds the repository, the key, the folder's device and inode, the owner file's hash and the record state, not the folder's contents: apply removes whatever the folder holds at that moment, and a device number that changes after a reboot or remount makes the token stale (`preview_stale`; preview again). Apply needs no owner file; it refuses live, ambiguous and unreadable keys, an unsafe `.owner.json` (`unsafe_owner_entry`) and a folder on another file system (`work_filesystem_changed`), but cannot detect a bind mount on the same device. Stop anything writing to the folder first. A failure part-way returns `partially_removed` with the removed count, the failing entry, operation and errno; nothing is restored and no permission is changed, so repair the cause, then preview and apply again. Native Windows previews without a token and refuses apply with `safe_work_io_unsupported`; removing the folder there is the operator's own action.
- Give every extra file in the wave folder a disposition before the final docs validation and the close write. Run `wf_close_wave(mode='dry_run')` and read its advisory `record_extras_present`. It lists each entry in the folder other than `wave.md`, the admitted specs and `events.jsonl`, at any depth and including hidden files: its path relative to the folder, its size and its citation state, largest first, up to 50 files with the total count and the number not listed, plus totals per top-level directory. Citation state is `cited_in_ledger` when `events.jsonl` contains the file's relative path (or the folder's repository-relative path followed by it), `cited_in_record` when only `wave.md` or an admitted spec does, and `not_cited` otherwise. The booleans `name_in_ledger`, `name_in_record`, `directory_in_ledger` and `directory_in_record` say whether the file name, alone or as the tail of another path, or a containing directory followed by `/`, still appears in those texts; such a loose mention never makes a file cited. `events.jsonl` is matched against the decoded string values of its lines, so a JSON escape does not hide a path. Paths are compared exactly as written, in forward-slash form, on every platform: a citation written with backslashes or in another letter case reads as `not_cited`. The report appears whenever the folder holds extras or its coverage is incomplete, on the dry run and on the close write's own response, blocked or not; it never removes, moves or blocks anything. The report lists at most 50 files, so list the folder yourself and review every extra, including the files the report does not list, and give each one a disposition under the same rules. When `complete` is false, likewise review the folder by hand. A file the report does not list has no citation state or flags from the tool, so judge it yourself: search `events.jsonl`, `wave.md` and the admitted specs for its path, its name and its containing directories, apply the same keep rules to what you find, and keep the file unless you establish that nothing refers to it. Give each extra one of three dispositions:
  - **Keep**: the file stays, and one line in `## Review Checkpoints` names it (or its group) and says why it is kept. When a file is kept only because of a loose mention, that line cites it by path, so later closes read it as cited.
  - **Summarize, then remove**: write the conclusion, the command that reproduces it, the source identity and the limits into `## Review Checkpoints` or a spec's Progress Log, then remove the file.
  - **Remove**: remove the file with no summary, because it adds nothing that the record, the tests or Git history do not already hold. Before removing a `not_cited` file whose four booleans are all false, search `events.jsonl` for the file's name stem (the name without its extension, and without any leading prefix that a copy of the file may have dropped) and search the folder's other extras for its name; a match means the file is referenced, so keep it.
- These rules decide the disposition:
  - Always keep a `cited_in_ledger` file, because the ledger is never rewritten.
  - Keep a `cited_in_record` file, or rewrite its citation in the same edit that removes it. When the citation sits in a spec section other than the Progress Log, keep the file: rewriting that citation changes the review-policy digest, and Close then blocks with `review_policy_receipt_stale`.
  - Keep a `not_cited` file whose `name_in_ledger`, `name_in_record` or `directory_in_ledger` is true, unless you establish that the text refers to a different file and say so in the record.
  - When ownership, uniqueness or use is uncertain, keep the file and say why.
  - Write summaries and rewritten citations only into `## Review Checkpoints` or a spec's Progress Log, never into another spec section. A summary in a Progress Log contains no line that starts with `## `, because such a line ends the region the digest excludes.
  - Before removing a file, check the kept extras for references to it; a kept manifest that lists a removed file is otherwise left pointing at nothing.
  - Every removal meets the manual-removal conditions above: only files established as belonging to this wave, verified redundant or summarized, with no live references, removed with contained I/O and an identity check. Dates and file names are not proof of ownership. Remove nothing from another wave's folder.
  - Removal is your edit, visible in the diff the operator reviews; the tool removes nothing.
  - Read `record_extras_present` again on the close write's response: a file added after the dry run appears only there.
- What is worth keeping in a wave folder:
  - Keep by default: `wave.md`, the admitted specs and `events.jsonl`.
  - Worth keeping: proof that cannot be reproduced from a recorded command, the tests and Git history. Examples: a baseline taken from a working tree that no longer exists; a measurement from a machine, data set or model that cannot be rerun; input received from outside the repository, such as a field report; a reproducer that is not suited to be a maintained test.
  - Summarize and remove: output whose conclusion fits in a few lines and whose command is recorded. Examples: green test logs, probe captures, census dumps, per-reviewer reports, and intermediate drafts of a result that the record states.
  - Remove: copies of files that exist elsewhere in the repository, generated output that a recorded command rebuilds, and scratch.
  - Cite a kept file by its path, not only by its directory. A large kept file needs a stated reason in proportion to its size.
- Group movable supporting files under `evidence/` when useful; no fixed layout is required. Keep ledger-cited paths stable. Update mutable links and reproduction commands after any move, and verify they resolve and remain usable. Leave other waves and unrelated files untouched.
- Consolidate repeated status notes into the final outcome and an evidence index in wave.md; do not erase historical review conclusions. Record the cleanup disposition and retained exceptions there, then run the existing docs gate. No separate cleanup report or new validator is required.

Promotion destinations may include:

- capture durable lessons as memory candidates
- `docs/references/project-context-memory.md` (required — see task 9)
- canonical behavior contracts (`docs/specs/*.md`)
- reliability, architecture, quality, security docs
- persona docs
- repo-local workflow and contributing docs

Commonly missed closure work to check explicitly:

- **`docs/scan-findings.json` not checked before close**: `wf_close_wave` hard-blocks on any `pending` or `suspected-secret` entry (unresolved — must be classified); `confirmed-secret` entries do not block but surface a standing reminder on every close. Before invoking `wf_close_wave`, read `docs/scan-findings.json` and resolve all unresolved (`pending`/`suspected-secret`) entries using the security reviewer (seed-213). If the file is absent or has no unresolved entries, proceed normally.
- `docs/references/project-context-memory.md` left empty or unchanged despite the change surfacing reusable workflow guidance
- **code review** missing, generic, or treated as optional when the wave changed non-trivial product logic — especially when per-key state or repeated-invocation paths were involved
- **`qa-reviewer` missing** on a **bug** or product defect wave when `docs/workflow-config.json` `review_policies.require_qa_reviewer_for_bug_fixes` is true — record retrospective QA or obtain an explicit waiver in the wave/spec
- review checkpoints written as "Passed" without documenting what was actually reviewed
- `wf_review_wave` enabled but `council-readiness` or `council-delivery` missing from `## Review Evidence`
- docs-contract review limited to wave/workflow files even though the implemented behavior changed a canonical behavior contract
- `Close wave` completed without a **Docs-contract review** checkpoint when `docs/specs/*.md` or other behavior contracts were updated during the wave
- closed wave still claiming "no remaining mismatches" after a follow-up review proved canonical docs were stale
- final review skipped a rerun of the readiness evaluation, so newly relevant persona or reviewer lanes were never invited back in
- memory candidates filled with success summaries instead of durable operating-memory signals
- persona guidance refresh when the change altered review heuristics or operating cautions
- handoff clearing when the feature is truly done, or handoff refresh when a successor wave remains
- stale caution and memory entry retirement skipped when this wave fixed the root cause — active cautions whose risk no longer exists must be removed, not left in place
- `docs/references/project-context-memory.md` updated with routine outcomes instead of problem-derived lessons — memory entries should answer "would this prevent a future mistake?" not "did this go well?"
- `docs/PLANS.md` or similar plan indexes still advertising the closed wave or its admitted specs as `active`
- ready/active-wave specs left in `docs/plans/` or otherwise missing from the wave folder (relocation belongs to `Prepare wave`)
- reports left in `docs/reports/` without being archived into the wave folder and summarized in `## Reports`
- duplicate regenerated wave-period reports left in `docs/reports/` after an archived copy already exists in the closed wave folder
- high-salience memory candidates left unvalidated at closure instead of being promoted, retained, rejected, or rewritten

Guardrails:

- Do not close if open wave obligations or review gaps remain.
- Do not close with an unreconciled `tree_moved_under_review` finding: a lane that saw the tree change under it holds evidence for an earlier tree, not this one (seed-209, wave 1wuju).
- Advisory docs-lint findings (`WARNING:` lines from sensors registered `advisory`, surfaced as `docs_lint_warning` diagnostics with `advisory: true`) are review notes at close, never a closure blocker; flipping a sensor to blocking is a recorded change decided at the release checklist, not at close.
- Do not leave final behavior or durable lessons only in transient wave artifacts.
- Before invoking inferential reviewer lanes, run `wf_run_sensors()` if the project has computational sensors configured — fix any sensor failures before proceeding. After all declared lanes have run, record their signoffs (on a declared wave, typed approval events via `wf_review_event`, projected into `## Review Evidence`; only legacy prose waves write the line `- <lane-name>: <verdict> (<severity> — <one-line summary>)` in `## Review Evidence` directly). Check `wf_review_wave()` to confirm `required_lanes` — any lane declared in `required_review_lanes` must have a recorded signoff before `wf_close_wave` will pass.
- **Operator review is required before calling `wf_close_wave(mode="create"|"apply")`.** The operator review lane gives the operator an opportunity to do manual testing, spot-checks, or any other review before the wave is permanently sealed. Approval is satisfied by one of two paths:
  1. **Operator-initiated close** — the operator explicitly said "close the wave" (or equivalent) in the current request. This counts as implicit operator approval; proceed with closure.
  2. **Agent-prompted approval** — if the operator has not issued a close request, the agent must stop and ask the operator for review approval before calling `wf_close_wave`. The prompt must include the `max_severity` from `wf_review_wave()` so the operator can triage. If `max_severity` is `critical` or `high`, name the findings explicitly. Invite the operator to do any manual tests or review they want first. Only proceed after receiving a positive confirmation.
- Completing review tasks, removing dead code, fixing test failures, or running `wf_close_wave(mode="dry_run")` does not constitute operator approval. When in doubt, ask.
- Record operator approval before or alongside the `wf_close_wave` call: on a declared wave, a typed `operator` approval event via `wf_review_event` (projected into `## Review Evidence`); only legacy prose waves write `operator-signoff: approved` in the `## Review Evidence` section of `wave.md` directly. `wf_review_wave` enforces this as a required lane and `wf_close_wave` blocks if it is absent.
- **If a wave was closed by mistake**, use `wf_reopen_wave` to restore it to `active` status. It works on waves with `Status: closed` **or** `Status: paused`, and removes the `Completed At` stamp. `purpose` is **required**: the tool cannot infer why you are reopening, and the choice decides which context-efficiency stage your work is attributed to.
  - Reopening to **review** (a pre-close second look at the plan or implementation): `wf_reopen_wave(wave_id, purpose="review")`, then `wf_review_wave` to confirm required lanes. Passing `purpose="review"` is what keeps the review's retrieval credited to the review stage.
  - Reopening to **keep implementing** (fixing a late defect): `wf_reopen_wave(wave_id, purpose="implement")`.
  - A missing or unrecognized `purpose` is rejected before anything changes: the wave status, the telemetry seal, and the focus stage are all untouched. Retry with an explicit value rather than working around it.

## Close spec

Shortcut: **`Close spec`** (alias: **`Close change`**). Backed by `wf_close_change(wave_id, change_id, mode)`. It closes ONE admitted change inside an open wave, the same way whether the wave has one change or many, and never closes the wave: **Close wave** remains the only wave close. Close spec is optional; `wf_close_wave` already accepts a change left `implemented`.

First, before any gate and with nothing written, it refuses a wave record it cannot read unambiguously (`wave_record_ambiguous`): an id in more than one record, a record with more than one status line (fenced or not, readable or not), or a fenced example id line that starts a record.

Gates, as implemented (every failing gate is reported, in `dry_run` and `create`):

1. The wave is OPEN (`active` or `implementing`).
2. The change is admitted to that wave (pass the FULL change id).
3. Its spec exists and is readable.
4. Its status is closable (`ready`, `active`, `review` or `implemented`) and agrees between the wave record and the spec.
5. It has no silent `[ ]` AC or task.
6. Every dependency on its wave-record `Depends On:` line is done (terminal or `implemented`).

Behavior:

- `dry_run` is the default and writes nothing; run it first, then `mode='create'`.
- `create` writes `complete` into the spec and the wave record, and moves each `planned` or `blocked` dependent whose dependencies are now all done to `ready` (never `active`).
- It records no review evidence and writes no ledger event; the review-policy receipt does not move.
- A completed change cannot be reopened, so run Close spec only after **Review wave** has cleared that change.
